# Benchmarks

This guide covers how to run the benchmarks and read their numbers. [AGENTS.md](../AGENTS.md) lists the commands, and [Device sessions](devices.md) covers phones and tablets.

The benchmarks compare null3D with three.js in the same browser. These points come from the first checkpoint's measurements.

A comparison measures equal work: the same scene content and comparable quality settings ([D-52](decisions/D-52-intent-parity.md)). Each engine may draw an effect with its own technique. Where the two images differ by design, the report gives a quality note beside the timings.

## Production builds

The benchmarks measure the engine as developers ship it. A production build leaves out the engine's development checks, such as the handle and argument checks, so the benchmarks leave them out too.

- `bench/vite.pages.config.ts` builds every benchmark page for production: null3D's pages, three.js's pages and the scene-code pages. The development checks are off, and Vite minifies as it does in any production build. So three.js runs minified too, as it ships.
- `bun run bench:run`, `bun run bench:profile`, `bun run bench:allocation` and `bun run bench:soak` build the pages into `target/bench-pages` before each run. `vite preview` serves the build on the preview port, the dev server's port plus 2.
- A page build refuses a core that came from other Rust sources than the checkout holds. A production build ships the core as built bytes and drops the check that a development build makes when it loads. A core built before a Rust change then runs beside page code that expects another core. The page fails at run time with a GPU error, or with no picture. The page builds of `tests/lib/load-server.ts` and `tools/build-test-pages.ts`, and `tools/lib/pack.ts` before it packs, compare each core's stamp with the checkout's. They name `bun run build` when the two differ. The shared cache's key covers the core crates' sources, so a hit holds the right core. Without the check, every page build takes a `packages/engine/dist` older than its sources as it is. A stale core can then build 6 entries for the final pass where the page code declares 7. The S5 soak and the allocation check then fail.
- `bun run bench:run`, `bench:allocation`, `bench:profile` and `readme-media` run Chrome in a window. With `CI` set, `bench:allocation` runs Playwright's Chromium without a window instead, on SwiftShader ([Allocation and profiling](#allocation-and-profiling)). Each gives focus back to the app that was in front after Chrome starts and after each new page. Each page's window then parks almost wholly past the main display's left edge, at its own size, as [Device sessions](devices.md#browser-apps-on-the-mac) says. Chrome's switches keep a window in the background or under other windows drawing at full speed. So the timings hold while the person at the Mac works.
- These tools run in Bun, and each starts its browser with `launchChromium` in `packages/cli/src/browser.js`. Bun 1.3.14 closes Playwright's pipe to Chrome at random, and Playwright then waits forever. The guard in `launchChromium` fails the waiting calls at once with `BROWSER_GONE` instead ([Releases](releases.md#the-fresh-project-test)).
- `--dev` runs the dev server's pages instead, where the engine runs its development checks. Run the same pages with and without it to see what the checks cost.
- `bun run test:bench` checks the production build, as the benchmarks run it. The image test manifest and `bun run parity` still load the dev server's pages. So does null3D's side of each feature scene's [parity test](image-tests.md#parity-with-threejs), so `bun run test:bench` starts the dev server too.
- CI runs `bun run test:bench` on SwiftShader in ten shards, the `bench` jobs, with the WebAssembly files that its `build` job built once. Shards 1 and 2 run the page tests of S4 and S5, which `BENCH_SHARD_S4` and `BENCH_SHARD_S5` in `.github/workflows/ci.yml` name for `--grep`. Shard 4 runs S3's page tests, which `BENCH_SHARD_S3` names. S4's and S5's tests each run in order in one worker. Two heavy SwiftShader tests side by side slow each other 1.5 to 4 times on the runner's 4 cores. In test run 40074539496, S4's tests took 3.0 minutes alone and S5's 4.7. In one shard, both took 6.1 minutes, and 8.1 in full run 40072668205. So each scene has a shard of its own. Shards 5 and 6 run S5's two visual tests of the shadows, one GPU path each, and shard 7 the other visual tests. Shards 8 to 10 run the parity tests, whose groups `PARITY_TESTS` names. Shard 3 runs every other test, with `--grep-invert`, so each test runs in exactly one shard. Playwright's own `--shard` splits by count in file order. That can give one shard 221 tests and 13.5 of its 15 minutes, and the other 4 tests and 3 minutes. So the page tests split by measured time. The parity tests split with `--shard`, by the weights in `PWTEST_SHARD_WEIGHTS`: each weight is the count of tests that a shard takes, in Playwright's order. Each scene's tests share its twins' images and run in order in one worker, and `--shard` keeps that group whole. By count alone, in run 40053442909, the first parity shard took 4.3 minutes of tests, with the room environment's, and the others 2.7 each. The weights 48:111:90 give each about 3.3 by that run's times. Work them out again when a parity scene joins or a shard runs far longer than the others. In shard 3 of that run, S5's two visual tests ran one after another on one worker, for 3.4 and 2.5 minutes. So each has a shard of its own. The parity tests take more time than their own figures show, because each scene first draws its three.js twins. A shard that holds every parity test beside page tests takes 20 to 23 minutes ([D-194](decisions/D-194-ci-jobs-in-parallel-on-enterprise.md)). A new scene's page tests go to the shard with less time. A new parity scene joins the parity shards by itself. Each test of `bench/tests/pages.spec.ts` opens a page of its own, so the file runs its tests in parallel. S4's and S5's tests are the exception: each scene's tests run in order in one worker. Neither shares a shard with the parity tests. S4 keeps SwiftShader's processor busy, and two S4 runs side by side can measure no whole second, so the trace comes back empty. Each of their tests opens its page in a browser of its own, which is killed when the test ends ([What S6 found](#what-s6-found)).
  - When a shard's job nears 12 minutes, move page tests or parity scenes by the measured times of recent runs. The list reporter in each `bench` job's log prints each test's time. The gaps between a scene's tests hold the setup of its three.js twins.
  - A slow runner stretches the same tests by 23 to 38%. Run 39033887390 took 24.4 seconds for S2's shadows on WebGPU, 56.1 for S4's and 2.9 minutes for S5's. With the same code, run 39026576346 took 19.9 seconds, 43.2 seconds and 2.1 minutes. So each shard's job allows 28 minutes, above its measured time by more than that spread.
  - The bench config spreads the browser tests' config, and Playwright resolves each path in a config against that config file's own folder. A relative path to the browser config's global setup would then resolve under `bench/`, and the shards would fail with `Cannot find module './lib/priority-setup.ts'`. So the browser config names the file by an absolute path, and a config that spreads it finds the file wherever it runs. The bench shards are the guard: they run on every full run, so a path that stops resolving fails CI at once.
- A short run must measure for more than two frames at the page's slowest rate. The engine's `measure` counts a frame only when the sketch stepped it and the renderer drew it inside the measured time. The renderer draws each frame about one frame after its step. Run 37104979684 shows the risk. There, SwiftShader drew S2 with two cascades on WebGPU at 2.4 frames a second. Its window of 1 second presented a frame but counted none. So S2's short runs last 2 seconds.
- A slow runner can still leave a short run on SwiftShader with no frame. Run 37578361814 drew S4 on WebGPU at Low at 0.3 frames a second. The engine took 32 seconds to start, and one frame finished 7 seconds after its step. So the 8 second window counted none. Run 37581715923, for #384, failed the same way on S4 on WebGPU. It gave a 28 second start and 0.34 frames a second, with frames done 5.7 seconds after their steps.
- Those starts are usual, not slow. Both include the preset check, which tries each preset for a few seconds. In 115 runs, S4's five null3D page tests took 20 to 59 seconds each, with no trend. The two failed tests took 44.9 and 48.6 seconds.
- So on SwiftShader, a short run that counts no frame runs once more. Its test then gets three times the time limit. Runs on real GPUs never repeat, so their figures do not change.
- The second try keeps the first try's warm-up and measures longer, through the page's `?measure=` switch. It measures for five whole frames at the rate at which the first try finished its frames. That is from twice to eight times the first try's window. It warms up no longer, because the page keeps the first try's preset check. A second try of the whole page at eight times the window would warm up for 64 seconds, then measure 64. One runner was about 2.3 times slower than usual (CI run 40056066922). There, S4 and S5 in compatibility mode finished 0.12 and 0.16 frames a second and counted no frame. A whole-page second try took their tests to 3.6 and 3.7 minutes, where they usually take 30 to 36 seconds. That made their shard the run's slowest job, at 11.8 minutes. At those rates the second try measures for 42 and 32 seconds, after a warm-up of 8.
- The second try must not hide a slower page. Each short run on SwiftShader prints its frames and, for null3D's pages, its start time and frame rates in the log. The second try's start is short, because the page keeps the first try's preset check. A second try prints both tries' figures as a GitHub warning and adds them to the test's annotations. The test then fails when either try took 90 seconds or more to start, or finished 0.1 frames a second or fewer. S3's two pages have their own 180 seconds, because their starts ran from 22.8 to 84.8 seconds across runs. A page earns a figure of its own only from its own measurements. That figure is the last thing raised when the page drifts, because the shared one is what catches a page that got slower. When the queue's logs show other usual figures, change the limits in `bench/tests/pages.spec.ts` and here.
- Passing queue runs keep no page reports: the `bench` job uploads its test folder only when a test fails. Each run's log holds every null3D page's start time and frame rates on SwiftShader. So the logs of later runs give the trend, and show the merge where a page got slower. A drop in frame rate on a real GPU shows in the benchmark job's comparison first.
- The device runner's bench and scale plans load the production build through the dev server's load routes. [Device sessions](devices.md#benchmark-runs) says how.
- The build keeps hidden source maps beside its files, and the built files stay as a production build writes them. The profile and the allocation check read the maps to name each function and its source file, as the dev server's pages would.

### Build caches

The build caches live under one root, `~/.cache/null3d` by default, each in a named subfolder.
`shader-modules` holds the built shader modules, `shader-cache` the per-entry shader build, and
`wasm-artifacts` the built wasm and tool modules, which CI's build job keeps in the Actions cache under `bun tools/build-wasm.ts --cache-key`. Each file set is an entry under its own key, so on a miss the job restores the newest earlier folder and builds only the sets whose keys changed. Before it saves, `--keep-current` removes the entries that this build no longer writes. `size-memo` holds the size check's compressed sizes
([Download size](#download-size)), and `sccache` the compiled Rust crates when sccache is installed. `NULL3D_BUILD_CACHE` names another root and moves them all; the older per-cache
variables still name one folder. Clearing the root is always safe, because every entry is a pure
function of its inputs and a missing entry only costs the build time. Each checkout builds Rust into
its own `target` folder ([D-177](decisions/D-177-build-cache-module.md)).

The Mac measured these figures with one Rust build folder that every checkout shared. The build
gives each checkout its own Rust folder, as [D-177](decisions/D-177-build-cache-module.md) rules:

| build or edit | run again | from the cache |
| --- | --- | --- |
| a fresh worktree's first `--pages-only` build | 236.8 s | 0.32 s |
| a no-change `--pages-only` build | 114.5 s | 0.28 s |
| a worktree's shader modules | about 3 min | about 0.2 s |
| one shader's edit | about 500 s | about 10 s |

A library module's edit rebuilds only the entries that import it: 31 of 54 in one measurement.

A build whose entry cache holds nothing for the current compiler prints a notice before it starts:
the first build compiles every shader and can take a few minutes. It then reports how far it has
got on standard error, as a percentage of the variants to compile: a terminal gets one line that it
rewrites at each whole percent, and any other stream gets a line at each tenth, so a CI log shows
steady progress without flooding. A build that reuses the cache prints neither, because it finishes
in seconds. The notice and the percentage are for a reader who would otherwise think the build had
stopped.

CI keeps the two shader folders in the Actions cache ([CI's jobs](pull-requests.md#cis-jobs)). A
cold shader build on a CI runner takes longer than 34 minutes. A stopped run's finished entries,
669 MB, take 10.3 MiB in the Actions cache. The next run restores them in under a second (runs
38679915189 and 38683080955).

## What a report measures

- A report gives each engine's whole frame and its own work on the busiest thread. The desktop target uses own work, because both engines run the same scene code.
- null3D's own work comes from its phase timers: each thread's time less its `update` step. three.js's own work is its frame time less the scene code, timed alone on the scene-code page.
- The scene-code page's loop compiles to slower code than an engine's loop, so this estimate of three.js's own work is low.
- Compare results at the same display refresh rate. The engine measures it, and each result records it with the presented and finished frame rates and the GPU delay. Runs at 120 and at 144 frames per second differed by about 10% for both engines.
- Time frame rates in a visible browser window, never in a headless one. On the Mac, headless Chrome on the real GPU reports a 60 Hz display. The engine then aims for 60 frames per second, and the stats overlay says it defends 60, so no figure can pass 60. The Creek showcase, timed in headless Chrome, gave exactly 60 frames per second on every page, at full render scale. A visible window parked past the screen's edge reports 120 Hz. `launchInWindow` and `newParkedPage` in `tests/lib/app-window.ts` open one, and the comparison and showcase timing scripts use them.
- A timing test must end on its own. The on-and-off cost tests (`tests/image/*-cost.spec.ts`) wait until the 1-minute load is under 8, through `waitForQuietLoad` in `tests/lib/cost-runs.ts`. The wait fails the test after 10 minutes, and each test has a time limit. A cost test with no limit can wait 40 minutes for a load that stays at 11 to 13. It holds a slot in the shared queue all that time. For an untimed trial, `NULL3D_COST_TRIAL=1` skips the wait. A unit test (`tests/lib/cost-runs.test.ts`) fails when a browser test turns its time limit off or reads the load itself.
- **A figure taken on a machine too busy to time is not a figure.** When the load never comes down to where a timing run can hold, the record says "not measured", names the load it saw and what else ran, and says when it will be taken. Writing a number from such a run costs more than writing none: it has to be found, doubted and retracted by someone who was not there. This is the owner's ruling.
- A timing run needs the machine to itself while it measures. Whatever starts the run keeps a marker file in place for that time. The marker is `quiet-window` in the null3D cache folder, `~/.cache/null3d` by default, or the path that `NULL3D_QUIET_FILE` names. Its first line says what holds the window. While it stands, a tool that builds the engine or drives a browser refuses to start (`refuseInQuietWindow` in `tools/lib/quiet-window.ts`). The guard sits in the shader-module build, which every page build, dev server, example build and test run reaches. The WebAssembly, test page and CDN builds, the vendored module builds and the type check also check at their start. So do the browser tests, the fresh-project test, the test servers and each benchmark tool and probe. The commit hook runs the type check, so a commit outside the queue waits for the window too. A tool that the job queue started passes, since the queue holds its own jobs back during a window. So does each process that a passed tool starts, so a window that opens later never stops a run halfway. A timing run that holds the window outside the queue sets `NULL3D_QUIET_PASSED=1` for itself. No queue sees the page builds that sessions start in their own checkouts, so without the guard they spoil a window's figures. Cargo run directly is not covered, so run it through the queue.
- A spec that times frames on the computer's own GPU runs only when a variable asks for it, and names that variable `NULL3D_<NAME>_COST`, such as `NULL3D_FOG_COST`, and nothing else. Playwright's global setup (`tests/lib/priority-setup.ts`) refuses a run at background priority when any variable of that name is set, so a new spec needs no other edit. `tests/lib/priority-setup.test.ts` fails when a spec waits for a variable of another name. A list of names in the guard would fall behind, because a new spec can land without its entry.
- The Mac's own screen also changes its refresh rate by itself (ProMotion). In one parked-window run, the overlay read 60 Hz in 4 of 5 readings. So a timing script logs the display rate that the engine measured with each reading. It runs a reading again when that rate is not the one it expects.
- The timing tools guard against both traps. Before `bench:run` opens each page, it measures the display rate in the page's new window, with `displayRateCheck` in `tests/lib/app-window.ts`. It compares that rate with the main display's highest rate, which macOS reports. A window more than a twelfth below that rate gets a warning, and its result keeps the reason as `displayProblem`. A headless window at 60 Hz on a 120 Hz screen is one such case. Run such a page again. Timing scripts of your own open their pages with `launchInWindow` and `newParkedPage`, and call `displayRateCheck` before each reading. In CI, and on machines that are not Macs, the display's rate is not known, and the check measures nothing.
- The page switch `?fps=<n>` holds null3D's drawing at n frames per second, at most the display's rate. Use it to compare runs on displays of different rates. The three.js pages do not read it.
- On WebGL2, `measure` reports `visibleEntries`, the entries in each frame's list of visible objects, and the bench summary divides the upload by it. When only the camera moves, as in S1-static, the upload is about 4 bytes per entry.
- null3D's benchmark pages start the warm-up when the GPU finishes the first frame. On a first visit, `createEngine` resolves only after the preset check, which runs after the first frame. A later start in the same browser takes the check's stored result, and `createEngine` resolves before the first frame. Runs on phones and tablets keep the browser's storage, so without the wait their warm-up would shrink by the time to the first frame. Playwright gives each benchmark run on the Mac fresh storage, so those runs check the preset each time.
- `packages/cli/src/protocol.js` holds the protocol's warm-up, measured time and run count. It also holds the timed run of a null3D page, and the median and spread of runs. The command-line tool's `bench` command runs the same protocol on a project's page, so a change there changes both.
- **A start figure needs the same load at both ends.** A page's core load and its first frame follow the machine's load, so a row taken on a busy machine starts slower without any code change. The same commit read a core load of 2033 ms in one quiet row and 2292 ms in a busier one. A different commit read 4038 ms in a row beside the first. Compare starts only between rows taken at matched load, three per end back to back, and read the request list beside the time. The same untouched page read 4,038 ms for its core in one row and 2,292 ms in a row taken minutes later.
- **A build's module list is no evidence about the source graph.** The preload list of a built page follows the generated shader modules in the checkout, not only the engine's source. Building one commit with another commit's generated modules gave its page the other commit's preloads. Build both ends with their own generated files before you compare the lists or name a culprit from them.
- **Two requests for one file are a fault, whatever their cost.** Each device row keeps every request the page made, in `downloads.files`, with its time. The engine's core fetched twice, 1 or 2 ms apart, is a real fault even when the seconds it adds are in doubt: something on the page asks for it twice at once. Do not dismiss it because the cost is small.

## The benchmark job in CI

- The Benchmarks workflow compares a new commit with a baseline on GitHub's machines.
- On main it runs once a day, at 19:07 UTC, on main's newest commit. In the hour from 19:00 UTC, the fewest pull requests merge to main, so CI's Safari jobs need the Mac machines least then. Its baseline is the last commit on main that a run measured, which `bench/ci-baseline.ts` finds. So one run measures every merge since the last measured commit. The commit before would leave those changes unmeasured.
- When main has not moved since the last measured commit, the run stops after `choose the commits`, and no build or Mac machine starts.
- The owner chose a daily run, with S5 and S6 in the comparison. A run on each push to main would hold Mac machines that CI's Safari jobs also need, and those jobs would wait behind it.
- Main's runs share one concurrency group, so two never overlap. A running run is never cancelled. A newer run replaces a run that waits, and measures its commits too.
- A run measured its commit when the report's step `Merge the shards into one comparison` passed, whether the verdict then passed or failed. A cancelled run, a run whose builds failed and a run whose shards left a page out measured nothing. The next day's run skips them and measures the same commits again.
- The search reads the latest 30 finished scheduled runs on main, and the push runs from before the schedule. The runs that found nothing to measure fill that list too, so it covers about a month without a merge. Runs started by hand do not count, because they can measure any commit.
- To measure main at once, start the workflow from the Actions tab. That run compares with the commit before, unless you name a baseline, and the daily runs do not count it.
- A failed verdict counts too, so a slowdown fails the one run that holds it. The next run compares with that commit and judges only the changes after it. If only a run that passed counted, one false alarm would keep the baseline on an old commit. Each run after it would then compare with that commit. A false alarm on S1 WebGL2 failed main's run 7 times in a row that way. The owner's Mac measured no change between those commits.
- Without such a commit, the baseline is the commit before.
- Each build runs its own commit's benchmark pages: `bench/pages` and `bench/scenes`, less their tests. The commits from the baseline to the new commit can change those pages or the comparison's switches. Then the two builds measure in different ways, and the summary says **Measurement changed**. It names the change and lists the time changes that would fail as not judged. The run passes, and the next run on main compares with its commit. Otherwise a change of measurement alone would fail a run. An example is new pages that take a fixed preset against baseline pages that choose their own (#217). A page that the new build kept too few runs of still fails the run: its page is broken, which no change of measurement explains. Without that rule, a branch whose S6 fails to load in every run of both builds would pass, because the branch changes the pages.
- For a pull request it runs on demand, against the pull request's merge base. Add the `benchmark` label, and each push runs it again while the label stays. You can also start the workflow from the Actions tab with a pull request's number, a branch or a commit.
- GitHub's machines are shared, and their speed changes from run to run. So each Mac machine runs the pages of both commits. A page's new build is judged only against the baseline that ran on the same machine.
- The workflow has four kinds of jobs:
  - `choose the commits` picks the baseline and the new commit.
  - `build (baseline)` and `build (new)` each build one commit on a Linux machine, with that commit's `bun run build`. That build also makes the commit's shader modules. The built files are the same on every platform, so each job packs them into an artifact.
  - The `benchmark (shard i of 8)` jobs run on Mac machines. Each one makes a git worktree of each commit, unpacks its build there, and runs `bun run bench:run --compare <baseline>,<new> --shard i/8` in Chrome. The command builds each commit's benchmark pages for production, into `target/bench-pages-baseline` and `target/bench-pages-new`, and serves each build on a port of its own. Each server runs `vite preview` in its own commit's worktree. That worktree's config and built asset tool make the files that the pages ask for, such as the sample content's environment maps. A server in the job's checkout, which the shard never builds, fails S6's environment map with HTTP 500. The city then never becomes whole, and every S6 run times out. The shards need no Rust toolchain, because `vite preview` does not build the shader modules that a dev server needs.
  - `benchmark report` downloads the record of each shard, `runs.json`, and runs `bun run bench:run --merge`. It judges every page as one comparison would, with the same rules and the same trailers, and writes the verdict to `summary.json`. The step `Judge the new build` then fails when the verdict does. Its summary and artifact are the run's result.
- Each worktree runs `bun run samples:fetch` with its own `tools/samples/lock.json`. S5's pages import the Knight from the sample content, and S6's city files name its images, so each build needs the files of its own pin. The cache keeps each pin in a folder of its own ([Sample content](sample-content.md#where-the-files-live)). A build with the checked-out commit's pin finds its files there, from the samples action. A build with another pin downloads its files, about 180 MB, in each shard. With only the checked-out commit's pin, a change of pin such as #426's for S6 leaves the baseline's build with no Knight. A failed build measures nothing, so the baseline would stay where it is, and every run on main would fail the same way.
- S1, S1-static, S1-cells, S2, S3, S4, S5 and S6 run on null3D's two GPU paths. Each scene on each path is one page, so the plan has 16 pages. A shard runs every eighth page, from its own place in the plan. So each shard runs 2 pages.
- A scene that one of the two commits has no page for runs in neither. So a pull request that adds a benchmark is compared on the other scenes.
- Each shard runs 10 rounds. Each round runs every page of the shard once in each build, the two runs back to back. Even rounds run the new build first. Each run has 5 s of warm-up and 5 s measured.
- Every page of a comparison runs with `?preset=high&governor=off&anim=every`, unless `--switches` names the same switch. Both builds then draw the same work in every run:
  - Without a named preset, the engine chooses one and checks it with the first frames' rate. On the shared Mac, a slow moment during that check lowers the preset in one run and not in the next. Run 37013358376 for #198 drew 42 of its 240 runs below the desktop's preset. In two rounds of S2 on WebGL2, the baseline drew at Low and the new build at Medium. One of them gave the page's lowest ratio, 0.57.
  - The preset explains only part of that run's noise. S2's highest ratio on WebGL2, 2.16, came from a round in which both builds drew at Medium. S2's times there were 0.2 to 0.5 ms per frame, so a short stall moves a round's ratio far.
  - High is the preset that a desktop gets, within each GPU path's ceiling, so WebGL2 draws at Medium. A named preset also skips the check and the crash marker. Low was rejected, because it would measure less work than a desktop draws.
  - The quality governor is off in every scene but S4, whose sketch turns it on. `?governor=off` keeps it off there too. A governor step during the measured seconds would change what the rest of that run draws. Dropping such runs was rejected: a slower build takes more steps, so its runs would be the ones dropped.
  - A scene adds switches of its own where its page would otherwise draw other work than its twin does. S5's pages take `?anim=every`, which holds every knight's pose at every frame ([The crowd](#the-crowd)).
  - Dropping the rounds whose builds drew at different presets was rejected too. It would discard runs, and could leave a page with too few rounds to compare.
- The summary gives the preset of each page. A page whose runs drew at different presets gets a list of each round's preset in each build. It also gives the quality steps in the measured seconds of S4, the page that records a trace. Each run's preset and steps stay in `summary.json`, under `quality`.
- The comparison drops a run that measured no frames, and a run that measured another refresh rate than most runs of its page did.
- A page's ratios can still swing far on a busy CI Mac. In one pull request's run, S2's WebGL2 ratios ran from 0.57 to 2.16, with no change to S2's code path. Three runs of 10 rounds on a MacBook Pro measured that page at -9.1%, -2.5% and -9.5%. Read a page whose ratios swing that far as noise, and measure it again.
- Each run gives two medians of CPU time per frame: the busiest thread's time, and the engine's own work on that thread. A run in a browser that times the GPU gives a third measure: the median GPU time per frame. For each page and measure, the comparison divides the new build's median by the baseline's in each round. The change is the median of these ratios. A machine that changes speed between rounds then changes both runs of a round alike.
- Each change also gets its noise: the standard error of the median ratio, from the spread of the rounds. The summary's table gives it beside the change.
- A page fails when the busiest thread's change is more than 8% and more than 0.05 ms. It also fails when own work's change is more than 15% and more than 0.05 ms. It fails when GPU time's change is more than 25% and more than 0.3 ms too. In each case the change must also be more than twice its noise. GPU time counts only on a page with at least 2 rounds in which both builds timed the GPU. Otherwise the page's table has no GPU row. "Faster" follows the same rules.
- The fixed 0.05 ms decides on the pages whose frames take less than about 0.6 ms: S1-static, S1-cells, S2, S3 and S4. There, 8% of a frame is a few steps of the browser's 5-microsecond timer. 0.05 ms is 0.3% of a frame at 60 Hz.
- GPU time's rule is wide, because it has to catch a large slowdown of the GPU's work, not a small one ([D-109](decisions/D-109-gpu-time-guard.md)). The GPU changes its clock with its load, and no comparisons of identical builds have measured GPU time yet. On the owner's Mac, two builds with the same WebGL2 shaders took turns in two rounds. Round by round, their GPU times differed by 2% to 3% in S4 and 3% to 6% in S6. One build's two rounds of S6 at High on WebGPU gave 6.17 ms and 6.75 ms, 9% apart. The fault that the rule is for took S4 from 1.9 ms to 23 ms or more ([D-89](decisions/D-89-webgl2-texture-units.md#the-webgpu-slowdown-from-a-switch-on-the-maps-slot)). 0.3 ms keeps a page whose GPU work takes about 1 ms from failing on the clock's steps.
- The rule was replayed on 14 comparisons that helpers ran on the owner's Mac. 13 of them timed the GPU, on 17 pages in all. Two builds of the same commit, f46c068, differed by 6.5% in S4. Only one page failed: S4 on WebGPU, from 1.27 ms to 1.60 ms, from f46c068 to #309. That was a real cost: #307 found two shadow fixes between those commits that added 0.1 to 0.2 ms each to S4's GPU work. The benchmark pages changed between those commits too, so that comparison judged nothing.
- These CPU rules catch a slowdown of about 15% in S1, or 0.1 ms on the other pages. A smaller change needs device runs or a comparison on a quiet Mac. [How the rules were chosen](#how-the-rules-were-chosen) gives the replay behind them.
- A shard fails when one of its own pages fails, and the report fails when any page fails. Each shard's page shows the summary of its own pages, and the report's page shows them all.
- To measure a shard again, open the run and use "Re-run failed jobs". GitHub then runs the failed shards and the report again, with the same commits and the same builds. The shards that passed keep their records, and a shard that runs again replaces its own.
- The report also fails when no record holds a page of the plan, such as after a shard ran out of time. Its log names the missing pages.
- A pull request that makes a benchmark more than 3% slower still needs its written reason (hard rule 17). One run cannot tell such a change from the machine's noise, but its table shows every change.
- The shards run on GitHub's Mac machine (`macos-15`, 3 cores of an Apple M1 in a virtual machine). Its GPU is shared with other machines. Device sessions and comparisons on a computer with a GPU of its own measure the GPU.
- So the job judges CPU time only, and a change that slows only the GPU passes it. Chrome on that machine gives no GPU timer at all. None of the 240 runs of main's run 37644306103 timed the GPU, so its summary has no GPU line. That run's new commit held #389. With MSAA, #389 made every textured draw of the standard material many times slower on WebGPU. On the owner's Mac, S4's GPU time per frame went from 1.9 ms to between 23 and 62 ms ([D-89](decisions/D-89-webgl2-texture-units.md#the-webgpu-slowdown-from-a-switch-on-the-maps-slot)). The run passed, and S4's CPU times on WebGPU did not change. Its frames in a measured run fell from a median of 267 to 242. The time from a frame's submit to the GPU's finish rose from 27.0 ms to 28.8 ms. The shared GPU held S4 under 60 frames per second before #389 too. That time then stops growing at about two frames. WebGL2's S4, whose shaders did not change, moved more in the same run, from 24.8 ms to 31.9 ms. So on this machine those figures cannot tell a GPU slowdown from noise.
- Each run takes about 12 s with its load. 80 runs then take about 16 minutes, after about a minute to set up. The Linux builds come first.
- Every CI job should take at most 15 minutes, by the owner's rule, so the 16 pages, with S5 and S6, run in 8 shards. Each job's limit is 30 minutes. Each page takes 214 to 230 seconds for its 10 rounds in both builds. The setup takes about 2 minutes, and 2 to 2.5 minutes more when the cache of the city files misses. A shard of 2 pages then takes about 9.3 minutes, and 11.8 when the cache misses. Six shards would hold 3 pages in four of them, for about 13 minutes, and 15.5 when the cache misses. The pages, the rounds and the machines are those of the recorded history, so the figures compare with it. In a trial of S6 alone (run 38266744830), the city stood whole 3 to 6 seconds after each page's start. In the first run of a build it took 10 to 14 seconds. The step that compares took 5.3 minutes for S6 on WebGPU and 5.9 for S6 on WebGL2, with the pages' production build, and building the city files took 2.6 minutes when the cache missed. Every eighth page puts each S6 page in a shard with an S2 page, the 7th and the 8th. In run 38281675491 the city cache missed in the first shards, and each built the city files in 2.3 minutes. Its shards took 8.8 to 11.4 minutes, the slowest a shard without S6 whose cache missed. - The organization's Enterprise plan gives up to 50 Mac machines at once, and a full run's Safari shards take 22 of them ([D-194](decisions/D-194-ci-jobs-in-parallel-on-enterprise.md)). A full run follows each push to a pull request that is ready for review, and each merge to main. The benchmark run asks for 8 machines, once a day on main. ### How the machine was chosen

Trial jobs compared two builds of identical engine code, so every change they measured was noise.

- On the Linux machine, the software GPU drew S1 and S1-static at under one frame per second. A run of 10 s measured 5 to 7 frames, and the software GPU took the processor from the engine's threads. Identical builds differed by up to 29% in own work. The job also dropped every run of S2, whose refresh rate varied from 20 to 30 Hz.
- The Mac machine kept every run at 60 Hz, but its speed changed often. The same scene code took 3.4 to 5.4 ms per frame in runs 20 seconds apart. So the job compares the builds round by round. The builds' plain medians differed by up to 22% on identical builds.
- Six jobs on the Mac ran 5 rounds of 10 s, 10 rounds of 5 s or 15 rounds of 3 s each. Round by round, the largest slowdowns of identical builds were +4.7% for the busiest thread and +12.0% for own work, both in S1. In S1-static and S2 the largest was 0.012 ms. Shorter runs gave noisier rounds, and 10 rounds of 5 s gave the least noise for the time.
- Own work is the busiest thread's time less the scene's update: a small difference of two larger times. In S1 it also waits for a job worker, whose timing varies on 3 cores. Both make own work noisier, so its rule is wider.
- These six jobs alone gave rules of 5% and 0.01 ms for the busiest thread, and 15% and 0.02 ms for own work. 3% failed three jobs, and 4% failed two.
- More rounds narrow the noise only slowly. A job of 20 rounds would take about 45 minutes, and its medians would still wander by about 2%.

### How the rules were chosen

Tighter rules failed nearly half of main's runs: 71 of 149. They were 5% and 0.01 ms for the busiest thread, and 15% and 0.02 ms for own work. The failing pages changed from run to run. So the rules come from a replay of main's recorded runs.

- The replay read the records of 148 finished runs on main. In 18 of them, the commits changed no engine, page or build file, so both builds were identical. The file `bench/lib/fixtures/identical-builds.json` holds their rounds, and the comparison's unit tests replay them. A 19th, the first job, ran another protocol and is left out.
- The 5% rules failed 11 of the 18 identical comparisons, on 16 page measures. S1's busiest thread failed 4 times, at up to +7.6%. The short pages failed 12 times, by 0.04 ms at most. The run of #217 flagged S2 on WebGL2 at +6.3%, 0.027 ms, the same kind of noise.
- In every page, the rounds of identical builds differ by about 5% to 11% (the median absolute deviation, as a standard deviation). This holds for S1's 5 ms frames and for S1-static's 0.15 ms frames alike. Short frames are no noisier in share. Their rule was too tight in time. The median of 10 such rounds wanders by about 2% to 5% between comparisons. A rule of 5% over 24 page measures then fails most runs.
- Three changes were tested against the replay and against 4000 comparisons drawn at random from the identical runs' rounds:
  - Judging the sum over rounds failed more identical comparisons, 15 of 18. Its total takes in the slow rounds that the median leaves out.
  - Measuring more frames per round would not help. Each page draws about 300 frames in a run of 5 s, at 60 Hz, whatever its frame time. The noise comes from the machine's speed between runs, not from the frame count.
  - A fixed limit of 0.05 ms removed every failure of the short pages. It left S1's 4 failures.
- S1's noise is in share, so its share had to grow. Alone, 8% for the busiest thread left 2.1% of the random comparisons failing, and 10% left 1.2%. A noise check does better: a change counts only when it is more than twice its noise.
- The chosen rules (8%, 15%, 0.05 ms and twice the noise) failed none of the 18 identical comparisons, and 0.9% of the random ones. They catch a 15% slowdown of S1 in 97% of the random comparisons, and 0.1 ms on the short pages in all of them. In the recorded comparisons, one run's S1 rounds on WebGL2 ranged from 0.38 to 1.42 times the baseline. There, a 20% slowdown stays within the noise.
- Of the 129 comparisons that changed engine files, the 5% rules failed 65 and the chosen ones 37, without trailers. 32 of those 37 compared with one of two stale baselines that main's runs kept for days, so each of those runs held many changes.
- Without the noise check, a run on a busy machine fails on its noise alone. With it, the summary shows a page with a large change but larger noise as the same. Read such a page as unmeasured, and run the comparison again.

### Mark an expected slowdown

A commit that makes a benchmark slower on purpose names the change and gives the reason in a `Bench-Expected:` trailer:

```text
Bench-Expected: s1/null3d-webgl2: the batch pass now writes normals, about 0.1 ms per frame
```

- Before the colon, name the benchmarks: a scene, then a page and a measure if needed. For example `s1`, `s1/null3d-webgl2` or `s1/null3d-webgl2/own-work`. The measures are `busiest-thread`, `own-work` and `gpu-time`. A `*` stands for any part, and a comma separates two benchmarks.
- After the colon, give the reason. A bare value such as "yes" does not count.
- The comparison reads the trailers of every commit from the baseline to the new commit. A squash merge keeps them, because main's squash messages list each commit's message.
- A trailer that does not parse excuses nothing, and the summary lists it.

### Run a comparison on your computer

Build two checkouts, such as a git worktree of main beside your branch, with `bun run build` in each. Then run `bun run bench:run --compare ../main,. --runs 10 --seconds 5`, the job's settings. The baseline's pages are served on the port that `NULL3D_PORT` names, and the new build's pages on the next one. With `--dev`, each checkout's dev server takes its port instead.

On a computer with a GPU of its own, such as a Mac, Chrome times the GPU, so the comparison judges GPU time too. That catches a change that slows only the GPU, which CI's job cannot see. For a change to shaders or to how the engine draws, `bun run bench:gpu-check` compares the pages with the most GPU work with main. [The GPU check](pull-requests.md#the-gpu-check) says when a pull request must run it.

A comparison keeps each checkout's build of the pages in `target/bench-pages-baseline` and `target/bench-pages-new`, with a stamp of the sources that it came from. The stamp covers the commit, the changes that git sees, the files that git does not track yet, and the engine's build. The next comparison builds the pages again only when the stamp changed.

### The GPU check's two steps

The GPU check needs a quiet computer only while it times. So it runs in two steps, and only the second needs the quiet computer ([D-109](decisions/D-109-gpu-time-guard.md#two-steps-and-a-shared-baseline)).

- `bun run bench:gpu-check --prepare` uses only the CPU. It runs `bun run build` in the checkout, unless `--no-build` is given. It builds the checkout's pages. Then it makes sure that the shared cache holds a prepared baseline of the checkout's merge base with origin/main.
- `bun run bench:gpu-check --measure` builds nothing. It fails when the cache lacks the merge base's baseline, or when the checkout's pages are older than its sources. The message names the step to run again.
- With neither option, the check runs both steps in turn.
- The cache is `~/.cache/null3d/gpu-check-baselines/`, or the folder that `NULL3D_BASELINE_CACHE` names. It holds one folder per commit of main: that commit's production build of the pages, about 110 MB, and `baseline.json`. The record gives the commit, its subject and the switches that its comparison gives every page. Every copy of the repository on the computer uses the same cache. So the checks of all branches on one main commit build that commit once.
- The `builder` worktree in the cache checks out each new commit, installs, and builds the engine and the pages. It keeps its Rust build and its packages from the commit before, so a new commit of main rebuilds only what changed. A lock lets one check build at a time, and another check waits for it. A check whose baseline is in the cache does not wait.
- The cache keeps the 6 baselines that checks used last. It removes older ones, but never one that a check used in the last 2 hours, since that check may still be timing it.
- `bun run bench:run --compare <dir>,.` also takes a prepared baseline's folder as its baseline.
- `--prepare` may run beside a browser run of the same checkout. A build that deletes the engine's output folder and writes each core in place in several passes lets the page read part of a core. The page then fails with E1406: "not a WebAssembly module", the file "fell off" its end. So the build makes each core in its own build folder under `target/`, and each file goes in place whole. It is copied to a temporary name beside its place, and a rename puts it there in one step. A reader gets the old file or the new one, never part of one. The build tools' modules go in place the same way. The code is `tools/lib/atomic-files.ts`, and its unit test checks that a reader of the old file still reads it whole.

- A control tree answers whether one call costs enough to move it. Commit the change in a second checkout, and run `--prepare --base <checkout>` from the checkout that times; a `--prepare` inside the control prepares it as a branch instead. A control with the aerial perspective left out of `lib/mesh.wgsl` gave four readings that moved +1.0%, −7.8%, +7.3% and +2.1%. That is inside the machine's own variation, so every mesh build keeps the call.

On the owner's Mac, `--measure` holds the quiet window for about 3.75 minutes and builds nothing. A check that also builds holds it for 6.6 to 14.3 minutes, most of it for builds. A first `--prepare` with an empty cache took 30 minutes in the CPU lane, while other builds ran. [D-109](decisions/D-109-gpu-time-guard.md#two-steps-and-a-shared-baseline) gives the figures.

Two builds of the same engine moved s4 high by about 5 per cent, so a smaller change is the check's own spread.

Add `--shard 2/3` to run only the pages of one shard, as a CI shard does. Each run writes its record to `runs.json` beside its summary. `bun run bench:run --merge <folder>` judges the records under a folder as one comparison, as the report job does. It needs no browser, and fails only when the records miss a page: the verdict is in `summary.json`.

## Visual figures and captured frames

A change can make a scene faster and make it look worse, such as a smaller shadow map. So the device runner's bench plan measures how each scene looks, beside its timings. It also keeps frames for people to look at.

- After the timed runs, the bench plan runs the visual page of each scene on each GPU path of its null3D pages. Each item has the name `visual-<scene>-<path>`. [Image tests](image-tests.md#visual-checks) says what the page measures, and why. The page loads from the dev server, because only development builds draw debug views. It runs after every timed page, so it changes no timing.
- The page draws the desktop's preset, `?preset=high`, as the image tests do. Each scene's limits come from that preset's shadow settings, so every device measures the same settings.
- The bench summary prints two columns beside the GPU time of each null3D page. The first is the share of pixels whose shadow changed between frames. The second is the shadow edge offset in pixels. A figure over its scene's limit reads `OVER` and the limit, and the visual item fails. A scene without limits, such as S1, whose sun casts no shadows, prints its figures alone.
- The visual page captures PNG files from hold mode. They are the first and last stability frames, the reference, and 4 consecutive frames of the moving scene, 1/60 s apart. The runner saves them in `target/runs/<run>/<runner>/frames/<scene>-<path>/`, with `figures.json`. Hold mode gives consecutive frames exactly. A live engine cannot: `captureFrame` draws the newest frame again and reads it back, which takes longer than a frame on a phone.
- The first timed run of each null3D page also captures its live frame with `engine.capture()`, after its measured seconds. The runner saves it as `frames/<scene>-<page>-live.png`. It shows what the device drew at full speed, with the quality governor's settings and the far cascades' update schedule. Hold mode runs neither. A plan that sweeps job worker counts captures nothing.
- The runner prints the frames folder after the summary. The coordinator looks at the frames after each run.
- `bun run test:bench` checks the same figures for S2 with three cascades and S4 on SwiftShader in CI (`bench/tests/visual.spec.ts`).

## Hold frames

- A benchmark page with `?hold` draws one frame at the scene's hold time, 2 seconds, and publishes its pixels. `?hold=<seconds>` holds at another time.
- The image test manifest compares null3D's hold frames with their references. `bun run parity` and the device runner's parity plan compare them with three.js's frames. The benchmark page tests check that three.js's frames show the scene.
- The null3D pages start the engine in hold mode with that time. The engine steps the sketch from 0 to the time at 60 steps per second, then draws that one frame and reads it back. The sketches pose their scene at `time.now`, and hold no time of their own.
- The three.js pages pose their scene at the hold time and draw one frame into a render target, which they read back. The scenes are functions of time, so both engines draw the same moment.
- Before it draws, a hold at 2 seconds runs 121 frames of the scene's update and the engine's steps. S1's hold page on the Mac takes about 0.6 seconds with 100,000 instances.

## Runs on phones and tablets

- Phones and tablets run the benchmarks through the device runner. First find the device's scale with the `scale` plan. Then `--plan bench --n <count>` runs the protocol at that count, with five runs of each page. The pages take turns run by run.
- Both plans load the production build of the benchmark pages, as the tools on the Mac do.
- The bench plan runs S1 on its usual pages. `--pages` and `--scenes` pick others. For example, to compare two null3D paths on a phone: `bun tests/real-browsers.ts --plan bench --allow-no-webgpu --android chrome --scenes s1-static,s2 --pages null3d-webgl2,null3d-webgl2-low`.

## The results archive

A run folder holds every page's full result, with frames and images, and stays on the machine that ran it. The command `bun run bench:archive` keeps a small record of each run in `bench/results/<run>.json`, so the figures outlive the machine. [Benchmark results](benchmark-results.md) takes its tables from these records.

- Give it run folders, or run names that this checkout's `target/runs`, `target/bench` or `target/gate` holds. It reads runs of the device runner, of `bun run bench:run` and of `bun run gate`.
- It keeps benchmark, job worker, comparison, sweep, scale, governor, soak, startup and gate runs. Other plans, such as the checks plan, have no figures to keep.
- A benchmark record keeps the plan's pages, each runner's device and browser, and each page's medians. It also keeps each null3D page's share of three.js, by whole frame and by own work. Each run's figures stay too: CPU time, own work, frame interval percentiles, frames per second, GPU time, preset and heat. Where the browser times passes, each pass's GPU time stays too.
- A comparison keeps its verdict, each page's medians and changes, and each run. A gate run keeps each step's figure and verdict, and the benchmark runs of its timing steps.
- The governor, soak and startup plans keep the runner's report, and each page's result without images, browser facts or lists of more than 120 entries.
- Records keep no frames, images, per-second lists of benchmark runs, or WebGL call tables. Fractions keep four significant digits. A record takes under 1 KB to 35 KB, and 229 runs take 1.75 MB.
- The commit comes from the run's own record where it has one, as the gate and comparisons do. Otherwise it is the commit that the checkout held at the run's start, read from the checkout's HEAD reflog. Edits that were not committed do not show.
- A run in Playwright records the machine that archives it as its device. So archive such runs on the machine that ran them.
- Pages from before the engine's rename get null3D's page names in the record.
- The command prints the run's rows for the results page. `--rows` prints the rows of every record, one table for each scene.
- `bench/lib/archive.ts` holds the reading and the rows, and `bench/lib/archive.test.ts` tests them on small run folders.

## Grid-cell culling

- S1-cells spreads S1-static's boxes over 8 x 8 grid cells, 8 km on each side. Its camera flies low along -Z at 200 m/s, so a few cells are in view. New ones come into view about every 5 seconds.
- The page kinds that end in `-half` start null3D with `?half=on`, so the scene shaders do their color math at half precision. [D-09](decisions/D-09-half-precision.md) gives the commands and the results on the Mac, the iPad and the S24+.
- The page kind `null3d-webgpu-index` starts null3D on WebGPU with `?instances=index`, so the vertex shaders read each culled instance by index from storage buffers instead of a copy. [D-23](decisions/D-23-index-instances.md) gives the commands for the Mac and the iPad.
- The page kinds that end in `-cells-off` start null3D with `?cells=off`. Culling then skips no cell: WebGPU's culling pass covers every source. WebGL2 culls every object. It builds no clusters for a static batch whose rows lie in several cells.
- On the Mac, compare both paths with and without cells: `bun run bench:run --scenes s1-cells --pages null3d-webgpu,null3d-webgpu-cells-off,null3d-webgl2,null3d-webgl2-cells-off,threejs-webgpu,threejs-webgl,scene-code`.
- On the phone: `bun tests/real-browsers.ts --plan bench --allow-no-webgpu --android chrome --scenes s1-cells --pages null3d-webgl2,null3d-webgl2-cells-off,threejs-webgl`.
- The MacBook Pro ran S1-cells in Chrome at 144 Hz, 3 runs of 10 s per page (`target/bench/20260930-052100-bench`). Other builds loaded the machine at the time. On WebGL2, cells cut the busiest thread's CPU time from 0.21 ms to 0.07 ms per frame. They cut all threads' time from 0.54 ms to 0.12 ms. Each frame then listed 79 entries instead of 1,517. three.js's WebGL renderer took 0.07 ms.
- On WebGPU the CPU time stayed at 0.10 ms, because the GPU culls. The culling pass took 0.025 ms of GPU time with cells and 0.039 ms without them, and the drawing pass 0.082 ms either way.

## Many point lights

- S3 stands 20,000 still boxes in one instance batch on a floor 200 m wide. 256 point lights with a range of 12 m light them, and each light moves on a circle of its own. The camera orbits. `?n=` sets the box count, and the lights stay at 256.
- The boxes stand on a grid, one per cell, and never touch. Where two boxes meet, some pixels have equal depth, and the GPU can draw them in either order. With random places, the image test's two thread modes differed by one pixel on SwiftShader.
- The sun and the ambient light are dim, so the point lights stand out. The twin's hold frame shows a pool of colored light under each point light.
- The three.js twin draws the 256 lights as `PointLight` objects with a distance and a decay. WebGPURenderer shades them through three.js's clustered lighting, the `ClusteredLighting` addon (Forward+). It assigns each light to the clusters of the view that its range reaches, so each fragment shades only its cluster's lights.
- WebGLRenderer has no clustered lighting. Its shader for 256 point lights needs more than the 1,024 uniform vectors that the Mac's GPU gives a fragment shader in Chrome. The shader fails to build there, and the WebGL page reports the GPU's reason and draws nothing. A benchmark run then lists the WebGL page as failed. A device without WebGPU has no three.js twin of S3 when its GPU has the same limit. WebGLRenderer fails to build that shader in Chrome and Brave on the S24+, and in Safari on the iPad. The error is "FRAGMENT shader uniforms count exceeds MAX_FRAGMENT_UNIFORM_VECTORS(1024)".
- SwiftShader gives a fragment shader 4,096 uniform vectors, so the WebGL twin's shader builds there, but only after minutes. The page tests leave that page out on SwiftShader. The WebGPU twin's short run warms up for 5 seconds and measures for 5, because its first frames take seconds on SwiftShader.
- The parity checks leave S3 out, because each of them compares with WebGLRenderer's frame. `LEFT_OUT_OF_PARITY` in `bench/lib/parity.ts` lists why a scene is left out: a feature that its twin draws and null3D does not draw yet, a twin that cannot draw it, or a tier whose frame differs from the twin's by more than the checks allow.
- On WebGPU a compute pass lists each cluster's lights (M1-E3), and the CPU only uploads the light list. A comparison with `bench:run --compare` measured it in 10 rounds on the Mac in Chrome at 144 Hz. S3's own work per frame on WebGPU went from 0.140 ms to 0.070 ms. The busiest thread went from 0.153 ms to 0.087 ms. WebGL2, where the job workers still list the lights, did not change. The GPU time per frame went from 2.85 ms to 3.06 ms: the pass's three dispatches take about 0.2 ms at the clock speed the GPU keeps in this scene.
- On the Mac: `bun run bench:run --scenes s3 --pages null3d-webgpu,null3d-webgl2,threejs-webgpu,scene-code`.
- On the phone: `bun tests/real-browsers.ts --plan bench --allow-no-webgpu --android chrome --scenes s3 --pages null3d-webgl2,null3d-webgl2-low,scene-code`.
- On the iPad: `bun tests/real-browsers.ts --plan bench --lan ipad-safari --scenes s3 --pages null3d-webgpu,null3d-webgl2,threejs-webgpu,scene-code`.
- [D-06](decisions/D-06-success-targets.md#s3-s4-and-s1-at-phone-scale-on-each-device) gives S3's figures on the S24+, the iPad and the Mac.

## The phone scene

- S4 is a town of 4 x 4 blocks. Its 5,000 still objects are buildings, what stands on their roofs, street furniture and road marks, in 48 mesh and material buckets. 200 vehicles drive the streets as dynamic objects, in 4 more buckets. They drive along X in 10 lanes, 20 to a lane, and each lane keeps one speed. So no two vehicles ever overlap. Overlapping surfaces at equal depth draw in either order on WebGPU, and the image test's thread modes then differed by a pixel. ### What S5 found

- glTF names a KTX2 image only through `KHR_texture_basisu`, so the asset tool turns that extension on whenever it writes KTX2 files. Without it, three.js can load no model that the tool optimized.
- On WebGPU, the objects that the skinning pass skins each draw from a bucket of their own, and every bundle names every bucket. A fixed room of 16,384 words in the draw list would fail 500 knights' first frame with E1501. So the builder reserves the words that the camera, prepass, cascade and tile bundles can take, for the layouts as they stand. A Rust test draws 5,000 skinned copies on both builders.
- The Knight's material is double-sided, so both engines draw its lit faces into the shadow map. null3D's default `normalBias` of 0.02 m keeps those faces from shading themselves. So the cascades of S4's and S5's twins take null3D's default `normalBias`, which three.js gives in meters too. Without a normal offset, three.js speckles the sunlit helmets with acne. null3D's frame then differs from three.js's in 0.93% of its pixels on WebGPU, 0.95% in compatibility mode and 1.76% on WebGL2. three.js's two renderers differ by 0.69%. With knights that receive no shadows, both tiers differ by only 0.12%.
- By [D-52](decisions/D-52-intent-parity.md), S5's comparison with three.js is strict: skinning poses, animation sampling and the glTF material are shared building blocks. The twin's offset gives both engines comparable shadow settings, as equal work asks. The shadows' own technique still differs. S5 passes because its frame differs from three.js's less than three.js's two renderers differ from each other.
- With the offset, S4's figures hardly move: 0.156% on WebGPU, 0.173% in compatibility mode and 0.242% on WebGL2, against 0.159%, 0.174% and 0.248% without it.
- S5 and its twin blend clip weights, and each character starts its clips at its own time ([D-62](decisions/D-62-clip-weights-and-blends.md)). On the Mac's GPU, 0.261% of S5's pixels differ on WebGPU, 0.307% in compatibility mode and 0.197% on WebGL2, against 0.451% between three.js's renderers. SwiftShader gives 0.272%, 0.293% and 0.193%, against 0.536%.

- At 500 knights, each frame moves about 1,500 small runs of rows in the resident texture. One write per run held null3D's WebGL2 path at 8.4 frames per second on the Mac, with the GPU 233 ms behind. So the upload joins runs that lie close together ([Implementation notes](implementation-notes.md#safaris-webgl2-path)).
- The Mac ran S5 at 500 knights at High with the governor off. Each page had 3 runs of 10 seconds' warm-up and 10 measured, taking turns (`target/bench/20261004-112928-bench`). null3D's WebGL2 page took 1.25 ms of CPU per frame (1.20 to 1.39). It held 120 frames per second at 120 Hz with 42 draw calls. three.js's WebGL renderer took 54.02 ms (51.62 to 60.58) and drew 18.4 frames per second. null3D's WebGPU page took 2.32 ms (2.07 to 2.75) and 7.38 ms of GPU time. It drew 20,002 draw calls, one per skinned object in each pass. The display ran at 60 Hz during its turn, so its frame rate gives no figure.
- Another run timed WebGPU with `?skinning=vertex` too. It took 1.50 ms (1.40 to 1.54) against 1.93 ms (1.83 to 1.93) with the compute pass, at 4.75 and 4.35 ms of GPU time. three.js's WebGPU renderer took 133.65 ms and drew 7.5 frames per second.

## The city

- S6 draws the generated city of the sample content: 19,173 objects in 200 materials. Its 144 blocks hold towers, kit buildings, roads and street props. `?n=` keeps only the objects nearest the camera's start, up to the whole city. The layout comes from the sample content's seeded generator ([Sample content](sample-content.md#the-city-of-s6)).
- `bench/lib/city-files.ts` turns the layout into two model files. The kit file holds each part of the 98 Kenney models once, as a node of its own. The tower file holds one mesh per material, 200 in all, each with every one of the 1,849 boxes in that material, and the layout's 200 materials. So each material's towers take one draw ([D-106](decisions/D-106-s6-city.md#one-tower-mesh-per-material)). A box's texture coordinates count meters, so a stretched box keeps the texel size of a small one. Occlusion, roughness and metalness of each texture set go into one image, in glTF's channels. The asset tool then optimizes both files, as for any model a page imports with `?optimized`. Both engines load the same files.
- The optimized files take 35.5 MB: the kit 1.8 MB, the towers 0.8 MB of meshes and 33 MB of KTX2 textures. On the GPU the textures take 87 MB as ETC2 or ASTC, and 133 MB as BC7. The scene draws about 3.85 million triangles. The tool gave 63 of the 122 kit parts a blocker. Each tower mesh blocks with its own boxes, since no blocker of one or two boxes fits boxes spread over the city. On WebGL2 the tower meshes then crowd the kit's blockers out of the frame's budget, so occlusion hides about 80% fewer index list entries than with a mesh per box ([D-106](decisions/D-106-s6-city.md#blockers-by-connected-part)).
- null3D makes one object per model part and row, and one per tower mesh, with `createMesh`, from the nodes of the loaded files. A copy from `scene.instantiate` would add a group per copy. Each object casts and receives shadows. Each keeps the tool's blocker choice through the node's `occluder` field. The whole city makes 19,089 objects, so the page asks `createEngine` for room for 19,100 with `expectedObjects`, and the object tables never grow in play.
- The scene streams in. The setup waits for the layout and the kit file, creates the nearest objects and returns, so the first frame comes early. Each frame then creates the objects of up to 3,000 more rows, nearest first, and the tower meshes once their file is in, in the order of each material's nearest box. A tower mesh comes whole, so `?n=` below the whole city draws every box of each material that its rows reach. The sketch then tells the page the time of each stage. A timed run warms up only when the city is whole. A held frame loads everything first.
- An evening sun casts shadows, and 32 street lights light the camera's route. A Poly Haven environment lights the rest, and the analytic sky fills the background. Bloom and ambient occlusion are on. The preset decides the shadows and ambient occlusion (High and Ultra). Every preset leaves software occlusion culling off, as it cost more than it saved here on WebGL2 ([D-22](decisions/D-22-occlusion-presets.md#software-occlusion-culling-on-webgl2)). The page turns GPU occlusion culling on. The engine's `?occlusion=on` turns both methods on, and `?occlusion=off` turns both off.
- The camera drives the layout's closed route at 12 m/s and 8 m high, looking 30 m ahead. Clicks pick buildings through pointer events, and a label names the picked building at the hit point. On a tower mesh, `s6BuildingAt` finds the box nearest the hit point among that material's boxes, in both engines. Labels follow the eight tallest towers. `?demo` adds the stats overlay, and Space pauses the drive.
- The three.js twin loads the same two files with `GLTFLoader`, `KTX2Loader` and `MeshoptDecoder`. Each kit part draws as one `InstancedMesh` with a row per copy, which three.js advises for many copies of a mesh, with shadows. The tower meshes stay the meshes the loader made, one per material. It streams in as null3D's page does. `PMREMGenerator` prefilters the environment, and the `Sky` addon draws the sky. Its shadows come from the cascaded shadow addon, as in S4's twin. WebGPURenderer shades the street lights with clustered lighting. On WebGLRenderer, `EffectComposer` runs `GTAOPass` at the preset's ambient occlusion scale, `UnrealBloomPass` and `OutputPass`. On WebGPURenderer, the render pipeline runs the same as nodes. `Raycaster` picks with three-mesh-bvh's trees, and `CSS2DRenderer` draws the labels. three.js has no occlusion culling.
- Each engine draws bloom and ambient occlusion with its own technique. null3D's bloom works down a chain of mip levels, where three.js runs `UnrealBloomPass`. null3D's occlusion darkens only ambient light, and `GTAOPass` darkens the whole image. So the parity checks leave S6 out, and its frames carry a quality note ([D-52](decisions/D-52-intent-parity.md)).

### What S6 found

- The sample content's generator moves each lot's props in from the lot's edge by their footprint's reach (null3d-engine/sample-assets#1). So no object stands on the route at the camera's height. Props placed up to 95% of the way to the edge, whatever their size, put 7 industrial tanks into the streets. Each was 15 m wide and 9.6 m tall. The camera drove through them for 123 m of its 2,240 m route.
- The street tiles meet edge to edge, each a copy of one of two Kenney road models. Each copy's corners go through its own matrix, so the two sides of a shared edge do not land on the same screen points. A pixel on the edge can then fall inside both tiles at the same depth. WebGPU draws the copies of one mesh in the order that the culling shader kept them, and that order changes from frame to frame. So such a pixel shows either tile. On SwiftShader, the image test's two thread modes differed by 15 and 106 pixels on WebGPU this way. S1-cells and S4 meet the same case. So `createS6` raises every other street tile by 1 cm, in a checkerboard. The higher tile then wins the shared pixels. A step that small shows in no pixel, and both engines draw it. With the step, SwiftShader's modes matched in 2 runs of 2.
- Other copies of one mesh still meet, in the kit buildings and props. On the Mac, the two modes differed in 2 of 4 runs on WebGPU's tiers. They differed by 1 and by 3 pixels, each by one step of one color. WebGL2 culls in a fixed order, and its modes never differed in 8 runs on both GPU sets. So S6's image test draws one thread mode, and the reference's usual tolerance covers those pixels. The other benchmark scenes check that every mode draws the same image. A fixed order in WebGPU's culling would end such flicker in any scene; that is engine work of its own.
- `GTAONode` on WebGPURenderer reads depth with `textureGather`, which takes no multisampled texture. With the renderer's MSAA, its shader failed to build. The twin's scene pass draws without MSAA when it feeds ambient occlusion, as three.js's own example does.
- On SwiftShader, three.js's WebGPU twin held no frame of the whole city in 90 seconds. On CI's runners, null3D's S6 pages took 30 to 45 seconds to start and drew 0.14 to 0.23 frames a second at 1,000 objects. Two of their five short runs gave no result in 90 seconds, and the benchmark shard ran past its 15-minute limit (run 37709876565). On the owner's Mac, SwiftShader drew the same pages at 8 to 19 frames a second. So the page tests run every S6 page but three.js's WebGL twin and the scene code on real GPUs only, as they do S4's twins. S6's image tests still draw null3D's held frames on SwiftShader. The streamed load runs only in the page tests, so CI checks it on no GPU path; the Mac and device runs do.
- A closed page's work keeps SwiftShader busy. S6's WebGL twin draws about one frame in 8 seconds there. So a browser that ran S6's group takes minutes to set up a new context. The next test on that worker was the S2 shadow test on WebGPU in `bench/tests/visual.spec.ts`. It timed out after 120 seconds while Playwright set up its browser context (jobs 113130738055, 113137014028 and 113135325811). Where it passed, it took 1.9 of its 2 minutes (run 37721425306), against 31 to 50 seconds with no S6 before it. Declaring the group's skipped pages skipped saves their contexts, but the next test after the group still sets one up in the same browser.
- So each test of S4's, S5's and S6's pages opens its page in a browser of its own, the `testInOwnBrowser` fixture of `bench/tests/pages.spec.ts`. The fixture starts the browser with `launchServer` and kills it when the test ends, and SwiftShader's work goes with it. The next test then starts at once. Playwright refuses a group's own `launchOptions`, which would have given the group a worker of its own. A longer time limit would only hide the wait, and each test after the group would lose minutes.
- The page tests check that a hold frame shows more than a sky by its share of pixels at sharp edges. The city's hold frames hold 2 to 5% of them, and a sky alone almost none, so the bar is 1%.
- The first build on a machine generates the city files in about 27 seconds and optimizes them in about 100 seconds on the owner's Mac. Later builds take both from their caches. The benchmark pages' build server in `bench/playwright.config.ts` waits up to 10 minutes. In CI, the `load-pages` job of `ci.yml` builds them once per run, since the benchmark pages bundle them, and hands them to the jobs that load S6 as artifacts ([Sample content](sample-content.md#the-city-of-s6)). The Mac shards of the benchmark job build each compared build's city files into one cache folder, linked into each build's copy. The asset tool keys each optimized model by its inputs, and the city files' folder names the pin, so one cache serves both builds. The cache's key holds exactly the files that the build reads: `bench/lib/city-files.ts` with what it imports, the plugin's asset module, and the asset tool's optimizer with what it imports and its formats' crate. So files that an older version of any of them built are never restored ([Sample content](sample-content.md#the-city-of-s6)). A key that holds more costs time. With all of the command-line tool's sources in it, a change to the tool's add-on check rebuilt the city (run 40053442909). That took 122 s on the run's longest chain. A key that misses an import reuses stale files, so `tools/lib/ci-workflow.test.ts` fails on an import that the key leaves out.

- Across sessions the same page moved further than the cold page alone explains: 23.6 to 23.9 frames in the twelve-page sessions, 28.5 to 30.0 warm in the interleaved session. three.js held 30.8 to 32.0 in the same sessions. A single page, or two pages from different sessions, cannot settle an engine gap; alternate the engines and drop or warm the first page.
- Alternating the engines with three.js first measured three.js at 30.7 frames and null3D at 27.9, then three.js at 17.3 and null3D at 27.7 in the same session ([the run](tested-devices/iphone-17-safari/20261019-053000-battle-webgpu-engines.md)). The device's page-to-page variance is as large as the gap, so that session's pairs only bound it at 2.8 to 7.5 frames.
- A cloud run that judges an engine should therefore warm the device before its first measured page, discard that page, alternate the engines and repeat the rounds. The twelve pages of [the run](tested-devices/iphone-17-safari/20261019-050200-battle-webgpu-twelve.md) keep the figures as measured.

## The depth prepass

- The page switch `?prepass=on` or `?prepass=off` turns the depth prepass on or off, whatever the preset says. Both GPU paths draw it ([Depth on WebGL2](implementation-notes.md#depth-on-webgl2)). `?prepass=on` on a benchmark page, with `measure`'s `gpuPassMs`, gives the prepass's GPU cost in the scene's render pass.
- The page kinds that end in `-prepass` start null3D with `?prepass=on`, so a bench run takes turns between a page and its prepass twin: `bun run bench:run --scenes s2 --pages null3d-webgl2,null3d-webgl2-prepass,null3d-webgpu,null3d-webgpu-prepass`.
- In M1-A7's runs, S2 ran on WebGPU in Chrome on the MacBook Pro, 3 runs of 10 seconds each way. Its GPU time per frame was 0.28 ms without the prepass and 0.41 ms with it. The scene's render pass grew from 0.13 ms to 0.26 ms. S2's trees hide few others, and its shading is cheap, so a second pass over its vertices costs more than it saves.
- M2-R2 ran S2 again with the `-prepass` pages, 5 runs of 5 seconds each, in turns. WebGPU's GPU time per frame went from 0.28 ms to 0.40 ms. On WebGL2 the draw calls went from 101 to 201, and the render worker's time per frame from 0.075 ms to 0.080 ms. Chrome on the Mac has no GPU timer on WebGL2, so the WebGL2 GPU cost needs a device.

So every preset draws the prepass on WebGL2, and WebGPU keeps it off ([D-43](decisions/D-43-webgl2-prepass.md#the-prepass-on-webgl2-at-every-preset)). The page `null3d-webgl2` therefore draws the prepass too. Compare it with WebGL2 without the prepass through `?prepass=off`.

## An alpha-masked lit fragment under MSAA

- The `alpha-mask-cost` page draws a 6 by 4 grid of lit quads that fills the view once, with no overlap, so every pixel shades one fragment. Diagonal bands of vertex alpha cut half of each quad's fragments. The page swaps every quad between the masked build of the standard material and its opaque build in turns, so the two sides shade the same pixels of the same geometry and differ only in the alpha test and the discard that follows it. This is the study's pattern: the fragment shader reads its material from a runtime-sized storage array and then discards ([D-226](decisions/D-226-alpha-masked-lit-fragments-under-msaa.md)).
- `?aa=msaa` or `?aa=none` sets the antialiasing when the engine starts, because the mode stays fixed while an engine runs. The page also sets `?prepass=off`, so no side is skipped by a depth already in the target, and `?preset=high`.
- The masked build's cost is the difference between the two sides at one antialiasing mode, for a full screen of it. The part that MSAA adds is the difference between those two differences. GPU time is the figure on every path: Chrome times WebGL2 here through the extension that the engine uses, which earlier sections of this guide say it lacks.
- Run it on the Mac in a quiet lane: `NULL3D_ALPHA_MASK_COST=1 bun run test:browser -- alpha-mask-cost.spec.ts`. The spec turns on Chrome's developer features, without which Chrome rounds the GPU timestamps it reports. `NULL3D_ALPHA_MASK_GPUS` and `NULL3D_ALPHA_MASK_MODES` narrow the run to some paths or modes. On a device through the runner, which needs the browser's window in front: `bun tests/real-browsers.ts --plan alpha-mask-cost Safari --front`.
- On this Mac the masked side is no slower than the opaque one in Chrome on any path. In Safari with MSAA it is 0.29 ms slower at most, for a screen of about 1.5 million pixels. So a scene whose masked areas cover much of the view pays under a third of a millisecond for them there.
- In a real scene the prepass draws the opaque objects and leaves the masked ones out, so the two builds are not equal work there: masked surfaces shade their hidden layers on the paths that keep the prepass. [D-226](decisions/D-226-alpha-masked-lit-fragments-under-msaa.md) gives the figures and what they mean.

## Directional light maps

- The `lightmap-cost` page draws a 6 by 4 grid of lit quads that fills the view once, with no overlap. So every pixel shades one fragment. Each quad reads a normal map whose ridges turn the normal across it, and a light map. The page swaps every quad between the plain light map's build of the standard material and the directional one. The directional build reads a second texture of the bake's own size and weights the baked light by the surface normal. The two sides shade the same pixels with the same radiance. So their difference is the direction texture's read and the arithmetic that follows it ([D-258](decisions/D-258-directional-light-maps.md)).
- The sides take four rounds each, and the order reverses on alternate rounds. A clock or a cache that changes during the run therefore favors neither side.
- Before the timing, the page draws one frame of each side and publishes the share of pixels that moved past four steps. A direction texture that the engine dropped leaves the light map plain. That happens when the direction belongs to another texture array than the radiance's, and the share is then zero. So the test refuses a figure of nothing.
- The page sets `?prepass=off`, so no side is skipped by a depth already in the target, and `?preset=high`.
- Run it on the Mac in a quiet window: `NULL3D_LIGHTMAP_COST=1 bun run test:browser -- lightmap-cost.spec.ts --workers=1`. `NULL3D_LIGHTMAP_GPUS` narrows the run to some paths, as a list. The spec polls the computer's load every fifteen seconds until it is below 8, and it does not check again during the rounds. It prints the load beside its figures.
- A file's tests already run in one worker, so the three paths follow one another rather than timing at once. `--workers=1` states that, so a change to Playwright's defaults cannot make them contend.
- In headless Chrome on this Mac's GPU, the direction cost about a tenth of a millisecond on every path. It was 0.06 ms on WebGPU (0.99 against 1.05 ms) and 0.15 ms in compatibility mode (1.11 against 1.26). On WebGL2 it was 0.10 ms (1.48 against 1.58), for a 1600 by 900 frame. The direction moved 55.71%, 55.46% and 55.48% of the pixels. The figures come from `1c76d6cf8`. The three gates read 7.5, 7.9 and 7.5 before their pages. WebGPU and WebGL2 then measured while the load drifted upward, to 9.9 and 9.2 by the end of their paths.
- An indexer ran at 180% to 280% through the whole run. The two clean paths' gates still read 7.5. Their medians match their trials to 0.00 ms on WebGPU and 0.03 ms on WebGL2's directional side. The compatibility path shared about twenty seconds with another job's commit hook and shader-set copy. Its plain time is 0.12 ms above its trial's and its difference 0.09 ms above. Both carry that doubt, so take that row again first in a quiet window.

### Sky map refreshes

A sky map draws again only when its sun turns half a degree, a color value drifts by a fiftieth, or its clouds drift a tenth of a cell of their pattern. One last fill captures the sky exactly when its sun rests ([D-118](decisions/D-118-sky-environment.md#a-map-draws-again-only-for-a-change-that-shows)). So the cost of a moving sky is the frames that record a stage, not the frames that move the sun.

- `cargo test -p null3d-render --test sky_maps a_day_cycle -- --nocapture` counts them, at 60 frames a second, for a sun scripted to cross the sky. The cases are a still sun with drifting clouds, an hour-long day, a ten-minute day, the showcase's 80-second day and a day a minute. Each case prints the frames that drew a stage, and one fill every 20 frames gives the fills a minute. The test takes about seven seconds and needs no browser. Its output:
  ```text
  sky map fills, at 60 frames a second:
  Still sun, clouds drifting: 100 of 1800 frames drew a stage, 10 fills a minute
  An hour a day: 100 of 1800 frames drew a stage, 10 fills a minute
  A ten-minute day: 700 of 1800 frames drew a stage, 70 fills a minute
  The showcase's 80-second day: 1794 of 1800 frames drew a stage, 179 fills a minute
  A day a minute: 1796 of 1800 frames drew a stage, 179 fills a minute
  ```
  Without the rule, every one of those frames would draw a stage.
- `bun run --cwd tests test image/sky-step.spec.ts` weighs the steps in the picture. It sinks the sun from 8 to 6.5 degrees above the horizon, where its light changes fastest, in three half-degree steps, then fails when two captured frames lie more than 8 levels of 255 apart, when the sweep does not move the light 6 levels, or when it moves in fewer than three steps. It runs on every GPU tier, and takes about half a minute for all three. Each step measures 3 to 4 levels, and the sweep moves the light about 11 levels, on the Mac's GPU and on its software GPU.
- A stage's own GPU time comes from `tests/pages/sky-map-cost.ts`, as [Stages by faces](decisions/D-118-sky-environment.md#stages-by-faces) gives it: about 1 ms on the Mac and about 5 ms on a software GPU.

A sun that crosses a half-degree step faster than a fill's 20 frames keeps the map drawing in every frame, which is why the showcases' own day cycle saves nothing and a still sky saves almost all of it.

## Sweeps for the open defaults

Three sweeps measure the defaults that are still open: the latency mode, the job worker count and the shared memory's maximum. Each runs on the Mac, and on a phone or an iPad through the device runner.

- The page kinds that end in `-low` run null3D in low-latency mode, and the bench plan runs them beside the pipelined pages. On the Mac, run `bun run bench:run --pages null3d-webgpu,null3d-webgpu-low,null3d-webgl2,null3d-webgl2-low`. Compare the presented frame rate, the 95th and 99th percentiles of the frame interval, and the busiest thread. In low-latency mode the sketch worker draws, so its time includes the drawing.
- The page switch `?jobs=<n>` lets the engine start up to n job workers, at most one for each logical core of the device. The job workers start as the scene's parallel work grows ([D-126](decisions/D-126-lazy-job-workers.md)), so a scene with too little parallel work starts fewer. Sweep counts at a size whose parallel work starts them all, and check the job workers that each run's figures name. On the Mac, S1 at 100,000 boxes starts 4 to 16 job workers on WebGPU, more under load, and all 16 on WebGL2. On the Mac, `bun run bench:run --jobs 1,2,4,8,16` runs null3D's two GPU paths at each count. On a phone, add the counts to the bench plan: `bun tests/real-browsers.ts --plan bench --allow-no-webgpu --android chrome --n 300000 --jobs 2,4,6,8`. The summary gives each count's frame time, busiest thread and the sketch worker's own work. A run whose engine took another most fails.
- The page switch `?memory=<MiB>` sets the shared memory's maximum, from 256 to the 4096 MiB that the engine core declares. The engine ignores a value outside that range. It wins over the `memory` option of `createEngine`. The `memory` plan loads the engine test page 20 times at each maximum from 256 to 4096 MiB. It names the largest maximum that loaded every time. A failed allocation counts as a failed load, and `--runs <n>` changes the number of loads.
- Before the loads at each maximum, the memory plan counts how many shared memories with that maximum fit at once. That is how many engines a page can hold. `--runs 0` runs only these counts.

## Download size

- The size report builds the engine test page for production with hidden source maps, which leave the built files unchanged. Vite names each file after a module and adds a hash. The report therefore names each file of the engine's JavaScript by the engine module that it holds. The list of parts is `ENGINE_PARTS` in `tools/lib/size-report.ts`. A new file of engine code fails the report until the list names it.
- The report measures each file three ways: uncompressed, after gzip at level 9 and after Brotli at quality 11. Most hosts send Brotli. GitHub Pages and nginx with its gzip module alone send gzip, and a plain static server sends files as they are. Each budget has a size in each column, and a file over any of them fails the build.
- The report gives two budgets for the engine's JavaScript. [D-14](decisions/D-14-js-budget.md#decision) gives the Brotli column, and [a later section](decisions/D-14-js-budget.md#decision) the others. Only the owner raises a budget, in writing. What a page downloads at its start may take the Brotli figure that [D-14](decisions/D-14-js-budget.md) holds, 448 KB after gzip and 3,328 KB uncompressed. That holds in each thread mode on each GPU path, and the report prints a row for each. A row holds the mode's files, its GPU path's renderers and the largest shader file of that path. Each file that no mode downloads at its start may take 18 KB after Brotli, 24 KB after gzip and 64 KB uncompressed. Such a file loads on a feature's first use, as the glTF loader does with the first glTF file. Or it loads after the first frame, as the preset check does. Or it loads at the first call that reads it, as the frame figures behind `measure()` and the fixes of the errors' messages do. The report lists these files in a section of their own, and no start counts them. `LATER_PARTS` in `tools/lib/size-report.ts` names them.
- Shader files that load on a feature's first use have a budget of their own. Each may take what one start shader file may: 56 KB after Brotli, 320 KB after gzip and 1,792 KB uncompressed ([D-14](decisions/D-14-js-budget.md#first-use-shader-files)). The Brotli figure holds the water add-on's largest set. Each such file holds every build of one feature for one value of the bits that a device fixes. So it cannot fit the limits of other files that load later. Each `[first_use.<feature>]` table of the shader manifest declares one feature's files ([D-56](decisions/D-56-first-use-shader-files.md)); the WebGL2 morph builds are one such feature ([D-51](decisions/D-51-morph-targets.md)). The texture generators' shaders load on first use as a whole, one file per GPU path (`first_use = true` on the shader in the manifest), and count against the same budget. `isFirstUseShaderPart` in `tools/lib/size-report.ts` finds them, and the report lists them in a section of their own.
- A feature that a page does not use adds nothing to the page's start. Its code loads on first use, in a part of its own: add the part to `ENGINE_PARTS` with the part that loads it. A file that loads on a feature's first use must not load on a page that does not use the feature. An engine test checks each such part: "a page that uses no feature that loads on first use downloads none of their files". It runs in every thread mode on both GPU paths, on the dev server and in a production build. Mark a part that every page loads after its first frame with `afterFirstFrame`, and the test leaves it out. Mark a part that loads at the first call that reads it with `onFirstCall`, as the measurement's frame figures and the errors' fixes do. The test leaves those parts out too, and a second test, "a page that measures nothing and throws nothing downloads neither file", checks that such a page downloads neither.
- The thread that draws loads the renderers of its GPU path on demand, as soon as the probe has chosen the path. A page downloads one path's renderers, and the test above checks that it downloads no file of the other path's. `drawingParts` in `tools/lib/size-report.ts` names each drawing thread's files. They are `<thread>-webgpu.js` and `<thread>-webgl2.js`, and `<thread>-gpu-shared.js` with the code that both paths use. In a worker, the null3D Vite plugin starts the shared file's download together with the path's file, as Vite does on the page. A file that loads on demand reads the development constant itself. Its development checks then keep no code of the start's files alive. The split saves 8.5 to 9.2 KB after Brotli in each start ([D-14](decisions/D-14-js-budget.md#one-gpu-paths-renderers-for-each-page)).
- The report lists the WebAssembly modules that load on first use apart from what a page downloads at its start. Its `first-use/` files are two modules. A page downloads the KTX2 transcoder's with its first KTX2 file, and the meshopt decoder's with its first glTF file that holds meshopt data. They have no budget. The transcoder's script goes into the KTX2 task's file, `job-worker-ktx2.js`, which the 18 KB limit of first-use files covers. The growth check covers them all as it covers every file.
- `bun run build:check-size` compares each file's size after Brotli with a build of a base commit. The base is main's own build. The repository keeps no size record, so pull requests cannot conflict over one.
- The base is HEAD's merge base with main. CI tests a pull request as GitHub's merge of it into main, so the base there is the main commit that it merged into. `--base <ref>` picks another commit.
- The check builds the base in a git worktree, `target/.size-base/tree`, with the base's own build script. The base therefore keeps its own flags, toolchain and list of parts. The script's `--sizes-only` builds only what the report measures, without the shader compiler, and writes the sizes. The engine test page's production build reads no module that only a build tool loads. So the base build needs none. A build of the base commit in a clean worktree, with no shader compiler and no asset formats module, writes the page and its KTX2 transcoder, on both GPU paths and in every thread mode.
- A base build can lose its worktree. A tidy-up of worktrees, or a clean of the checkout's `target` folder, removes the folder while the build runs. The build then fails with ENOENT on a file that it had just written. The check looks at the worktree when the build fails. A tree that is gone, or whose checkout is damaged, is made again and built once more. A failure beside a whole checkout is a real failure, and the check reports it at once. So a lost worktree costs one rebuild, and the check always builds a base that has none.
- The shader modules go into the engine's JavaScript, so each base needs its own. The base's build script builds them in the worktree from that base's shader sources. The first such build in a worktree also compiles the shader build's own crates. On a MacBook Pro, that makes the base build take 39 s instead of 21 s.
- The check keeps the sizes of each base commit in `target/.size-base/<commit>.json` and reuses them. Locally it fetches main first. For a new base commit, the check rebuilds only what changed in the worktree.
- In CI, the `size-base` job builds the base beside the `build` job, at the base commit, with that commit's own toolchain, packages and build script. The size check's job, `wasm-checks`, then measures the `build` job's files with `--prebuilt` against the base's sizes, so it builds no WebAssembly. The `build` job builds the same files with the same flags. Building the head's files, then the base's in a worktree, then running the shader compiler test, would take 11 of the job's 15 minutes.
- Almost all of the size check's time goes into compressing the engine test page's files. Compressing one file at a time, the check's step took 23 minutes in CI run 39261942127. A browser job of the same run built the same page in about 40 s. The build held about 6,000 JavaScript files, 2.5 GB uncompressed, and the shader files that load on first use hold 99% of those bytes. Brotli at quality 11 takes 97% of the time. On a MacBook Pro, gzip and Brotli together measured 2.1 MB a second on one core. So the check compresses as many files at once as the machine has cores, on the runtime's worker threads. On that Mac, eight 0.5 MB files take 1,442 ms one after another and 224 ms at once. The report keeps the files' order either way.
- So the check can run in parts at the same time. `bun tools/build-wasm.ts --check-size --prebuilt --part <i>/<n>` builds the page and measures part i of n of its files. It writes their sizes to `target/size-parts/part-<i>-of-<n>.json`, prints its progress and judges nothing. The heaviest files go out first, each to the part with the least weight so far, so the parts take about equal time. Every part builds the same page from the same commit, so every part makes the same split. The parts split the build's files: one build serves every thread mode, and the report works out each mode's download from its sizes.
- A file's sizes depend only on its bytes and the compressors, so the check takes them from the size memo when it can: the sizes of the files that the last measuring met, by the SHA-256 of each file's bytes, in `size-memo/sizes.json` under the build caches' root (`tools/lib/size-memo.ts`). It compresses only the bytes that the memo lacks, and each set of bytes once, however many files hold it. The memo's stamp names the compressors, their levels, zlib's version and the runtime's, so a memo that other compressors made serves nothing. A measuring that compressed a file keeps the entries of the files that it met as the new memo, so the memo holds one build's files and does not grow. In CI each part restores the newest memo from the Actions cache and writes its entries beside its sizes, as `memo-part-<i>-of-<n>.json`. The judge merges them, and `wasm-checks` saves them as the next memo when a part compressed a file. Without the memo, each of four parts built the page in about 63 s (run 39900270572). Each then compressed its 718 MB share for 154 to 302 s, 17 runner-minutes in all. Most of those files held the same bytes as in the run before. The memo also names the set of shader modules that it was measured from, which hold nearly all of the page's bytes. CI's `build` job reads the newest memo and runs one size part when it names this run's set, and four otherwise: in run 39932295661 each of four parts compressed none of its files and took 1.6 to 2.6 minutes, nearly all of it its own build of the page. `NULL3D_NO_CACHE=1` measures without the memo.
- `bun tools/build-wasm.ts --check-size --prebuilt --judge-parts <dir>` reads every part's file from the folder in place of building the page. It measures the build job's WebAssembly files itself. It then prints the same report, writes the same `target/size-report.json` and judges it as a single run does, with the base and the `Size-Growth:` trailers. It refuses a missing part, a part there twice, and parts of different builds or counts. A unit test checks that the merged parts give the same sizes, in the same order, as a single run.
- A part needs the `page-wasm` artifact, and a shallow checkout serves it. The judge needs the `page-wasm` artifact, the `size-base` artifact and every part's file, with the whole history for the base and the trailers. Without either option, `--check-size` builds and measures everything in one run.
- CI keeps the base's sizes in the Actions cache, under the key `size-base-<commit>`. Each run on main saves its own commit's sizes there, in its `wasm-checks` job, also when the check fails. Only main's runs save. A run on main compares with main's commit before its push, which CI passes to the check as `PUSH_BEFORE`, and reads the trailers of every plain commit after it. That commit's own run kept its sizes, so `size-base` usually builds nothing. The commit before, `HEAD^`, would be the wrong base: after a merge of main into a branch and a push, it is the branch's own commit. When no run kept the base's sizes, the `size-base` job builds the base. That happens to a pull request pushed before main's run of its base reached `wasm-checks`. Building it takes about as long as the `build` job, and the size check waits for both.
- The folder is hidden because `bun test` runs the tests of any git checkout inside a folder that is not hidden, even an ignored one.
- The check copies this checkout's Rust build folders, with their file times, into a new worktree. Cargo then compiles only the engine's own crates. Never share one Rust build folder between two checkouts. Cargo finds the engine's crates at the same paths in both, and judges them fresh by file times. The next build of one checkout can then take the other's crates.
- A file fails the check when it grows after Brotli by more than 2% and by 64 bytes or more. A new file of any size fails too, except a file that loads only on the first use of a feature: one of the shader manifest's family tables or combination loaders. Such a file adds nothing to a page's start, and its own budget caps it. A `Size-Growth:` trailer on a commit after the base explains the growth. It names each file as the report prints it and gives the reason. The squash merge copies the messages of the pull request's commits into main's commit, so keep the trailers when you edit a squash message. It drops the messages of merge commits. So the check reads the trailers only of commits that are not merges, on a pull request too. A trailer on a merge commit explains nothing. Put it on a plain commit; an empty commit can carry it.
- The owner's rule: a pull request must never fail CI for a failure that anyone can predict. Small files grew past 2% on nearly every engine pull request with no change to their own code. That is why the check has a byte floor.
- `js/early-core.js` is 231 bytes after Brotli, and it holds the hashed names of both core builds. Each change to the core moved it by about 8 bytes, or 3.5%. Some small files import shared code, such as `js/page-preset-check.js`, `js/page-frame-stats.js` and the call timing files. They moved by 8 to 35 bytes when the bundler renamed or moved that code. Without a floor, each such move needs a commit with a trailer that explains nothing.
- The floor of 64 bytes is about twice the largest change that came from names alone, 35 bytes. In a week of size checks, each growth of 64 bytes or more in a small file came with code of its own. The environment loaders grew by 92 and 105 bytes, the job worker by 83 bytes and the KTX2 loaders by 67 to 104 bytes. Growth of 36 to 63 bytes in a small file passes with no trailer. An example is 62 bytes in the smallest texture coordinate shader file.
- The floor changes nothing for a file over 3,200 bytes after Brotli, because 2% of it is more than 64 bytes. That covers the cores, the start files and most files that load on first use. The smallest budget for one file is 16 KB, and 64 bytes is under half a percent of it. So growth below the floor cannot bring a file near its budget. The budgets do not change.
- Each machine must build the same bytes, or the check on a computer cannot predict CI's. The Rust library's source is installed, because the threaded core compiles the library. The compiler then writes the source folder's place on the machine into the panic locations of the library code. The crates that cargo downloads write their source paths the same way, from cargo's home folder. A Mac's single-threaded core holds the toolchain's folder 9 times. Its threaded core holds it 19 times, and cargo's home once, for the allocator. Each toolchain path on CI's Linux machines is 6 bytes longer than on the Mac, so the cores would differ by 56 and 112 bytes. The hashed name of every file that names a core would then differ too, and so would that file's size after Brotli. The file `js/render-worker-webgl2.js` had the same length on both machines, 53,347 bytes. It measured +1.8% against main on the Mac and +2.1% on CI, so CI failed the check where the computer's check passed. The build therefore gives the library's source the fixed path `/rustc/<commit>`, as the toolchain's own build does. It gives cargo's home the fixed path `/cargo`. Both go through the compiler option `--remap-path-prefix` (`librarySourceRemap` and `cargoHomeRemap` in `tools/build-wasm.ts`). The build hands cargo its options through `CARGO_ENCODED_RUSTFLAGS`, so a folder with a space in its name stays one option. It then refuses a module that holds the toolchain's folder, cargo's home, the checkout's or the home folder. Such a module would also send the machine's folder names to every page that loads it. In CI run 40228450589, no built file held a machine's folder. The single-threaded core and both glue files matched a Mac's build byte for byte. The threaded core and the two tool modules had the same lengths, but their data and a few functions sat in another order. So the page files still differed by 2 to 45 bytes after Brotli. Two clean builds on one Mac match byte for byte, so the build repeats on one machine. One cargo call for both tool modules merges the features of the dependencies they share. With the shader compiler beside it, the asset module's `half` gains `num-traits` and its `libm` gains `arch`. So each tool module builds in a cargo call of its own. Whether that closes the tool modules' difference with CI is not yet measured. A single-crate build on the Mac still differed from CI's asset module by 1,054 bytes. The threaded core's difference is still open: it is the one build that compiles the Rust library from its source. A file that stops a few bytes under the limit can therefore pass on a computer and fail on CI. The check warns about a file that grew by more than 64 bytes and stopped within 64 bytes of the limit (`nearLimit` in `tools/lib/size-check.ts`). Give such a file a `Size-Growth:` trailer.
- A start or a budgeted file that passes 97% of its budget in any column gets a warning, which names the bytes left. Under GitHub Actions each warning of the size check is an annotation on the run's page, since a line in a long log goes unread. Without the warning, a first-use shader file can stand at 99.8% of its uncompressed budget with no word from the build. The next branch then takes it past ([D-14](decisions/D-14-js-budget.md#first-use-shader-files)).
- The check prints each file's growth in the log, and CI adds the table to the job summary.
- On GitHub's Linux machines, the base build takes about 28 s, because it compiles only the engine's own crates and builds no shader compiler. On a MacBook Pro, the first local run took 21 s, and the base build took 12 s of that. A later run with the same base took 14 s, against 8 s for `bun run build`, and the fetch of main took most of the difference.

## Startup

- `bun run bench:startup` times the start of the engine test page in Chrome, from navigation to the first frame. It builds the page for production, serves it with `vite preview`, and drives Chrome through its debugging protocol.
- Without options it times three cold loads in the pipelined mode, on WebGPU and Slow 4G. Each cold load gets a fresh Chrome profile, so even the GPU shaders compile from scratch.
- `--loads cold,warm` adds warm loads, `--network slow-4g,full` adds loads at full speed, and `--modes all` runs every thread mode. The tool also takes `--runs`, `--gpu` and `--switches`.
- `--android` drives Chrome on the phone instead. It makes five loads of each kind, in every thread mode, cold and warm, on both networks. [Device sessions](devices.md#startup-times) says how cold loads avoid the phone's caches without clearing them.
- Chrome refuses network limits on a worker. It applies the page's limit to a worker's own requests only once the debugging protocol's Network domain is on in that worker. So on Slow 4G the tool attaches to each worker, which waits at its start until the domain is on.
- Without that step, the workers would load the core's loader and the sketch at full speed. The first frame would then come about a second early.
- On Slow 4G the start is a chain of round trips of at least 562 ms each. After the page and its script come the core, the probe worker and every other download that the start needs. With worker threads these are the workers and the sketch module. In single-threaded mode they are the core's loader, the sketch module and the renderer. The workers then load the core's loader while the core still downloads.
- So the core is the last download in most modes, and the engine is ready soon after it. [Implementation notes](implementation-notes.md#start-order) give the order and the times.
- In Chrome 154 on the MacBook Pro, a cold load in the pipelined mode finished its first frame after 4.0 s on Slow 4G. A warm load took 0.7 s, and both took about 0.1 s at full speed.
- The shader file of the device's GPU path and fixed bits downloads with the core. The page starts it right after the GPU probe, as [D-13](decisions/D-13-shader-variants.md#the-download-after-the-core-t-28) says. A request after the core would come one round trip later.
- The MacBook Pro also ran Slow 4G and WebGL2 in Chrome 154, while other work loaded it. A cold load took 4.20 to 4.26 s in each thread mode, and a warm one 0.68 to 0.71 s. Each figure is a median of 10 loads. With the file asked for after the core, a cold load took 4.76 to 4.83 s, and a warm one 0.68 to 0.77 s. In those loads the core was 249.4 KB after Brotli, and a cold load downloaded 363 to 371 KB.

## Soak

- `bun run bench:soak` runs the production build, and samples every 30 seconds. Before each sample, the page, the sketch worker and the render worker collect their garbage, so a sample counts only what they keep.
- While the engine runs, a job worker blocks inside the job system's loop, so it never runs a collection that the debugger asks for. The soak reads its heap as it is, garbage included.
- The WebAssembly memory's size comes from `Runtime.queryObjects` on the page, because the engine keeps the memory out of the page's global scope.
- The soak judges the run after a 2-minute warm-up. The sketch worker's and the render worker's heaps may each grow by 256 KB. The growth is the median of the last three samples less the median of the first three.
- The WebAssembly memory may not grow at all, and the engine must still draw at the end.
- `--scene s4` soaks S4, the phone scene, as M1's exit gate asks. Its shadows, street lights, moving vehicles and quality governor run frame code that S1 never reaches. S4 has a fixed count of objects, so the soak ignores `--n` there. `bun run bench:allocation --scene s4` samples the same scene, on WebGPU or with `--gpu webgl2`.
- `--scene s5` soaks S5, the crowd, and `--scene s6` soaks S6, the city, as M2's exit gate asks. Each runs at its own count unless `--n` names one. The page runs the scene with `?keep`, as a timed run draws it, until the page closes, and measures nothing. A demo would add its controls and the stats overlay. S6 streams its city in after the first frame, so the soak and the allocation check wait until the city is whole before the warm-up starts. The page sets a flag when the scene that the sketch builds is whole, and they wait up to 5 minutes for it.

## Allocation and profiling

- `bun run bench:allocation` samples allocations after a warm-up of at least 30 seconds and 3,600 frames. The browser optimizes code that runs once per frame only after thousands of frames, so a display at 60 Hz takes a minute. `--warmup-frames` sets another count for a quick look. A shorter warm-up can fail on code that the browser has not optimized yet.
- A page that runs slowly is not always the scene's fault. A software GPU runs both sides of a
  branch, so texel reads in a plain branch cost every software page, even with their feature off.
  Four such reads for sharpening made S1's allocation warm-up 1.4 times slower on the same Mac.
  Every counter was the same except the GPU time, and the extra time sat in the final pass. Read the
  per-pass GPU times before blaming a scene, and put optional reads in a loop of no rounds rather
  than a branch.
- While it warms up and samples, the check moves the mouse over the canvas and presses a key and the mouse button. So the samples cover the sketch's reading of input, and that code is warm when they start.
- Two render-worker places are judged per browser call, not per frame: the browser's own objects between tasks, `(IDLE)`, and objects in the JS engine's code, `(JS)`. The browser calls the render worker at the display's rate, while the check counts frames. On SwiftShader a frame that takes a second takes about fifty calls. These places then weigh about fifty times as much per frame. Judged per frame, two slow runners failed at 865 and 965 bytes a frame at `(IDLE)`. A run of the same code whose warm-up was 2.6 times faster read 698 for the whole worker. The budgets are 48 and 24 bytes per call, the figures a real GPU reads per frame. The render loop counts the calls for the check. The software GPU keeps per-frame figures as a fallback, of 1,024 and 640.
- Places that allocate because the browser does have budgets with their reasons in `bench/allocation.ts`. The frame's pending reads allocate 18.2 bytes per frame, with S1 reading once a frame. The sketch worker's frame wait allocates the result and promise of its `Atomics.waitAsync` call once a frame. The check counts the wait's objects in `runPipelined`, the loop that awaits them. The browser's inlining moves them between the two places. Every other place must stay under 4 bytes per frame. Add `--n 30000` to include the staging ring.
- A budget names its place by function and file. A function that moves to another file loses its budget, and its place falls to the 4 bytes. A move of each GPU path's renderer into a file of its own (#457) failed the check on both paths this way. Its drawing step allocated the same 156 bytes per frame on WebGPU and 48 on WebGL2. So a unit test checks that each budget's file still defines its function.
- A figure belongs to the tree that made it, which need not be main. The check builds the pages from the working tree, so each place names that tree's code. A branch that stands on an older main reports that main's code. A branch from before `2b999f25b` read the impostor switch at 187 KB per frame, from the per-card `Math.hypot` that the commit took away. So read `git log origin/main -- <the file the place names>` before a figure goes to the coordinator. Report the commit that the branch stands on too.
- `--terrain` and `--impostors` put the terrain and impostors add-ons' frame paths under the check, and both pass. The impostor switch passes on main at 230.5 bytes per frame, with a static batch and no per-card `Math.hypot`. The terrain switch passes at 308.1 bytes per frame, and every terrain place is under the 4 byte budget. The terrain's path avoids four things that each make one object per call. They are a leaf key past the small-integer range, `Math.hypot` and `2 ** level`, and a search callback inside the engine's vertex update. The fourth is fractions that cross the call into the add-on's `update`. The add-on's frame step takes the camera's position array, `terrain.update(eye)`, as the impostor add-on's does. A fraction that crosses a call the browser does not inline becomes an object ([Implementation notes](implementation-notes.md#hot-paths-without-allocation)).
- `--splats` puts the splats add-on's task path under the check: a cloud of 50,000 Gaussians above S1, of which 20,000 draw, cut into chunks whose counts a job worker chooses from the orbiting camera's position in every frame, through the public task hook. The switch asks about once per frame, so the loader's message and promise objects would weigh once per frame too. The check counts the sketch worker's tasks (`__null3dTaskCalls`) and judges those places per call, as it judges the render worker's `(IDLE)` and `(JS)` per browser call; `TASK_CALL_BUDGETS` in `bench/allocation.ts` holds each budget and its reason. On the Mac with WebGL2 at `dc1e9d557` the run read 506.7 bytes per frame on the sketch worker and 138.3 on the render worker, and passed. Each sample held 266 task calls, with 360.5 of 560 bytes at the loader's `run` and 145.0 of 240 at its answer handler. The promises took 94.8 of 160 and the add-on's `choose` 38.7 of 64, and every per-frame place stayed inside its budget. On SwiftShader's WebGPU path at the same commit it passed at 1,159.7 bytes per frame on the sketch worker and 534.6 on the render worker: 39 task calls in each sample, 434.9 of 560 at `run`, and 98.1 of 128 at `pose`, the frame step that inlines the ask there, which the Mac charges to the loader's places. The render worker's 534.6 is six times the 91.9 that the run before the streaming rewrite read there, and it stays inside every budget: the replay's two draw places took 173.1 of 400 and 135.2 of 512. The add-on's own frame step makes no array and no number object: the camera's position is a typed array that the path copies into, and a small step passes it to the add-ons; the task writes the counts into the buffer that both threads share, the packing keeps each chunk's prefix views, and the loader reuses its waiting records, request objects and empty transfer list. A production page needs two things from the plugin here. It builds a TypeScript task module for the worker, and it keeps Vite's page preload helper, which reads `document`, out of the sketch worker. The spec `tests/image/addon-tasks.spec.ts` proves the thread, and this switch proves the path.
- CI runs the check, by the owner's decision ([D-125](decisions/D-125-allocation-check-in-ci.md)). The `allocation` job samples S1 on WebGPU and on WebGL2. Each GPU path gets a machine of its own with no other work, since a busy machine moves the figures. The job runs on each push to main. On a pull request that is ready for review, it runs only when the pull request changes what the check covers. That is `packages/engine/src/render/`, `gpu/` or `sketch/`, the check and the files it uses, or the CI workflow. The `changes` job decides that ([Branches and parallel work](pull-requests.md#cis-jobs)).
- In CI, and wherever `CI` is set, the check runs Playwright's Chromium without a window, on SwiftShader, as the browser tests do. SwiftShader draws S1's 100,000 boxes at under one frame a second, so the check draws 1,000 boxes there. Each frame runs the same engine code whatever the count. On CI's machines SwiftShader drew 1,000 boxes at 3 to 8 frames a second. So the warm-up of 3,600 frames took 8 to 18 minutes. The browser's optimizing compiler takes a function after 3,000 calls, and frame code gets one call per frame. So on SwiftShader the check lowers those counts, and warms up for 1,200 frames. S1 also draws at half the pixel ratio on SwiftShader, so a frame shades a quarter of the pixels. A frame's engine code is the same at any size. At the full pixel ratio the warm-up took 167 to 332 seconds in four full runs. At half, it took 63 seconds on WebGL2 and 94 on WebGPU in test run 40076045763, and both checks passed. With the browser's own counts, 1,200 frames are too few: the sketch's phase timer and the canvas view's helper still allocate ([D-125](decisions/D-125-allocation-check-in-ci.md)).
- On a real GPU the engine draws a frame at each of the display's frames, so the check counts the display's frames on the page. On SwiftShader the page got 3 to 10 times as many frames as the engine drew. Bytes per display frame would then show a third to a tenth of the truth. So there the check counts the frames that S1's sketch steps, which the page's `frames` switch publishes. So the check samples only S1 on SwiftShader.
- The browser still calls the render worker at the display's rate. So on SwiftShader, work that runs at each call weighs several times as much per frame. `SWIFTSHADER_BUDGETS` in `bench/allocation.ts` replaces three budgets there. Two are the browser's own objects between tasks, `(IDLE)` and `(JS)`. The third is the completion tracker's clock reading at each check of a frame that the GPU still holds. After the full warm-up, CI's runs failed only on those places with the Mac's budgets. Every place of the engine's frame code stayed in its budget. The Mac's budgets hold for `bun run gate` and for runs on a real GPU.
- The check opens the page with `?keep`, which runs the scene as a timed run draws it until the page closes, and measures nothing. A demo would draw the same in S1 to S4, but S5's and S6's demos add their controls and the stats overlay. A timed run long enough to outlast the samples does not serve either. On SwiftShader the warm-up can outlast it, and the page then stops the engine while the check waits for frames. A frame count that stands still for a minute fails the check.
- After the warm-up, each call to the browser has a time limit of one minute. That covers the heap profiler's start, each sample's start and stop, and the frame count. When one runs out, the check fails and names the call. The mouse and key presses are the exception. On SwiftShader one of them now and then never returns, and the input stops while the frames go on. The check then prints a warning and judges the samples as usual. Its summary line gives the input steps that the samples held. A stuck input call stopped 3 of 12 trial jobs. Without the time limit, one of them waited for 40 minutes with no output, until CI ended the job.
- `--animated 64` adds 64 animated characters of 40 joints to S1. Each plays a clip, a masked layer and an additive layer, and has event handlers. Each frame, the sketch sets a layer weight of every character, and a blend value or a clip weight. Now and then a character cross-fades, plays its blend again with other points, or fades its clips to new weights, with options and points in frozen constants. Every fourth character turns two joints with a set and an added rotation, and every fourth from the fourth aims a chain of three joints at a moving point, at a moving weight. The crowd makes those joint calls from a small step of their own, which reads the time from an array. So the browser inlines them and boxes no weight. Both GPU paths pass with them. The sketch worker allocated 207 bytes per frame on WebGPU and 218 on WebGL2. No place of the joint calls, the crowd's code or the animator showed. Each character is a skinned mesh, a small box at each joint, in rows in front of S1's boxes. The job workers pose them, and both GPU paths skin them each frame. - Chrome's heap profiler charges each object to the outermost optimized function on the stack. When the browser inlines a function into its caller, the function's objects count in the caller's place. So a budget also covers the functions that the browser inlines into its place. A change that alters what the browser inlines can move the same objects to another place. The WebGPU backend makes the canvas texture's view in `colorView`, which the browser does not inline into the replay (#384). The canvas hands out a new texture each frame, so its view must be made each frame, at 33 to 35 bytes per frame. So the check counts `colorView` and `targetView` in the replay, whose budget holds the canvas texture and its view. `COUNTED_IN_CALLER` in `bench/allocation.ts` lists them. On SwiftShader the objects move between `colorView` and the replay from run to run, while their sum holds. In five runs, `colorView` read 7.3 to 52.8 bytes per frame and the replay 76.8 to 100.8. With samples of 420 frames, `colorView` read 30.5. With a budget of its own of 48, it failed full run 40080490543 at 52.8. The sum of the two still spread from 101 to 130 bytes per frame across those runs. That spread is the size of the samples, not the profiler's split. The profiler records one object for about every 128 bytes. At about 125 bytes per frame, a sample of n frames then holds about n records. Its figure then strays by about one part in the square root of n. A 5 s sample on SwiftShader holds about 135 frames, so the sum strays by about 9%, some 11 bytes. With 20 s samples of 420 frames it strays by about 5%, some 6 bytes, and test run 40082352148 read 126.6 that way. At the full pixel ratio, 40 s samples of 297 frames read 120.8. Those five sums also took each place's lower sample on its own, sometimes from different samples, which pulls a sum down. Read a sum near 130 against that spread before you look for a cause.
- `--no-inline` starts Chrome with V8's inlining off. Each function's objects then count in its own place, so a place that a budget hides shows by name. Calls cost more and box more, so the budgets do not hold. Compare the places with a run of the same scene without the feature, not with the verdict. The labels' half-width helper was found this way. It hid in the sketch's frame step, whose figure swings by up to 80 bytes per frame from run to run.
- The check takes two samples of 5 seconds each, and judges each place by the sample where it allocated less. Allocation in every frame shows in both. Some events happen once, in one sample only, such as a function that runs unoptimized for a moment. The report shows each place's larger figure too.
- When the browser installs code that it has just optimized, it makes a few large objects: the code and its tables. The heap profiler charges them to the first function that runs in the next task, which can be any callback. In one branch's runs, it put five objects of 0.2 to 7 KB in the render loop's frame callback. In each sample, the check sets aside one burst per place. A burst is a run of objects that the profiler sampled one after another at one place. It has at most 16 objects, and it holds at least a tenth of the place's bytes in the sample. A place that allocates in every frame has hundreds of runs between other places' objects, so it has no burst. Code that the browser throws away and compiles again every second or two makes more than one burst in a place, and the others count. That is how the check found S4's replay compiled every 1.5 seconds. The report's larger figure keeps the bursts.
- The browser keeps compiling the render worker's frame code for minutes. A trace of S1 on WebGPU ran on a 120 Hz display. From 30 to 145 seconds after the start, the browser compiled frame code 24 times, to its top or middle tier. It compiled the replay's `passCommand` at 38 seconds. Without bursts set aside, the wake-up timer of the render worker failed 3 of 5 runs on a quiet Mac. The load was 4 to 6, and the timer took 6.1 to 6.8 bytes per frame of 4. Its callback is empty. One burst of 9 objects, 17 KB in all, was the installation of `passCommand`. With the timer turned off, the same burst went to the GPU completion callback, which then failed 3 of 3 runs. So no other way to wake the thread avoids it, and the load of the Mac does not cause it. On WebGL2 the same bursts came near the budget but passed 3 of 3 runs.
- After about 140 seconds, the browser compiled the render loop's `draw` with the renderer's `drawFrame` inlined. It did not inline the completion tracker's `afterSubmit`. The queue's promise and its reaction then show in `afterSubmit`, at 136 bytes per frame on WebGPU, and no longer in `drawFrame`. The check gives `afterSubmit` its own budget for them, so a long `--warmup` passes too.
- The check samples the production build. The build's source maps give each place its function and file, so one set of budgets holds for the build and for `--dev`. With `--dev`, the development checks allocate a little more on the sketch worker, which a budget allows.
- `bun run bench:profile` shows where the render worker's replay spends its time. A browser call costs the same from any language. The engine's own share of the replay is therefore the most that a replay loop in another language could save.
- The profile samples the production build, and names its functions through the build's source maps. With `--dev`, it profiles the dev server's pages, whose development checks then count in the engine's share.
- The profiler samples every 50 microseconds after a 20-second warm-up. Code the browser has not optimized yet counts as the engine's, so a shorter warm-up overstates the engine's share.
- `--thread sketch` samples the sketch worker's frame step instead, and splits it between the engine's code, the engine core and the browser. It also lists the engine's per-frame phase times on that thread, such as the update and the batch pass.
- The shipped core has no function names. Build it with `bun tools/build-wasm.ts --names` before a profile, so the profile names the core's functions. The names add size, so that build skips the size checks: build again without it before you check sizes.
- Chrome's page-wide memory measurement waits up to a minute for the job workers, and it counts shared memory once per worker. Chrome's debugger gives exact heaps per worker through `Runtime.getHeapUsage`.

## WebGL call times

The page kinds that end in `-timed` start null3D on WebGL2 with `?gl-timing`. The thread that draws then times each WebGL call while the page measures. The report adds two tables: the calls that took the most time per frame, and the slow calls of the slowest frame, in order. The timing wraps every call and allocates for each one, so these pages are not for comparisons.

- Safari runs WebGL in a process of its own. It answers a call that returns a value only after that process has run every call before it. So the time of such a call holds the process's work on the calls before it.
- The page kinds that end in `-synced` start null3D with `?gl-timing=sync`. Each call then ends with `getError`, which waits for that process, so a wait there counts toward the call that caused it. Writes into a texture count apart for each texture, named by its size and its format's GL code.
- On the iPad: `bun tests/real-browsers.ts --plan bench --scenes s4 --pages null3d-webgl2-timed,null3d-webgl2-synced --runs 2 --seconds 10 --lan ipad-safari`.
- These pages found the two waits that [Safari's WebGL2 path](implementation-notes.md#safaris-webgl2-path) describes. In S3, `fenceSync` took 22 ms per frame. In S4, the synced page put 16 ms on one texture write per frame.

## How the GPU time is measured

- On WebGPU, `measure` and the stats overlay report `gpuMs` from timestamp queries on each pass. A timed frame's commands open with a start mark, an empty compute pass that the timer dispatches first, and each pass writes a timestamp when it begins and when it ends.
- The frame's time is the latest pass end less the earliest pass begin, the start mark's. It is not the sum of the passes' own times: a tile GPU overlaps the spans of its passes, so a sum counts the shared time more than once. A pass that the GPU left untimed, or timed out of order, stays out of the span and of the frame's parts, and the frame keeps the others.
- The browser gives no period for its timestamps. The step between them is the greatest common divisor of the offsets that the frame reads back, not a constant of the device, so the figure follows a browser that rounds to any grid. `gpuStepMs` holds that step in milliseconds, or null when the times look exact.
- Timing runs start the browser with `GPU_TIMING_ARGS` from `packages/cli/src/browser.js`: `--enable-webgpu-developer-features` and `--disable-dawn-features=timestamp_quantization`. Dawn otherwise rounds every timestamp to its privacy grid, and a short pass then reads as 0 ms. `bun run bench:run`, the timing browser tests and the command-line tool's `bench` command use those flags.
- Every test that times a cost starts its browser with these flags, through `tests/lib/timing-browser.ts`. On the Mac, that is its own GPU. The sky map's test also runs on CI, so it keeps the run's browser and adds the flags to it. Without them, a cost test's medians sit on the timer's rounded grid, which [D-136](decisions/D-136-bump-displacement-wireframe.md) measured at a step of about 0.07 ms. A figure is only as fine as its step, so every cost test asks for the exact one. The device runner's Safari and phone browsers take no Chromium flags, so their figures keep the browser's own step. `gpuStepMs` reports that step where the device has a WebGPU timer.
- `bun run bench:run` keeps the medians of the figure in each run's result, and `engine.measure` reports `gpuStepMs` beside it. The stats overlay shows the mean of the last half second, from the same records, and `debug.frameStats()` gives the same figures. A run that still rounds reports its step there, and its `gpuMs` is then only as fine as that step.
- On WebGL2 the frame's replay runs inside one query, so there is no span to take and no step to find: `gpuMs` covers the whole frame, and `gpuStepMs` is null.

## GPU time per pass

- On WebGPU, `measure` returns `gpuPassMs` beside `gpuMs`: the copies before the frame's first pass, each pass, and the time between passes. The bench plan's results keep it in each result's stats.
- In Chrome, the time between the culling pass and the main pass is Chrome's own check of the indirect draws. At 240,000 boxes it takes about 0.1 to 0.3 ms.
- WebKit checks each indexed indirect draw that uses vertex buffers inside its render pass. The check adds two pipeline switches and two vertex to vertex barriers. It also runs an indirect point draw over the draw's whole index count, and it makes two scratch allocations. An empty draw costs almost as much as a drawn one. A raw-WebGPU probe measured about 2.8 us per draw on the iPhone 17, 4.3 on the iPad 10 and 7.3 on the Mac. Every arm of the probe held the same 131 k triangles. The same draws made directly cost 0.06 to 0.5 ms in the whole frame. The cost grows with the passes too: on the Mac in Safari the same 1,024 draws cost 9.8 ms with one pass and 27.0 ms with three, while direct draws stayed near 1.1 ms ([D-174](decisions/D-174-apple-gpu-direct-draws.md)).
- The timer copies a frame's timestamps out only after the GPU has finished the frame, in a submit of its own. Firefox writes them late, so a copy in the frame's own commands read an earlier frame's values ([implementation notes](implementation-notes.md#browser-faults)). A pass without timestamps is left out of `gpuPassMs`, and its frame keeps its other parts.
- The timestamps cover only the GPU passes. Work that the browser does outside them shows in `gpuLatencyMs` and in the frame rate, as [Safari's frame path](implementation-notes.md#safaris-frame-path) describes.
- The timer times one frame in 11, a prime above the longest far cascade interval of 8. Low's far cascade draws once in 4 frames. Timing one frame in 8 would land every timed frame on the same frame of that cycle, chosen by when the run began. On the Mac, every timed frame of one build then fell between the far cascade's turns, so it read too low. On the owner's iPad, every timed frame of f46c0686 held the far cascade, so it read too high. All 225 timed frames held 4 render passes. A unit test holds the count against every interval from 1 to 8. The draw call counts have no such fault: they count every frame.

## Safari's own work

Safari runs WebGPU in its GPU process, `com.apple.WebKit.GPU`, and no engine timer sees the work it does there. Instruments shows it. With Xcode installed, run these while a benchmark page runs in Safari with `?demo`:

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
xcrun xctrace record --template 'Metal System Trace' --all-processes --time-limit 3s --output metal.trace
xcrun xctrace record --template 'Time Profiler' --attach <pid> --time-limit 4s --output safari-gpu.trace
xcrun xctrace export --input metal.trace --toc
```

- The Metal trace names the GPU process's id. Other apps that embed WebKit have GPU processes of their own, so `pgrep -fl com.apple.WebKit.GPU` can list several.
- Export a table with `--xpath '/trace-toc/run[@number="1"]/data/table[@schema="<name>"]'`. `metal-gpu-intervals` gives each encoder's GPU time. `metal-application-command-buffer-submissions` gives each command buffer's time from creation to commit. `time-profile` holds the CPU samples.
- In S1-static at 240,000 boxes, the Metal trace showed about 1.5 ms of GPU work per frame. The profile showed Safari's GPU process spending 9.6 ms of CPU per frame on a native render bundle. The engine makes no such bundle.
