# D-155: The repository runs Bun 1.4.3, whose pipe to Playwright's browser holds

Status: proposed by the helper of M2-EX42, for the owner's ruling. The coordinator asked for the record. Built: main pins Bun 1.4.3 in `packageManager` and CI (`be8606696`), and AGENTS.md states it as a rule. No owner's ruling is recorded. Task: M2-EX42.

Summary: Bun 1.3.14 closes Playwright's pipe to Chrome at random, and Playwright then waits forever. In a loop on CI's machines, 20 of 135 rounds failed on Bun 1.3.14, and 0 of 360 on Bun 1.4.3. So CI, the Mac and `packageManager` run Bun 1.4.3, and a test holds every pin to one version.

## Question

Should the repository move from Bun 1.3.14 to Bun 1.4.3, a new release, to end the hangs of Bun scripts that drive a browser?

## Rule

Move when the newer Bun removes the fault in the same loop that shows it on the older one, installs the same packages, and passes CI's full run. A fault that a guard can only turn into a fast failure still fails runs, so the guard alone does not settle it.

## Data

Each round opens a fresh browser and starts the four pages of the website's build, as the fresh-project test does. Three CI machines ran each row, on the build of PR #534's run.

| Bun | How the browser starts | Rounds | Hung for good | Load timed out | Pipe closed in Chrome's log |
| --- | --- | --- | --- | --- | --- |
| 1.3.14 | Playwright over its pipe | 135 | 11 | 9 | 20 |
| 1.4.3 | Playwright over its pipe | 180 | 0 | 0 | 0 |
| 1.4.3 | A browser server in Node, over a WebSocket | 180 | 0 | 0 | 0 |

At Bun 1.3.14's rate of 20 in 135, the chance of no failure in 180 rounds is about 1 in 10^12. Bun 1.3.14 cannot connect to a browser server at all: its HTTP client mishandles the WebSocket handshake, and Playwright's `connect` waits until its time limit. So no fix that avoids the pipe works on Bun 1.3.14. Bun issue [#34785](https://github.com/oven-sh/bun/issues/34785) reports Playwright's launch failing at random on Bun 1.3.14 on Linux, in the same pipe, and a comment there finds it fixed in Bun 1.4.0's builds.

`bun install` with Bun 1.4.3 leaves `bun.lock` as it is.

How the data was produced: the branch `debug/ex42-site-hang` ran `tests/debug-site-hang.ts`, with `DEBUG=pw:browser`, in runs 38275529510 and 38281539152. [Releases](../releases.md#the-fresh-project-test) gives the fault in full.

## Decision

Proposed: move to Bun 1.4.3. The loop meets the rule, and the lockfile stays as it is. CI's full run on the commit that moves the pin checks the rest. The owner rules, because the release is new and every helper and CI job uses it.

## Consequences

- Every workflow's `BUN_VERSION`, `packageManager` in `package.json`, and the README's requirement name 1.4.3.
- `tests/lib/bun-version.test.ts` fails when a workflow pins another version than `packageManager`, or when an older Bun runs the tests. So the Mac runs `bun upgrade` once the commit that moves the version lands.
- The guard in `launchChromium` stays. It fails a Bun script's browser calls at once with `BROWSER_GONE` if a browser's process ends under Playwright, on any Bun.
