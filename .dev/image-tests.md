# Image tests

This guide covers the image test manifest, its references, and the review that makes a new image a reference. [AGENTS.md](../AGENTS.md) lists the commands, and [Device sessions](devices.md) covers the runs on phones, tablets and the Mac's browser apps.

## The manifest

- `tests/image/manifest.ts` lists every image test. One harness, `tests/lib/images.ts`, runs each test in Chrome through Playwright. The device runner's checks plan runs each test in the other browsers.
- A sketch test names a sketch module and a hold time. The image page, `tests/pages/image.html`, draws the sketch in the engine's hold mode. The image is 320 x 180 pixels unless the test gives another size.
- A page test names a test page that draws and publishes its image itself, such as the texture page or a benchmark page.
- Each demo in `examples/demos.ts` is a sketch test named `demo-` and the demo's name, held at the demo's hold time. A new demo needs no entry of its own in the manifest. A unit test checks that `examples/demos.ts` lists every demo folder, and that each sketch stays under 150 lines.
- A test draws on all three GPU tiers unless it lists fewer. A sketch draws in the pipelined thread mode unless it lists others.
- Every thread mode of a test must draw the pixels of its first mode exactly. A thread mode changes only when the engine draws a frame, so the pixels must stay the same.
- A test can borrow the references of another test: the same scene drawn another way, such as with `?uploads=copy`. A test can also require that every tier draws the image of its first tier.
- A test can require values in its page's result besides the image, such as the replay page's counts of visible boxes.
- A test can add switches on SwiftShader alone, with `swiftShaderSwitches`, for a scene that CI's software GPU draws too slowly in full. Its SwiftShader references then show that lighter scene, and every other place draws the full scene. Only S5 does this: it draws 100 characters on SwiftShader, not 500 ([D-88](decisions/D-88-software-gpu-loads.md)).
- Surfaces that overlap in a test scene never share one plane. In one plane, the draw order picks which surface shows, and the engine may change that order. The texture budget scene drew its small picture in the plane of its two large ones. It lost that picture on WebGL2 when the depth prepass came to every preset there ([D-43](decisions/D-43-webgl2-prepass.md)). Its small picture now sits 1 cm in front.
- Test images live in `tests/pages/assets/`, and sketches fetch them from their own address. The texture tests decode one small picture from PNG, JPEG, WebP and AVIF files, and make their other images in code.
- The KTX2 tests load files that `basisu` 2.50 encoded from PNG files with `-ktx2 -mipmap -y_flip`. The file `quarters-etc1s.ktx2` holds `quarters.png` in ETC1S, with `-q 255`. The file `quarters-uastc.ktx2` holds it in UASTC, with `-uastc` and a half transparent quarter. The ramp of 30 x 20 texels adds `-linear`. The `?compression=` switch draws the `ktx2-bc7`, `ktx2-astc` and `ktx2-rgba8` tests, so every device draws each route. They borrow the `ktx2` references: on the Mac and on SwiftShader, every format drew within 0.003% of the pixels of that image. The texture budget's test page loads `budget-checker-etc1s.ktx2`, the image of `budget-checker.png` in ETC1S.
- `packages/engine/src/scene/ktx2.test.ts` transcodes every KTX2 test file into every format that the engine asks for. It compares each result's SHA-256 with what the official Basis Universal 2.50 build writes. A new test file needs its hashes from that official build. Hashes from the engine's own build would make the test compare the engine with itself. Download the archive that `tools/build-basis-transcoder.ts` pins, and check its SHA-256 there. Then run `transcodeTestFiles` from `tools/lib/basis-transcoder.ts` on the archive's `webgl/transcoder/build/basis_transcoder.js` and `.wasm`. On 7 October 2026 the official build and the engine's build wrote the same bytes for all 20 file and format pairs.
- The command-line tool's tests, `tests/image/cli.spec.ts`, run `bunx @null3d/cli shot` in the fixture project `tests/fixtures/project`. Its images must match the references of the manifest's `project` test, which draws the same sketch. Change the fixture's sketch, and its references change too.
- The tests of `bunx @null3d/cli test`, `tests/image/cli-test.spec.ts`, run it in copies of the fixture project, each with its own `null3d.json`. A copy's references are copies of the manifest's `project` references, so its passing tests need no reference images of their own.
- The harness and `bunx @null3d/cli test` judge images with the same code and the same default tolerance, from `packages/cli/src/compare.js`.
- A page may paint over what GPUs draw differently, and publish it as data instead. The depth precision page paints each pixel where depth fought as the nearer surface, so every GPU matches one reference. It publishes the fighting pixels as fields. The cube and 3D texture page filters a texture of 32-bit floats, which only some GPUs can do. It publishes whether the texels blended, and paints that cell black.

## Adding a test

1. Add the test's entry. A sketch stays under 150 lines, and takes its settings from the query of its path, such as `sketch.ts?fog=exp2`. A module whose path ends in a value with a dot, such as `?scale=0.5`, reaches the dev server as JavaScript. Its type annotations then fail to parse. Put such a value before the others, or keep the sketch free of type annotations, as `bloom-sketch.ts` does. A test page that picks a sketch's settings at run time sets them on the address with `searchParams.set`, after `new URL('./sketch.ts', import.meta.url)`. Vite rewrites a template literal there whose only variable part is the query, such as `` `./sketch.ts?mode=${mode}` ``, into a fixed address. The sketch then reads the text `${mode}`. The destroy test once drew its reference scene twice that way, so it checked nothing.
2. Run the test on the Mac: `bun run test:images -g <name>`. It has no reference yet, so it fails and saves its image.
3. Look at the image with `bun run images:review`. Make it the reference with `bun run images:review --accept <name>`.
4. Make its SwiftShader reference the same way: `CI=1 bun run test:images -g <name>`, then review and accept the image. On the Mac, Playwright's Chromium draws CI's SwiftShader images almost byte for byte. CI's machines are x86 and the Mac is ARM, and SwiftShader can round a pixel one step apart on the two. The city of the occlusion tests differed so in one pixel. So never compare with a reference at zero tolerance across machines. To require the same pixels, draw both images in one run, as the occlusion spec does.
5. Run `bun run check` before you push. It fails when a test lacks a reference in either set, and it names each missing file and the command that makes it.
   After a change that alters what any test draws, also run every test on the Mac's GPU, `bun run test:images`, besides `CI=1 bun run test:images`. Then accept the changed images in both sets. "References" says why.
6. Run the checks plan in Safari and Firefox on the Mac. Run it on the phone and the iPad too, when their GPUs may draw the test another way.

A CI run that finds a missing or changed image saves it too. `bun run images:review --ci <run>` fetches those images for review.

## The feature demos

Each demo in `examples/` is a sketch that the examples page runs live and the manifest holds at one time. These rules keep the held frame and the live page in step:

- A demo computes its motion from `time.now`, not by adding up each frame's step. The character's walk uses the integral of its speed, and the sparks use their flight formula. The held frame is then the same on every machine. Seeded `math.random` calls at setup are safe, because hold mode seeds the generator.
- A demo that starts the engine in large-world mode sets `largeWorld` in `examples/demos.ts`. The examples page passes it to `createEngine`, and the manifest adds the image page's `largeWorld` switch.
- A demo that loads large files sets `timeoutSeconds`, which its image test takes. The glTF model, the character and the environment demos load files of 4 to 11 MB, or filter HDR images on the GPU. On SwiftShader on the Mac they took 14 to 21 s each, with four tests at once, against the default limit of 30 s. CI's machines are slower, so they take 60 s, as the environment tests do.
- Demos load sample content through `sampleUrl('...')` with a string literal, so the sample check finds each file. On a new machine, run `bun run samples:fetch` before the dev server shows them.
- A demo can post a `label` message with `{ id, text, active }`. The examples page then makes an element for the label, binds it with `engine.labels.bind`, and shows the text. The picking demo uses this. The image tests read only the engine's pixels, so they do not show labels.
- The demos use only lights that light surfaces now: no hemisphere lights, which are stored but do not light yet. On 8 October 2026, three demos with hemisphere lights drew their scenes much darker than planned.

Checks of the demos, made on 8 October 2026 while M2-L5 made them:

- Ambient occlusion drew dark dots along the bottom row and the right column of the image. The cause was a normal that is not a number at the occlusion texture's edge. #414 fixed it, and the post effects demo's references were then made again in both sets.
- The character demo's first Mac references framed the camera lower and closer than its SwiftShader references, from the same commit. After the merge with main, the Mac's GPU drew the SwiftShader framing in 9 of 9 runs, so the Mac references were made again. The cause of the first framing was not found.
- Safari in CI drew the glTF model demo with its camera at the start angle, and 6.852% of its pixels differed from the reference. The demo turns its camera with the orbit controls' auto-rotate, which stops when the user asks for reduced motion. GitHub's macOS runner image turns Reduce Motion on (`defaults write com.apple.universalaccess reduceMotion -bool true` in the runner image's `configure-system.sh`), so Safari there reports `prefers-reduced-motion: reduce`, and hold mode passed that to the sketch. Chrome on the Mac's GPU with reduced motion emulated drew the same image as CI's Safari: no pixel differed by more than 3 of 255. Main had the same gap, but no held image on main read the preference. Hold mode now tells the sketch that no reduced motion is asked for ([implementation notes](implementation-notes.md)), so a held frame no longer depends on that machine setting, and the live page still honors it.
- A first look suggested that ambient occlusion and a custom effect together gave wrong colors. That comparison was not fair. The image with both drew brown crates, and the images with one drew gray-blue crates. A fair test drew one scene twice: with occlusion alone, and with occlusion and an effect that changes nothing. Both drew the same pixels. So compare effects in one scene, with an effect that returns its input, before you report a fault.

## Visual checks

Image tests compare one frame with its reference. So they catch a change, but not a fault that shows only over time, or a fault in the reference itself. Ambient occlusion's references held dark dots along the image's edges until 8 October 2026, under the tolerance. So `tests/image/ao-edges.spec.ts` now measures the edges against the scene without occlusion ([D-21](decisions/D-21-effect-chain.md#notes-for-ambient-occlusion)). Three shadow faults reached main, and only the eye caught them. Cascades shimmered as the camera turned (fixed by #198). Shadow edges in the middle distance were jagged (fixed by #211). Moving cars' shadows trailed their cars. The visual checks measure the first two faults as figures with limits. The lag of far cascades that skip frames shows only in live frames, so it has a test of its own: `tests/image/moving-shadow.spec.ts`. It runs each preset with that preset's own `followMovingCasters` and far cascades every 8th frame, and reads 60 frames, or 24 on SwiftShader ([D-88](decisions/D-88-software-gpu-loads.md)). A fourth fault reached main that way. On 5 October 2026, Low kept its far cascade's turns around moving casters. The test set that setting itself, so it never saw Low's own value ([D-16](decisions/D-16-moving-casters-and-bias.md#the-ipad-soak-and-the-second-ruling-5-october-2026)).

- The visual page, `tests/pages/visual.ts`, draws a scene through the shadow check sketch, `tests/pages/sketches/shadow-check-sketch.ts`. The sketch wraps the scene's own sketch and holds the scene at one sketch time. It draws the scene in the `'shadows'` debug view, where a pixel's gray is the shadow factor: 0 in full shadow, 1 in full light. Every frame comes from hold mode. So a GPU draws the same pixels on every run, and the figures can have tight limits.
- Stability: a still observer camera stands where the scene's camera stands, and draws the frames. The scene's camera places the cascades, through `debug.shadowCamera`. It draws 6 frames at steps of 1/60 s. In each step the camera moves 4 mm ahead and 2.5 mm to the side, and turns 0.03 degrees. That is less than a texel of a near cascade, as a slow walk moves a camera. Nothing else moves. So a pixel whose shadow changes by more than 8/255 between two frames shows a cascade that crawls. The figure is the largest share of changed pixels between two frames.
- Edges: the page draws the reference, the same frame with the largest shadow map and the widest filter. The map has 4,096 texels on each side, and the filter blends 5 texels. The figure is how far the frame's half-shadow line strays from the reference's, in pixels. It counts the pixels on opposite sides of the two lines, and divides by the length of the reference's line. A filter blurs an edge evenly to both sides, so blur leaves the line where it is. Steps of coarse texels move the line. The line includes the edges of objects against the black background. So compare a scene's figure only with the same scene's.
- Stair steps: the still shadow scene, `tests/pages/sketches/shadow-scene-sketch.ts`, has one long straight shadow edge at a slant to the texels. The page finds the edge in each row of a box of the frame, and fits a straight line through it. The figure is the root mean square distance of the edge from the line, in pixels.
- Contact: the page also draws the normals view of the same frame, where sides and the ground have different colors. In each column it finds each foot: a dark side above the ground. The side is dark because it faces away from the sun or lies in shadow. So the ground just below it should lie in shadow too. The gap figure adds the shadow factor of each ground pixel down to the first pixel in shadow, within 4 pixels. That is the light between the foot and its shadow, in pixels of full light. A foot with no shadow within those 4 pixels is left out, as its caster's shadow falls elsewhere. The rim figure reads upward: the shadow on a lit top, such as a roof, within 4 pixels of its edge. It catches casters that shadow their own lit tops.
- Seam: the shadow scene's long edge crosses the seam between its first two cascades. In each row of the edge's box, the page measures the edge's soft width, between the shadow factors 0.9 and 0.1. A median of three rows takes out the texels' small steps. The figure is the largest change of that width from one row to the next. Where cascades meet with no blend, the width jumps there in one row. The limit is 1.2 px. With the blend, the scene measures 0.63 px to 0.68 px on the Mac's GPU and SwiftShader. Without it, it measures 2.87 px to 3.19 px ([D-73](decisions/D-73-cascade-blend.md)). A test runs the scene without the blend, and the figure must then be over twice the limit.
- Acne: the page finds the pixels of level surfaces that the reference shows in full light. Each lies at least 3 pixels from any of the reference's shadows. The figure is the mean shadow on those pixels in the frame, in percent: each pixel adds one less its shadow factor. The reference's fine map shows no acne on flat surfaces. So the figure catches stripes and rings of self-shadow, such as those on a pavement slab's lit top. The margin keeps out shadow edges, which the frame's coarser texels soften and move.
- `tests/image/shadow-contact.spec.ts` runs the contact checks on car-sized boxes under S4's sun, on both GPU paths, in `bun run test:browser`. It looks near the camera, in the last cascade, and just past the end of the first cascade. In a fourth view the ground casts shadows too. Its limits on the share of the frame in shadow and on acne catch acne on the ground's top. Three more views stand the boxes on a pavement slab 20 cm thick that casts shadows, with the 5 x 5 filter. Their suns stand as high as S4's, 35 degrees up and 20 degrees up. A fifth slab view, `far-slabs-low`, has the 3 x 3 filter and texels as coarse as S4's last cascade on the Low preset. Their limits hold the slab's acne. `CONTACT_LIMITS` in `tests/lib/visual-checks.ts` holds the limits.
- `tests/image/shadow-checks.spec.ts` runs the shadow scene on both GPU paths in `bun run test:browser`. `bench/tests/visual.spec.ts` runs S2 with three cascades and S4 in `bun run test:bench`. `VISUAL_LIMITS` in `tests/lib/visual-checks.ts` holds each scene's limits. Both tests save their frames and figures in `test-results/visual/`.
- The device runner's bench plan runs the same page for each scene after its timings ([Benchmarks](benchmarks.md#visual-figures-and-captured-frames)).

### The figures and the faults they catch

D-16 gives shadow biases in meters, and picks each receiver's cascade by its distance from the camera ([D-16](decisions/D-16-moving-casters-and-bias.md)). After it, on 3 October 2026, Chrome on the Mac's GPU and SwiftShader on the Mac gave these figures:

| Scene | Pixels changed, % | Edge offset, px | Stair steps, px |
| --- | --- | --- | --- |
| Shadow scene | 0.0008 (SwiftShader 0.0015) | 0.100 to 0.109 (SwiftShader 0.092 to 0.108) | 0.15 (SwiftShader 0.155); the reference 0.095 |
| S2, three cascades | 0 | 0.099 to 0.117 (SwiftShader 0.095 to 0.127) | |
| S4 | 0.0017 to 0.0022 (SwiftShader 0.0004 to 0.0009) | 0.100 (SwiftShader 0.100 to 0.103) | |

The casters' offset ([D-16](decisions/D-16-moving-casters-and-bias.md#lit-lines-at-the-base-after-the-ipads-check)) moved S4's edge offset to 0.097 to 0.103 px (SwiftShader 0.099 to 0.111 px). It moved S2's to 0.120 to 0.122 px (SwiftShader 0.124 to 0.136 px). The reference's fine map keeps a little of the lit line at each base, which the offset closes in the frame. So the half-shadow lines differ there. S4's contact gap measured 0.024 to 0.027 px (SwiftShader 0.042 to 0.043 px). Without the offset it measured 0.040 to 0.050 px (SwiftShader 0.072 px).

Two faults, put back on purpose in builds of their own, show what the figures catch:

- Cascades that no longer snap to whole texels, as before #198, changed 0.52% of the shadow scene's pixels (SwiftShader 0.49% to 0.50%). They changed 0.30% to 0.36% of S2's and 3.6% of S4's. The limit is 0.05% for every scene.
- The second fault is the split that leaned 80% toward the logarithmic spread, as before #211. It raised the long edge's stair steps from 0.15 px to 0.23 px on both GPUs. It raised S4's edge offset from 0.100 px to between 0.116 px and 0.123 px. It lowered the shadow scene's edge offset to between 0.070 px and 0.082 px. It left S2's alone, because S2's trees cast few shadows in the middle distance.
- The limit of the stair steps is 0.19 px. The limit of S4's edge offset is 0.114 px: it was 0.11 px until the casters' offset raised SwiftShader's figure to 0.111 px. The edge offset limits of the shadow scene and S2 are 0.15 px. They catch only large faults, as the split fault does not raise those figures.
- The limit of S4's contact gap is 0.06 px. It fails S4 without the casters' offset in CI, and catches only larger faults on the Mac's GPU. The contact scene's limits sit between its figures with and without the offset. The rims' limits sit between the figures with the offset and with a full texel for every back face, uncapped. So does the limit of the casting ground's share in shadow. D-16 gives the figures.
- S4's acne measured 0.70% to 0.72% before each read of the filter compared with the receiver's plane, on the Mac and SwiftShader. It now measures 0.011% to 0.035%, and its limit is 0.2%. The slab views measured 15.5% to 21.0%, and now measure 3.7% to 7.4%. Their limits are 6%, 10% and 11%, from the highest sun to the lowest. [D-16](decisions/D-16-moving-casters-and-bias.md#acne-on-flat-casters) gives the figures.
- Before D-16, the stair steps measured 0.29 px, and the split fault raised them to 0.53 px. S2's edge offset measured 0.073 px to 0.085 px. Biases in meters, capped at one texel, raised S2's figure, so its limit rose from 0.10 px.

### Why the checks work this way

- A camera that turns on the spot moves every pixel by a map that its angles give. So `shadow-turn.spec.ts` maps each frame back onto the first. A camera that moves also shifts near things against far things, and no such map exists. A still observer needs no map at all: any change it sees comes from the cascades.
- The first edge figure was the root mean square difference of the shadow factor at edge pixels. The reference's edges are much sharper than the frame's, so blur set the figure. It was 17.1% with the current split and 18.0% with the split of 80%. The offset of the half-shadow line ignores blur, and rose by 39% with that split.
- The visual page runs on the dev server, because only development builds draw debug views. So the timed pages keep the production build, and the visual checks cost no measured frame.
- In three.js, the `CSMHelper` shows the cascades' boxes, and the cascaded shadow maps take their camera as an option. `debug.shadowCamera` gives null3D the same choice of camera.

## Large-world jitter

Image tests compare still frames, so the `cells-6378km` test shows that a scene far out draws as at the origin. A moving camera rounds its position again in each frame, and a rounding that changes makes the image jump. The jitter check measures that over a flight. [D-80](decisions/D-80-large-world-jitter.md) gives its design, figures and tolerance.

- The jitter page, `tests/pages/jitter.ts`, flies five flights. Each runs in its own engine in large-world mode. The flights stand at the origin, 1,000 km out and at the Earth's radius. Then the two far ones fly again with every grid cell taken, as without cells. The sketch `tests/pages/sketches/jitter-sketch.ts` builds the scene. `tests/pages/lib/jitter.ts` holds the layout, the figures and the limits.
- The camera moves 12 cm sideways per frame, for 16 frames, past six white squares that face it. Each square sits at its own depth in its own band of rows. The page moves the camera through the sketch's messages, and reads each frame back with `captureFrame` from a live engine. Nothing else moves, and the governor is off.
- Each square's center comes from its band's linear brightness, so edge pixels count in part. The figure compares each square's motion from one frame to the next with the same motion in the flight at the origin. It is the largest difference. Far flights must stay within 0.05 px. The flights without cells must exceed 0.5 px, so the check can see jitter. Each square must keep 95% of its largest area in every frame.
- `tests/image/jitter.spec.ts` runs the page on WebGPU, compatibility mode and WebGL2, on the Mac's GPU and on SwiftShader in CI. It also checks that each flight without cells logs the engine's warning that the cells ran out, once. It saves each flight's first and last frames and the figures in `test-results/jitter/`.
- The device runner's `jitter` plan runs the same page on each GPU path ([Device sessions](devices.md#the-jitter-plan)).

## Parity with three.js

- Parity tests check intent: that null3D shows what files and authors mean ([D-52](decisions/D-52-intent-parity.md)). A scene compares with three.js's rule only where both engines draw the same building block. These blocks are lighting terms, tone curves that both engines offer, skinning poses, animation sampling and glTF interpretation. A feature that null3D draws with a better technique gets its own references. Its parity scene then takes a looser limit, which checks only that the effect sits in the same place and has a similar size. The scene's entry gives the reason.
- A test of a feature scene can have a three.js twin: a page in `bench/pages/threejs/` that draws the same scene. Both engines build the scene from one data module in `bench/scenes/`, such as `ortho-camera.ts`.
- `FEATURE_SCENES` in `bench/lib/parity.ts` lists each such test with its twin. `bun run parity` compares them on each tier by three.js's rule, after the benchmark scenes. Exit gate item 2 therefore runs in one command. On the Mac it draws in Chrome on the real GPU: `bun run parity -- --tier webgpu,webgl2` gives the gate's two tiers. `--scene` names one scene, by its image test.
- `bench/tests/parity.spec.ts` compares the same list in `bun run test:bench`, on SwiftShader in CI. The twin loads from the production build of the benchmark pages. The test's image loads from the dev server, because the image test page loads its sketch by address.
- The list covers standard materials: the grid over metalness and roughness, texture maps, the mask alpha mode and blending. The `alpha-coverage` and `alpha-hash` scenes draw the masked cards with three.js's `alphaToCoverage` and `alphaHash`. The `transparency-solids` scene compares double-sided see-through solids, whose back faces draw before their front faces, and a tube with `forceSinglePass` ([D-82](decisions/D-82-transparency-parity.md)). The `sprites` scene compares sprite batches with three.js's `Sprite` and `SpriteMaterial`: blended sprites at frames of an atlas, and opaque sprites sized in pixels ([D-37](decisions/D-37-sprites.md)). The `points` scene compares point batches with three.js's `Points` and `PointsMaterial`, on its WebGLRenderer alone. It draws opaque, cut-out and see-through points, sized in world units and in pixels. It takes a limit of 0.2% ([D-37](decisions/D-37-sprites.md#points)). The `lines` scene compares line batches with three.js's `Line2` and `LineSegments2`: widths in pixels and in world units, round joins, colors at each point, dashes, a loop and a blended line. The `lines-basic` scene draws the same lines one pixel wide against `LineBasicMaterial` and `LineDashedMaterial` ([D-46](decisions/D-46-wide-lines.md)). The `lines-lit` test has no twin, as three.js has no lit lines. It also covers point and spot lights, a texture background, and both fog types. Then come the four tone mappings at two exposures, the orthographic camera, the directional light's shadows, and bloom at two settings against `UnrealBloomPass`. Ambient occlusion compares at two settings with `GTAOPass`. Color grading compares with `LUTPass`: the `lut-cube` test, by three.js's rule. The `lut-vignette` test, at 0.7 of the table's intensity with the vignette, is a sanity comparison with `VignetteShader` under its own limit of 2%. On 5 October 2026, 1.10 to 1.14% of its pixels differed on the Mac, all in the outer corners ([D-77](decisions/D-77-final-pass-order-and-formats.md)). The `lut-3dl` test has no twin. three.js's `LUT3dlLoader` refuses the sample file's input grid, whose steps differ by one from rounding. The directional and ambient lights shine in the material scenes.
- The color grading tests load their tables from the sample content: `sources/luts/` in [sample content](sample-content.md). So the CI jobs that draw image tests and parity fetch it first.
- The environment tests light the standard material's grid with the built-in room and with Poly Haven's Venice Sunset. Two more load HDR files that the engine filters itself at load. The sunset's Radiance file borrows the references of the sunset's tool map. The small studio's OpenEXR file has its own. The sunset's file draws in every thread mode, since its panorama reaches the thread that draws in each mode's own way. The room's test draws in every thread mode, since its generator reaches the thread that draws in each mode's own way. Each of its runs may take 60 s, not 30. The held frame makes the whole room at once, and SwiftShader on CI's shared runners takes many seconds for that. A browser test, `environment-generator.spec.ts`, compares the room that each GPU path makes with the asset tool's, texel by texel. It does the same for three HDR files that the engine's readers read. They are the sunset, Kloofendal's sky, whose sun passes the shared-exponent limit, and the studio's OpenEXR file. Another, `room-light.spec.ts`, asks for the room, or an HDR file, during play and captures frame after frame. The sketch sets the room and a blue background in the same step. So each capture with that background is a frame that uses the room, and each must match the steady frame. With the room's wait for its generator taken out, it fails in the default thread mode on all three paths. A third test turns the sunset a quarter about +Y. The sample content holds the sunset as an HDR file. The dev server and the preview server build its environment map with the asset tool on the first request. They serve it under `/sample-environments/`, with the HDR file's path (`tools/lib/sample-environments.ts`). The tool writes the same bytes everywhere, so the map needs no copy anywhere. It waits in the shared samples cache, keyed by the HDR file's SHA-256 and the tool's module. The first build takes about 5 s. Their twin, `bench/pages/threejs/environment.ts`, prefilters the same HDR file and three.js's `RoomEnvironment` with `PMREMGenerator`. [D-19](decisions/D-19-environment-maps.md) gives the figures.
- Hemisphere lights are not in the list: the engine stores them but does not draw them yet. The lights twin draws them with `?scene=hemisphere`, and so does the lights sketch. The pull request that draws them adds a `lights-hemisphere` test to the manifest and to the list.

## References

- References live in `tests/image/references/<set>/<tier>/<test>.png`. Each environment has a full set. `chromium-swiftshader` is Chromium on SwiftShader, the software GPU that CI draws with. `chrome-real-gpu` is Chrome on the Mac's GPU.
- A new test needs its references in both sets before you push it. CI's Chrome tests draw only with SwiftShader. CI's Safari and Firefox jobs compare with the `chrome-real-gpu` set, so a missing Mac reference fails there, after a full run.
- `bun run check` runs `tests/check-references.ts`, which needs no browser and takes under a second. A test needs a reference in each environment's set, and in the set of each device in its `devices`. A test that borrows references, or a tier that must draw the first tier's image, needs none of its own. The check lists each missing reference with the command that makes it. It also lists each file that no test compares with, such as the reference of a removed test. CI runs it in the quick checks, so a missing reference fails a draft pull request's run too, before the browser jobs run.
- `bun run check` checks only that each reference exists, not that it still matches what the engine draws. A stale Mac reference passes every check of a pull request. CI's Chrome draws only with SwiftShader, and CI's Safari and Firefox jobs compare at the device tolerance of 0.5%. After #198 changed S4's shadows, only its SwiftShader references were made again. S4's Mac references then differed in 0.18% of the pixels on all three paths, and only later local runs found it. So after a visual change, run every image test on the Mac's GPU too. On 8 October 2026 the same happened to `custom-vertex-offset` on WebGL2: its Mac reference dated from #150, and 0.103% of the pixels differed on main at 6a1d0dd25, against the limit of 0.100%, only at the moved shapes' outer edges. On the same day `points` drifted on all three paths: since #399, masked materials smooth their cut edges with alpha to coverage by default, and only `points`' Mac references, from #337, were not made again. On main at 0c9c06b8d, 0.109% of the pixels differed on WebGPU and 0.102% on WebGL2 and in compatibility mode, only at the edges of the cut-out discs. The other masked tests (`alpha-mask` and its prepass, coverage, hash and shadow variants, `custom-dissolve` and `gltf-alpha-modes`) stayed within the limit on all three paths, so they keep their references. The new `points` references pass 9 of 9 runs on each path.
- SwiftShader and the Mac's GPU differ at object edges, in up to 0.35% of S1's pixels.
- `NULL3D_SWITCHES` gives every page of a Playwright run more switches: `NULL3D_SWITCHES=half=on bun run test:images` draws the scene shaders at half precision against the usual references. The image manifest and the shadow contact checks read it. The device runner takes `--switches` for the same purpose.
- Playwright's runs use the SwiftShader set in CI, and the real-GPU set elsewhere. With `CI=1`, a run on the Mac uses CI's SwiftShader setup and draws CI's images.
- A comparison passes when at most 0.1% of the pixels differ by more than pixelmatch's threshold of 0.1. A test can set its own tolerance.
- A few tests count every changed pixel. The far-out tests of `cells`, `debug` and `ortho-camera` use a threshold of 0. `vertex-types` allows no pixel past one step from `vertex-types-float`. A change of the final pass's dither moves every pixel of their images by up to one step. So it needs new references in both sets. Remake only those tests: `bun run test:images -g <name>` and `CI=1 bun run test:images -g <name>`, then `bun run images:review --accept <name>`. A passing test saves no candidate, so move its reference aside first. On 7 October 2026 the dither moved to the end of the final pass ([D-77](decisions/D-77-final-pass-order-and-formats.md)), and `vertex-types-float` was remade in both sets this way. Every other test stays within the default threshold, about 13 steps. A device's own references go stale the same way: the Galaxy S24+'s `debug` reference (`sm-s926b`) needs a new image at its next run.
- pixelmatch skips a pixel that it finds on an anti-aliased edge, from neighbors of exactly one color. The engine dithers its output, which leaves few such neighbors, so most edge pixels count.
- An image without a reference, or one that differs from its reference, fails its test. The harness saves it as a candidate in `test-results/images/<place>/<tier>/`, with the reference, the diff and the facts of the comparison.
- Only `bun run images:review --accept` turns a candidate into a reference. The review lists each candidate in the terminal, and writes a page that shows it beside its reference and its diff.
- A candidate of a test that borrows another test's references cannot become a reference. Neither can a candidate of a tier that must draw the first tier's image. The review says why: fix the drawing, or change the other test's reference.

## CI

- CI splits the browser tests, the manifest among them, into shards that run at once, as the `browser` job's matrix lists them. CI's `build` job builds the WebAssembly files once, and each shard downloads them. Add a shard when one takes more than about 5 minutes.
- Playwright splits the tests by count, not by time. A file that runs its tests in parallel, such as `images.spec.ts`, can split between shards, and any other file stays in one shard. The manifest's image tests are quicker than most other tests, so the shards that hold them finish first.
- So the `browser` job gives each shard a weight in `PWTEST_SHARD_WEIGHTS`. It holds one number per shard, in order and joined by colons. Playwright gives each shard its weight's share of the tests, in its own order of them. A file that does not run its tests in parallel goes whole to the shard where its first test falls. Each weight is the count of tests in one part of that order, and the parts take about the same time. On 5 October 2026, with even shares, the slow image tests and the room environment tests met in one shard. It took 12.9 minutes, and another took 4.5.
- Retune the weights when one shard takes much longer than the others, or when a change adds many tests. Retune them too when the shard count changes, since Playwright refuses a list of the wrong length. `bun run test:browser-weights` works them out with the GitHub CLI. It reads each test's time from the `list` output in the browser jobs' logs. It takes the last 5 CI runs on main that passed and ran the browser job, and each test's median time in them. Main's runs from before [D-99](decisions/D-99-no-merge-queue.md) ran no browser job, so it skips them. It lists the tests in Playwright's order and groups them as Playwright does. A file that runs its tests in order is one group. Each test of a file that runs its tests in parallel is a group of its own. It treats each shard as 2 workers that take the groups in order. Then it finds the cuts between groups that keep the slowest shard shortest in every one of those runs. It prints each shard's time with the workflow's weights and with the best weights, and the time of the tests that run alone. Copy the best weights into `PWTEST_SHARD_WEIGHTS`. `--runs <n>` takes another count of runs, `--run <id>` one run of your choice, and `--shards <n>` finds weights for another count of shards.
- `shaders.spec.ts` compiles every generated shader in parts of at most 150 GLSL programs, which run in parallel and can split between shards. The page's `?part=k&parts=n` picks every nth program and WGSL module from the kth. SwiftShader has no parallel shader compile, so it compiles one program at a time, and the time grows with the number of programs. On 4 October 2026, the WebGL2 skin builds (M2-C4) raised the programs from 298 to 566. The single test then took 15.3 to 16.8 s on SwiftShader on the Mac, against 8.1 to 8.4 s before. In CI it took 41.7 s, past its 30 s limit. In four parts, each took 6.5 to 7.3 s on the Mac, with the four running at once. More shader variants make more parts, so no part outgrows its limit. Fewer variants were not an option: every skin build draws a skinned mesh on some device. On 5 October 2026 the build began to write each GLSL stage from its own entry point (D-56). Builds that differ only in the other stage now share a stage's text. Compiling each distinct stage once could then save time; the test still compiles each program.
- On 7 October 2026, parts of this test timed out three times on the Mac while its load was 21 to 37. Each part passed alone. Several suites ran at once then, and the fixed limit of 30 s per part left no room. Each part now waits for its result for as long as its page notes new steps. The page notes a step after each batch of GLSL programs and after every 20 WGSL modules. A part fails when its page notes no step for 30 s, or after 5 minutes in all. So a busy machine slows a part without failing it, and a stuck compile still fails.
- A shard that fails uploads its `test-results/` folder with the candidates. `bun run images:review --ci <run>` downloads them with the GitHub CLI.
- In each full CI run, the `real-browsers` jobs run the manifest in Safari and in Firefox, each in shards of its own. Safari runs on GitHub's macOS machines, and Firefox on its Linux machines. [Device sessions](devices.md#browser-apps-on-the-mac) says how they split. A shard that fails uploads its runs and candidates as `real-browser-runs-<browser>-<shard>`, and `bun run images:review --ci <run>` downloads those too. The runs folder also holds each dev server's output, in one log per port (`server-<port>.log`). So a failed page can be checked against what the server said. A Safari E1410 on 7 October 2026 could not be, because the runner then threw that output away.
- In the `real-browsers` jobs, each page runs in a frame that the runner page removes, all in one tab. What one page leaves held, the next page lacks. Safari frees dropped shared memories late, at times minutes late on GitHub's Mac. A page that filled the room to count it left the pages after it room for no engine. On 6 October 2026 the queue's Safari refused same-canvas starts with E1109 twice. So the restart pages count the room only up to a cap, through `tests/pages/lib/room.ts`, and test pages never fill it ([the implementation notes](implementation-notes.md#failures-on-the-gpu)).
- A count that Safari refused did not mean that the room was gone. On CI the same request, made less than a second later, was granted every time. So a count asks again a few times, after short pauses, before it accepts a refusal. On 7 October 2026 the queue failed `frame-destroyed-restarts-low-latency` on a count of 3, although the same page then started 43 more engines ([the implementation notes](implementation-notes.md#failures-on-the-gpu)).

- The projects `<environment>, alone` and `production build, alone` take the tagged tests, one test at a time. The other projects leave them out. In CI the seven shards run with `--grep-invert @alone`. The `browser (tests that run alone)` job runs `--grep @alone --workers=1`, so nothing runs beside these tests.

## Tests on slow machines

- CI's software GPU on a busy machine draws far fewer frames than a desktop. On 4 October 2026, other suites loaded the Mac. SwiftShader then drew the raycast page at 0 to 9 frames a second, where it draws about 60 alone. So a browser test checks frame rates only where the frame rate is its job. A test that counts work over frames measures until the frames have come.
- The raycast test checks that a batch of 10,000 rays reaches every job worker. It used to measure one second, and each worker's median busy time per frame had to be above zero. So each of the 16 workers on the Mac had to take part of the batch in more than half of the frames.
- That depended on luck twice. The job system gives a loop's chunks to whichever thread claims them first, the thread that casts the batch among them. The workers sleep between frames, so a worker that wakes late misses that frame's batch. With one or two frames in the second, one late worker failed the test. A second with no frame at all left the test no figures.
- In the frames that ran, the engine gave work to almost every worker, so the engine was not at fault. Before the change, main at a1168724 failed 14 of 20 runs on SwiftShader with 10 copies at once. One at a time on the busy Mac, it failed 12 of 20. Every failure had 9 frames or fewer in its second.
- So the raycast page adds up each job worker's busy time over all the measured frames. With `?everyWorker`, which only this test gives, it measures for 1 second, then for 2, 4, 8 and 16, until every worker has taken work. The test fails only for a worker that took no work in all that time. On a quiet machine the first second is enough.
- Each measurement is twice as long as the one before, because a measurement counts only the frames that start and end within it. On the busy Mac, SwiftShader took 0.3 to 1.4 seconds for a frame. Ten measurements of one second each then found 0 or 1 frames in 8 of about 14 runs.
