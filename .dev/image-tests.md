# Image tests

This guide covers the image test manifest, its references, and the review that makes a new image a reference. [AGENTS.md](../AGENTS.md) lists the commands, and [Device sessions](devices.md) covers the runs on phones, tablets and the Mac's browser apps.

## The manifest

- `tests/image/manifest.ts` lists every image test. One harness, `tests/lib/images.ts`, runs each test in Chrome through Playwright. The device runner's checks plan runs each test in the other browsers.
- Playwright's test runner runs in Node, not Bun, so a tool that a browser test calls must work on both. The CDN test builds the add-ons inside the runner, so that build spawns through `node:child_process`. A `Bun.spawn` call on that path throws "Bun is not defined" and fails all seven CDN tests in CI. A machine that reuses a stale build still passes them, because the build's freshness hash covers the engine's sources and not `tools/`. Delete `target/cdn` before checking a change to that path. A unit test, `tests/lib/node-runtime.test.ts`, follows the imports of every Playwright spec and of the Playwright and Vite configs. It fails on a module they reach that uses Bun's own API, so the fault shows in every run. The pack step lives in `tools/lib/pack.ts`, apart from the library build that the CDN test loads. The docs that it generates are read with Bun's parsers.
- A sketch test names a sketch module and a hold time. The image page, `tests/pages/image.html`, draws the sketch in the engine's hold mode. The image is 320 x 180 pixels unless the test gives another size.
- Hold mode runs each step of the sketch's fixed steps and update up to the held time. The passes run with those steps. It reads no page input unless a timed script is given, and it draws one frame. A bake that the page finishes in a later frame can still miss the held frame. The probe grid is the worked case: its late-update bake leaves the held frame with no grid at all. A run of `probe-grid` then comes out byte-identical to `probe-grid-off` on all three tiers. The test cannot see the fault in either. The rest is in [D-146](decisions/D-146-light-probe-grid.md#tests-first-use-entry-and-switches).
- A first use that needs frames the engine draws runs on a live page instead of hold mode. Hold mode records its held frame without starting the loop, so a pick asked there answers by ray before any draw and loads no picking shader. A first-use picking test in hold mode therefore measures nothing. The picking case runs on `tests/pages/first-use-live.html`, which starts the engine normally. Its sketch picks on the frame after the first drawn one, posts the outcome, and fails the page when the pick rejects. The other features keep their hold-mode measurement.
- A feature whose state builds over the frames before it may still have a held picture. Hold mode steps the sketch's updates up to the held time. A render pass runs with each step, so the state builds by the time the frame draws. Such a picture needs a control rather than a reference. `tests/image/wind-wake.spec.ts` holds the wind add-on's sketch at 1.2 s, with the body stopped. It compares that picture with the same page's `?push=0` control at the same time, so the difference is the air that the pushes left. Two live pages would draw a different number of frames on a busy machine. A held pair draws the same frames every time. With both pages' pushes off, the three paths differ by 0.00000 of their channels.
- A page test names a test page that draws and publishes its image itself, such as the texture page or a benchmark page.
- Test pages and benchmark pages draw every frame: `tests/pages/lib/result.ts` adds `?still-camera=off` to a page's address unless it names `?still-camera`. A live engine whose view holds still would otherwise blend its frames and then stop drawing ([D-114](decisions/D-114-still-camera-accumulation.md)), which changes captured images, frame counts and timings. Hold mode turns it off too. The still page, `tests/pages/still.ts`, asks for `?still-camera=on`, and its `still` test captures the converged frame of a resting view. The page draws without anti-aliasing: the accumulation smooths the edges, and compatibility mode with MSAA takes the 8-bit path, which never accumulates. The test also asks for `?target-fps=1`. On a slow software GPU the frame-budget governor otherwise lowers the render scale while the page waits for the view to rest. That resets the accumulation and draws the converged picture upscaled, so its edges miss the reference. On the webgpu tier 1.076% of pixels differ, and on compat the view never rests. A test page that waits for a multi-frame effect pins the frame rate for the same reason.
- Each demo in `examples/demos.ts` is a sketch test named `demo-` and the demo's name, held at the demo's hold time. A new demo needs no entry of its own in the manifest. A unit test checks that `examples/demos.ts` lists every demo folder, and that each sketch stays under 150 lines.
- A test draws on all three GPU tiers unless it lists fewer. A sketch draws in the pipelined thread mode unless it lists others.
- Every thread mode of a test must draw the pixels of its first mode exactly. A thread mode changes only when the engine draws a frame, so the pixels must stay the same.
- A page test whose modes must draw one picture pins the render scale for the frame it captures, with `quality.set({ minRenderScale: 1, maxRenderScale: 1 })`. The frame-budget governor lowers the scale when frames take too long, and a frame drawn below the canvas's size puts its pixels elsewhere. Unpinned, `canvas-texture` differs between modes over 20 to 65 percent of the image, in steps under 25. Its reference checks ignore such steps, so only the comparison between modes catches it. Five of its modes drawn at once give CI's figure exactly, 57,655 pixels. The canvas page pins the scale when `start` arrives, so the frames it measures and the frame it captures all draw at the canvas's size, and its two measured windows compare at one scale. On a busy machine the same cause moves other pictures too. The sharpening pictures move by 13 to 19 percent, because their edge vote runs in the two-step pass below the canvas's scale. The destroy pair moves by 43,526 pixels, because two engines on one page choose different scales and their geometry meets different samples. Pin the scale in every picture that draws below the whole canvas, even one whose subject is not resolution. An experiment's pin must not outlive the experiment. A pin that rides into a branch on a merge makes the next real-browser run's difference look like a browser fault.
- A page that measures what its frames upload starts after a frame that uploaded nothing. The setup's whole-canvas upload can otherwise land inside the window. It then reads as a frame that refreshed everything, which fails the check that a refresh uploads only a rectangle.
- A live page that waits for frames on screen bounds the wait by time as well as by count. A software renderer draws a few frames a second. In CI, 90 presented frames take longer than 30 s, while the same pages finish in about 5 s here. The 2D and 3D label pages sample for at most 25 s, and their tests check a floor of more than 30 samples.
- A test page's poll reads a cheap value, and a capture is one check rather than the poll. The resize page reads the canvas's CSS box and the size of its drawing buffer. The thread that draws sets that size when it resizes. A capture draws a frame and reads it back, so a poll through it spends a GPU round trip on every attempt. On this Mac a new window size reaches the buffer in 0.14 to 1.55 s. Yet the pixel ratio cap test's six resizes and the page's start can outlast Playwright's minute-long test limit, while every resize stays well inside its own wait. A test that walks several sizes therefore sets its own limit, and the figure behind it sits in the comment.
- A test can borrow the references of another test: the same scene drawn another way, such as with `?uploads=copy`. A test can also require that every tier draws the image of its first tier. A scene that fades a level or a distance band cannot: the fade dither's phase follows each copy's number in its draw, which a GPU path numbers its own way, so two paths draw the same share of the pixels in a different pattern and each keeps a picture of its own. `lod-range` carries that note in the manifest.
- No two tests of one scene may keep the same picture. Tests of a scene differ by the switches that turn its features on, so a picture that two of them share is a picture of neither feature, and every one of them passes. When a held frame draws no area light, for example, the bench's four area-light scenes share one black image. `bun tests/check-references.ts` and the image spec report such a pair, which needs no browser. A test whose picture must match another's borrows its references with `reference`; a copy that draws another test's image and keeps its own references says so with `samePicture`.
- A test can require values in its page's result besides the image, such as the replay page's counts of visible boxes.
- A test can widen its tolerance on SwiftShader alone, with `swiftShaderTolerance`, for a scene that the software GPU rounds differently on different machines. The debug lines test matches exactly on the real GPU. SwiftShader on a Mac and on CI's runners rounds one gray pixel of it a step apart, so there one pixel may differ.
- A test can add switches on SwiftShader alone, with `swiftShaderSwitches`, for a scene that CI's software GPU draws too slowly in full. Its SwiftShader references then show that lighter scene, and every other place draws the full scene. S5 draws 100 characters on SwiftShader, not 500 ([D-88](decisions/D-88-software-gpu-loads.md)). S6 draws the 4,000 objects nearest its camera. Night town's tests draw 8 of its 25 blocks, and 2 on SwiftShader, in both engines' tests. three.js's renderers take 40 s to over 3 minutes to build the lights of 4 to 25 blocks on SwiftShader, and over 3 minutes for 25 blocks on a busy Mac ([D-121](decisions/D-121-comparison-tier.md#night-town)). The image tests run in Playwright's Chromium. Its version 153 takes about 90 s to start null3D's WebGL2 Night town at 300 lights or more, where Chrome 155 takes 1 to 2 s. It also fails to build one of three.js's WebGPU pipelines when Night town draws all its effects. The held tests draw 96 lights or fewer and give no such error. Timing runs use the installed Chrome instead ([Examples](examples.md#the-ramp)).
- A test that measures a frame rate measures the machine as much as the engine, so on SwiftShader it asks only that a frame drew. The software GPU draws a heavy scene at under one frame a second, as the allocation check records for S1's boxes. CI's software GPU draws the splat stream page's first frame after 41.8 to 60 s, and cannot draw two frames in a two-second window. So that test measures for 20 s on SwiftShader, and its rate is judged on the real GPU only. A window that draws no frame at all still fails. The selection gives every chunk the budget reaches an eighth of itself, so ten thousand splats cover five chunks rather than one. At the window's size, CI's software GPU cannot fill them inside the window. So that run draws the page in a 320 by 180 canvas and keeps the same 10,000-splat budget. On this Mac's software GPU, at loads of 62 to 89, a frame of the page takes 950 ms at the window's size and 283 ms in the smaller canvas. Almost all of every frame is its raster work, and the smaller canvas holds 66 frames in the 20-second window. The test checks that the draw stays inside the budget, and it waits for the nearest megabyte of the cloud's chunks, five of the six that its budget wants. The test cannot see that boundary: the sixth chunk arrives between the run becoming ready and the first report, so the report holds six loaded. The bound is proven by `firstViewCount`'s unit test and by the chunks' served bytes, not by this page.
- Surfaces that overlap in a test scene never share one plane. In one plane, the draw order picks which surface shows, and the engine may change that order. The texture budget scene draws its small picture 1 cm in front of its two large ones. In their plane, WebGL2 loses the small picture, because the depth prepass runs on every preset there ([D-43](decisions/D-43-webgl2-prepass.md)).
- Test images live in `tests/pages/assets/`, and sketches fetch them from their own address. The texture tests decode one small picture from PNG, JPEG, WebP and AVIF files, and make their other images in code.
- The KTX2 tests load files that `basisu` 2.50 encoded from PNG files with `-ktx2 -mipmap -y_flip`. The file `quarters-etc1s.ktx2` holds `quarters.png` in ETC1S, with `-q 255`. The file `quarters-uastc.ktx2` holds it in UASTC, with `-uastc` and a half transparent quarter. The ramp of 30 x 20 texels adds `-linear`. The `?compression=` switch draws the `ktx2-bc7`, `ktx2-astc`, `ktx2-etc2` and `ktx2-rgba8` tests, so every device draws each route. The switch leaves only the named family in the device's capability flags. So `ktx2-etc2` stands in for a device with no other family, such as one that asks only for ETC2. A device that lacks the named family draws the RGBA8 route. They borrow the `ktx2` references: on the Mac and on SwiftShader, every format draws within 0.003% of the pixels of that image. The texture budget's test page loads `budget-checker-etc1s.ktx2`, the image of `budget-checker.png` in ETC1S. The `ktx2-background` test sets `quarters-etc1s.ktx2` as the scene background, behind the texture background test's boxes, so a KTX2 background stands upright and fills the view as a PNG one does (M1-D7's follow-up, closed in M2-R6). `ktx2-background-rgba8` draws it through the RGBA8 route, with `?compression=none`, and borrows its references.
- `packages/engine/src/scene/ktx2.test.ts` transcodes every KTX2 test file into every format that the engine asks for. It compares each result's SHA-256 with what the official Basis Universal 2.50 build writes. A new test file needs its hashes from that official build. Hashes from the engine's own build would make the test compare the engine with itself. Download the archive that `tools/build-basis-transcoder.ts` pins, and check its SHA-256 there. Then run `transcodeTestFiles` from `tools/lib/basis-transcoder.ts` on the archive's `webgl/transcoder/build/basis_transcoder.js` and `.wasm`. The official build and the engine's build write the same bytes for all 20 file and format pairs.
- The command-line tool's tests, `tests/image/cli.spec.ts`, run `bunx @null3d/cli shot` in the fixture project `tests/fixtures/project`. Its images must match the references of the manifest's `project` test, which draws the same sketch. Change the fixture's sketch, and its references change too.
- The tests of `bunx @null3d/cli test`, `tests/image/cli-test.spec.ts`, run it in copies of the fixture project, each with its own `null3d.json`. A copy's references are copies of the manifest's `project` references, so its passing tests need no reference images of their own.
- The recording tests draw no references. `tests/image/recording.spec.ts` records a live session through the page at `tests/pages/recording.html`, saves it, and replays it on the same page: the two frame logs must match line for line, so the file gives the sketch the same time, step and input in every frame. It records the session until the page has posted ten frame lines, not for a fixed span of time, because a software GPU draws only a few frames in one. The same spec records through the device page, which drives its own key and touch and holds a long frame. It replays that file too, and compares every frame line. It demands no frame count, because a software GPU draws fewer frames in the session's fixed time. A run whose threaded core comes from another worktree can stop both pages with E1402 before either test runs. `tests/image/cli-replay.spec.ts` records a session the same way, then runs `bunx @null3d/cli shot --replay` on the file and checks the last frame and the report's replay facts. The report's frame count is the recording's own frame count, not the frames that the runner drew, so a recording that holds few frames reads as that number. It records until the page has posted ten frame lines, not for a fixed span of time. In a fixed half second CI's software GPU records only five frames, and the test asks for more than five. `tests/image/recording-replay.spec.ts` replays a recording that a real device made, which is kept in `tests/fixtures/recordings/`: the device run's plan item is `record-phone` in `tests/lib/plans.ts`, and the test compares the phone's frame lines with the replay's, one for one. `NULL3D_RECORDING` replays another device run's result instead.
- The tests of the timed script, `tests/image/cli-script.spec.ts`, run `bunx @null3d/cli shot --script` twice. The first run is in a copy of the fixture project, and its script drives the sketch through three states with a key, the pointer and a property write. It checks the files, the summary and the dump lines, and that each of the three images differs from the other two. The second run is in the repository itself. Its script drives the night town showcase through three states on WebGL2, each of which compares with a reference. The states are a turn, a walk and a closer view, and the camera takes the `c` and `w` keys and the pointer, so every state comes from an input step. Each state keeps its own reference: the real GPU's set comes from this Mac, and the software set comes from CI's own drawing. The showcase's runs are in `tests/image/script-runs.ts`, not in the manifest, because the command draws them rather than the image page. The software GPU draws the showcase at its Low preset, as the manifest's showcase tests do. `tests/check-references.ts` reads both lists.
- The harness and `bunx @null3d/cli test` judge images with the same code and the same default tolerance, from `packages/cli/src/compare.js`.
- **That tolerance answers one question: do two draws of one scene match?** It counts a pixel only past a tenth of full scale per channel, so a change that moves many pixels a little counts as nothing. A test that asks how far a feature *moves* a picture is asking the opposite question, and must not use this bar: give the comparison a pixelmatch threshold of 1/255 instead, which counts a two-step change in a channel and not a one-step change. A switch the page never reads moves exactly nothing, so that comparison still fails on a feature that is absent. `tests/image/terrain-shading.spec.ts` does this, and a test that used the default tolerance there reported zero movement for both of the features it was written to prove.
- A page may paint over what GPUs draw differently, and publish it as data instead. The depth precision page paints each pixel where depth fought as the nearer surface, so every GPU matches one reference. It publishes the fighting pixels as fields. The cube and 3D texture page filters a texture of 32-bit floats, which only some GPUs can do. It publishes whether the texels blended, and paints that cell black.
- A hand-built page that binds one of the engine's standard layouts must fill every binding the layout names, with a texture or a buffer of the kind and the format that binding declares. That holds even for a binding its shader never reads. WebGPU drops the whole command buffer of a bind group that misses an entry or mismatches one, so the page then draws nothing and reports no error of its own. `tests/pages/replay.ts` is the worked case. The culling layout's binding 10 is `skin_firsts`, a texture for the skinned copies of one mesh that draw in one instanced draw (`2014be260a`). A page that binds only ten entries loses its compute dispatch, and `replay-instanced` draws `visible [0, 0]`. The page binds a 1 x 1 `r32uint` texture there. The frame's group holds 18 bindings. The light tables are a filterable array of layers at binding 3 (`efb65024b`). The light probe grids sit at binding 10 (`792e680c7`), and the row values and the object ranges at 16 and 17 (`f662b3de8`). A page that fills 17 of the 18 loses every command of the frame, so nothing clears or draws the target texture. The test then sees `visible [0, 0]`, which the page writes before the frame, and reads back the target's untouched pixels. Every one is zero, which differs from the reference at 96.770% of them. The page makes a 1 x 1 `rgba16float` array texture of one layer for the light tables and a 1 x 1 `rgba16float` 3D texture for the probe grids, and fills every entry. It also keeps what the device reports as an uncaptured error and publishes it, which the harness fails on, as the other replay pages do. A page whose list drifts from the engine then names the wrong binding instead of drawing nothing.

## Adding a test

1. Add the test's entry. A sketch stays under 150 lines, and takes its settings from the query of its path, such as `sketch.ts?fog=exp2`. Vite takes a module's language from the last dot of its address. So a module whose path ends in a value with a dot, such as `?scale=0.5`, reaches the dev server as JavaScript, and its type annotations fail to parse. The image page adds Vite's marker `&lang.ts` after a sketch's query, so manifest tests are safe. The `subsurface-scale-50` test would fail without it. Any other page that loads a sketch with such a query must put the value before the others, or keep the sketch free of type annotations, as `bloom-sketch.ts` does. A test page that picks a sketch's settings at run time sets them on the address with `searchParams.set`, after `new URL('./sketch.ts', import.meta.url)`. Vite rewrites a template literal there whose only variable part is the query, such as `` `./sketch.ts?mode=${mode}` ``, into a fixed address. The sketch then reads the text `${mode}`. A destroy test built that way draws its reference scene twice and checks nothing, and the shimmer page fails with E1405.
2. Run the test on the Mac: `bun run test:images -g <name>`. It has no reference yet, so it fails and saves its image.
3. Look at the image with `bun run images:review`. Make it the reference with `bun run images:review --accept <name>`.
4. Take its SwiftShader reference from CI's own drawing. Push the branch, and start a full run on it with `gh workflow run ci.yml --ref <branch>`. The test fails there for want of a reference, and its job saves the image. Then accept it with `bun run images:review --ci <run> --accept <name>`. `--accept` refuses a SwiftShader image that this machine drew, also with `CI=1`, and names the test and the file. A local drawing taken on purpose needs `--local-reason "<why>"`, which records the reason in `tests/image/local-references.json` until you accept a CI drawing of that test. A `CI=1` run on the Mac still checks a change against CI's images before the push. On the Mac, Playwright's Chromium draws CI's SwiftShader images almost byte for byte. CI's machines are x86 and the Mac is ARM, and SwiftShader can round a pixel one step apart on the two. The city of the occlusion tests differs so in one pixel. Text that a page draws in a 2D canvas is the exception, since each machine's Chromium rasterizes it its own way. So never compare with a reference at zero tolerance across machines. To require the same pixels, draw both images in one run, as the occlusion spec does.
5. Run `bun run check` before you push. It fails when a test lacks a reference in either set, and it names each missing file and the command that makes it. It also fails when two tests of one scene keep the same picture, which no browser run can catch: look at the picture, name the other test in `reference` when the two must draw one image, and add `samePicture` when the copy keeps its own references.
   A commit that adds or changes a test, or the manifest, carries a `Limits-Checked:` trailer with what `bun run limits` reported, as [Branches and parallel work](pull-requests.md) says.
   After a change that alters what any test draws, also run every test on the Mac's GPU, `bun run test:images`, besides `CI=1 bun run test:images`. Then accept the real-GPU set from the Mac, and the SwiftShader set from a CI run. "References" says why. SwiftShader references drawn on the Mac turn CI's tasks red, because CI's machines do not draw them alike.
- A run that names one test file and a project puts the file first, or gives the project with an equals sign: `bunx playwright test image/cli-replay.spec.ts --project=chromium-swiftshader`. The bare `--project` flag takes a list of names, so it reads a file that follows it as a second project and refuses the run. In a busy queue that refusal can come after 85 minutes of waiting, and the whole wait is lost.
- Several Playwright runs one after another, as a helper's chain does, need their ports free between them. A run that is stopped, or that hangs in its own teardown, leaves its dev server and preview server listening. The next run then fails at once with "already used". Stop this worktree's listeners between the steps. A run prints its failure messages only with the report at its end. A run stopped before that report loses them, so run the failing tests alone to read them.
- A picture drawn while a sketch's own values change between runs proves nothing until the sketch is known to have read the change. A page that puts the settings on the sketch's address with `searchParams` must check that the address carries them. Otherwise a sketch that reads `new URL(import.meta.url).searchParams` takes its own defaults without a warning. Then four candidates that differ only in a material are one picture. Have the sketch post back the values it built, and have the page report them before you trust any difference. The dev server also answers a sketch address whose query carries a `v=` value with `Cache-Control: max-age=31536000, immutable`, while every other address answers `no-cache`. [Tests](tests.md), item 9, gives the rule. The measurement that settles freshness is a marker: open the page twice with two markers, have the sketch report the one it read, and compare. Do that before drawing a look frame, not after.
- The dev server joins a page's own WGSL of a template, such as a sky layer's, to the engine's template. It keeps the build it made. After a change to the template alone, a running server still serves the build from before the change. The next run then reads the old behavior, as if the change were not made. A test of the change fails with the old numbers. Restart this worktree's server after a template changes.
6. Run the checks plan in Safari and Firefox on the Mac. Run it on the phone and the iPad too, when their GPUs may draw the test another way.

- A sketch that must draw a level of detail at a distance gives the level an error that puts its
  switch there, not a bias raised in setup. A bias is a command that the next structure change
  applies, and a slow path can draw its held frame before the change lands. With a bias, the
  skinned-level picture draws its level on the Mac's GPU and on SwiftShader's WebGL2, and the base
  mesh on SwiftShader's WebGPU. The level's own error is part of the file, so every path picks the
  same level at the same distance.

A CI run that finds a missing or changed image saves it too. `bun run images:review --ci <run>` fetches those images for review.

A test that compares two of its own frames rather than a reference, as `showcase-hud.spec.ts` does for the HUD's switches, must read them while the canvas holds still: a scene whose camera flies, or whose look eases, changes every pixel between two reads, so a difference carries no meaning. Wait for two frames in a row to match, then compare. A page that compares its own frames also sets `governor: false` through `quality.set`. The frame-budget governor then cannot lower the render scale and raise it again between two reads. On a loaded software renderer the governor can step below the whole scale, draw at 0.95, and raise the scale back. Two reads either side of that change differ over half of the staged-levels picture. Two more traps come with such a reading. `page.locator(...).screenshot()` returns a PNG that Chromium writes as RGB, which `decodePng` refuses, so use `decodePngRgba` from `packages/cli/src/png.js`. And a screenshot taken a frame after a control moved can still show the scene mid-ease, so take the reading that a switch is judged against before the control is clicked, not after.

## The feature demos

Each demo in `examples/` is a sketch that the examples page runs live and the manifest holds at one time. These rules keep the held frame and the live page in step:

- **A change to a demo's look updates the tests that already draw it.** Where the manifest holds the demo, the same change redraws its references in every set and tier that draws it ([References](#references)). Draw them on the Mac's GPU and with `CI=1` before the push. The change also rechecks every other test that names the demo. That covers its parity scene where one exists, its benchmark and budget runs, and its references on the devices that draw it. A demo changed on its own is the commonest way a branch goes red on a device nobody ran. Add a picture test for a demo that has none only where its visual output is critical and no existing test covers it. Be judicious, and do not test every demo.
- A demo computes its motion from `time.now`, not by adding up each frame's step. The character's walk uses the integral of its speed, and the sparks use their flight formula. The held frame is then the same on every machine. Seeded `math.random` calls at setup are safe, because hold mode seeds the generator.
- Every demo takes the user's input while it runs. With no input, as in hold mode, its interaction moves nothing, so the held frame is the scripted frame ([Examples](examples.md#always-on-interaction)). A change to a demo's interaction that changes its held frame is a fault in the change, not a reason for new references.
- Hold mode draws the held frame as it does after a GPU loss. So an effect that smooths its result over frames, with a small offset each frame and a blend with the last frame, draws its raw single frame there. The volumetric fog's grid does: the light shafts demo's held frame shows the grid's cells on WebGL2, which runs at most Medium's coarse grid ([D-133](decisions/D-133-volumetric-fog.md#smooth-reads-on-a-coarse-grid)). Judge such an effect in the held frame and in live play, on each GPU path at the highest preset that path runs, from zoomed crops. A roughness figure misses those steps, as each spans many pixels. The blend itself never runs in a held image test either. The fog's blend reads the last frame's grid with code of its own on WebGL2, whose rows run bottom first, so only a test in play draws it. A test of such a blend runs in play, as `tests/image/fog-live.spec.ts` does: each GPU path draws the scene with a still camera until the blend has drawn 20 frames, and both other paths must draw one WebGPU frame. The page waits for a frame count, not a time, because a software renderer draws only a few frames a second and a fixed time would capture too few. It holds a second limit of its own, in seconds, so that a page whose frame loop has stopped reports the few frames it drew instead of waiting forever. That limit is a small multiple of what a working software renderer needs for the same frames. Too small a figure fails a busy machine on the frame count, and a page that has stopped reaches it with too few frames and fails either way. A limit of 20 seconds is too small and fails a CI shard on that count, so the page allows 150. The two paths compare against one WebGPU frame in one test rather than two, which saves a load of the scene.
- A demo that starts the engine in large-world mode sets `largeWorld` in `examples/demos.ts`. The examples page passes it to `createEngine`, and the manifest adds the image page's `largeWorld` switch.
- A demo that loads large files sets `timeoutSeconds`, which its image test takes. The glTF model, the character and the environment demos load files of 4 to 11 MB, or filter HDR images on the GPU. On SwiftShader on the Mac they take 14 to 21 s each, with four tests at once. CI's machines are slower, so they take 60 s, as the environment tests do. The default limit is 60 s too. A custom shader's WebGPU pipelines take about 18 s to compile on a passing run, and a slower runner can give no result within 30. A demo that makes the built-in room environment takes 60 s too. The math, instances and generators demos take 6 to 15 s each there. The forest demo sets 300 instead. It loads no files. It draws 56,000 trees and 30,000 bushes in one frame. Its three tiers take 17 to 27 seconds each on SwiftShader on the Mac, with three tests at once, and a busy machine stretches those to 51 seconds. CI's machines are slower, and the forest sits in the Scale group. So CI draws its full look, and not a Showcase demo's Low preset. On the fog page's figures, CI's software renderer is about ten times slower than this Mac's. A tier therefore costs about 200 seconds there. A limit of 60 fails the test on the count before the demo draws, so CI cannot see a fault in its picture, even a 37 percent difference. The three tiers cost a shard about ten minutes together. CI has never drawn this demo, so 300 is an estimate from the figures above and not a measurement. The first run that draws it gives a tier's real time; raise the budget from that figure if 300 is too small.
- A page that carries a hand-written shader draws slowly on a loaded machine, because the dev server compiles those materials one at a time behind one pool of compiler threads. The pages with a whole look built from them take 35 to 78 seconds. Those pages take `timeoutSeconds: 120`, so a busy machine fails them on their picture and not on the clock. Under a 60-second limit, two of them finish at exactly 60.0 seconds. A demo that carries one hand-written material beside the engine's own keeps the default 60, as the environment and aurora demos do. The pool compiles one material far faster than a page of them, and CI draws the aurora page in 6.5 s.
- Demos load sample content through `sampleUrl('...')` from `examples/lib/samples.ts`, with a string literal, so the sample check finds each file. A demo loads files only when loading is what it shows, and its entry gives the reason ([Examples](examples.md#procedural-first)). On a new machine, run `bun run samples:fetch` before the dev server shows them.
- A demo can post a `label` message with `{ id, text, active }`. The examples page then makes an element for the label, binds it with `engine.labels.bind`, and shows the text. The picking demo uses this. A label that is a plane of the scene also gives `width` and `height` in CSS pixels. Those are the scene's units, and the page then styles the element as a card. The 3D labels demo uses that. The image tests read only the engine's pixels, so they do not show labels.
- The demos use only lights that light surfaces. A light that the engine stores but does not draw leaves a scene much darker than planned. Hemisphere lights light surfaces ([D-128](decisions/D-128-hemisphere-lights.md)).
- A demo with a scene pass or a reflection pass may light its scene with point and spot lights. A pass draws the ones that its view sees ([D-104](decisions/D-104-scene-passes.md#point-and-spot-lights-in-scene-passes)). A light that only the pass sees casts no shadow in it. Several demos light their passes' scenes with the sun, the ambient light and the environment. The security camera demo's floodlight is the directional light, with a glowing lamp on the pole. The post effects demo moves a point light, so its wet ground has smooth puddles and no reflection pass.

Faults and lessons from the checks of the demos (M2-L5):

- A normal that is not a number at the occlusion texture's edge spoils ambient occlusion (#414). It draws dark dots along the bottom row and the right column of the image.
- The character demo's Mac and SwiftShader references share one camera framing: the Mac's GPU draws the SwiftShader framing in 9 of 9 runs. A Mac reference framed lower and closer has no known cause, so draw it again rather than accept it.
- Hold mode tells the sketch that no reduced motion is asked for ([implementation notes](implementation-notes.md)). So a held frame does not depend on the machine's setting, and the live page still honors it. GitHub's macOS runner image turns Reduce Motion on (`defaults write com.apple.universalaccess reduceMotion -bool true` in the runner image's `configure-system.sh`), so Safari there reports `prefers-reduced-motion: reduce`. The glTF model demo turns its camera with the orbit controls' auto-rotate, which stops when the user asks for reduced motion. A held frame that read the preference would leave the camera at the start angle, and 6.852% of its pixels would differ from the reference. Chrome on the Mac's GPU with reduced motion emulated draws that same image: no pixel differs from CI's Safari by more than 3 of 255.
- The security camera demo shows a scene pass's texture on a monitor. In compatibility mode the monitor draws lighter than on core WebGPU and WebGL2, as [D-104](decisions/D-104-scene-passes.md#display-color-on-the-8-bit-path)'s option B expects: the texture holds tone mapped color turned back to linear, and the monitor's material applies the tone curve a second time. In the held frame on the Mac's GPU, the feed's ground draws at (135, 145, 115) in compatibility mode against (123, 133, 104) on core WebGPU. The ACES curve applied twice to the core color predicts (135, 146, 113). A crate, the robot and the sky in the feed come within 3 steps of their predictions too, and SwiftShader draws the same figures within 1 step. Option A, display color stored as it is, draws the minimap's ground about 45 steps lighter than core WebGPU. Outside the monitor the three paths differ by at most 1 step. The feed shows the night sky above the yard, as scene passes draw the scene's background.
- Compare effects in one scene, with an effect that returns its input, before you report a fault. Two different scenes can differ for reasons of their own. An image with ambient occlusion and a custom effect draws brown crates where the images with one draw gray-blue crates. Yet one scene drawn with occlusion alone, and with occlusion and an effect that changes nothing, gives the same pixels.

## The reflection tests

The reflection tests of the manifest draw boxes on a mirror floor, on rippled water, and on a mirror at a quarter of the render size ([D-120](decisions/D-120-planar-reflections.md)). A magenta box lies wholly below the floor, where only a reflection without its clip plane would show it. `reflections.spec.ts` checks that each box's reflection hangs below it on its own side, and that no magenta shows. With the clip turned off on purpose, the check fails on all three paths.

In compatibility mode the floor shows the sky grayer than on core WebGPU and WebGL2. That path keeps display color in the pass's texture, and the floor's material applies the tone curve a second time, as [D-104](decisions/D-104-scene-passes.md#display-color-on-the-8-bit-path) expects.

The screen-space reflection tests draw boxes, a ball and a lamp on a steel floor that reflects no environment, so the floor shows only what the reflections find ([D-134](decisions/D-134-screen-space-reflections.md)). They cover a rough floor, a wet plastic floor, a quarter-size grid, half the render scale, ambient occlusion on the same grid, a planar reflection on the floor's left half, and a glass ball. `ssr.spec.ts` checks that each box's reflection hangs below it on its own side, and that the floor shows no box without the reflections.

The reflections read the frame before's colors, and hold mode draws only its last frame. So when the last frame reads the frame before, hold mode steps the sketch once more at the same time, and the thread that draws draws both frames in turn: the control slot `HeldFrom` names the first. Without that, a held frame shows no reflections.

## The probe tests

The probe tests draw a closed room whose walls glow a color each, with a mirror floor and a chrome ball, and a reflection probe that fills the room ([D-149](decisions/D-149-reflection-probes.md)). Variants blur the floor, turn box projection off, and split the room into two probes that blend. `probes.spec.ts` checks that the ball reflects the green wall on its left and the red wall on its right, and that the floor reflects the lit room rather than the black of a scene with no environment. A probe whose faces land on the wrong sides, or whose map never fills, fails it.

A probe captures in one frame and lights surfaces from then on, one probe a frame. So hold mode records the held frame once more while a probe waits for its capture, and the thread that draws draws both frames in turn. It keeps two frames' lists, so a held frame shows at most two probes. A test or a demo with more probes shows the environment in the rest of their boxes.

The moving-object test runs the engine live instead, in `tests/pages/probe-capture.ts`. A held frame draws no frame before the held one. So the probe's first capture happens at the held time, whatever the sketch calls. No hold test can show a map that a call refreshed. The page puts a glowing sphere on a dark mirror floor. It moves the sphere twice: once with `probe.capture()` after the move, and once without. After each move it reads the floor's reflection of the sphere from a settled frame. The reflection follows the call and stays where it was without one. So the test fails if a call captures nothing, or if a probe that refreshes once captures on its own. It runs on every GPU tier.

## The cookbook's recipes

Each recipe on the docs' cookbook page, `docs/cookbook/index.md`, is a complete sketch. The tests of the skills' sketches run them too (`tests/lib/skill-sketches.ts`): the unit test type checks each one against the engine, and `tests/image/skill-sketches.spec.ts` draws each one in hold mode on every GPU tier. A recipe that picks a camera must draw more than its background. The tests compare no reference image, so a recipe can change without new references in both sets. The demos in `examples/` carry the reference images instead.

- The cookbook has this test and not a manifest entry per recipe (M2-M1). The page promises that each recipe is a tested example. Reference images for 12 short recipes would add 24 files and a GPU run in both sets for every wording change, and the demos already hold the look of each feature.
- A recipe names its files as a project serves them, such as `/models/knight.glb`, so readers can copy it. `RECIPE_FILES` in `tests/lib/skill-sketches.ts` maps each such address, in single quotes, to a pinned sample file, and the tests write the sketch with the sample's address. The map names each sample with `sampleUrl('...')`, so the sample check covers it. A recipe that names an address the map lacks fails its browser test with the load's error.

- Recipes that load the KayKit Knight, an HDR sky or a glTF model take the 60 s limit of every sketch test. The character demo's load takes 14 to 21 s on SwiftShader on the Mac, so the limit leaves room.

## Visual checks

Image tests compare one frame with its reference. So they catch a change, but not a fault that shows only over time, or a fault in the reference itself. Dark dots along the image's edges can sit in ambient occlusion's references under the tolerance. So `tests/image/ao-edges.spec.ts` measures the edges against the scene without occlusion ([D-21](decisions/D-21-effect-chain.md#notes-for-ambient-occlusion)). Some shadow faults show only to the eye, such as cascades that shimmer as the camera turns (#198). Others are jagged shadow edges in the middle distance (#211), and moving cars' shadows that trail their cars. The visual checks measure the first two faults as figures with limits. The lag of far cascades that skip frames shows only in live frames, so it has a test of its own: `tests/image/moving-shadow.spec.ts`. It runs each preset with that preset's own `followMovingCasters` and far cascades every 8th frame, and reads 60 frames, or 24 on SwiftShader ([D-88](decisions/D-88-software-gpu-loads.md)). A test that set that setting itself would never see a preset's own value, such as Low's far cascade keeping its turns around moving casters ([D-16](decisions/D-16-moving-casters-and-bias.md#why-low-follows-moving-casters)).

- The visual page, `tests/pages/visual.ts`, draws a scene through the shadow check sketch, `tests/pages/sketches/shadow-check-sketch.ts`. The sketch wraps the scene's own sketch and holds the scene at one sketch time. It draws the scene in the `'shadows'` debug view, where a pixel's gray is the shadow factor: 0 in full shadow, 1 in full light. Every frame comes from hold mode. So a GPU draws the same pixels on every run, and the figures can have tight limits.
- Stability: a still observer camera stands where the scene's camera stands, and draws the frames. The scene's camera places the cascades, through `debug.shadowCamera`. It draws 6 frames at steps of 1/60 s. In each step the camera moves 4 mm ahead and 2.5 mm to the side, and turns 0.03 degrees. That is less than a texel of a near cascade, as a slow walk moves a camera. Nothing else moves. So a pixel whose shadow changes by more than 8/255 between two frames shows a cascade that crawls. The figure is the largest share of changed pixels between two frames.
- Edges: the page draws the reference, the same frame with the largest shadow map and the widest filter. The map has 4,096 texels on each side, and the filter blends 5 texels. The figure is how far the frame's half-shadow line strays from the reference's, in pixels. It counts the pixels on opposite sides of the two lines, and divides by the length of the reference's line. A filter blurs an edge evenly to both sides, so blur leaves the line where it is. Steps of coarse texels move the line. The line includes the edges of objects against the black background. So compare a scene's figure only with the same scene's.
- Stair steps: the still shadow scene, `tests/pages/sketches/shadow-scene-sketch.ts`, has one long straight shadow edge at a slant to the texels. The page finds the edge in each row of a box of the frame, and fits a straight line through it. The figure is the root mean square distance of the edge from the line, in pixels.
- Contact: the page also draws the normals view of the same frame, where sides and the ground have different colors. In each column it finds each foot: a dark side above the ground. The side is dark because it faces away from the sun or lies in shadow. So the ground just below it should lie in shadow too. The gap figure adds the shadow factor of each ground pixel down to the first pixel in shadow, within 4 pixels. That is the light between the foot and its shadow, in pixels of full light. A foot with no shadow within those 4 pixels is left out, as its caster's shadow falls elsewhere. The rim figure reads upward: the shadow on a lit top, such as a roof, within 4 pixels of its edge. It catches casters that shadow their own lit tops.
- Seam: the shadow scene's long edge crosses the seam between its first two cascades. In each row of the edge's box, the page measures the edge's soft width, between the shadow factors 0.9 and 0.1. A median of three rows takes out the texels' small steps. The figure is the largest change of that width from one row to the next. Where cascades meet with no blend, the width jumps there in one row. The limit is 1.2 px. With the blend, the scene measures 0.63 px to 0.68 px on the Mac's GPU and SwiftShader. Without it, it measures 2.87 px to 3.19 px ([D-73](decisions/D-73-cascade-blend.md)). A test runs the scene without the blend, and the figure must then be over twice the limit.
- Acne: the page finds the pixels of level surfaces that the reference shows in full light. Each lies at least 3 pixels from any of the reference's shadows. The figure is the mean shadow on those pixels in the frame, in percent: each pixel adds one less its shadow factor. The reference's fine map shows no acne on flat surfaces. So the figure catches stripes and rings of self-shadow, such as those on a pavement slab's lit top. The margin keeps out shadow edges, which the frame's coarser texels soften and move.
- `tests/image/shadow-contact.spec.ts` runs the contact checks on car-sized boxes under S4's sun, on both GPU paths, in `bun run test:browser`. It looks near the camera, in the last cascade, and just past the end of the first cascade. In a fourth view the ground casts shadows too. Its limits on the share of the frame in shadow and on acne catch acne on the ground's top. Three more views stand the boxes on a pavement slab 20 cm thick that casts shadows, with the 5 x 5 filter. Their suns stand as high as S4's, 35 degrees up and 20 degrees up. A fifth slab view, `far-slabs-low`, has the 3 x 3 filter and texels as coarse as S4's last cascade on the Low preset. Their limits hold the slab's acne. `CONTACT_LIMITS` in `tests/lib/visual-checks.ts` holds the limits.
- `tests/image/shadow-checks.spec.ts` runs the shadow scene on both GPU paths in `bun run test:browser`. It runs the scene again 1,000 km and 6,378 km from the origin in large-world mode, under the same limits. A control test puts the scene 6,378 km out without large-world mode, and the checks must fail it. `bench/tests/visual.spec.ts` runs S2 with three cascades, S4, and S5 with 100 knights held still, in `bun run test:bench`. `VISUAL_LIMITS` in `tests/lib/visual-checks.ts` holds each scene's limits. Both tests save their frames and figures in `test-results/visual/`.
- The device runner's bench plan runs the same page for each scene after its timings ([Benchmarks](benchmarks.md#visual-figures-and-captured-frames)).

### Why the checks work this way

- A camera that turns on the spot moves every pixel by a map that its angles give. So `shadow-turn.spec.ts` maps each frame back onto the first. A camera that moves also shifts near things against far things, and no such map exists. A still observer needs no map at all: any change it sees comes from the cascades.
- The edge figure is the offset of the half-shadow line, not the root mean square difference of the shadow factor at edge pixels. The reference's edges are much sharper than the frame's, so blur sets that root mean square figure: 17.1% with the current split and 18.0% with the split of 80%. The offset of the half-shadow line ignores blur, and rises by 39% with that split.
- The visual page runs on the dev server, because only development builds draw debug views. So the timed pages keep the production build, and the visual checks cost no measured frame.
- In three.js, the `CSMHelper` shows the cascades' boxes, and the cascaded shadow maps take their camera as an option. `debug.shadowCamera` gives null3D the same choice of camera.

## Large-world jitter

Image tests compare still frames, so the `cells-6378km` test shows that a scene far out draws as at the origin. A moving camera rounds its position again in each frame, and a rounding that changes makes the image jump. The jitter check measures that over a flight. [D-80](decisions/D-80-large-world-jitter.md) gives its design, figures and tolerance.

- The jitter page, `tests/pages/jitter.ts`, flies five flights. Each runs in its own engine in large-world mode. The flights stand at the origin, 1,000 km out and at the Earth's radius. Then the two far ones fly again with every grid cell taken, as without cells. The sketch `tests/pages/sketches/jitter-sketch.ts` builds the scene. `tests/pages/lib/jitter.ts` holds the layout, the figures and the limits.
- The camera moves 12 cm sideways per frame, for 16 frames, past six white squares that face it. Each square sits at its own depth in its own band of rows. The page moves the camera through the sketch's messages, and reads each frame back with `captureFrame` from a live engine. Nothing else moves, and the governor is off.
- Each square's center comes from its band's linear brightness, so edge pixels count in part. The figure compares each square's motion from one frame to the next with the same motion in the flight at the origin. It is the largest difference. Far flights must stay within 0.05 px. The flights without cells must exceed 0.5 px, so the check can see jitter. Each square must keep 95% of its largest area in every frame.
- `tests/image/jitter.spec.ts` runs the page on WebGPU, compatibility mode and WebGL2, on the Mac's GPU and on SwiftShader in CI. It also checks that each flight without cells logs the engine's warning that the cells ran out, once. It saves each flight's first and last frames and the figures in `test-results/jitter/`.
- The device runner's `jitter` plan runs the same page on each GPU path ([Device sessions](devices.md#the-jitter-plan)).

## Parity with three.js

- Parity tests check intent: that null3D shows what files and authors mean ([D-52](decisions/D-52-intent-parity.md)). A scene compares with three.js's rule only where both engines draw the same building block. These blocks are lighting terms, tone curves that both engines offer, skinning poses, animation sampling and glTF interpretation. A feature that null3D draws with a better technique gets its own references. Its parity scene then takes a looser limit, which checks only that the effect sits in the same place and has a similar size. The scene's entry gives the reason.
- A test of a feature scene can have a three.js twin: a page in `bench/pages/threejs/` that draws the same scene. Both engines build the scene from one data module in `bench/scenes/`, such as `ortho-camera.ts`.
- `FEATURE_SCENES` in `bench/lib/parity.ts` lists each such test with its twin. `bun run parity` compares them on each tier by three.js's rule, after the benchmark scenes. Exit gate item 2 therefore runs in one command. On the Mac it draws in Chrome on the real GPU: `bun run parity -- --tier webgpu,webgl2` gives the gate's two tiers. `--scene` names one scene, by its image test.
- `bench/tests/parity.spec.ts` compares the same list in `bun run test:bench`, on SwiftShader in CI. The twin loads from the production build of the benchmark pages. The test's image loads from the dev server, because the image test page loads its sketch by address.
- The list covers standard materials: the grid over metalness and roughness, texture maps, the mask alpha mode and blending. The `alpha-coverage` and `alpha-hash` scenes draw the masked cards with three.js's `alphaToCoverage` and `alphaHash`. The `transparency-solids` scene compares double-sided see-through solids, whose back faces draw before their front faces, and a tube with `forceSinglePass` ([D-82](decisions/D-82-transparency-parity.md)). The `sprites` scene compares sprite batches with three.js's `Sprite` and `SpriteMaterial`: blended sprites at frames of an atlas, and opaque sprites sized in pixels ([D-37](decisions/D-37-sprites.md)). The `points` scene compares point batches with three.js's `Points` and `PointsMaterial`, on its WebGLRenderer alone. It draws opaque, cut-out and see-through points, sized in world units and in pixels. It takes a limit of 0.2% ([D-37](decisions/D-37-sprites.md#points)). The `lines` scene compares line batches with three.js's `Line2` and `LineSegments2`: widths in pixels and in world units, round joins, colors at each point, dashes, a loop and a blended line. The `lines-basic` scene draws the same lines one pixel wide against `LineBasicMaterial` and `LineDashedMaterial` ([D-46](decisions/D-46-wide-lines.md)). The `lines-lit` test has no twin, as three.js has no lit lines. It also covers point and spot lights, a texture background, and both fog types. Then come the four tone mappings at two exposures, the orthographic camera, the directional light's shadows, and bloom at two settings against `UnrealBloomPass`. Ambient occlusion compares at two settings with `GTAOPass`. Color grading compares with `LUTPass`: the `lut-cube` test, by three.js's rule. The `lut-vignette` test, at 0.7 of the table's intensity with the vignette, is a sanity comparison with `VignetteShader` under its own limit of 2%. The grading tests draw with plain AgX, and the vignette takes the porting mapping for AgX: an intensity of 1 at most and a falloff of 3. With that mapping, 0.000% of its pixels differ on every path, on the Mac's GPU and on SwiftShader. A vignette of a size 0.1 off differs in 2.2 to 40.5%, and a missing one in 52 to 67% ([D-77](decisions/D-77-final-pass-order-and-formats.md)). ## References

- References live in `tests/image/references/<set>/<tier>/<test>.png`. Each environment has a full set. `chromium-swiftshader` is Chromium on SwiftShader, the software GPU that CI draws with. `chrome-real-gpu` is Chrome on the Mac's GPU.
- A new test needs its references in both sets before you push it. CI's Chrome tests draw only with SwiftShader. CI's Safari and Firefox jobs compare with the `chrome-real-gpu` set, so a missing Mac reference fails there, after a full run.
- **Redraw the references in the same change that moves them.** A change that draws differently needs its references in both sets before it lands. The same change also rechecks every other test that names the scene, such as its parity comparison and its benchmark or budget run: a demo or a feature scene is judged by more than its picture. Leaving them to a follow-up costs a second full pass of the manifest, and CI stays red or flaky in between.
- **A remake names the cause.** A reference redrawn after a merge from main names the commit that moved the frame, and says why that move is intended. Find that commit by bisecting the merge's main side with the one test (`bun run test:images -g "<the test's name>"` at each candidate), and take each candidate that touches the shaders or the engine. Without it, a regression another branch introduced becomes the new reference, and the next failure of that test cannot be read.

## Other browsers and devices

- The checks plan compares each image with its `chrome-real-gpu` reference at the device tolerance, 0.5% of the pixels by default.
- **A device is judged against a device tolerance, never against a Mac picture at zero.** Each GPU rounds some of its own pixels, so the only zero-tolerance comparison that holds is one drawn by the same machine in the same run. A test whose scenes must match exactly keeps the default device tolerance, or records its own device references. It never narrows `deviceTolerance` below the test whose references it borrows: that test passes on the same device with the same frame, so the borrowed picture cannot be held to more. At a device tolerance of zero, `asset-scene-lod-copied` fails on CI's Firefox by 8.895%, for a frame identical to the one its reference owner passes.
- Each test's page gets `?preset=high`, unless the test's switches name another preset. The references come from desktops, where the engine chooses High within each GPU path's ceiling. So a page on WebGL2 or in compatibility mode runs at Medium, those paths' highest preset (`TIER_CEILINGS` in `quality/chooser.ts`), on every device, and its report names Medium. That is the ceiling, not a fault. A phone chooses Low, and a tablet Medium. Low smooths edges with FXAA and caps anisotropy lower, which changes the edges and textures of most tests. On Low, the S24+ fails 41 WebGL2 tests by 0.3% to 11% of the pixels, and the Mac draws the same tests on Low within 0.012% of the phone's pixels. The hold pages of `bun run parity` and of the parity plan get `?preset=high` too.
- A test whose scene covers little of its frame records a tighter device tolerance, so a frame that lost its scene still fails. S2's trees cover under 1% of its frame, and its device tolerance is 0.2%.
- Where a device's GPU draws a test another way, add the device to the test's `devices`, such as `ipad` or `sm-s926b`. That device then compares with its own references in `tests/image/references/<device>/`, at the test's own tolerance. Its next run saves the images to accept.

Both the Galaxy S24 (`sm-s921b`) and the S24+ (`sm-s926b`) have the Xclipse 940, so the S24 shares the S24+'s references. A cloud device gives its model number as `model` in `tests/lib/browserstack-devices.ts`. Its runs then find the same references as the phone's runs over the local network.
- A device that lacks a GPU path keeps references only on the paths it has. The table of device tiers in `tests/lib/images.ts` lists them, such as WebGL2 alone for the S24+, which has no WebGPU.
- A device's candidate that compared with the real-GPU references cannot become its reference. ## CI

- CI splits the browser tests, the manifest among them, into shards that run at once, as the `browser` job's matrix lists them. CI's `build` job builds the WebAssembly files once, and each shard downloads them. Add a shard when the slowest shard's tests pass 12 minutes. The job's own limit then leaves room above that for its setup and for a machine that runs the tests slowly.
- The production build projects' tests run in one job of their own, `browser-production`, in two parts. The part that runs the CDN test packs the terrain add-on, whose packed library that test loads from the second origin. It packs in the background after the part's page builds, while the part's other tests run, and the CDN test runs once it has packed. Every other build in the repository resolves packages to their source, so this is the only test of the packed files. Each part builds the pages that its test files load with `bun run build:test-pages <page...>`, so no page builds twice. Then it runs those test files, and then their tests that run alone, one at a time, on the same build, with `NULL3D_PRODUCTION_PAGES=prebuilt`. Each page's build takes about 10 GB of memory at its peak, so the builds run one at a time. A new production build test file goes into the part that builds its pages; the workflow test names the file and page that a part misses. The first part runs the engine, KTX2, policy and CDN tests, and the second the errors, sketch shaders, stats and glTF tests. A check that the engine test page downloads no part of a loader belongs in `engine.spec.ts`. Then a loader's own test file loads only its own page, and can run in the other part. Every other browser job sets `NULL3D_PRODUCTION_PAGES=skip`, which leaves out the production server and those projects. A build of the pages in every browser job would cost each job 283 s on average (run 39554447893). Only 2 of 40 shards run a test that reads them ([D-220](decisions/D-220-production-pages-once.md)). `tools/lib/ci-workflow.test.ts` keeps the build in that one job.
- The tests that run alone go one at a time in a job of their own, `browser-alone`, in 3 shards. Each shard has a machine to itself, so no other test runs beside one. The showcase HUD file holds four tests, each in a `showcase` job of its own with a 35-minute limit. It reads each test's time from the `list` output in the browser jobs' logs. It takes the last 5 CI runs on main that passed and ran the browser job, and each test's median time in them. Main's runs from before [D-99](decisions/D-99-no-merge-queue.md) ran no browser job, so it skips them. A file that runs its tests in order is one group. Each test of a file that runs its tests in parallel is a group of its own. Playwright orders a project's groups by the worker that each needs before their files, so a file whose options start a worker of its own, such as the shaders test's launch options, runs after the files that share the default worker. The order of `--list` alone is therefore not the shards' order. A model in that order puts other tests in each shard: in run 39981283455 a shard weighted for 11 tests ran 145. With Playwright's own groups, the model gives that run's slowest shard 18.0 minutes, where it took 17.3. It prints each shard's time with the workflow's weights and with the best weights, for the `browser` job and for `browser-heavy`. It prints the time of the tests that run alone too. Each of its tests opens a page of its own, so the file runs them in parallel. ### Tests that run alone

- Some browser tests check a frame rate, a time limit, or the frames or the work that come in a fixed time. Others check that a loop allocates nothing. Such a test runs alone: no other test may run beside it. It passes `ALONE` from `tests/lib/alone.ts` as its details, which tags it `@alone`.
- The projects `<environment>, alone` and `production build, alone` take the tagged tests, one test at a time. The other projects leave them out. In CI the shards run with `--grep-invert @alone`. The `browser-alone` job runs `--grep @alone --workers=1` in 3 shards, so nothing runs beside these tests.
- They run alone because CI runs each shard with 2 workers on a runner with 4 processor cores, GitHub's standard Linux runner for a public repository: Playwright's default is half the cores, and each shard's log says 2 workers. SwiftShader draws on several threads of its own, so the two workers' pages share the four cores. A heavy test on the other worker takes processor time from the test beside it. One example is `environment-parity.spec.ts`. It builds a 2K map on the processor and filters it with three.js on SwiftShader. Beside such a test, the engine test of the pace of drawing on the main thread with WebGPU fails, with frames exactly every 50 ms. The engine's other pacing tests, the pointer event allocation test and the layers test fail the same way.
- A project of its own with `workers: 1` is not enough. In Playwright 1.63 a project's `workers` limits only that project's own tests, so a test of another project still runs on the other worker. A project's `dependencies` would run the alone tests after the others, but Playwright runs a dependency project whole in every shard and for every file filter. So CI runs the alone tests in a job of their own.
- `bun run test:browser` with no filter runs every project in one run, so a heavy test can run beside an alone test there. For a local run in which those checks count, run the two parts as CI does: `bun run test:browser --grep-invert @alone`, then `bun run test:browser --grep @alone --workers=1`.
- The tests that run alone start with the engine tests that check the pace of each thread mode and of the main thread. The engine tests of the threads without `Atomics.waitAsync` run alone too, and so does the start under a strict Content-Security-Policy. Then come the frame tests (`frames.spec.ts`), the volumetric fog in play (`fog-live.spec.ts`), whose page counts its frames in a bounded time, the raycast test that waits for every job worker, the layers test, the governor's stages, and the four allocation tests. A test that only waits for frames, however long they take, needs no tag. The four tests of `showcase-hud.spec.ts` wait and carry the tag anyway. Their pictures need their page's frames at all, which a test beside them starves. Each waits for minutes, which no shard's 25-minute limit holds beside the tests' own failure on a slow machine. As one test, the file takes 14 to 24 minutes on CI's software GPU, which would set the length of every CI run. So it holds four tests: the toasts, the sky, the fog and the environment light. Each opens the page afresh and first sets up the state that its checks need, so CI can run them side by side. Each name starts with "the showcase HUD", and the job of the other tests that run alone leaves them out by those words. The first frame may take 300 seconds and a switch 180, inside a test budget of 25 minutes. On a loaded machine the first frame can take over three minutes. With a one-minute wait no new frame arrives, and a switch reads 0.46 of a step where it must move 1.5.
- A wait bounded by a count of frame reads is not bounded in time. A read costs milliseconds on a real GPU and about 5 seconds on CI's software chip. So a wait of 40 reads for a look that has come to rest runs for about 200 seconds at each switch there, and spends the test's whole budget. `showcase-hud.spec.ts` stops that wait after 10 seconds by its own clock, the window the 40 reads take on the machine that chose the figure. Bound a wait like this on the test's own clock, and let the number of reads follow from the speed of the machine.
- The model of `bun run test:browser-weights` gives each shard's time within 0.5 minutes, and Playwright's own split matches the model's counts in every shard (CI run 37383868982). The model can still read about 0.7 minutes under the real tests, and a job takes about 1.3 minutes more to set up. One after another, the alone tests take 4.8 minutes at the median times, and their job about 6 minutes with its setup.
- A test's time follows the speed of the machine that CI gets. Across 20 runs, each WebGPU quality test takes 33 to 38 seconds on fast machines and 1.2 to 1.9 minutes on slow ones. A slow machine can double every test of a shard. So a test that looks twice as slow after a change may only have met slow machines. Check it on one machine with and without the change: the 8 moving shadow tests take 31.0 seconds with #457 and 31.4 without it.
- A file that runs its tests in order puts them all on one worker, so the moving shadow tests for each preset run in parallel. They read fewer frames on SwiftShader, and S5 draws a smaller crowd there ([D-88](decisions/D-88-software-gpu-loads.md)). The Factory comparison file skips 4 of its 10 tests on SwiftShader and runs short steps, so it takes 27 seconds on the Mac rather than 75.
- When the job's limit cancels a shard, every test in it reports nothing. The run's failure list is then incomplete, and the faults hidden in it read as faults that never existed. Stale weights cause this as the suite grows: a shard weighted for 185 tests can run 233. Many short shards cost about the same runner time as fewer long ones, and the job ends sooner. See [Branches and parallel work](pull-requests.md#commit-messages-and-pushes) for a run that lost jobs.
- The organization's Enterprise plan runs 500 jobs at once, so CI can split its browser tests into many shards ([D-194](decisions/D-194-ci-jobs-in-parallel-on-enterprise.md)). The real-browser model counts the browsers' real page times (`tests/lib/plans.ts`), and the real-browser job's limit is 30 minutes. Every shard keeps its runs folder as an artifact. Each runner writes `page-times.json` there and prints its slowest pages, so the model can follow the browsers' real times. The checks plan's own shard test fails when any shard passes 10 minutes in the Safari model.
- Weights split by count, such as halves of an earlier list, put slow tests together. Weights from one run whose failing tests ran twice mislead too. Take the weights from the median of several full runs.
- Claim a picture failure from the failing test's own saved result. Never claim it from a job's name, a shard's title, or a summary of either. A cancelled shard reports no results at all. So a run's list of failed jobs is not a list of its faults, and a job marked failed may have stopped before its first test. A run's own record of the checks it passed is not a list of its failures either.

## Tests on slow machines

- CI's software GPU pays for a shader's code in every frame, even for a loop that no pixel enters. CI's x86-64 runners compile SwiftShader's shaders with Subzero, which keeps such a loop; the Mac's arm64 SwiftShader compiles with LLVM, which drops it. So a branch that adds code to a pass that every frame draws can slow CI's browser jobs by several times while the Mac shows little. The final pass's upscale and sharpening run in loops that run no rounds at the whole canvas's scale. Yet they make S1 draw 4 to 6 times slower on one runner than without them ([D-236](decisions/D-236-final-pass-upscale-build.md)). Keep code that a frame does not run out of the build that it draws, with a permutation bit.
- One runner can run the same code 2 to 3.6 times faster than another. To time a change on CI's software GPU, run both builds on one runner, in one job, and read the figures that the page reports, not the settings it was asked for. The diagnostic run of D-236 shows the way: a workflow on a branch that never lands, which keeps only the jobs that build the pages and times each variant in turn.

- CI's software GPU on a busy machine draws far fewer frames than a desktop. With other suites loading the Mac, SwiftShader draws the raycast page at 0 to 9 frames a second, where it draws about 60 alone. So a browser test checks frame rates only where the frame rate is its job. A test that counts work over frames measures until the frames have come.
- The restart page (`tests/pages/failures.ts`) checks that the later engine on one canvas draws. In one half-second window, CI's software GPU draws no frame in 5 of the 18 cases where a worker draws, though each case takes as long as a passing one. A trace of the drawing thread shows the engine refusing frames only while two are unfinished on the GPU. So the page repeats the half-second window while the engine draws nothing, ten windows in all. It fails only an engine that draws nothing in five seconds. The errors page shares that loop with it, through `framesDrawn` in `tests/pages/lib/measure.ts`.
- The raycast test checks that a batch of 10,000 rays reaches every job worker. Take a check over one second, with each worker's median busy time per frame above zero. It needs each of the 16 workers on the Mac to take part of the batch in more than half of the frames.
- That depends on luck twice. The job system gives a loop's chunks to whichever thread claims them first, the thread that casts the batch among them. The workers sleep between frames, so a worker that wakes late misses that frame's batch. With one or two frames in the second, one late worker fails the test. A second with no frame at all leaves the test no figures.
- In the frames that run, the engine gives work to almost every worker, so the engine is not at fault. Such a check fails 14 of 20 runs on SwiftShader with 10 copies at once (main at a1168724), and 12 of 20 one at a time on the busy Mac. Every failure has 9 frames or fewer in its second.
- So the raycast page adds up each job worker's busy time over all the measured frames. With `?everyWorker`, which only this test gives, it measures for 1 second, then for 2, 4, 8 and 16, until every worker has taken work. The test fails only for a worker that took no work in all that time. On a quiet machine the first second is enough.
- Each measurement is twice as long as the one before, because a measurement counts only the frames that start and end within it. On the busy Mac, SwiftShader takes 0.3 to 1.4 seconds for a frame. Ten measurements of one second each then find 0 or 1 frames in 8 of about 14 runs.
- The job workers start only when the frames hand out enough parallel work ([D-126](decisions/D-126-lazy-job-workers.md)). The page's first frames cast no batch, so the engine pauses its timing of the loops. That pause is 4.5 seconds of sketch time at any frame rate ([D-126's addendum](decisions/D-126-lazy-job-workers.md#the-pause-after-a-light-window-is-a-time)). A pause counted in frames, such as 270, takes SwiftShader over 30 seconds to draw. The test then measures all 31 seconds with both job workers idle.
- The job worker test of `tests/image/failures.spec.ts` waits for a job worker to run before it waits for the failure. The engine asks for job workers only once 30 frames have shown enough parallel work. On CI's software GPU those frames take longer than the test's 15 seconds. Run 40350518899 had the pipelined and low-latency pages count their whole window and hear nothing, where a faster run took 16 to 22 seconds. So the page watches its trail for a job worker that reported ready. It starts its 15 seconds then, and it names the absence in its result when no worker starts within 60 seconds. The test allows 2.5 minutes. A page held at one frame a second with `?fps=1` reproduces the fault on any machine. With the wait removed, all four modes reported no code and 310 ticks. With it, all four reported E1404.
- The layers test (`tests/image/scene.spec.ts`) checks that objects, a batch and the camera can change layers every frame with no rebuild of the draw tables. A check of more than 10 frames in one second fails in CI's WebGPU run with 9 frames when the shards put the test beside the room-light tests. Those keep SwiftShader busy for about 20 seconds each.
- The engine is not at fault. On the Mac the test draws 51 to 59 frames in its second, 40 of 40 runs, with no rebuild. Beside the WebGPU room-light tests it draws 19 to 22 frames, again with no rebuild. Its median frame interval is 33 ms, and the slowest frames take up to 120 ms. A CI runner has far fewer cores. Away from those tests, the test passes all 133 CI runs that reach it.
- So the scene page's `?frames=` switch sets the fewest frames to measure. As on the raycast page, each further measurement is twice as long as the one before, up to 15 seconds in all. The three pages share that loop (`tests/pages/lib/measure.ts`). The frames and the rebuilds add up over the measurements. The layers test asks for 11 frames, and it still allows only one rebuild: the first frame's, when the measurement starts before it.
- The scene tests check the GPU's pass times where the device has timestamp queries. The GPU timer samples one frame in 11. After a loss of the GPU, the new device starts its timer again. So WebGPU single-threaded can draw a few frames after the loss with no pass time, and the test then fails on an empty list (run 37591471417).
- So the scene page measures again until its measurements hold a frame and, on such a device, the pass times. The first measurement with frames gives the other figures. The loop is the one above, with up to 15 seconds in all.
- The vertex-draw page compares the bytes a frame uploads at 1,000 copies with those at 50,000. A measurement counts only frames that both start and end inside its window. A window shorter than one frame holds none, and reports zero uploads and zero draws. The 50,000-copy frame on CI's software GPU took longer than the page's two-second window (runs 40524770063 and 40532851592). So the page measures through `measureDrawing`, which doubles its window while it holds no frame. The test also fails a sample that holds no frame. Its message says so, so a reader does not take it for a missing draw.
- The pointer event tests (`tests/image/object-events.spec.ts`) wait for the sketch to read the input and run its handlers. Playwright's default wait of 5 seconds is too short for that.
- The pan test waits for 9 frames of the pan, which can take longer on SwiftShader on a busy machine. With the page's thread slowed 4 times and 16 copies of each test at once, a 5-second wait fails 9 of 288 runs, all in the pan test's wait.
- So each wait lasts up to 30 seconds, and each test up to 2 minutes. Under the same load, 288 of 288 pass, and the slowest test takes 60 seconds.
- The stats test with 20,000 instance rows (`tests/image/stats.spec.ts`) reads the memory figures. The sketch thread publishes them in frames whose number is a multiple of 8, and in the first sampled frame ([D-116](decisions/D-116-stats-overlay-figures.md#the-memory-figures-from-the-first-sampled-frame)). Without that first publish, the first figures can wait 7 frames. On SwiftShader in CI a frame of that scene takes more than 1.4 s, so the test reads 0 mesh bytes. The page waits up to 20 s for the figures.
- Before it listens, the mouse test clicks the right box, then waits until the sketch has read the click. A wait for the pointer on the box with no button down is not enough, because the click's move alone gives that state.
- The sketch can read the press and the release only after the handlers come, so the first step gets a whole click that it does not expect. So the test presses, waits until the sketch shows the button down, then releases and waits until it shows the button up.
- Each step waits until the lines are the expected lines, not only until their count is right, and a failure shows the lines that came.
- The test of a click on a frame of the setup must click while the frame of the box is on screen. A click before that frame reaches the screen picks nothing, through pointer events and through `camera.screenToRay`. Only "ray nothing" then comes, in pipelined mode.
- A warm-up ends once the frame's pipelines are built, and the thread that draws reports that just before it draws the frame. In pipelined mode that thread is not the sketch's. So a setup that says it waits once its warm-up ends lets the page click before the frame reaches the screen.
- Such a click names no frame. Its ray then takes the camera as it stands, which the setup has already turned away from the box. The engine does what its docs say, so such a fault is in the test.
- On SwiftShader on the Mac, with 32 probes at once, the frame is not yet on screen when the warm-up ends in 96 of 96 probes. It comes about 6 ms later, before the test's click. A busy CI runner can take longer to draw it.
- With the first frame's draw held back 300 ms in a local build, a click at the warm-up's end fails 8 of 20 runs with CI's lines. All 4 pipelined runs fail, and all 4 runs with the sketch on the main thread. The other modes draw on the sketch's thread or the page's, which runs the click.
- So the setup waits until a frame is on screen before it says that it waits. With the same hold, the test passes 20 of 20. Without the hold, it passes 20 of 20 alone in pipelined mode. In all five modes, with 16 copies at once and the page's thread slowed 4 times, it passes 80 of 80.
- A fault in the engine's input reader, which [the implementation notes](implementation-notes.md#input) describe, fails the orbit controls test on WebGL2, at the wheel after the right drag. It shows in 1 of 128 runs of the 8 orbit control tests, in 16 copies at once with the page's thread slowed 4 times, with CI's exact difference. With the reader correct, they pass 128 of 128, and the WebGL2 test passes 20 of 20 alone.
- The engine checks of the engine test page (`engineProblems` in `tests/lib/engine-checks.ts`) include frame-rate checks. They are the median frame interval, the floors on the frames and the sketch's updates, and a measured refresh rate. The thread that draws needs 32 frames to measure that rate.
- Only the tests whose job is the pace of the frame loop keep these checks, and only on a real GPU. In `tests/image/engine.spec.ts` they are the tests that:
  - run the engine in each thread mode, on each GPU path;
  - run the sketch and the drawing on the main thread, with low latency or with drawing on the main thread asked for;
  - run the engine without `Atomics.waitAsync`, where the threads wake each other with a message for each frame.
- The engine runs of the device plans keep them too, on a real GPU. The content security policy test keeps them as well.
- On CI's software GPU the GPU sets the pace, not the frame loop. There the tests without `Atomics.waitAsync` fail in three thread modes of the production build, even for a change to tools alone. Their median frame intervals of 41.7 and 50.0 ms are over the limit of 34 ms. The single-threaded WebGPU test fails at 50.0 ms too.
- So `engineProblems` leaves out the frame-rate checks for any result that a software GPU drew. The engine's probe names the GPU: the WebGL2 renderer and the WebGPU adapter. A name that matches SwiftShader, llvmpipe, softpipe or Microsoft's Basic Render Driver marks a software GPU, as in the record of tested devices. The results still need frames and the sketch's updates, at any rate. On a real GPU, such as the Mac's or a phone's, every check stays.
- This also leaves out a measured refresh rate on a software GPU. SwiftShader can report 12 Hz, outside the display range, and fail the worker-growth test (CI run 38328260291). So the check skips a measured rate there as well as a missing one. A unit test covers both pacing settings and keeps the range check for real GPUs.
- On WebGPU, where the device has timestamp queries, the engine checks also ask for GPU times, on a software GPU too. At least half of the frames that the GPU timer samples must have one. The timer samples one frame in 11 while the page measures. Firefox 157 on the Mac keeps 0 or 1 of about 22, which a check for a single GPU time passes in 4 of its 5 thread modes ([implementation notes](implementation-notes.md#browser-faults)).
- The same tests count more than 10 frames after a pause. At 50 ms a frame, a half second holds about 10. So the engine page's `?resumed-frames=` switch counts on until that many frames come, as the layers test's switch does. The tests ask for 11.
- The GPU loss tests (`tests/image/gpu-loss.spec.ts`) check that the engine draws on after a loss. On a busy machine the new device and its first frame can take longer than a fixed second, and a half-second window after it then holds no frame. At loads of 21 to 30 on the Mac, full local runs on SwiftShader fail so, while the tests pass alone.
- So the GPU loss page measures with the same loop until a frame comes. It starts at half a second and stops at 15.5 seconds in all. The loss in the middle of a frame counts its frames the same way. On a quiet machine the first half second is enough.
- The other tests of that file turn the frame-rate checks off with `{ pacing: false }`. Each checks something that a slow frame does not change. They still need frames and the sketch's updates, at any rate. They are the tests of:
  - the shared memory maximum that the page asks for, in each mode;
  - the order of the start's downloads;
  - the request for the shader file while the core downloads, in each mode, and where a worker cannot draw;
  - no download of the files that load on first use;
  - the high-performance and the low-power GPU;
  - the count of job workers that `?jobs=` asks for;
  - the single-threaded start in a page without cross-origin isolation;
  - the start that draws on the page where a worker cannot draw. The test of drawing on the main thread checks the pace of that loop.
- With the frame-rate checks, the download test fails single-threaded in CI with a median frame interval of 50 ms, though it passes 20 of 20 alone. On the Mac, with the page's thread slowed 4 times and 16 copies of the test at once, 11 of 16 fail so. Their medians are 50 to 125 ms. With the switch, 16 of 16 pass at medians up to 175 ms.
- With the measurement loop and the switch, three tests pass 20 of 20 each on SwiftShader on the busy Mac, one at a time and with 10 copies at once. They are the raycast test on each GPU path and the download test in single-threaded mode.
- An image test that compares frames of play fixes the render scale at 1 and turns the governor off. Its sketch calls `quality.set({ minRenderScale: 1, maxRenderScale: 1, governor: false })`, as the outline, grading, occlusion and late skinning sketches do. A held frame needs neither, as hold mode has no governor. A page that draws live frames before it captures cannot rely on a frame-rate target to hold the scale either. A frame that takes longer than a second still misses a target of one frame a second, and the governor steps anyway. That moves the probe-capture picture on a slow CI runner. On a slow GPU the frames miss the budget, and the governor lowers the render scale once its grace of 2 s ends. Below a scale of 1 the upscale takes the place of FXAA, so every edge changes. A capture early in play passes only because it comes before the governor may step.
- The late skinning test (`tests/image/skinning-late.spec.ts`) adds characters during play. Without a fixed scale, that run drops to a render scale of 0.95. - The engine draws every frame right for its scale. The governor's step must not come too early, as [the implementation notes](implementation-notes.md#render-scale) describe. With that, 16 of 16 runs keep the whole canvas, and the test fixes the scale too.
- The shared memory test fails in CI the same way with the frame-rate checks, single-threaded and with low latency, at a median frame interval of 50 ms. On the busy Mac, with the page's thread slowed 4 times and 16 copies of the single-threaded test at once, 2 of 16 fail. Their medians are 58 and 75 ms, with 10 frames. With the switch, three rounds of 16 pass 48 of 48. In those rounds, 4 page loads have medians from 42 to 50 ms, which the frame-rate checks fail. Alone, the test passes 20 of 20.
- Without a pause, the pointer event allocation test (`tests/image/object-events.spec.ts`) fails about 1 run in 6 on SwiftShader, alone too. Each failure finds 0.0144 bytes per iteration at one place, which changes between runs: `fill` in `frame-cameras.ts`, or the core glue's `visibleEntries`.

So the engine's frames run between the loop's runs, and about 3 of them come around each sample. Chrome's sampling profile scales each sample by its chance to be sampled. At the check's interval of 64 bytes, a number object of 12 bytes counts as 72 bytes. Each failure is two such samples in one frame. The other two never do inside five minutes, and the engine's loading overlay stays at "Starting the sketch". This is a property of running several pages that draw at once on one software GPU. It is not a fault in any page ([D-186](decisions/D-186-showcase-page-never-reaches-its-controls.md)). It is why a test can fail in a busy shard and pass alone. It is also why a shard's worker count is part of what its tests can ask for.

A page posts its controls while its sketch builds the scene, which is before the engine's first frame, and on a software GPU that frame comes much later. Run here, the spec's own first read fails with E1414, "the frame's pipelines were still building after 30 s", in three runs of three. It runs alone (`@alone`), for two reasons. Its pictures need the engine to draw frames, and on CI's runner a heavy test beside it starves this page's frames, which is the fault D-186 measures. And its budget cannot sit in a shard: a shard's 25-minute limit covers its tests taking twice as long as the median, and this test's failure is exactly a slow machine. [D-185](decisions/D-185-software-gpu-loses-the-sky.md) holds the correction of what the first reading of these switches meant, and the empty canvas it mistook for a lost sky.
- The showcase controls test's check that a part comes back must not measure the machine's speed. The engine restores the look, and the reader gives fresh frames. On the Mac's software renderer the engine draws 16 to 23 frames a second. The frame that comes back sits 0.6 to 1.0 of 255 from a frame of the settled scene, against the scene's own change of 0.5 to 0.8 between two frames read a second apart. The sky's light is drawn into the environment map a stage a frame. So after the mood picks, the look keeps settling for about ten seconds on the software renderer, and longer on CI's machine. The test's `settle` accepts two frames a quarter of a second apart that differ by less than 0.5, and the settling look changes by less than that in a frame. The return then reads a mean of 5.288 of 255, where the check asks for less than 1.5 (CI run 38951143101). **A check that a part comes back must read both looks in the same few seconds.** The test reads the look with the part off as it makes the pick that turns the part on. It asks that the part coming back moves the canvas from that look by at least half of what turning it off moved it from the look with the part on. Neither the settling nor the scene's own motion can decide that, and a part that does not come back leaves the canvas at the look with the part off, which the check refuses. - Because the round at which the start-up ends follows the machine, the test does not assume a warm-up of ten rounds. The sketch checkpoints after every round, 200 in all. The test takes the first round whose figure equals the last round's, and requires it within the first 150 rounds. It requires that figure and the mesh and texture bytes to hold for every round from there to the end. A leak that keeps growing never reaches the last figure before the end, so the test fails. A one-time start-up allocation is warm-up, and the steady window still spans at least 50 rounds.
