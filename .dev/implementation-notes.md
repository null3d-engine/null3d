# Implementation notes

This guide holds lessons from building the engine: habits that keep the hot paths fast, and the browser faults that shaped the code. [AGENTS.md](../AGENTS.md) holds the hard rules that these notes serve.

## Hot paths without allocation

The engine's hot paths stay allocation-free with these habits (hard rule 1):

- Read typed arrays by index rather than by destructuring.
- Reuse WebGPU descriptors (`RenderPassSetup` and `submitOne` in `packages/engine/src/gpu/webgpu/reusable.ts`).
- Hand WebGPU a fraction only in a property whose first value was not a number. Chrome reads a descriptor through its bindings. Each fraction that a property holds unboxed then becomes a new 12-byte number object at every call. A property that started as `null` holds its number as an object, and Chrome hands that object over. On a test page, one call that reads a color (`setBlendConstant`) allocates 36 bytes per call for a color with three fractions. That holds for a color made by a literal, written into a literal of numbers, or held in an array of numbers. It allocates nothing for the same color in properties that started as `null`, or in an array that started with `null`s. So the render pass setup makes each clear color once, with parts that start as `null`. It keeps up to four, and finds one by its parts in a `Float32Array`. Compare a fraction only with another typed array element. A comparison with a property that once held `null` boxes the fraction, three objects per pass. A pass that loads its target gives no clear color, so the browser reads none. A clear color made at each call costs a render pass that draws color about 48 bytes more than one that draws only depth. With the setup's colors, the WebGPU replay of S1 with ambient occlusion allocates 223 bytes per frame, against 508 with colors made at each call. S4's replay allocates 258 against 355, and S1's with bloom 521 against 1,323. `tests/image/pass-setup.spec.ts` checks the setup's color in a loop ([Benchmarks](benchmarks.md#allocation-and-profiling)).
- Pass typed arrays straight to WebGPU, as `setBindGroup` reads dynamic offsets from the draw list.
- Keep reused lists at a fixed length.
- Do not wrap browser promises in `async` functions, and use `Math.sqrt` rather than `Math.hypot`.
- Keep closures out of functions that run every frame, even in a branch that rarely runs. Until the browser optimizes such a function, it allocates the variables a closure captures on every call.
- Shrink a reused list with `pop`, never by setting its length to 0. In Chrome, a length of 0 frees the list's storage, and the next `push` allocates it again. The sketch's list of touches works this way.
- To forget the entries of a reused list, store `undefined` in each with a loop. Do not use `fill`: on a sparse array, such as a cache indexed by texture unit, Chrome's `fill` takes a slow path that allocates. The WebGL2 backend forgets its cached bindings after each stage of a sky map. With `fill(undefined)` that allocates 390 bytes per frame in `bench:allocation --sky-environment`, and with a loop nothing ([D-118](decisions/D-118-sky-environment.md#data)).
- Build no list in a function that runs for every pass. Even an empty array is an object the browser makes on each call. A pass's attachment list for `invalidateFramebuffer`, made in the WebGL2 backend's `endPass`, costs 57 to 96 bytes per frame in `bench:allocation --gpu webgl2`, against a budget of 4. So the backend keeps a constant list for every case and names the one the pass needs, and allocates nothing.
- Loop over a small array with an index in code that runs every frame, not with `for...of`. Until the browser optimizes the function, `for...of` makes an iterator at each loop. A `for...of` loop over the two targets whose texels the sky map's stage copies allocates 133 bytes per frame.
- Keep numbers that change every frame in typed arrays, not in an object's properties. Playwright's headless Chromium 153, which CI tests with, makes a new object for each fraction stored in a property, while Chrome 154 does not. Six such stores in the camera controls' update make 144 bytes of garbage a frame there, so the controls keep those numbers in one `Float64Array`.
- Pass fractions to a per-frame helper in a typed array, not as arguments. A call that the browser does not inline puts each fraction it passes in an object of its own. Whether the browser inlines a helper changes from scene to scene. A call to `RenderPassSetup.setColor` with a pass's clear color as four numbers is inlined in S1 but not in S4. So each of S4's four passes boxes the fog color's three fractions. The WebGPU replay therefore reads the color from the draw list's floats. S4's replay then allocates about 250 bytes per frame, against about 420 with four arguments. The refresh meter's method that sorts the samples is not inlined either. Passed each callback's interval in ms, it costs the drawing thread's frame callback 9 to 13 bytes per frame. So the meter's `tick` stores the interval itself.
- A large frame function can use up the browser's inlining budget. The small calls it makes then stop being inlined, even calls that the browser inlines elsewhere. Each fraction such a call passes becomes a 12-byte number object, and the heap profiler charges it to the caller, not to the engine. Made inline in the crowd's frame function, the crowd's joint calls cost 183 to 247 bytes per frame on both GPU paths. That is in `bench:allocation --animated 64`, against a budget of 4. With `--no-inline`, no engine function allocates, and all 1,417 bytes per frame sit at the crowd's call sites. So the crowd makes the joint calls in a small function that takes the animator and its index. The function reads the frame's fractions from a `Float64Array`, and the check passes on both paths. When the check blames code that you did not change, run it again with `--no-inline` to find the real call site.
- Call a browser method with the same kinds of argument every time. Say one call site passes a number in one frame and `undefined` in the next. The browser's optimized code for the call then throws itself away at the first `undefined`. It compiles the same code again a second or so later, and the cycle repeats while the page runs. When S4's replay binds some vertex buffers whole (size `undefined`) and others in part, the browser throws its replay code away every 1.5 seconds. Each new compile leaves about 10 KB of objects in whichever callback runs first, the wake-up timer or the GPU completion callback. So the replay calls `setVertexBuffer` and `setIndexBuffer` without the size in one branch and with it in another.
- A function that runs once per frame can stay on the browser's middle tier for minutes. That tier inlines only small calls. In S4, the benchmark's camera step does not reach the top tier in 45 seconds. A call from it to the camera's `lookAt` is not inlined, and its three fractions are boxed every frame. So the step computes the rotation with `quat.lookAt`, which reads arrays, and passes it to `setRotation`, which is as small as `setPosition`. Run Chrome with `--js-flags=--log-code --log-deopt --logfile=<file>` to see which tier each function reaches and which code the browser throws away.
- The pipelined sketch loop awaits its `Atomics.waitAsync` promise once per frame. The browser makes the wait's result and its promise, and the await adds its reaction, about 93 to 111 bytes per frame in S1. A loop that resumes from the promise's `then`, with no await, allocates more: 120 to 135 bytes. So the loop keeps its await, and `bench/allocation.ts` budgets it.
- Never pass an array to a core function that runs every frame. The generated glue copies a slice argument in through the core's general allocator. It copies a `&mut` slice back through two new typed arrays. Such a function writes its result into the engine's own memory instead, and TypeScript reads it through a view made once. `worldMatrix` works this way (`CoreMemory.readWorldMatrix`). Sketches call `getWorldPosition` in their frames, and the camera ring reads the active camera every frame ([D-31](decisions/D-31-frame-cameras.md)).
- Never pass a fraction to a core function either. The browser seldom inlines a call into the core, and where it does not, each fraction argument becomes a 12-byte number object. A setter writes its numbers into the core's call values, a block of 64-bit floats that `CoreMemory.callValues` views, and then calls the core with whole numbers only. The core reads the block before it does anything else. `post.set`, the environment and the background have blocks of their own for this. The other setters use the call values. They set light values and colors, the camera's lens, material values and custom uniforms, a line batch's width, the fog and the background color. Passed as fractions instead, two `setIntensity` calls a frame cost about 23 bytes per frame in `bench:allocation --hemisphere`, against a budget of 4, on both GPU paths. The unit test `core-arguments.test.ts` reads the core's exports and fails on any fraction parameter, except the calls that make content. The check `bench:allocation --setters` calls each per-frame setter in every frame, colors included, and `--hemisphere` the two hemisphere lights' intensities. Two places still box a number. A material's `set` and a line material's `set` read their numbers from the options object that the caller passes, and the browser boxes each such read where the call has seen objects of a few shapes, so `--setters` sets the two materials once, before the frame. And a step that calls a number setter runs in the sketch's frame code; where the browser does not inline the setter, the fraction that the step passes becomes an object, as it does for S1's camera step, which has a budget of its own. `SETTER_BUDGETS` in `bench/allocation.ts` budgets those two places for the two switches.
- Write an options object's numbers into the core's call values, and read them from the object once each. A material's `set` writes each number it reads into the call values, so no fraction reaches the core, and it makes no closure. It reads each number by its own name, inside a test that the object holds that name, as a point below says. A loop over names boxes every fraction. A trim for the start budget can put such a loop back while the doc comment still promises no allocation. So `bench:allocation --setters` calls a standard and a custom material's `set` in every frame ([Benchmarks](benchmarks.md#allocation-and-profiling)).
- Convert a color into an array that the caller keeps (`writeLinearColor`). The conversion reads each 8-bit sRGB level from a table, so it calls no function with a fraction and allocates nothing. Lights, materials, the fog, the background, post-processing and custom effects all convert this way, so a sketch can change any of their colors in every frame.
- Where the page draws, code that must change the DOM in step with the canvas runs in the frame loop's `presented` hook. A frame callback of its own can fail. Callbacks run in the order the page asked for them. So a loop that started inside another callback can run before the engine's draw in each browser frame, and trail the canvas by a frame. The labels work this way ([D-38](decisions/D-38-labels.md)).
- Reading a fraction from an options object that a game passes makes a 12-byte number object at each read, even in optimized code. One engine function sees objects of many shapes, one per call site of the game. Past four shapes, its read goes through the browser's generic property lookup. That lookup copies the fraction into a new number. With four or fewer, an option that some shapes lack still merges with `undefined`, so the read value is boxed. Node 24 runs the same engine as Chrome. A direct count in it found 97 to 162 bytes per round of plays, against 0 for the same loop without the reads. Freezing the object changes nothing about the read itself. So the animator reads a frozen options object or points object once, and keeps what it read in a `WeakMap`. Later plays copy the numbers into engine memory with one `Float32Array.set`. A frozen object cannot change, so the record stays true. Without the record, a play with a fade and a weight makes 3 such objects (36 bytes), and a blend switch 1 (12 bytes). That comes to 8.5 bytes per frame in `bench:allocation --animated 64`. An object that is not frozen is read at every play. Other calls that take options objects in a hot path need the same rule.
- Read an option that some shapes lack only inside a test that the object holds it: `if ('roughness' in values) { const value = values.roughness; ... }`. The read's place in the code then sees only the shapes that hold the name, and the browser loads the fraction without an object, up to four such shapes. A plain read by name boxes the fraction as soon as one of the shapes lacks the name, because the result merges with `undefined`. In Node 22, a million frames that set three options objects of three shapes made 64 garbage collections with plain reads by name, and 2, the same as no reads, with the test. With five shapes that hold the name, the read goes through the generic lookup and boxes again. A material's `set` reads its numbers this way. A loop over the names in an object (`for (const name in values)`) boxes each fraction even for one shape.
- Read each number of a settings object by its own name, never by a key from a list. A loop such as `group[keys[k]]` reads many names at one place in the code, so the browser reads them through its generic lookup, which copies each fraction into a new number object. That holds for one object shape too. A shared copy loop of this kind in `post.set` costs 11 to 14 bytes per frame when ambient occlusion's intensity changes every frame. The check `bench:allocation --ao` blames `setAo` for them, against a budget of 4, on both GPU paths. With `--no-inline` it puts them in the loop. So `post.set` reads each setting by name and stores it into the core's block, and its unit test refuses a read by key in that file.
- The allocation checks of the math helpers and the camera controls sample a loop in a test page (`tests/lib/allocations.ts`). Give such a loop fractions, as real input has: whole numbers never allocate, so they hide these faults.
- Keep every number a hot path computes inside the small-integer range. Chrome holds a whole number up to 2147483647 in the value itself and makes an object of every one past it, so a frame path that computes a large key allocates one object per call. A terrain quadtree key that packs a leaf's level, column and row into `level * 2 ** 30 + column * 2 ** 15 + row` passes that limit at level 2. The check `bench:allocation --terrain` then blames `key src/quadtree.ts` for 23.8 bytes per frame against a budget of 4 (S1 on WebGPU). So the key counts a leaf from its own level's base, `(4 ** n - 1) / 3`. That keeps every key of all 15 levels a terrain may take below the limit, and `quadtree.test.ts` fails on a key above it. The power `2 ** level` also makes an object at level 0, where `1 << level` does not, and `Math.hypot` allocates as the habit above says.
- A search with a callback that closes over a value makes one object at every call, and an add-on's frame path can reach such a search inside the engine. In an update of a mesh's vertices, a lookup of the attribute's spec with `ARRAYS.find((array) => array.name === name)` and of its typed array with `INTEGER_ARRAYS.find(([, n, p]) => n === type || p === type)` allocates at every call. The check `bench:allocation --terrain` blames them for 38.1 bytes per frame in `updateProblem scene/mesh-arrays.ts` and 8.5 in `arrayClass`, both against a budget of 4. So both read a map built once at module load. A table that a frame path searches by name needs one.
- A frame path that parks entries and takes them back several times should keep its list at its longest and hold a count, rather than pushing and popping. The terrain's block pool parks an evicted block's mesh and takes one back in the same selection. With pushes and pops there, `bench:allocation --terrain` blames `push (built-in)` for 6.8 bytes per frame against a budget of 4. With the list kept at its longest and a count, the place stays under its budget. The habit above still holds for a list that only grows and is emptied between frames: shrink it with `pop`, never with a length of 0.

## Allocation in Rust

- Rust tests that count allocations use `null3d_core::testing::CountingAllocator`, from the core crate's `testing` feature. It counts only the threads a test marks, so the test runner's own threads cannot reach the count.
- A marked thread counts only while the test that marked it holds the counter. `std::thread::scope` returns when each thread's closure ends. The thread can still free memory after that, as it exits. Such a free can make the next test count 1 call.
- A test may start and stop job workers more than once under one hold. It must then mark each worker with `CountingAllocator::track_while`, which stops counting the thread when its work returns. Each scoped thread first tells the scope it is done. It then frees 2 blocks: its share of the thread's result, and the boxed closure it ran. On a busy machine the scope returns first, and the test's next count sees those frees. In CI, cargo-nextest runs the test files side by side. There the light grid's "on the calling thread" case can count 3 such calls while the light grid allocates nothing. A call to `JoinHandle::join` waits for the whole exit, so a pool joined that way, as in the core tests' `Workers`, is safe either way.
- The frame recorder sizes a frame's upload arena for the most that any frame can copy for the scene as it stands. It keeps its layout tables and scratch space between rebuilds. Only the frames right after the scene grows allocate.
- Pipelined frames keep one arena per frame parity, so the allocation tests change the structure on both parities after warm-up.
- `no_alloc.rs` counts steady frames of each feature that the frame loop draws, on both builders. It covers decals turning, a weighted layer rising, particles, the exposure meter, the physical sky, the volumetric fog, bloom, depth of field and the probe grid. A scenario first checks that a warm-up frame draws the feature's own template. It then counts the steady frames' allocations. So a scenario that stops covering its feature fails, and so does one that lets an allocation in.
- A frame's draw list grows to at least twice its size when a command needs more room ([D-57](decisions/D-57-capacities.md)). Each parity keeps its list, so only the first frame of a larger size allocates. Never reserve a bound for a writer: growth covers every writer. Lists that must not allocate, such as the parallel recorder's, use `DrawList::with_limit` with the limit equal to their size.
- A frame that fails publishes an empty list. A failure after the frame recorded a command halts the builder until `reset_gpu`. Its state then claims GPU objects that the dropped commands would have made. So check what can fail, such as a cap, before the frame's first command, as the skinning layout does in its rebuild.
- A thread can run any number of a parallel loop's chunks, from none to all of them. The calling thread runs every chunk that no job worker claims, for example while the workers wake. Storage that one thread fills across chunks therefore needs room for the whole loop. Give each thread's list in the parallel draw-list recorder room for a whole recording. Tests reach this case with a job system whose workers never start.
- A core call that reads the staging words borrows them. `std::mem::take` hands their storage to the call, which frees it. The next `animationStaging` then allocates it again, so a call that runs on each blend switch, such as `animatorPlayBlend`, would allocate at every switch. Only calls that run once per asset, such as `createSkeleton` and `createClip`, take the words. A large asset's staging storage then does not stay.
- Take frame scratch from `ArenaPool`. A thread whose arena is full continues in the other arenas, so the pool holds a frame however its chunks fall. Size the pool with `ArenaPool::new`, from the frame's total and its largest allocation, which `FrameArena::bytes_for` counts.

## Uploads

- A frame's upload room is the sum of the terms in the builder's `upload_bound`. Every table that a frame copies needs a term, and the term must count the rows that the copy writes. The GPU-driven layout copies a row of the bucket table for each source and, in the layout that owns the tables, a row of the layer table, a place in the cell order and a texel of the ranges texture. Without the ranges texture's term, a scene of 124,000 sources asks for 1.49 MB less room than it copies. Its first frame then fails with E1501. So `Layout::upload_bound` counts every table. The unit test `the_room_a_layout_asks_for_covers_every_table_a_rebuild_copies` records a rebuild into an arena of exactly that room.
- A frame that runs out of upload room publishes no draw list at all. The render worker then replays nothing, so the canvas keeps its last whole frame. A scene that outgrows its room therefore freezes while it grows. It does not draw the new objects, and it does not lose parts of them either. On the signed-address page, such a scene records 541 words up to frame 54, then 0 words from frame 55 on. The draw list address stays put, and the picture stops changing.
- Uploads from 64 KiB to 4 MiB take the route that the render worker measures as faster on the device: `queue.writeBuffer` or the staging ring.
- In Chrome on a Mac the ring is 3 to 6 times faster in that range, as `writeBuffer` takes up to 0.8 ms per MB. In Safari `writeBuffer` wins at every size, because unmapping a staging buffer costs time in proportion to its size. Outside that range `writeBuffer` wins in every browser measured.
- Each frame lists the runs of changed rows, with room for 4,096 runs. A frame with more scene runs widens its last run to cover the rest, rows between runs included. Both world buffers hold the latest matrix of every row that draws, so those rows upload unchanged.
- A list that overflows instead makes the frame upload every row up to the highest slot ever used. The shadow tiles then forget every caster and draw again. Moving objects that take turns with still ones make one run each. So the Factory comparison passes the limit at about 2,100 moving cells, about 4,300 runs. With room for 200,000 parts and 21,399 shown, an overflow uploads all 300,000 rows, 14.4 MB. Widening the last run gives the busiest thread there 2.35 ms per frame on WebGPU, against 4.77 ms with the overflow. On WebGL2 it gives 2.64 against 4.42 ms.
- The scene's runs leave room for each instance batch's, so only batch runs past the room still overflow the list.
- Without the overflow, the shadow tiles check each moved caster against each tile of the frame's lights. Once every tile must draw, they stop checking and only remember where the remaining casters went. Without that stop, room for exactly 50,000 Factory parts, all moving, costs 1.7 ms more per frame than the fresh start of an overflow. With it, the frame takes the same time as that fresh start, 2.45 to 2.54 ms on WebGPU.
- Both GPU paths join scene runs that lie close together into one write. On WebGPU each write is a call of its own on the render thread. At 21,399 shown parts, joining gives the render thread 0.19 ms per frame against 0.41 ms, for 0.6 MB more upload.

## Download size

- The page and the sketch worker load the renderer and the GPU layer (`render/draw.ts`) with a dynamic import, only in the modes where they draw. A pipelined page then downloads the GPU layer once, in the render worker.
- In their other modules, import only types from the renderer and the GPU layer: a value import bundles the GPU layer into their files again.
- Code that loads on first use imports only types from the files that the start loads, too. A value import makes Rolldown move the imported module into a file that the start and the late code share. Three functions that the texture generators imported from `gpu/webgl2/programs.ts` would bring all of `generated/shaders.ts` with that module: 1.6 MB of shaders, the debug views' among them. So the backend hands the generator what it needs (`programHost`).
- The page and the sketch worker start that import while the core downloads, as "Start order" says. As the only early download, it slows the core's download and delays the first frame by 22 to 37 ms. The other downloads start early too, so the renderer is the last download to arrive unless it starts early.
- The page loads the sketch runner and the scene API (`sketch/runner.ts`) with a dynamic import, only in single-threaded mode, where it runs the sketch itself. Other page modules import only types from them.
- The page starts that import as soon as it knows the mode, while the core downloads, because it needs the runner right after the core. In `bun run bench:startup --switches threads=off`, the first frame comes at a median of 4,131 ms over 14 runs. With the runner in the page's file, it comes at 4,131 ms too. A start after the core's download gives 4,135 ms.
- In single-threaded mode the page imports the sketch module while the core downloads too. The module's top-level code runs when the module arrives. Hold mode imports it after the sketch runner has seeded the thread's random numbers, so that code draws the same numbers on every run.
- Keep `loadSketch` in `sketch/define-sketch.ts`, where the page imports it. That import keeps `defineSketch` in the page's file, which the sketch worker finds in the browser's cache. In a file of its own, `defineSketch` costs the sketch worker one more request before the sketch runs. On Slow 4G, that request adds a round trip of 562 ms.
- Each thread loads the error fixes (`errors/fixes.ts`) with a dynamic import at its first error, so no file of the start holds their text. Until the file arrives an error holds its code and detail, and the fix then completes its message. A failed start waits for the file before it rejects, through `errorFixesReady`. A worker's first synchronous errors reach its sketch before the file arrives; later errors carry the fix at once. A value import of the fixes in a module of the start puts their text back into that module's file.
- `errors/codes.ts` holds each code's docs text for the docs generator and the tests. Runtime code must not import it: a value import bundles every code's docs text into the engine's files.
- `quality/preset-docs.ts` holds the preset table's docs text in the same way. The compiler asks for an entry there for each setting in `quality/presets.ts`, and runtime code must not import it.
- The page loads the frame figures (`page/frame-stats.ts`) with a dynamic import at the first `measure()`, and in hold mode when it publishes the held figures. `threadRoles`, the one piece of that module that the start reads, lives in `shared/metrics.ts`. Other modules import only types from the frame figures. A measurement's window opens when `measure()` is called, before the import, so work that the caller starts right after the call is counted even when the import is cold. A window that opened after the import would miss such work. A page may ask its sketch to add an object right after `measure()`, and the sketch then builds the object's pipelines during the import.
- The page hands the key names (`shared/key-codes.ts`) to the sketch worker when it starts it. The sketch worker's file then holds no copy of the list.
- The input ring's record format is plain constants, not enums. The bundler writes a constant into the code as a number, while a TypeScript enum ships as an object that holds each member's name. A `const enum` ships the same object.
- In Rust that the WebAssembly files hold, write `max` and `min`, not `clamp`, when a bound is not a constant. Its check that the bounds are in order panics with a message that prints them. That pulls in the code that formats floats. In the raycasts of sprites, points and lines ([#382](https://github.com/null3d-engine/null3d/pull/382)), `f64::clamp` adds about 17 KB before Brotli. A `twiggy diff` of two builds with function names shows such a cost.
- A page builds only its GPU path's text. Each module packs WGSL and GLSL in tables of their own, and gives each source field a getter that builds the text the first time something reads it. `ShaderTemplates` sends the thread that draws the builds of the page's path only. The other path's text then stays in the module's tables, as JSON text that the page never parses. Heap snapshots of Battle at 1,000 units on WebGPU find 8.8 MiB of strings in the render worker. With both paths' text built, they find 34.1 MiB. Its whole heap is 10.5 MiB against 36.2. The sketch worker's strings are 10.0 MiB against 15.7.

## Quality presets

- One table in `quality/presets.ts` holds every setting with its value on each preset. A feature adds its setting there as planned, then marks it applied where it reads the value. An applied setting that a sketch can change is also a member of `QualitySettings`, and a unit test keeps the two lists equal. The docs generator writes the preset tables on `concepts/quality-presets` from the table and the chooser's constants.
- A setting whose value differs on WebGL2 has a `webgl2` row beside its `presets` row. Only the depth prepass has one ([D-43](decisions/D-43-webgl2-prepass.md#the-prepass-on-webgl2-at-every-preset)). The functions that read the table take the GPU path. Tests that compare a WebGL2 engine's settings with the table pass the path too.
- The docs generator and the device runner import the chooser and the table, and the tools' type check has no browser types. So `quality/presets.ts`, `quality/chooser.ts`, `quality/preset-docs.ts` and `shared/tier.ts` import no module that names a browser type, not even for types.
- The page chooses the preset: workers have no media queries and no screen. The memory maximum follows the device hints and the crash marker alone, which the page has at once. So the core's download and the shared memory never wait for the GPU probe.
- Hold mode and `?preset=` neither read nor write the crash marker, so a test that crashes can never lower the next test's preset.
- Hold mode reads no display preference. Its sketch sees `preferences.reducedMotion` as false and hears of no change, whatever the machine asks for. Passing the machine's motion setting on would let a held frame change with a machine setting. GitHub's macOS runners turn Reduce Motion on, so the glTF model demo's camera would not turn in CI's Safari ([image tests](image-tests.md#the-feature-demos)).
- `quality.set` takes the live settings only. A start-time setting changes with `quality.setPreset`. The core should take its new value in the first frame after the change, which waits for its pipelines. The sketch runner marks it where it takes the restart from `SketchQuality` in `frame()`.
- The preset check runs at the end of `SketchRunner.setup`, before the frame loop steps the sketch. It publishes setup frames, one after another, as a warm-up does. Its code (`sketch/preset-check.ts`) loads with a dynamic import after the first frame, and the runner keeps drawing while it arrives. The size report names its files apart from the downloads before the first frame.
- The page sends the `?fps=` rate to the sketch thread once, in the runner's setup. The governor and the preset check both read it there. A second copy in the check's own start field, beside the governor's, would let a change to one path leave the two disagreeing (M2-R6).
- The check reads the render and completion rings with `RingSums`, from the thread that runs the sketch. Only a preset that the engine chose, above Low, gets a check, so pages that name a preset never download its code.
- Tests that assert a preset-dependent value on a live engine fix the preset with `?preset=`, or compare the preset that the engine chose (`presetCheck.from`). The check of a busy machine can lower the preset of any scene.

## Render scale

- The render scale crosses into the core as whole thousandths, an argument of `recordFrame`. Whole numbers never become number objects, and the core turns them into sizes in pixels with integer math, the same on every device.
- The frame-budget governor (`quality/governor.ts`) moves the render scale, then the far cascades' interval and the shadow filter. It runs in the frame loop of the thread that records frames, before the sketch's update. It reads the render and completion rings with `RingSums`. The loop writes the frame's clock reading into its typed array, so it allocates nothing. Hold mode has no governor and draws at the highest scale with the shadow settings as set.
- Once per window the governor reads what casts shadows from the core (`shadowCasters`): the main directional light's cascades, and whether point or spot lights cast shadows. It also reads whether textures wait to upload. It takes no shadow step that would change nothing. A shadow step gives the core the new shadow settings and calls the sketch's change handlers.
- The governor's budget comes from the refresh rate that the thread that draws measures from its frame callbacks. When the sketch runs on that thread, a sketch frame longer than a refresh slows the callbacks. The measured rate then falls, and the budget grows. Then the governor sees no overload. The default modes keep the sketch on a thread of its own.
- Safari runs a drawing worker's callbacks from a timer, and the timer slows while the worker waits for the GPU. On the iPad the worker's meter reads 38 to 65 Hz, and 44 to 46 Hz under the hold's load. A budget from that meter grows to match the slow frames, and the render scale never drops.
- So once a worker's callbacks have matched no display's rate, the metrics hold the rate that the page measures. The page's callbacks follow the display. Under load, a worker's meter can still snap to a display rate, as it does at 48 Hz in Playwright's WebKit. So the switch to the page's rate lasts for the engine's life.
- Chrome's worker callbacks follow the display, so Chrome keeps the worker's own meter, which a busy page thread cannot slow. A page that draws on its own thread (`?render=main`) has no idle thread to measure the display. Safari's page callbacks there slow with the GPU too. On the Mac's 72 Hz display, the WebGL2 hold's callbacks come 26 to 36 ms apart, at no refresh, and the meter reads 34 Hz. With that meter the render scale never drops.
- So the page's thread measures the display from the interval after two callbacks in a row that drew nothing. The callback after a frame that the GPU held up comes part of a refresh later. Such intervals read 120 Hz on the 72 Hz display. The interval after a second quiet callback measures 13 to 15 ms.
- Callbacks never come faster than the display. So a measurement of all the callbacks that is faster than the display rate held raises it at once. Only the quiet intervals can lower it. The metrics hold that rate. A display that turns slower, such as a window moved to a slower screen, shows through the checks below.
- While all the callbacks come slower than 90% of the display rate, the thread draws nothing at two callbacks now and then. The stretch starts at 30. Each measurement that finds the display's rate unchanged doubles it, up to 240. A page that stays slower than the display then delays one frame every few seconds. A scene whose governor has run out of steps is such a page. The stretch starts at 30 again after a first measurement or a changed rate. It also does after a quiet interval of 125% of the display's period or more. So a display that turns slower shows within a few seconds. Until the quiet intervals have measured the display, the rate compared is at least 60 Hz. So callbacks slowed from the first frame do not pass for the display. A page that draws at 60 Hz or more never checks. Each check delays a frame by about two refreshes, and a measurement takes 8 checks.
- `?display-check=off` stops the checks, so a run can measure what they cost. The page's thread then measures the display only from callbacks that drew nothing on their own, such as those before the first frame.
- In single-threaded mode (`?threads=off`), the sketch's own time slows the page's callbacks too, in every browser. The same rule covers it: the governor's walk, which spins the sketch for two frame budgets, keeps 72 Hz as the refresh rate.
- Held to a 60 Hz display, Safari's timer calls the worker about 64 times a second. About every 16th frame then waits an extra callback, and comes 31 ms after the last. A quarter-second window holds one or two such gaps.
- In Playwright's WebKit, held to 60 frames per second with `?fps=60`, the windows measure 97% to 105% of the budget. Room tested window by window breaks every second or two, and the walk takes no step up in 60 s. The iPad takes 1 of its 4 steps up on WebGPU that way, and none on WebGL2.
- So the frames' room is their mean since the room started. Each window's GPU delay must stay within its limit. When the mean is over the line at the end of a wait, the stretch starts again. Long frames from long ago then never hold a later step up back.
- A step down judges the last second, as the benchmark reports count seconds. It needs a mean frame rate under 95% of the target, the share in `HELD_PERCENT` of `shared/stats.ts`. Every window of that second must also miss the room line, so a single stall takes no step. The governor and the reports read the same constant, so the governor cannot rest where the reports count a miss ([D-11](decisions/D-11-frames-in-flight.md#the-warm-ipads-gate-at-low-m1-k5)).
- The governor takes no step in the first 2 s of play (`GRACE_MS`). A gap of half a second between frames, as after a pause, or a window while textures wait to upload, starts its windows again. Such a restart never moves its first judgment earlier. So a stall within the grace, or within the wait after a step, leaves the rest of that time. A gap is a pause only when no frame was drawing through it: the busiest frame that finished in the gap must hold half of it (`HELD_FRAME_PERCENT`) or more, and the frame then counts as one of its length and fills up to the second that a step judges. A frame that the GPU still holds has no busy time, since a completion is recorded only when the GPU finishes the frame: a frame presented with no completion after it, or a frame the tracker gave up, was drawing through the whole gap. A resume of the page is a pause, whatever the rings hold. A page that draws a few frames a second is judged this way. A frame that a sketch on a thread of its own held is a pause, since the render scale does not lighten the sketch's own work. A step down is on trial: when its first judged second comes a tenth slower or more, or no second is judged within 4 s, the governor takes it back and closes that level for a wait that doubles with each failure. On a device whose reported names say that it draws on the CPU, the failed step below the whole render scale closes the render scale instead: the two-step upscale costs about what the smaller scene saves there, so the governor never repeats it ([D-237](decisions/D-237-governor-slow-frames.md)).
- A restart that judged from its own time would let a driver that compiles a program at its first draw cut the grace short. SwiftShader takes 0.53 to 0.83 s for the first draw of skinned meshes added 30 ms into play, after their pipelines are built. The restart comes 0.7 to 1.1 s after the first frame. Judged from there, the governor lowers the render scale to 0.95 at 1.75 to 2.4 s. The slow frames after the stall give that step, not the stall: SwiftShader on the busy Mac draws 34 to 42 frames a second. With the grace kept, the first step can come 3 s after the first frame, as without the stall. The late skinning image test checks this ([image tests](image-tests.md#tests-on-slow-machines)).
- Scene passes of a relative size set the viewport and the scissor after `BeginRenderPass`. A pass at the whole canvas records neither, so its draw list is the same as without a render scale.
- Those passes draw into the top-left corner of targets that keep the canvas's size. A new scale therefore makes no texture, view, bind group or pipeline, so a step costs nothing and allocates nothing. The live test counts the GPU objects over frames that each change the scale.
- The governor judges in whole numbers, milliseconds and microseconds in 32-bit integer arrays. It runs only a few times a second, so the browser may leave it unoptimized. There each fraction it computes becomes a number object. So does each number it reads from a `Float64Array`, even a whole one, and each whole number past 31 bits.
- A page must be able to run for weeks ([D-58](decisions/D-58-failure-handling.md)). Times kept in `Float64Array`s allow that, but in V8's interpreter each judgment then makes about 290 bytes of number objects. At 144 Hz that is 5.4 bytes per frame, enough for S4 on WebGL2 to fail the allocation check of the M1 gate (at 89a1d629). So the governor's clock counts whole ms from an origin. The frame loop moves the origin forward when the clock reaches about 6 days, so every time stays within 31 bits. A time from before the new origin takes the origin's place, which lies further back than any span that the rules compare. In the interpreter alone, 20,000 judgments and 200 steps allocate nothing.
- The governor's arrays of levels are sized for the widest range of the render scale and the budgets' steps. They also cover one step of each kind past the scale. Each such kind has a named count of its own, and the level count sums them. Two of the kinds' counts are the same `+ 1`, and folding them into one leaves the count one short. The deepest level would then share a slot with the level before it. No run shows that fault: `minRenderScale` cannot go below 0.25, so the scale's steps stop three short of the widest range.
- Under `?fps=`, the governor takes the held rate as its target. Against the display's rate, every frame held at 30 per second counts as over budget, and the scale falls for nothing.
- The final pass's four taps run in a loop that has no rounds at the whole canvas. A software GPU runs both sides of a branch for every group of pixels. With the upscale in a branch, each pixel pays for five tone mapped texels at the whole canvas. SwiftShader in CI then draws too few frames for the engine start tests.
- Below a scale of 1, the upscale takes the place of FXAA, because the scaling softens edges already. In the FXAA mode, FXAA runs at the whole canvas.
- The final pass takes the scene color's coverage as at most 1. Additive blending adds alpha with each surface, so over a covered pixel the coverage passes 1. The pass divides the color by the coverage before its encoding and multiplies it back after. Without the cap, additive light comes out brighter on targets with alpha: one surface of the overdraw view draws 87 for 63.
- The final pass filters by hand: four `textureLoad` reads, each tone mapped, then blended. A sampler would blend HDR color first, and a small share of a very bright texel turns its neighbors almost white. A WebGL2 program also cannot read one texture both with `textureLoad` and through a sampler.
- The 8-bit path resolves straight into the canvas only while the lowest scale is 1. Hold mode keeps that rule, so its images show the passes that play draws. Every path builds the final pass's pipeline with its first frame, so a change of range draws at once.
- WebGPU draws a corner into a target's first rows. The WebGL2 backend flips the viewport, and GL counts rows from the bottom, so it draws the corner into the last rows. An effect step that reads another target must place the corner on each path. Bloom's step blocks carry the corner's origin, and the final pass's bloom build adds it on WebGL2. Without the origin, bloom at a scale of 0.5 on WebGL2 reads outside the corners, and 89% of the pixels differ from WebGPU's.
- A full-screen step reads the texel under its own fragment at `position.xy` on both paths, since WebGL2 counts the fragment's rows and the target's rows from the bottom alike. Only a place on the image, which counts from the top, turns around on WebGL2 (`size.w - position.y`). A step that turns its own texel around too shows each object's motion, in the motion debug view, at the mirrored row. That view's WebGL2 cases in the motion vectors spec catch this.
- Bloom's levels have a fixed number of texels on the canvas's shorter side (`Size::ShortSide`), which the render scale leaves whole. Only its first step reads the scene's corner, so a new scale uploads its blocks again and makes no texture. The governor's step draws every level into a corner of its target, which the blocks place on each path too.
- Below a scale of 1, a fragment's position covers only the drawn corner. A scene shader that turns the position into a place on the view, such as a light grid tile, divides it by the render size. The target's size is wrong there. The frame graph knows the render size after its `prepare`. A place on the image that a shader reads from a target keeping the canvas's size, such as the copy behind `sceneDepth(uv)`, lands at the render size's texel within that target: the target's own size would carry the place past the drawn corner, where the image holds nothing.

## The drawing buffer's size

- A canvas, and every render target of the canvas's size, must fit the GPU path's largest texture. Core WebGPU's default limit on a texture's width and height (`maxTextureDimension2D`) is 8,192 pixels, and compatibility mode's is 4,096. The engine asks the device for no higher limit, so each WebGPU device has exactly its feature level's default. WebGL2 also draws MSAA targets into renderbuffers and sets a viewport. Its limit is the smallest of `MAX_TEXTURE_SIZE`, `MAX_RENDERBUFFER_SIZE` and both of `MAX_VIEWPORT_DIMS`. WebGL2 promises at least 2,048 for the first two, and the engine counts a value the probe lacks as 2,048.
- The page fixes the limit at the start (`maxCanvasSize` in `page/limits.ts`), and the canvas watcher keeps the buffer within it. A larger canvas draws at a lower pixel ratio. The page writes that ratio with the size, so the sketch's pointer positions still match the buffer. `engine.capabilities.maxCanvasSize` reports the limit, and `engine.viewport.pixelRatio` the lower ratio.
- The two WebGPU feature levels need their own limits. With core's 8,192 in compatibility mode, a canvas wider than 4,096 device pixels asks for targets past the device's limit. A full-screen canvas on a 5K display is that wide. Chrome on the Mac shows it with `?gpu=compat`. A canvas of 20,000 by 8 CSS pixels at a pixel ratio of 2 gets a buffer 8,192 pixels wide. The resize browser test checks each path against the limit that the browser gives a device requested as the engine requests it.
- Rejected: asking core WebGPU for the adapter's higher limit, often 16,384. Targets at that size take four times the memory, and a canvas wider than 8,192 device pixels is rare. The default limit also makes every device of a path draw a large canvas the same way. Rejected too: clamping where the thread that draws makes its targets. The sketch would then read a pixel ratio that the buffer does not have, and pointer positions would drift.
- three.js sets the buffer to the CSS size times the pixel ratio and checks no limit. WebGL may then make a smaller buffer than asked, which the WebGL specification allows, and WebGPU refuses a canvas texture past its limit.

## Start order

The page starts every download that the start needs while the core downloads. On Slow 4G each download that waits for the core adds a round trip of at least 562 ms.

- The core's download starts before the page's own scripts run. The Vite plugin adds an early script (`page/early-core.ts`) to each built page whose scripts load the core. It is the first tag in the page's head. The script imports nothing, so it runs as soon as its 0.2 KB arrive, in the round trip that brings the page's scripts. The page's scripts must all arrive (24 KB) and run before `createEngine` can start anything. The early script picks the build as `createEngine` does, from isolation, shared memory and `?threads=off`. It fetches that build's core and leaves the response in a global slot. `loadCore` takes it once when the address matches, and compiles it as it streams in. A failed or wrong download falls back to the loader's own fetch.
- The early script cannot be inline: a strict Content-Security-Policy blocks inline scripts. A `<link rel="preload">` in the HTML would start one round trip sooner. But the HTML cannot know the build, and a wrong guess downloads 267 KB more. The early script holds the response itself instead of filling the HTTP cache, because a browser may not join a second request to one still downloading. Safari would then download the core twice.
- On the Mac on Slow 4G, the early script sends the core's request at 1.14 s after navigation, against 1.32 s without it. Every thread mode's first frame comes 0.19 to 0.20 s sooner. The rest of the start is the link's speed: from the core's first byte to its last, the link carries every start file at once. On the Galaxy S24+ the page's scripts take about 0.19 s longer to run than on the Mac. There the early script saves about 0.3 s ([releases](releases.md#t-28-the-cores-download)).
- The dev server's pages have no early script. Each module is a file of its own there, so the start has other waits.

- With worker threads the page starts the sketch worker, the render worker and the job workers before it probes the GPU paths. Each worker imports the core's loader as soon as it runs (`startWorker` in `workers/protocol.ts`). It then waits for its start message, which carries the core.
- The page fetches the sketch module into the HTTP cache (`prefetch` in `page/engine.ts`). The sketch worker imports it only after it has started the core, so the module's code runs no earlier than it would without the fetch. When the host serves build files as immutable, as the startup server does, the worker's import makes no request.
- In low-latency mode the page sends the sketch worker `load-renderer` as soon as it starts it, so the worker loads the renderer at once.
- Right after the GPU probe, the page works out the core device, whose fixed shader bits pick the device's shader file. It tells the thread that draws to start that file's download, so the file downloads with the core. A worker gets `load-shaders`, and the page calls `preloadDeviceFiles`. The same call starts the downloads of the GPU path's renderers and of the code that both paths share ([D-14](decisions/D-14-js-budget.md#one-gpu-paths-renderers-for-each-page)). The renderer's own imports later get the same modules. A file that waited for the core would cost each cold start one round trip more. On the MacBook Pro on Slow 4G that is about 0.57 s in every thread mode ([D-13](decisions/D-13-shader-variants.md#the-download-after-the-core-t-28)).
- Where the page draws, it imports the renderer while the core downloads. In single-threaded mode it imports the core's loader then too. Each of the two is the last download to arrive when only the other starts early.
- The page starts the render worker before the probe says whether a worker can draw. When one cannot, the page stops the render worker and draws itself.
- The probe worker's time limit starts when its script runs, not when the page asks for it. It covers the GPU checks, which can hang. A slow download must not make a device that can draw in a worker draw on the page. The script shares the link with the core, and the dev server compiles a sketch's WGSL before it answers other requests.
- The worker posts that it has loaded before its checks, and the page's 5 seconds start then. The browser reports a download that fails, so the wait for the script needs no limit of its own. Counted from the page's request, the 5 seconds fail the first two image tests of a CI shard on a cold dev server. Two sketches with custom materials compile their WGSL at once, the probe's script comes late, and the engine draws on the page.
- A probe worker that gives no answer within its 5 seconds gets a second one, with 10 seconds. The checks take milliseconds, and a page that gives up draws on its own thread for the whole session. When the page draws, `engine.mode.renderFallback` names why, and a development build warns once ([D-96](decisions/D-96-render-worker-fallback.md)).
- The engine starts of a page share one probe answer. A start that begins while a probe runs waits for that probe, and later starts take its answer. Firefox makes a new WebGL2 context wait for the WebGL work that other contexts have queued, such as a shader link. On a software renderer one link takes seconds. So a start's own probe can wait past both limits while another engine on the page compiles its shaders. On a canvas that a worker already holds, such a start fails with E1301, as it cannot draw on the page. A failed probe is not kept, and a lost GPU drops the kept answer, so the next start probes again ([D-96](decisions/D-96-render-worker-fallback.md#what-delays-a-probe-in-firefox)).
- A start that fails before the workers have the core stops them at once, because none waits in the job system yet. After that, a stop waits until each job worker leaves the job system. So the page sends the job workers the core before anything else that can fail, such as the canvas's transfer.
- The core arrives last on Slow 4G. Its download shares the link with the workers' scripts. In the pipelined mode it is ready about 300 ms later than a core that downloads alone, and the engine about 10 ms after it. In low-latency mode the engine is ready about 270 ms after the core. There the sketch worker asks for the renderer only once its own script has arrived.

`bun run bench:startup --modes all --loads cold,warm --network slow-4g,full` in Chrome 154 on a MacBook Pro measures the two start orders. The two ran in turns while other work loaded the machine. The table gives the first frame of a cold load on Slow 4G, in ms. Each value is a median of 15 loads of a start after the core, or 10 of a start with the core.

| Thread mode | Start after the core | Start with the core |
| --- | --- | --- |
| Pipelined | 4,183 | 2,674 |
| Low latency | 4,169 | 2,752 |
| Single-threaded, with the sketch module early | 3,166 | 2,607 |
| Drawing on the main thread | 4,298 | 2,661 |

Warm loads and loads at full speed stay within the spread between runs. Both columns of the single-threaded row download the sketch module with the core. Without that, the first frame of a start after the core comes at 3,580 ms. In single-threaded mode, starting only the renderer early gives 3,194 ms, because the core's loader is then last. Starting both gives 2,624 ms.

- A software GPU can leave a probe worker quiet past both limits. Every run of the showcase page on a Mac's software GPU carries the fallback warning: no probe worker answers within its 5 seconds, then 10. Yet the same page reaches its controls in four seconds in some runs and never in others. Two of five pages drawing at once never do. So the checks' milliseconds are a quiet machine's figure. A worker quiet past its limit can be a slow one, and not a stalled one. A page that gives up on the worker may still start. Where it then does not start, the cause lies elsewhere ([D-186](decisions/D-186-showcase-page-never-reaches-its-controls.md)).


## A sketch module that does not load

- `loadSketch` imports a sketch module that did not load once more, after 500 ms. The console and the thread's start trail note the second import. So it shows in test results and in user reports. The load fails with E1410 only when the second import fails too. Its message names the first failure, in the words of a single failed import. A block by the page's policy (E1422) fails at once, since a second import cannot pass it.
- The cause: Safari can fail one import of a sound module from a sound server with E1410 ("Importing a module script failed"). Unpacked, the custom-surface image page's four custom materials make a sketch module of 16.2 MB on the dev server. In 132 Safari CI jobs, 58 of which ran the page, one import of it failed after the sketch worker had waited 6.3 s. The next thread mode of the same page passed seconds later, and so did the rerun of the job. The dev server answers 24 of 24 cold double requests for the file in full, with no errors. So the fault is a one-off failure of the import in Safari, not a fault of the server or the sketch.
- Users can meet the same fault. Unpacked, a production sketch with custom materials is as large. The build puts the same compiled shader builds into the sketch file, about 4 MB per material. And the page's download of the module into the cache runs while the worker imports it. Without the retry, a dropped link, or Safari under memory pressure, fails the start.
- Browsers differ when a page imports a module again after a failed import. Measured with Playwright, on the page and in a module worker:

| Failure of the first import | Chromium 153 | Firefox 155 | WebKit 26.6 |
| --- | --- | --- | --- |
| HTTP 500 | fails again at once, with no request and a new error | downloads it again | downloads it again |
| Connection reset | fails again at once, with no request and a new error | the browser retries the request itself, so the first import loads | the browser retries the request itself, so the first import loads |
| The module's code threw, or did not parse | rethrows the same error object, with no request | the same | the same |
| Any of these, imported again with a query | downloads and runs it | downloads and runs it | downloads and runs it |

- The HTML standard says not to keep a failed download in the module map (whatwg/html#10327). WebKit and Chromium have implemented it, and Firefox has a bug open for it. The Chromium build that Playwright ships keeps the failure.
- So the second import goes to the same address first. Firefox and Safari download the module again there. A rethrow of the same error object means that the module's own code failed. Every browser keeps such a module, so the load fails with E1410 and asks for nothing more. Any other second failure is Chrome's kept download. The loader then imports the module at its address plus the query `null3d-retry=1`. A module that fails both real downloads in Firefox or Safari is therefore asked for a third time.
- The loader itself was checked the same way, on the page and in a module worker, in all three browsers. A sketch whose first answer was an HTTP 500 loaded in each, Chromium through the query. A reset connection loaded in each too. A sketch whose code threw gave E1410 after one request. A missing sketch gave E1410 after 2 requests in Chromium and 3 in Firefox and WebKit. Each failure added about 600 ms: the 500 ms wait and the 100 ms wait for a policy report.
- The query is safe for bundlers: the loader adds it at run time, after the build. A static server and Vite's dev server ignore a query they do not know. The query loads a new copy of the module, but the first copy never ran. The modules that it imports keep their own addresses. Only http and https addresses take the query: a `blob:` address with a query names no file.
- What the retry cannot fix: Chrome keeps a failed import of a module that the sketch imports. The query changes only the sketch's own address.
- Rejected: rerunning a page that failed with E1410 in the test runner. It hides the same fault from users. It also hides real E1410 failures, such as a wrong address. Asking the dev server for every custom sketch before the browsers start was rejected too. It removes only the test server's compile wait, and the server's answer is already good. Making custom materials smaller, which would make the module small, is a design change of its own.
- The module is small. The plugin keeps each distinct block of shader text and each distinct source once per module. The module builds the full text again when it runs. The custom-surface sketch is 1.05 MB on the dev server, against 26.5 MB unpacked. The same packing applies to production builds. [Image tests](image-tests.md#ci) gives the failures behind it, the sizes and the load times.
- A production build wraps each dynamic import in Vite's preload helper, which reads `document` to add link tags before the import. The sketch module is emitted as a page chunk but imported by the sketch worker. So a dynamic import in it, or in a chunk it shares with the worker, throws "document is not defined" there. The splats add-on's feature draw fails this way in a production benchmark page. The same page works on the dev server, which has no preload helper. So the plugin empties the preload lists (`__vite__mapDeps([...])` becomes `[]`) in every chunk that a worker imports, and `worker-preload.test.ts` checks it. The page's own chunks keep their preloads.
- A task's module address names a module that a worker imports, so the plugin emits that module as a chunk of the build. A TypeScript task module would otherwise reach the worker as raw source, which a browser cannot parse. Every selection of the splats add-on would then fail in a production page. An example with a `.js` module hides the fault. Built output under `dist/`, such as the engine's core, ships as it is.

## Textures on both GPU paths

- WebGL2 keeps GL's row order in everything a render pass draws: row 0 is the bottom row, and on WebGPU it is the top row. Uploaded and written texels keep their order on both paths.
- Draw lists give viewport and scissor rectangles from the top-left corner. The WebGL2 backend flips them, so each covers the same part of the image on both paths.
- A shader that samples a target that a pass drew flips its v coordinate in its WebGL2 variant. The texture test shader (`test_textures.wgsl`) shows the pattern, and so does the shadow map lookup (`null3d::shadows`).
- Materials sample a texture with v = 0 at its first row, which holds the bottom of an image, as three.js's render targets hold it on WebGL. So the texture of a scene pass, which materials sample like any map, must hold its bottom row first on both paths. WebGL2 draws it so. On WebGPU a copy pass turns the view's image over into the texture ([D-104](decisions/D-104-scene-passes.md)).
- On WebGPU, a view's bundle sets the map group of every bucket, also of buckets with no instance in the view. The backend replays bundles as render pass commands, so each group joins the render pass's usage scope, and a group that binds a texture which the pass draws into fails validation whether or not a draw reads it. So a view leaves out the buckets whose maps bind a pass's texture that it does not read, its own included. WebGL2 binds a map group only for draws with instances, but a draw there that samples its own target is a feedback loop, so it leaves the same draws out. The mock backend rejects such a group at `SetBindGroup` and at `ExecuteBundles`.
- GLSL ES 3.00 has no binding numbers. So the WebGL2 backend gives each WGSL binding a slot. A slot is a uniform block binding point, a sampler's place, or the place where a bind group leaves a texture. Each bind group starts at a slot of its own (`slotOf` in `gpu/webgl2/programs.ts`). The per-frame group has fourteen slots: the environment's cube map and its sampler take the last two, 12 and 13. Group 1 has three. Group 2 has eight: the instance textures, then the two textures of skinned meshes and the two of morphed meshes. Group 3 has the last sixteen: the eight map textures, then their samplers. The standard material's shared map units use the first six of each. A unit test checks every GLSL shader's bindings against the slots.
- Slots are not texture units. Each program numbers the textures it reads from unit 0, at its first use (`prepareProgram`). A texture that both stages read takes one unit. Setting a bind group only records each slot's texture and sampler. Before a draw, after a change of program, bind group or borrowed unit, the backend binds each of the program's units. Each unit gets its slot's texture and sampler. Slots used as units would run out with eight map slots and the environment map: the maps' textures would reach unit 32. WebGL2 guarantees 32 units, and uploads keep the last one. With units per program, adding bindings to a group costs a program only the textures it reads.
- WebGL2 guarantees only 16 texture units to each shader stage. A unit test counts every GLSL stage's textures, fails above 12, and prints the largest. So each stage keeps 4 units free for later features. Without sharing, the standard material's fragment stage with maps, an alpha mask and shadows would read all 16. It would read the material table, the split-sum table and the environment map. It would also read the two shadow maps, the light grid and list, ambient occlusion and the eight maps. [D-89](decisions/D-89-webgl2-texture-units.md) brings it to 12 on WebGL2, in three ways:
  - The maps share six units. Maps whose textures share an array and a sampler share a unit (`TextureStore::shared_map_group`). The row's value of each map holds its unit times 256 plus its layer (`MaterialTable::set_map_units`). The WebGL2 shader picks the unit with a switch. On WebGPU each map samples its own texture directly, with no switch. A switch on the map's slot makes textured draws many times slower in Chrome on Apple GPUs with MSAA ("Browser faults"). A material whose maps need more than six units draws without the ones that come last in `MapSlot::SHARING_ORDER`. Packing by format alone would fail for compressed maps, which each have an array of their own. Group 3 keeps its sixteen slots: the units take the first six textures and the first six samplers.
  - The light grid's words and the light records share one `RGBA32_UINT` data texture. The records fill the first 1,280 columns, five to a light, and the words the next 512, four to a texel. The shader turns the records' bits into floats.
  - The split-sum table fills the 16 columns after each row's texels in the material table's texture. That texture needs 16 rows, so the WebGL2 builder keeps room for 8 materials or more.

  New per-pixel inputs of the standard material take a texture array layer, an atlas part or a place in a shared texture. The [technique review](technique-review.md#webgl2-texture-units) gives the rules. A new map slot takes a shared unit. The unit test fails when a stage passes 12.
- WebGPU counts a pipeline's resources per shader stage over every entry of its groups' layouts, whether or not the shader reads them. The frame group gives the fragment stage 8 textures and the maps' group 8 more, so a standard material with maps reads all 16 of WebGPU's default. The decal templates bind the scene's depth as well, so they bind a frame group of their own (`layout::DECAL_FRAME`), which leaves out the light probe grids' texture. No decal build reads that grid. A decal with maps reads exactly 16 textures per stage, WebGPU's default, so the next texture a decal wants needs a layout change. It keeps the copy of the opaque color, because the reflections' lit code reads that copy in every lit build. With the probe grid's binding, textured decals would read 17, and their pipelines would fail on WebGPU while the WebGL2 path drew them. A unit test (`gpu/webgpu/pipelines.test.ts`) sums each build's sampled textures, samplers and buffers per stage over its layouts. It covers every template with the layout bits that its shader lists in the manifest, custom materials and effects, and the compute pipelines, and it fails above WebGPU's default limits.
- Writes and uploads land when the GPU queue gets them. On WebGPU that is before the commands recorded since the last submit. A draw list therefore writes a resource before any command in the same submit that uses it. The mock backend rejects a write after such a use.
- A data texture's item must fill the whole texel that its shader reads, because the write takes each item's bytes from the upload. The distance bands' ranges texture holds one `RGBA32F` texel for each source, whose `.xy` the culling shader reads. A layout that writes two floats a source puts every second source's range in another's texel and reads past the block. The WebGPU paths then hide every object inside a band, while WebGL2, which reads the ranges on the host, draws them. The layout's unit test pins the width of the item.

## Cube, 3D and high dynamic range textures

The GPU layer has these texture kinds for environment maps, skies and color grading tables (M2-E1). Color grading tables (M2-F3, [D-33](decisions/D-33-color-grading.md)) use 3D textures in the scene code. The texture store keeps each table as a 3D texture of its own, with no bind group of the store's. The final pass binds it.

- `CreateTexture` names the kind as its binding view: 2D, a 2D array, a cube or a 3D texture. Compatibility mode and WebGL2 both fix the kind when the texture is made, so the draw list gives it then.
- A cube texture has 6 square layers, its faces, in WebGPU's order: +X, -X, +Y, -Y, +Z, -Z. WebGL2's face targets come in the same order, so the WebGL2 backend adds the layer to `TEXTURE_CUBE_MAP_POSITIVE_X`.
- A 3D texture keeps its depth in the layers word. The depth halves at each mip level, as the width and height do (`view::level_layers` in `drawlist.rs`). Writes and copies name a depth slice where they name a layer of the other kinds.
- On WebGL2, writes, image uploads, copies and render targets reach a cube face through calls in two dimensions, one call per face. Arrays and 3D textures take calls in three dimensions.
- Both paths store written texels with row 0 at t = 0 of each face. Both pick a face and its texel by the same rules. So a written cube reads the same way on both paths.
- WebGL2 stores what a render pass draws bottom row first. A pass that draws a whole cube face therefore turns its geometry upside down in its WebGL2 variant: the vertex shader negates clip y. The face then holds WebGPU's rows, and every shader reads a cube the same way on both paths. `vs_face` in `test_cubes.wgsl` shows it.
- The other choice was a flip in every shader that reads a cube. The flip depends on the face that a direction picks. It also depends on whether a pass drew the cube or writes filled it. So the flip stays on the side that draws. It holds only for a pass over the whole face, because the backend also flips viewports. A viewport over part of a face lands mirrored on WebGL2.
- Nothing draws into a 3D texture. WebGPU draws into a 3D slice only through a `depthSlice` attachment, which the GPU layer does not have. Color grading tables come from files, so writes fill them.
- WebGPU copies images into 2D textures only, which include cube faces. A 3D texture takes texel writes.
- WebGL2 promises at least 2,048 texels for a cube face and 256 for each side of a 3D texture. Devices may offer more, but the mock backend refuses larger ones (`CUBE_TEXTURE_SIZE` and `TEXTURE_3D_SIZE` in `caps.rs`). Color grading tables of 32 or 64 texels a side fit.
- The GPU makes mip levels for 2D arrays of 8-bit color only. Cubes and 3D textures get every level from writes, copies or draws. A prefiltered environment brings one level per roughness step. A cube of six plain images would need its levels made. That waits for the WebGL2 mip path fix of the Adreno 830 fault (`fix/adreno-webgl2`), so that one mip path serves every kind.
- The mock backend refuses a pass that reads any part of a texture that it draws into, another face or level included. WebGPU allows reads of other levels, but Adreno 830's WebGL2 refuses them (see "Browser faults").

### Formats by GPU path

The test page `tests/pages/replay-cube-3d.ts` checks each format on each path. It fills cubes, 3D textures and 2D arrays in each format, then reads them with nearest and linear filters at fractional mip levels. Its image test, `replay-cube-3d`, requires every path to draw one image.

| Format | Bytes per texel | WebGPU, core and compatibility mode | WebGL2 |
| --- | --- | --- | --- |
| `rgba16float` | 8 | Filters, draws, copies. Compatibility mode has no multisampling of it | `RGBA16F` filters. Drawing into it, and copying from it, need `EXT_color_buffer_float` or `EXT_color_buffer_half_float`, which the backend asks for |
| `rgb9e5ufloat` | 4 | Filters and copies. No device draws into it | `RGB9_E5` filters. WebGL2 cannot draw into it or copy it, because copies read through a framebuffer |

A WebGL2 context without `OES_texture_float_linear` reads black from a 32-bit float texture through a linear filter. On the Mac, a run that does not ask for the extension reads black. A run that asks reads blended texels.

### Cubes that the GPU makes

The engine makes the built-in room environment's cube on the GPU (M2-E2, [D-19](decisions/D-19-environment-maps.md#the-built-in-room-on-the-gpu)). Its generator runs in the thread that draws, at the draw list's `GenerateTexture` command.

- No path draws into `rgb9e5ufloat`, and WebGL2 draws into `rgba16float` only with an extension. So each draw writes its texels packed as `rgb9e5ufloat` into the four bytes of an `rgba8unorm` target. WebGPU copies the target into a buffer and the buffer into the cube's face. WebGL2 reads the target into a pixel pack buffer and unpacks the same buffer into the face, with `UNSIGNED_INT_5_9_9_9_REV`. Both copies stay on the GPU. On WebGL2 each step calls `finish()` between the pack and the unpack, since Firefox on the Mac fills the pack buffer late ("Browser faults").
- Each draw fills a whole level, its six faces side by side in the target, and the copies take each face's part. A draw of one face of a small level keeps few of the GPU's lanes busy, and each texel loops over thousands of reads. On the Mac, the faces side by side make the room twice as fast as draws of one face.
- The command makes the whole map in one submit, in the first frame after the generator arrives (D-66). It runs outside the upload budget and before the frame's passes. `assets.builtinEnvironment` resolves only once the generator has arrived. So the first frame that uses the room already has its light.
- Do not split the room's or a file's work over frames. On the cloud phones, steps of rows cost 4 to 9 times the whole map (prototype L1). A step of a small level lasts one texel's loop of thousands of reads, however few rows it holds.
- A sky map refreshes during play, so it runs in stages, one a frame, that the core records ([D-118](decisions/D-118-sky-environment.md)). Its steps stay few and short. The sky draws into every level of its chain at once, so no level waits for another. Its filter takes a quarter of a file's directions. Its finished levels wait in a buffer until the last stage copies them all into the map. On WebGL2 a stage unpacks a buffer that an earlier frame packed. It asks a fence whether the GPU has run the pack, and calls `finish()` only when it has not.
- A sky map's stage runs every frame while the sun moves. So it allocates only what the browser returns: one render pass encoder on WebGPU, one fence on WebGL2. It keeps its textures, buffers, bind groups and descriptors from its first stage. It reads the generators' code with `generatorCodeFor`, which makes no array.
- The generator builds its pipelines with `createRenderPipelineAsync`, or with `KHR_parallel_shader_compile` on WebGL2, before it counts as arrived. A WebGL2 program that it prepares outside a replay puts the program in use back, so the backend's state cache stays true.
- The shader writes each byte as (byte + 0.25) / 255. A GPU may round or truncate when it stores 8 bits, and the quarter step keeps the byte either way.
- The shader takes its texel from the fragment's place, not from texture coordinates. WebGPU's copy reads the target's top row first and GL's reads its bottom row first. Each of those rows holds the fragments of row 0, so the face's rows come out the same on both paths, with no flip.
- The WebGL2 generator binds its own program, sampler, textures, uniform buffer and framebuffer. The backend sets its fixed-function state first, through its cache, and forgets the cached bindings afterwards.
- Its constant tables are functions with `switch`, not constant arrays. A WGSL constant array becomes a GLSL array type with its size, which Arm's Mali GPUs reject ("Browser faults").

### Draw-list numbers held for M2

The opcode numbers that M2 tasks need are reserved (M2-E1), so lanes that work at once do not collide. The task that adds a command moves its number from `reserved` into `Op` in `drawlist.rs`.

- 43, `DISPATCH_INDIRECT`: workgroup counts from a buffer. Skinning on WebGPU (M2-C3) skins only the meshes that culling found visible. Two-phase occlusion culling (M2-I1) dispatches its second phase from the first phase's count.
- 50, `COPY_TEXTURE_TO_BUFFER`: GPU picking (M2-D6). It is in `Op`, as "Draw-list readback" says.
- 52, `DESTROY_PIPELINE`: `material.destroy()` (M2-J3) and shader hot reload (M2-J2) release pipelines. It is in `Op` too.
- 53, `READ_BUFFER`: GPU picking (M2-D6) reads the ids under the pointer back into engine memory a frame later. It is in `Op` too.
- Format code 19 is `RGB9E5_UFLOAT`, and view codes 2 and 3 are `CUBE` and `D3`.

## Texture uploads

- The texture store (`crates/null3d-render/src/textures.rs`) keeps every texture in a layer of a 2D array of its size, format and mip count. A frame's texture work comes before its passes. Arrays are made or grown first, then a submit follows when an array grew. Releases, uploads and mip levels come after it. A grown array's copies must land before the uploads, and WebGPU would run the uploads first within one submit.
- A capture replays the frame's list a second time. So a list never releases what it uses itself. The next frame's list releases images and outgrown array textures. A release of an image that the backend no longer holds does nothing. The store's tests replay every list twice.
- The engine core gives each image an id in the order the sketch thread sends them. The thread that draws counts the images it received in the control block (`Slot.ImagesArrived`), so every id up to the count arrived. One `MessagePort` carries them, so they arrive in order. The sketch thread holds them until the thread that draws says, through the port, that it receives ([browser faults](#browser-faults)). Where one thread runs the sketch and draws, the images go straight into its table.
- The image table lives outside the renderer, so a new GPU device uploads the images that the thread still holds. The store learns which were released from the frames that the thread took.
- Hold mode draws one frame, which records as after a GPU loss. The sketch thread waits for every image to arrive first, and that frame uploads them all, whatever the budget.
- Both backends draw each mip level of one layer with the mip shader (`mipmap.wgsl`), which samples the level before. On WebGPU the shader reads that level through a view of every layer, as compatibility mode binds whole arrays only. On WebGL2 the texture's base and highest levels are that level while the shader draws. The draw then reads no level that it writes.
- WebGL2 has two shorter ways to make mip levels, and neither works here. `generateMipmap` on a 2D array texture remakes the levels of every layer. Each upload would then cost the whole array. In Firefox on macOS, a blit from one level to the next averages the stored bytes of sRGB texels, not their linear values. The levels then come out too dark.
- An upload of a band of rows reads the image from a row inside it: `copyExternalImageToTexture` takes an origin, and WebGL2 applies `UNPACK_SKIP_PIXELS` and `UNPACK_SKIP_ROWS` to image bitmaps.
- The sketch thread reads the texture constants from the core's generated module, not the GPU layer's. A value import of the GPU layer's constants would put them in a file of their own, which the size report refuses.

## Switches in the page's address

- The engine reads its test switches, such as `?gpu=`, `?hold=` and `?bench`, only in development builds. A production build reads them only when its Vite plugin has `urlSwitches: true` (`URL_SWITCHES` in `shared/dev.ts`). A shipped game ignores them. Otherwise a link could start 255 job workers on a phone or freeze the game in hold mode. It could also put the engine on `window` for any script (review R3, R3-14).
- The repository's Vite configs turn the option on, because the production build tests and the benchmarks set the switches in the address. The `null3d` command defines the same constant for its production runs, so it works with a project's own config.
- Without the option, the plugin leaves the constant undefined, and the engine follows its development flag. A build that defines the constant itself, as the `null3d` command does, keeps its value.
- `?replay-delay=` makes the thread that draws busy-wait before it replays each frame's list, from 1 to 1,000 ms. The sketch thread then steps the next frame first. Engine tests use it to find memory that a step moves or frees while the list being replayed still points at it ([D-103](decisions/D-103-growing-object-tables.md#the-thread-that-draws)). The page's main thread writes it to a slot of the control block at the start, so it works on every thread that draws.
- `?jobs=` sets the most job workers, at most one for each logical core, and `?memory=` counts only from 256 to 4096 MiB, the range of the `memory` option. A value outside counts as no switch, as other bad switch values do.
- The development flag and this one live in one module. It holds constants only, so the bundler folds them into each file that reads them. The files that load on first use still share no module with the start's files (review R8, R8-11).

## Messages from a sketch to the page

- A sketch's `page.post` reaches the page as a message. The engine keeps a message that arrives before the page listens, and gives it to the first handler alone, then forgets it: a second handler registered later never sees it. So a page that reads two kinds of message, such as a demo's labels and a showcase scene's help, registers one handler that routes each type. With one handler for labels and another for the showcase help, the examples page would drop the help that a sketch posts at its start. The on-screen help would then never show.
- `engine.onSketchMessage` returns a function that removes the handler.

## Public type declarations

- The package build strips members marked `@internal` from the type declarations (`--stripInternal`). Users then do not see the engine's own methods, such as the label projection of `ctx.ui` (review R3, R3-13). The build fails if a declaration still holds an `@internal` tag.
- A class that only the engine makes marks its constructor `@internal`. Stripping it would leave the class constructible with no arguments, so the build writes `protected constructor();` in its place. Protected, not private, so that the engine's own subclasses still type check.
- The internal entry point that tests import (`src/internal.ts`) leaves the package. The tarball check fails if it returns (review R8, R8-10).

## Shaders in a packed add-on

- A package's WGSL is compiled while the package is built, not in the project that installs it. `tools/lib/packages.ts` compiles each `.wgsl` file in a package's `src/` and writes `lib/<file>.wgsl.js`, in the shape that the Vite plugin gives a project's own WGSL: the shader's records, with its text in tables that it reads on first use, and a module for each set of a custom material's builds, which a device loads when it first needs one ([D-54](decisions/D-54-addon-modules.md)).
- The compile runs through the plugin's compiler pool, on worker threads. The add-ons build at the same time, once the engine and the plugin have. A shader that does not compile stops the pack with its file, line and column. The raw file stays out of the tarball, and the pack check refuses it and requires the compiled module.

## Loading WebAssembly under a strict policy

A game may send a strict Content-Security-Policy, such as `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'`. The engine starts under it in every thread mode. The production build tests (`tests/image/content-security-policy.spec.ts`) and the fresh-project test (`tests/fresh-project.ts`) check that.

- The page reads the core's memory limits from the core itself (`readMemoryLimits` in `shared/wasm.ts`). It splits the core's download in two. The browser compiles one copy as it arrives, and the page reads the other only up to the import section, which holds the memory's limits. The page then makes the shared memory before the compile ends.
- The limits cannot be a file of their own. Vite turns any file under 4 KB, such as a 46-byte JSON file, into a `data:` address, and the page would fetch that address. A policy's `connect-src`, or its `default-src`, blocks such a fetch, so a threaded page would not start under a normal strict policy (review R8, R8-01). Reading the core also takes one request away from the start.
- The engine names every file that it loads by address in the standard form, `new URL('<file>', import.meta.url)`, with no Vite-only query such as `?no-inline` or `?url` ([D-54](decisions/D-54-addon-modules.md#bundlers)). Vite turns a file under its inline limit into a `data:` address, and `script-src 'self'` blocks an import of one. So the null3D plugin sets Vite's `build.assetsInlineLimit` to a function (`inlineLimit`). It never inlines a file of a null3D package, and keeps the project's own setting for every other file. A file belongs to a null3D package when the nearest `package.json` above it names a published package of the `@null3d` scope. So the rule also holds in this repository, whose root does not install the engine. The built-in room's background shader files are under Vite's 4 KB limit, and the production build of the test pages would otherwise inline them. The core's glue is about 45 KB, so a game that raised its inline limit above that would otherwise get it inlined.
- A compile that fails tells the reason apart. The loader compiles the smallest valid module. If that fails too, the page's policy blocks WebAssembly, and the error is E1418, which names `'wasm-unsafe-eval'`. Otherwise the error is E1406. The file is then damaged, or it is not WebAssembly, such as a web page that a host sends in its place. Each names the file by its role, not by its address, which can be a long `data:` address.
- A browser starts a dedicated worker only from a script on the page's own origin. A CDN with every header cannot change that. So a worker whose script has another origin starts from a `blob:` bootstrap ([Workers from another origin](#workers-from-another-origin)).
- A start that fails before the job workers have the core marks the engine as stopped before it stops them. Each job worker's start then fails with "the engine stopped". The page does not report that as a false E1405 for each job worker (review R8, R8-08).

## KTX2 textures

- `assets.loadTexture` finds a KTX2 file by its first 12 bytes, and imports the KTX2 loader (`scene/ktx2.ts`) only then. The file's reader (`scene/ktx2-file.ts`, which imports only the shared limits) reads its header and level index on the sketch thread, and refuses a file whose counts pass what a texture may hold. The loader picks the format from the device's capability flags, which the page sets from the probe's WebGPU features or WebGL2 extensions.
- The transcoder runs as a task of the on-demand loader, in a job worker ([The on-demand loader](#the-on-demand-loader)). The sketch thread compiles its module once per page, and sends it with the first task to each job worker that runs one. The task's module (`scene/ktx2-transcode.ts`) imports the transcoder's script, starts it with that module, and reads the file with the same reader before it does: the transcoder allocates the sizes the file's level index declares, inside a heap the worker keeps for its life ([D-184](decisions/D-184-ktx2-level-index-limits.md)).
- The engine ships its own build of the Basis Universal v2.50 transcoder, not the official one. The official build makes its JavaScript bindings with `new Function` (Emscripten's embind), so a Content-Security-Policy without `'unsafe-eval'` stops every KTX2 load with that build. That happens when the host sends its policy on the transcoder worker's script. From a CDN it always happens, because a `blob:` worker takes the page's policy. A strict-policy test that loads no KTX2 file does not see it.
- `bun tools/build-basis-transcoder.ts` makes the build. It downloads the Emscripten SDK 4.0.15 and the v2.50 sources into `target/basis-transcoder`, each checked against its SHA-256, and installs nothing outside that folder. It compiles the official build's sources with its definitions and flags (`webgl/transcoder/CMakeLists.txt`), and adds three link flags. The flag `-sDYNAMIC_EXECUTION=0` makes bindings without code from strings. The flags `-sEXPORT_ES6=1` and `-sENVIRONMENT=web,worker` make the script an ES module that a module worker imports, with no code for Node.
- The script then transcodes the three KTX2 test files with both builds, into every format that the engine asks for, at every mip level. It fails unless the bytes match. All 15 match. A unit test keeps the official build's output hashes and checks the shipped build against them. It also checks that the script holds no `new Function` or `eval`.
- Sizes: the script is 47,675 bytes (11,371 after Brotli), against the official build's 50,538 (12,137). The module is 1,060,612 bytes (361,016 after Brotli), against 1,060,846 (360,825). The script goes into the KTX2 task's file: 8.9 KB after Brotli. The size report holds that file to the 16 KB limit of first-use files.
- The script's module comes from the loader, which compiled it on the sketch thread while the file downloaded. So after the KTX2 loader, the first KTX2 file waits for the transcoder's module and for the task's file in the job worker. They download at the same time.
- The loader imports only modules that the first file of its thread holds whole. An import of another module, such as the error message helper or the core's loader, splits that file. Rolldown then moves the modules that the loader shares with it into a new file. Every page would then download it at its start. The size report fails on such a file, as its part has no name.
- A compressed texture has an array of its own, with exactly its layers. Compatibility mode copies no compressed texels, so such an array could never grow. Its GPU texture has no `RENDER_ATTACHMENT` and no `COPY_SRC` usage.
- The texels go into engine memory as data does, level after level, each level's layers in turn. The store uploads them in bands of rows of blocks under the frame's budget. A write names its box in texels, cut by the level's edge. WebGL2 takes that box, and WebGPU rounds it up to whole blocks.
- WebGPU makes compressed textures of whole blocks only, so a size that is not a multiple of 4 texels becomes RGBA8, on both paths alike.

## The on-demand loader

Code and WebAssembly that a page needs only on first use load one way, for the engine's own decoders and for add-ons alike ([D-54](decisions/D-54-addon-modules.md)). The loader (`shared/tasks.ts`) runs in the thread that runs the sketch.

- `compileOnce` downloads each WebAssembly file and compiles it with `WebAssembly.compileStreaming`, once per page. Later calls get the same module. A failed download or compile lets the next call try again.
- `runTask` sends a task to a job worker: the task's name, its input, and each compiled module that the worker has not had. A worker only instantiates a module, and keeps the instance for its next tasks. The engine's own tasks are imported by name in `workers/tasks.ts`. An add-on's task comes by the address of its module.
- The glTF worker parses files, and meshopt and Draco decode where the file is parsed. So the glTF worker asks the loader for the decoders that a file needs, in the same answer that lists the file's buffers. The loader compiles them with `compileOnce` and sends them with the buffers. The meshopt decoder is a file of its own for that (`vendor/meshopt/meshopt_decoder.wasm`). The npm package packs it into a string in its script, which the browser could only compile from bytes. The tool `bun tools/vendor-meshopt.ts` writes it again from the pinned package. A unit test checks that the two agree. The engine needs SIMD, so it ships only the SIMD build. Draco's decoder is Google's glTF build, kept unchanged in `vendor/draco` with its script. `bun tools/vendor-draco.ts` fetches it again from the pinned release and checks each file's SHA-256, and a unit test checks the copy against the same hashes ([D-112](decisions/D-112-draco-decoding.md)).
- A job worker blocks in the core's job loop and cannot read messages there. So the loader asks the core to call the worker (`callJobWorker`) before it posts each task. The core's loop returns once no frame chunk is left to claim and a call waits, and only then. The worker runs its tasks, takes each call off the count, and enters the loop again (`workers/job-worker.ts`). The call comes before the post, so the count always covers a task that is on its way.
- Decoder tasks never hold up a frame. A worker leaves the loop only between frame chunks, and the sketch thread runs every chunk that no job worker claims. With two or more job workers, the first never takes tasks, so one always serves the frames. On the Mac, S1 loads the KTX2 sample model's 19 textures round after round, 893 files in 12 s. It keeps 719 or 720 of 720 frames at 60 Hz, with 16 job workers and with 2. The busiest thread's CPU time per frame at the 99th percentile stays within 5.1 to 5.5 ms ([D-54](decisions/D-54-addon-modules.md#frames-come-first)).
- Where the engine has no job workers, as in the single-threaded build, the loader starts one task worker (`workers/task-worker.ts`) with its first task. It loads no core. The transcoder has no worker of its own.
- **A job worker that does not start takes no task.** The page starts the job workers as the thread that runs the sketch asks for them. That thread cannot know by itself which of them started. A job worker whose script or its core did not load never answers. A task sent to it by index then waits for good, and the page draws nothing at all. Firefox on Linux can fail the download of the core's module in one of two job workers, as in `image-ktx2-hdr-webgl2-pipelined`. Such a page publishes no result, and the runner ends it after its 30 s limit. The engine means a job worker that did not start to be survivable ([Threads and shared memory](#threads-and-shared-memory)). So the page tells that thread which job workers started, once each batch of them has settled. The loader waits for that word before its first task. It then sends tasks only to the workers that run. `JobTaskHost.running` in `shared/task-host.ts` holds them. `taskTakers` gives the rule that the first worker keeps the job loop while another runs. With no job worker left to take the tasks, the loader uses the task worker of the paragraph above. So the page draws on.

## Workers from another origin

When a page loads the engine's files from another origin, such as a CDN, each worker starts from a small module at a `blob:` address (`shared/worker-start.ts`). The thread that starts the worker makes it. A `blob:` address has the page's origin, and the module imports the worker's real script.

- Bundlers find a worker's script only in the form `new Worker(new URL('<file>', import.meta.url), options)`. So the engine keeps that form, and `spawnWorker` runs it while the thread's `Worker` is a stand-in that adds the bootstrap where the script's origin needs it. A local class with another name, or a parameter named `Worker`, would hide the call from webpack, which only reads the global name.
- The stand-in is a plain function that returns the browser's own `Worker`, not a subclass of it. A subclass's prototype stays for the page's life, and its prototype chain holds `Worker.prototype`. So DevTools' count of the objects with that prototype (`Runtime.queryObjects`), which the restart test uses, would find one worker after every engine had stopped.
- The thread that runs the sketch holds the job workers' task ports and a call into its core, for the on-demand loader. The engine's stop takes them away again, or the thread would keep the stopped engine's memory and workers alive. The loader also closes those ports and drops their handlers at the stop. A port with a handler can keep the loader, and through it the core's memory, until the browser sees that the job worker has gone.
- The module holds the messages that arrive before the worker's script has run, and hands them on after. The script sets its message handler as it runs, and the browser would drop a message that arrives before.
- A worker from a `blob:` address takes the page's policy, not its script's. So the page's `worker-src` needs `blob:`, and its `script-src` and `connect-src` need the CDN.
- Firefox checks the modules that a worker imports against `worker-src`, not `script-src`. Chrome and WebKit use `script-src`. So the sketch worker's import of a sketch on the CDN fails in Firefox unless `worker-src` names the CDN too. The sketch's loader then gives E1422 with the directive, from the worker's violation report.
- When the import fails, the module reports why. A policy violation in the worker names its directive. Otherwise it downloads the script again: a failed download means no CORS header or no network (E1423), and an HTTP error is E1406. When the page refuses the bootstrap itself, the page's own violation report names `worker-src`. Both become E1422 with the directive.
- `compileWasm` tells a blocked download of another origin by the policy's violation report (E1422 with `connect-src`), and calls any other failed download E1423. The report can arrive after the failed fetch, so it waits up to 100 ms for it.
- The CDN test (`tests/image/cdn.spec.ts`) serves the production build's HTML and its files from its own server, under two host names. Chrome treats a response that Playwright fulfills as coming from a public address. Such a page may not reach a loopback server, and the browser applies no real CORS rules to fulfilled responses either.

## Custom effects that read bloom

An effect's WGSL that calls `effectBloom` reads a level of bloom's chain, and the API names which
level with `bloomLevel`.

- The chain normally runs after the effects, from their output. While an effect reads it, the chain
  runs before the effects, from the scene color that the first effect reads, and the final pass
  still mixes the glow into the effects' output. The render graph orders the passes from that edge:
  the effect's pass reads the level's target, so the step that writes it runs first.
- The texture that the first step binds comes from the same choice that the passes declare, so the
  two cannot drift apart. A held frame draws once, before it draws the effects. A chain that bound
  their target would read its clear color and draw no glow
  ([D-71](decisions/D-71-custom-effects.md#effects-that-read-blooms-chain)).
- Each effect binds one level, at binding 4 of its group, because the levels are separate textures
  and an effect names the level it wants. A group of joined effects binds one color and one level,
  so the compiler refuses to join an effect that reads bloom: it draws in a pass of its own, as an
  effect with textures does. The shader build detects the call and sets `EFFECT_BLOOM`, which
  declares the binding.
- The effect's block holds the scale and the offset from the image's place to that level's texture.
  A level whose chain is smaller than its target, as the governor's halving makes it, occupies a
  corner, and WebGL2 counts the rows from the bottom, so the map turns the row scale negative. The
  engine computes it from the same corner map that bloom's steps use.
- A level that the frame's chain does not draw, because the weights end before it, binds a one-texel
  texture instead, so the effect reads black rather than a stale level.
- The level is drawn only while bloom is on. A sketch that reads a level with bloom off reads black,
  which keeps the cost of the chain with the sketches that ask for it.

## The shader compiler

The shader compiler is the shader crate built as a WebAssembly module. Build tools such as the Vite plugin load it in Node or Bun, so pages never download a shader translator. The crate `null3d-shaders-wasm` builds it, and the wrapper in `packages/vite-plugin/src/shader-compiler.ts` loads it and gives its API.

- The module imports nothing. It takes and gives JSON through its memory, so it needs no wasm-bindgen glue, and the wrapper can make a new instance at any time.
- It holds the engine's library modules. Its build script lists the files in `wgsl/lib`, so a new library module needs no other change.
- A panic stops a call with a trap. The panic hook writes a response first. The wrapper then drops the instance, because a trap can leave its memory in any state.
- A WebAssembly function that returns a pointer returns a 32-bit value, which JavaScript reads as signed, so a pointer at or above 2 GB arrives **negative** and a typed array built from it throws `byteOffset cannot be negative`. That is a second fault of the same boundary as the memory limit. A module that survives far enough to hand such a pointer back leaves the wrapper unable to read it. So the wrapper brings every pointer the module returns to an unsigned number (`pointer()` in `compiler-calls.js`). Measured: with a 1.5 GiB heap the module's answer sits at 1.53 GiB, the top of its heap, so an answer pointer tracks the heap and any heap past 2 GB turns it negative.
- A manifest build's answer is written in pieces, one build's result each, into a buffer the module reuses. So the module holds the builds it writes from and no copy of the answer. It does not hold the whole answer for a second: the answer grows with the engine, and `standard_maps` alone holds 11,456 builds and answers with 1082 MiB of JSON, against the 4 GB a 32-bit module has at most.
- With the whole answer in one buffer, the module stops on `standard_maps` alone after about 13 minutes. **It then holds 3040 MiB of the 4096 MiB a 32-bit module has.** It does not run out of the whole 4 GB. A growing buffer asks for a replacement larger than itself, and with about 1 GB of the address space left that request no longer fits. Such a stop is an abort and not a panic, and an abort never reaches the panic hook, so no response is written at all and the caller reads the wrapper's fallback text, "the shader compiler stopped on an internal error ... RuntimeError: Unreachable code should not be executed". The `shader-compiler` job then fails with `"ok": false` against the native build's `"ok": true`. A change to how the buffer grows fails the same way, because the replacement stays as large. A stop that leaves no response says nothing about which shader or which rule is at fault, so read what the module held before blaming a shader. With the pieces, the same entry completes and the module's own memory is **1185 MiB**.
- `build` writes the first piece of its answer and `build_next` each piece after it. A caller runs `build_next` until `response_length()` comes back zero. The calls that answer with a few megabytes, `compile` and its neighbors, keep one buffer and need no pieces.
- `prepare_modules` builds the engine's own manifest once and answers with the file name of each module that its build makes; `module` renders one of them and answers with its path and text. The module keeps the build between calls. The library's `ModuleSet` computes the device modules and their shared paragraphs once, lists the names without rendering, and renders one module on demand, so a build tool writes the engine's modules one file at a time instead of holding the whole text at once. The set borrows the build, and the wasm crate keeps both in one value with the set declared first so that it drops first.
- `tools/shader-compiler.ts`, which the crate's tests run the module through, writes the answer to its output as it stands. Reading more than a gigabyte of answer into objects and writing it out again holds several copies of it at once. That takes 7.33 GiB of process for one entry, against 1.355 GiB for the same entry taken straight from the module. A caller of the module that only moves the answer along should do the same.
- A call that stops for want of memory says so. `std::alloc::set_alloc_error_hook` records the request the allocator refused, with its size, into a small buffer the call took room for before it started, and `stopped()` and `stopped_length()` serve that record; the wrapper reads it in place of the call's own response. That is worth the one unstable feature the crate asks for, `alloc_error_hook`: the request aborts the module, no panic hook sees it, and without the record a caller reads only that something stopped. The hook writes nothing that allocates, and it gives up rather than borrow its own record twice or ask for room it has just been refused.
- The crate's repository-wide test asks the module for one entry at a time, which is the scale a build tool asks for: a project's own manifest. The test compares without printing either answer unless they differ, because one entry's answer runs to hundreds of megabytes. It gives each process a list of entries and reads one answer to a line, so the entries of a list share the compiler and the library it composed, and it runs several processes at once, one for each core up to eight, because the module has no threads. A process for each entry would start and compose the library again for every entry.
- The build drops the function names and skips wasm-opt. On this module, wasm-opt takes longer than the whole build and saves 0.4% after Brotli, with no speed gain.
- The shader composer rewrites each file before naga reads it, and imported names get longer. Its own error reports count columns in that copy, so the build maps each place back to the original file.
- naga renames a name that two modules share, in every program that joins them. That makes the text longer, and it can rename a custom material's own argument. So library code gives each name its own word. It uses plain early returns too, because naga writes an `||` in GLSL as a local variable and an if-else ([D-74](decisions/D-74-native-fog.md)).
- GLSL ES reserves every name that starts with `gl_`, apart from its built-ins, which all go on with a capital letter, such as `gl_Position`. In one shader, naga's GLSL writer adds `_1` to the second of two names that clash, so a local `gl` in two functions of one build becomes `gl_1`. Every WebGL2 build that joins the clear coat with half precision then fails to compile in Chrome, Firefox and Safari: 2,592 programs (D-147). So the GLSL build fails on any such name, with the program, the pipeline and the fix in its message. So never name a WGSL value `gl`, or anything that starts with `gl_`.

## The asset tool

`bunx @null3d/cli assets optimize` is JavaScript in `packages/cli/src/assets/`, on the official WebAssembly encoders. [D-18](decisions/D-18-asset-tool.md) says why, with its timings on S6's content.

- The same input gives the same bytes on every machine. Each texture encodes on one thread inside the single-threaded Basis encoder, and the image code only adds, multiplies, divides and rounds. A step that writes output must never use `Math.pow`, `Math.sin` or another function whose last digit may differ between JavaScript engines. The sRGB table in `images.js` is written out for that reason.
- `optimize.test.ts` compares the tool's output on the test scene with the files in `tests/pages/assets/models/optimized/`. CI's Linux machines then check the Mac's bytes. After a change that the outputs must take, write them again with `NULL3D_WRITE_ASSET_SCENE=1 bun test packages/cli/src/assets/optimize.test.ts`, and check the image test `asset-scene-optimized`.
- The formats that the engine also reads come from its Rust core, through the `null3d-assets-wasm` crate. It is built like the shader compiler. It imports nothing, and a request and its response pass through its memory. The build drops names and skips wasm-opt. `bun run build` writes it to `packages/cli/dist/assets.wasm`, and `formats.js` loads it.
- The tool stores positions as 14-bit integers. The transform that turns them back into meters goes into the node, the instances or a new child node. For a skinned mesh it goes into the skin's inverse bind matrices, since glTF ignores a skinned mesh's node. So the position accessor's min and max of a skinned mesh count integer steps, not meters. A box made from them is wrong: the tool's Knight would get a `prefab.bounds` about 16,000 units wide, against 2.4 m for the source file.
- So the parser boxes each skinned copy as its joints place it at rest (`skinnedRest` in `gltf-animation.ts`). Each vertex moves by its joints' skinning matrices, blended by its weights, as the skinning passes move it. three.js's `SkinnedMesh.computeBoundingBox` does the same in the current pose. The box then holds the model in meters, whether or not the file is quantized. It costs one blended matrix per vertex, once per file, in the glTF worker. `skins.test.ts` checks that the Knight's boxes match before and after the tool. Culling of skinned objects does not use the box: each frame, it bounds them with joint spheres moved by the posed skinning matrices. Instance batches draw a skinned mesh with no matrix, so they take the main joint's skinning matrix at rest, as [D-93](decisions/D-93-skinned-meshes-in-batches.md) says.
- glTF-Transform drops extensions that it does not know. `lod-extension.js` teaches it `MSFT_lod`, and a new extension that the tool writes needs the same.
- The Vite plugin imports `@null3d/cli/assets` with a specifier in a variable, so neither TypeScript nor Vite resolves it until a project imports a model with `?optimized`.
- `bun run test:shader-compiler` runs the shader crate's build tests with `NULL3D_SHADER_COMPILER` set. Each build then runs again through the module in Bun, and both results must match. Plain `cargo test` skips that step, so a module built from older code cannot fail it. The same command runs the Vite plugin's WGSL tests, which build small projects with Vite. CI runs its parts, `test:shader-compiler:build`, `test:shader-compiler:plugin` and `test:shader-compiler:pack`, in jobs of their own ([D-218](decisions/D-218-efficient-ci-jobs.md)).
- The Vite plugin compiles WGSL from projects (`packages/vite-plugin/src/wgsl.ts`). It reads a module's comments with Vite's parser, so the `/* wgsl */` tag counts only as a real comment before a real template literal. It runs before TypeScript becomes JavaScript, so the literal's place in the code is its place in the file.
- Each project shader builds for WebGPU and, with the shader def `WEBGL2`, for WebGL2. It has one render pipeline for each `@fragment` entry point, with its one `@vertex` entry point. The plugin finds the entry points in the WGSL text, because the compiler takes the pipelines with the source.
- Plugin errors count columns from 1, as editors do. Rollup counts its own from 0, but Vite and Rolldown only print the place, and Vite's overlay opens the editor at it.
- naga turns off its checks of uniform control flow for derivatives and `textureSample`, because they reject valid shaders. The build therefore cannot catch `textureSample` in a branch that differs between pixels, which Chrome rejects when it creates the shader module.

## Tests that build a bundle

Some unit tests build a bundle of engine code with Vite inside the test process, such as
`math/tree-shaking.test.ts`. Build it the way a page is built, with a single input, and never with
`build.lib`.

- A library build inlines every asset as a base64 data URL, and does not copy it as a file. Vite's
  `shouldInline` returns true on `config.build.lib` before it reads `assetsInlineLimit`, so
  `new URL('./x.js', import.meta.url)` becomes a data URL.
- The engine's generated shaders are around 850 MB of assets. A worker build inherits the parent's
  `lib` setting, so each worker bundle encodes that payload again inside itself.
- One such build of a sketch that imports `vec3` takes 22 s and 13.8 GB of memory footprint. The
  same build without `lib` takes 4.8 s and 4.1 GB. A test file that builds twice holds 18.6 GB
  against 5.1 GB.
- The unit suite is one process on a 16 GB machine. A library build in it is killed without a
  message of its own: the log shows only a runner shutdown and SIGKILL.
- `rollupOptions.external` cannot avoid this. Vite resolves a `new URL(...)` on the filesystem in
  `vite:asset-import-meta-url`, not through Rollup's module resolution, so `external` never sees it.
- A build that must keep the entry's exports, as the shipped library has them, takes
  `rollupOptions.preserveEntrySignatures: 'strict'` instead of `lib`. Without it the entry's exports
  go and so does the code under test.
- A test that reads the shader text finds it in a copied file, not in the code, once the build is a
  page's. `debug/release.test.ts` reads both.

## Meshes on both GPU paths

- WebGL2 always reads the largest value of the index type as a primitive restart, because WebGL 2.0 keeps `PRIMITIVE_RESTART_FIXED_INDEX` on. A triangle that uses 16-bit index 65,535 draws nothing. Pages and mesh parts therefore hold at most 65,535 vertices on both paths.
- Each vertex attribute has a fixed shader location, and a pipeline reads only the attributes that its entry point declares. WebGPU needs a pipeline for each vertex format, since the format sets the stride and the offsets. On WebGL2 the vertex array holds that layout, so the pipelines of one template share one program.
- The culling shader counts each visible instance in every draw of its bucket, one draw per part of the bucket's mesh. The parts' draws then read the same slice of instances.
- Each visible instance adds 1 to its draws' counts with one atomic add, so many threads add to one word. Counting per workgroup, then adding once, speeds the culling pass in S1 by 72% to 77% on the Mac and 53% on the Galaxy S25. It makes the pass 8% to 35% slower on the iPad's A14, so the engine keeps one add per instance ([D-100](decisions/D-100-workgroup-counters.md)).
- A vertex format gives each attribute a type: floats, or the 8-bit and 16-bit integers that glTF allows for it ([D-25](decisions/D-25-vertex-types.md)). Mesh pages hold bytes, and each attribute takes whole 4-byte words, so a vertex's stride is always whole words.
- WebGPU reads a plain integer that a shader takes as a float through its normalized twin, such as `unorm16x4` for 16-bit unsigned positions. The pipeline then sets the override constant of that location to the type's largest value. Its id is 1000 plus the location. The functions `mesh_position`, `mesh_uv` and `mesh_second_uv` of `null3d::vertex` multiply by it. WebGL2 reads the integer as its whole value with `vertexAttribPointer` and `normalized` false, so its GLSL keeps each constant at 1.
- A compute dispatch reaches 65,535 workgroups per axis (`caps::MAX_WORKGROUPS_PER_DIMENSION`), and the mock backend refuses more. A pass whose work can pass it spreads its workgroups over rows, as the skinning pass does, and numbers each workgroup from `workgroup_id` and `num_workgroups`.
- A storage binding may not pass the device's `maxStorageBufferBindingSize`, 128 MiB by default. The skinning pass splits skinned vertices over up to 8 buffers within it. The WebGPU builder caps each mesh page at it too, since the pass binds a page whole. The culling pass sizes its source buffer by the same limit. Both size their buffers by the storage binding that the engine requested. That binding stays at the portable 128 MiB one where the adapter offers no larger limit. So a pass that needs more than the default spreads over bindings instead of failing. `capacities.rs` covers the split and `gpu_driven.rs` the source limit.
- The skinning pass writes normals and tangents as 8-bit normalized integers, one word each, and the passes read them through `snorm8x4`. The skinning shader's override constant `narrow_directions` (id 1100) writes 32-bit floats instead, for the measurements of `?skinning=full` and `?skinning=skip`. The core and the shader must agree. The core's skinned format (`skinned_format`) sets the stride and the offsets, and the WebGPU backend sets the constant from the same switch (`setSkinningMode`).
- The skinning pass skips an object whose regions hold its pose. Its animated instance's pose step and its morph weights have then held still since its last skin. Anything that leaves the regions without a known pose must clear `held` in `gpu_driven/skin.rs`. These are a new layout, a new skinned vertex buffer, a new GPU device, and frames whose skinning pipeline may still build. A frame that fails keeps the structure marked as changed, so the next frame lays out again and clears it. A path that loses the regions' contents some other way must clear it too, or a still character draws stale or empty vertices.
- The pose step comes from the animation step's compare of each instance's new matrices with the step before's. It costs one read of the other matrix buffer per joint, on the job workers. M2-C6's slower update rates must keep that compare true. An instance that a step leaves alone must keep its matrices in the buffer that step writes.
- Joints are the one attribute that shaders read as integers (`vec4u`). WebGPU reads them with `uint8x4` or `uint16x4`, and WebGL2 with `vertexAttribIPointer`. A WebGL2 program that declares an integer input must get an integer pointer, or the draw fails. So only shaders that read joints declare location 6.

## Pipelines and warm-up

- The thread that draws loads the shader module of its device's fixed bits. When bloom moves the 8-bit path to HDR color, pipelines ask for builds without the tone mapping bit, which that module lacks. `DeviceShaderSet` (`gpu/device-shaders.ts`) then loads the module of those bits once, and adds its builds to the variants that the backends hold. It loads a feature's module in the same way, as "Shader files that load on first use" says. The pipeline waits meanwhile, as a custom material's pipeline waits for its shader ([D-21](decisions/D-21-effect-chain.md)).

- A frame's draw list creates its pipelines before any other command. The renderer starts their builds the first time it prepares the frame, and replays the rest of the list later. The render crate's test world checks this order in every list it records.
- A list that creates a pipeline after other commands builds it at once. So a hand-written list, as on the replay test pages, draws everything in one replay.
- The first frame on a GPU device waits for its pipelines. Later frames draw at once, and a draw whose pipeline is still building draws nothing. So each frame loop asks the presenter whether a frame is ready before it takes the frame. The sketch thread computes no frame past it.
- A compute pass's dispatches skip while its pipeline builds, as a draw's do. One GPU-layer rule covers every pass. The engine's own passes and an add-on's `render.addPass` pass reach it through the same commands. Neither kind therefore dispatches into a pipeline that is still pending. `backend.test.ts` covers each kind.
- Without `KHR_parallel_shader_compile`, a WebGL2 program never counts as building, and its first draw waits for its compile. The switch `?compile=wait` gives that path in a browser that has the extension.
- A warm-up in the setup records a frame itself, since no frame loop runs yet. So the renderer must exist before the setup: low-latency and single-threaded modes start it first.
- The single-threaded build's memory detaches every view when it grows, and a write through a detached view is lost. So every core call that can grow the memory goes through `CoreMemory.checkGrowth`, which takes the new buffer. The sketch runner takes it after each frame step that sketch code or a development check follows, and at the end of each frame. Sketch code then writes through current views in every callback, between frames and after a warm-up.
- A change of preset starts the first frame's wait again. The sketch thread writes the frame in the control block's `PipelineHold` before it publishes the frame. The replay (`FrameReplay.prepare`) then holds that frame, and later ones, until one draws with every pipeline built. The canvas keeps the last frame meanwhile, on both paths.
- The direct loop takes the frames that the setup publishes only when `Presenter.due` allows, as it steps play frames. The preset check then measures at the pace of play, within the limit of frames in flight. The loop wakes waiters on `FramesTaken`, because the check's code on the same thread waits for each frame to be taken.
- With the depth prepass, each opaque pipeline has a prepass pipeline, which the frame's list creates beside it. So the first frame and an object's warm-up build both, and play builds neither. On WebGL2, whose presets draw the prepass, the warm-up check's first frame builds 21 pipelines where WebGPU's builds 15, and an added object builds 2 ([D-43](decisions/D-43-webgl2-prepass.md#consequences-of-the-prepass-on-webgl2)).
- Each backend counts the draw commands that a building pipeline skips, in `counts.skippedDraws`. The measurement sums them, and a test that expects no missing objects checks that the sum stays at 0.
- Custom materials, custom effects, their joined shaders and custom tone curves take template ids from one range. A joined shader is the shader of a group of effects that draws as one pass, or of the effects that fold into the final pass. When the last material of a custom template goes, the frame releases that template's pipelines, so it also checks that no effect, joined shader or tone curve uses the template. Effects and the final pass ask the cache for a pipeline id once and keep it. If the check counted only live materials, destroying any custom material would destroy the pipelines of every custom effect, joined shader and tone curve. They would draw on with the destroyed ids. A Rust test destroys a material beside three effects, two of them in a group and one folded into the final pass, and checks that no pipeline of theirs goes. Without the check of effects, or of the group and the fold, the mock backend refuses a draw with a destroyed pipeline.
- A template that only an add-on completes cannot build as an ordinary entry shader. The shader build compiles every `.wgsl` file at the top of `crates/null3d-shaders/wgsl/` on its own, so a template that calls a function the add-on supplies, such as a sky layer's `skyLayer`, fails there before any page runs it. Such a template takes a manifest marker, `custom_effects` or `sky_layers`, which makes the build prove it with a stub behind a shader def and write no module of its own. The add-on's build adds its WGSL after the template's last line and sets the def, which leaves the stub out ([D-242](decisions/D-242-sky-layers.md)). A template without such a marker can only sit under `wgsl/lib/`, inert, because nothing imports it.
- A template's pipeline binds groups of fixed layouts, which the render worker declares in `pipelines.ts`. `drawlist::groups` mirrors that table for the mock backend. The mock checks every group bound at a draw or a dispatch against the drawing pipeline's template. WebGPU refuses a draw whose group has another layout. WebGL2 reads another uniform, so such a frame draws nothing while every Rust test passes. An entry lists the layouts that either GPU path may bind at one index, because the mock reads both paths' lists. A template from `CUSTOM_FIRST` up has no entry, since its page decides its layouts. A test checks that every other template has one. WebGL2 binds the copy of the scene's depth that a custom material reads once for the whole view pass, so a pass that draws such a material beside a mesh template carries the depth's layout at that group too.
- The engine's shaders ship in one module for each GPU path and each value of the permutation bits that a device fixes ([D-13](decisions/D-13-shader-variants.md)). The thread that draws starts to load its module while it waits for the WebGPU device or the WebGL2 context. The renderer starts once both are ready.
- A device module holds the builds of each shader that a device with its bits asks for. The builds of features that load on first use are the exception. So the culling shader, which has no bits, is in every WGSL module. A device whose bits have no module fails to start its renderer, with an error that names the bits.
- On WebGPU, a pipeline that draws depth only has no fragment stage, so its pixels cannot be dropped. Shadow casters draw that way. So a shadow cutout template without a fragment stage casts each masked caster's whole shape on WebGPU. No error shows: the cutout code is in the shader, but no pipeline runs it. WebGL2 always builds a fragment shader, so it cuts the holes. A depth template that must drop pixels asks for its fragment stage (`depthFragment` in `gpu/webgpu/pipelines.ts`), with no color targets. The shadow cutout templates do so. The plain depth template skips the stage, which keeps solid casters cheap. The `alpha-mask-shadows` image test catches a missing stage on WebGPU. [D-82](decisions/D-82-transparency-parity.md#the-fragment-stage-of-cutout-casters) has the details.

## Shader files that load on first use

A feature that most pages do not use keeps its shader builds out of the start files ([D-56](decisions/D-56-first-use-shader-files.md)). Sprites, lines, skinning, morph targets, bloom, ambient occlusion, the texture background, GPU occlusion culling, area lights and the engine's test template do so.

- A feature declares its file with a `[first_use.<feature>]` table in `crates/null3d-shaders/shaders.toml`.
  - The engine test "the first use of X downloads its shader file once" (`tests/image/engine.spec.ts`) runs for every table, from the generated feature list. A feature without a sketch of its own draws in `tests/pages/sketches/first-use-sketch.ts`, whose `?feature=` names it. A new table fails that test until the sketch has a case that uses the feature alone.
  - `shaders` lists templates whose every build needs the feature.
  - `bits` lists permutation bits that a device does not fix. Every build with one of them needs the feature, such as every template's SKIN builds.
  - A build needs its template's feature and the feature of each of its bits that a table names. A build that needs one feature goes into that feature's file. A build that needs several, such as a SKIN build with ALPHA_HASH, goes into a file of its own for that set of features, which a page loads only once it uses each of them. So no feature's file grows by the builds of another feature ([D-56](decisions/D-56-first-use-shader-files.md#builds-that-need-several-features)).
- A value of the permutation word names one feature in each template, so two features can share a value ([D-156](decisions/D-156-template-scoped-permutation-bits.md)). `AREA_LIGHTS` shares `FXAA`'s value: only the lit templates list it, and only the final pass lists FXAA. The shader build refuses a template that lists two names of one value. A shared value's bit takes only the builds of the templates that list its name, and the generated main module's `FEATURE_MASKS` does the same at run time. An unshared bit counts for every template. Code that makes one template's key from another's keeps only the bits that it names, as `DrawKey::prepass` does.
- The shader build writes the feature's builds to `generated/shaders-<feature>-<target>-<bits>.js`, and the builds of several features to `generated/shaders-<feature>-and-<feature>-<target>-<bits>.js`, with the names in alphabetical order. There is one file for each value of the device's fixed bits that the builds vary in, and none for a set of features without builds. The size report holds each one to the limits of one start shader file, in a section of its own.
- A paragraph that at least twenty feature-set device modules of one kind hold is written once in that kind's table, `generated/shader-paragraphs-<target>[-<bit>...].js`, and each module imports the constants it uses. A kind is a target and one value of the device's bits. A kind's tables also split by feature family ([D-191](decisions/D-191-shared-text-split-by-feature-family.md)), so a module that holds a family's paragraphs imports its kind's table and that family's. A module of the start names no table, so a page's first download holds none of it. The Vite plugin emits every table that a copied module names, beside the modules that name it, and the offline list gives a module all of its tables. A plugin that took only the first table of each copied module would leave a build with 12 of the 164 tables. A browser that loads a feature's module then fails with "Failed to fetch dynamically imported module", which names the module, not the table it lacks. The size report holds each table to the same limits as a feature's shader file ([D-181](decisions/D-181-shared-shader-paragraphs.md)).
- The main module's `firstUseFile(shader, permutation)` gives the key of the file that holds a build: the names of its features, sorted and joined by `+`, such as `hash+skinning`. A bit counts only for a template that lists its name, because a value can name another feature in another template (D-156). `DeviceShaderSet` loads the file of that key the first time a pipeline asks for one of its builds, and nothing else.
- Device modules are plain JavaScript. With `new URL(address, import.meta.url)`, the main module imports each one by its address. Vite copies a file that an address names once, so the page's bundle and the workers' bundles share one copy. An `import()` by name would give each bundle a copy of its own. The null3D plugin keeps a small module from becoming a `data:` address, which a strict Content Security Policy blocks.
- A pipeline whose build is in a feature's file waits for the file, and then builds. Before the first frame, the frame waits with it. After it, the pipeline's draws draw nothing until it is built. That suits an object of its own, such as a sprite batch, which then appears once it is built. On WebGPU a compute pipeline waits in the same way.
- Two kinds of pass must not draw while their pipelines wait. They keep to what they had until `PipelineCache::built` says every pipeline they need is built.
  - A full-screen pass, which would leave the canvas without its frame. `FrameGraph::request_pipelines` keeps the final pass without bloom until bloom's pipelines are built.
  - A pass whose output another pass reads. On WebGPU the skinning pass writes the vertices that the other passes draw. So `SkinnedGate` (`skinning.rs`) leaves skinned objects out of every layout until their pipelines are built: the skinning pass's, and every one that draws them. The layouts still ask for those pipelines, and then take the objects in. The main pass, the depth prepass, the shadow passes and the transparent pass then show them in the same frame. Both builders use the gate. On WebGL2 it keeps in step the passes, each of which skins in its own vertex shader.
  - Every lit pipeline at once. `AreaShading` (`area_shading.rs`) keeps the lit templates on their builds without `AREA_LIGHTS` until the scene holds an area light, its tables have arrived, and the build with the bit of every lit pipeline in use is built. Only then do the layouts take keys with the bit, and the light grid list area lights. So no build meets an area light whose code it lacks, and no lit object vanishes while the file loads. Custom materials always build the area lights' code, so their keys never take the bit. A frame whose `pipelines_built` is 0, the first frame of a device, waits for every pipeline its own list creates, so the switch opens at once for it. The frame's light list is gathered before its builder runs, so `Settings::gather_lights` applies the same rule and lists area lights for such a frame. Otherwise the one frame that hold mode keeps draws the builds that shade area lights over a light list with none in it. The bench's four area-light scenes then keep one black picture. Every later frame reads the switch the frame before it left, and waits for the builds it asks for.
  - GPU occlusion culling's two phases write the indirect draws that the opaque pass reads. The WebGPU builder asks for their pipelines and the depth pyramid's in the frame after the scene's first marked occluder, as its layout counts the marks only once it lays out that frame. Until `Pyramids::built` says all three are built, each camera view culls once with the plain culling pipeline, into the draws that the opaque pass reads, and the frame records no occluders' pass. The culling shader's file holds `main` alone in the start files; its OCCLUSION build, with `early` and `late`, is the `cull_occlusion` shader of the `occlusion` feature.
- `PipelineCache::built` compares the frame whose list created a pipeline with the newest frame that the thread that draws drew with every pipeline built. Both steps of the WebGL2 builder must get that frame: the culling and the recording. A 0 reads as "before the first frame", when every pipeline counts as built.
- A page may load features' files before the first frame with `createEngine`'s `preload` list. The renderer awaits them beside the start's file. A preload loads each feature's own file, and each file of several features once the preloads so far have asked for each of them (`filesFor` in `gpu/device-shaders.ts`). On the 8-bit path, preloading bloom also loads the builds without the tone mapping bit, which bloom's HDR color needs.
- Each module that a preload asked for goes to the backend's `precompile` once it arrives, with the features that its builds need (`DeviceShaderSet.onPreloaded`). WebGL2 compiles a program for each build in the module, which its pipelines then share. WebGPU creates the shader modules, and the compute pipelines of skinning and occlusion culling, whose layouts are fixed. Skinning's and morph targets' mesh builds depend on materials, so neither path compiles them ahead, nor the builds of a file that needs skinning or morph targets on WebGL2, and `scene.warmUp()` builds those.
- Sketch code that knows a feature is coming calls `ShaderPreloads.need` (`scene/shader-preloads.ts`), which `Materials` holds. The request goes to the thread that draws with the images and custom materials' shaders. `ImageTable.preload` keeps it for every renderer, and the renderer's `DeviceShaderSet.preload` starts the download. The glTF loader asks for skinning as soon as a file with skins is parsed. Batches, texture backgrounds and `post.set` ask for theirs.
- A new feature adds its table, and moves no build that every scene draws. It gives each pass of either kind above the same wait. The engine test "a page that uses no feature that loads on first use downloads none of their files" then covers its files. A test of its own checks that its first use downloads one file once.
- A custom material's WebGPU SKIN builds load on first use too, from the sketch's own files rather than the engine's ([D-20](decisions/D-20-webgpu-skinning.md)). The shader compiler puts them in `skinVariants`, and the Vite plugin moves them to a virtual module, `virtual:null3d/skin/<hash>`, which the material's packed value imports with `skinBuilds()` (`packages/vite-plugin/src/skin-builds.ts`). The material's shader reaches the thread that draws marked `skinBuilds`. The first pipeline that needs one of those builds parks in `templateReady`, through `ImageTable.buildsReady`. The table asks the sketch's thread once, through the port of the images, or straight through `askBuilds` when one thread does both. `ShaderTemplates.answer` imports the module and sends the builds of its GPU path, and `ImageTable.addBuilds` puts them into the shader's own object of builds, which the backend's template holds. A failed import fails the pipelines that need the builds, with its reason. A hot update brings the builds with the others, so a late answer for the older shader is dropped. WebGL2 keeps a material's SKIN builds with its others.

## Depth on WebGL2

- Draw lists and shaders keep WebGPU's reversed depth. Each GLSL vertex shader maps its clip depth through one uniform, and the WebGL2 backend sets it once per program for its depth mode (`gpu/webgl2/depth.ts`). One set of GLSL programs then serves every mode.
- The `reversed` mode sets a clip range from 0 to w with `EXT_clip_control`. The `reversed-gl` mode moves depth into GL's range as 2z - w, where the vertex shader rounds far depths away. The `standard` mode writes w - 2z, and the backend turns clear values and viewport depth ranges around to match.
- Depth textures hold WebGPU's depth values in `reversed` and `reversed-gl`, so shaders that read depth work the same on both paths. In `standard`, they hold 1 minus WebGPU's value.
- Shadow maps therefore need no flipped comparison on WebGL2. In `standard`, the receivers' reference depths would not match the map, so every comparison sampler compares with `ALWAYS` there, and every surface is lit.
- A context that answers no `EXT_clip_control` draws `reversed` as `reversed-gl`, and never fails to start. A context lost while the backend starts answers no extension, and a failed start would end the engine's recovery from that loss.
- The depth precision page counts the fighting pixels of surfaces 1 cm apart from 1 m to 10 km. On the Mac, Chrome, Safari and Brave give the same counts, because all three draw WebGL2 through ANGLE on Metal.
- Firefox 156 on the Mac has no `EXT_clip_control`, so it draws `reversed-gl`. That fights in fewer pixels than `standard` there, as it does in every Mac browser.
- The opaque pass after the depth prepass shades only where its depth equals the prepass's. So both passes must give each pixel the same depth, to the last bit.
- On WebGPU, the prepass draws with a build of the shadow depth template that clips at the near plane, as the shading templates do. The two passes then give each pixel the same depth.
- On WebGL2, that depth-only program gives other depths than the shading programs in Chrome on the Mac (ANGLE on Metal). The shadows image then loses the ground in blocks of pixels, and 57.8% of it differs. Every GLSL vertex shader declares `invariant gl_Position`, and ANGLE's Metal code marks the position `[[invariant]]`, but Apple's compiler still optimizes the two programs' position math differently. The same build passes on SwiftShader.
- So WebGL2 draws the prepass with each shading pipeline's own vertex shader, linked with a fragment shader that writes nothing. Two programs with the same vertex shader give the same depth. All seven prepass image tests, skinned characters among them, match the images without the prepass bit for bit on the Mac. On SwiftShader they match too, apart from 16 edge pixels of the orthographic test, which WebGPU's prepass shows there as well. [D-43](decisions/D-43-webgl2-prepass.md) gives the options and the figures.
- Custom materials and sprites place their vertices in their own way, so on WebGPU too their prepass draws with their own vertex shader and a fragment shader that writes nothing. A vertex offset can read the material's textures, so the prepass binds them on both paths ([D-43](decisions/D-43-webgl2-prepass.md#custom-materials-and-sprites)).
- The WebGL2 backend reads the `PREPASS` bit on a mesh template's pipeline that way (`buildPermutation` in `gpu/webgl2/programs.ts`). The debug view template counts as one, since it replaces every material. The shadow depth template has no `PREPASS` build in GLSL.
- Two opaque surfaces at exactly the same depth both pass the opaque pass's test for equal depth, so the one drawn last shows. Without the prepass the one drawn first shows. The depth precision test's tie tile shows it on every tier with `?prepass=on`. Every preset draws the prepass on WebGL2, so the depth precision page turns it off.

## Reading the depth in a shader

- Ambient occlusion reads the depth that the prepass leaves, between the prepass and the opaque pass ([D-21](decisions/D-21-effect-chain.md#ambient-occlusion)).
- Compatibility mode refuses `textureLoad` on WebGPU's depth texture types: `texture_depth_2d` and the others. It also refuses a depth texture with a non-comparison sampler, and copies of multisampled textures. It does read a depth format bound as a plain float texture: a layout entry with `sampleType: 'unfilterable-float'`, and `texture_2d<f32>` or `texture_multisampled_2d<f32>` in WGSL. A probe of 1 and 4 samples passed in Chrome 154 on the Mac's GPU and on SwiftShader, in both WebGPU modes. Safari 26.6.2 and Firefox 157 passed it too.
- So every WebGPU path binds a depth target that a shader reads in that way. The proposal's restrictions name only the depth texture types, so the binding follows its rules. A device on OpenGL ES that refuses it is the case to watch in device runs.
- WebGL2 has no multisampled textures. A multisampled depth target that a shader reads lives in a renderbuffer, beside a texture of one sample. Each render pass that stores the depth blits it into that texture at its end, and bind groups read the texture. GL copies one sample of each pixel, as WebGPU's shaders read sample 0. A blit of a multisampled depth must cover the whole target, and the backend turns the scissor test off first.
- A shader reads the depth texture with `texelFetch`. The texture's own filters are nearest, and no comparison mode is set, so it returns the depth value.
- In the `standard` depth mode, depth textures hold 1 minus WebGPU's value. Ambient occlusion then finds the wrong surfaces, as shadows light every surface there. The mode is a test switch.

## Shadows

- The cascade split leans 65% toward the logarithmic spread. [D-15](decisions/D-15-cascade-split.md) gives the texel sizes, the options that lost and the cost.
- Each cascade but the last blends into the next over a band at its far end ([D-73](decisions/D-73-cascade-blend.md)). The uniform block holds where each band starts. It is in the distance that picks a receiver's cascade. The second read sits behind a branch, so only band pixels pay. A band pixel reads the next cascade only where the next box holds it with the filter's reach. A box kept from an earlier frame can miss it after a turn.
- Each cascade's sphere is fitted from the band before it, divided by `sqrt(1 + k²)`, where `k` is the tangent of the view corner's angle. Receivers pick their cascade by their distance from the camera. A point at a corner lies that many times further away than along the view. Fitting only the slice along the view leaves lit holes at the sides of narrow views (R5-06).
- A far cascade keeps its box only while the box holds the eight corners of its fresh part of the view. A corner counts as held up to the box's edge, not the filter's reach inside it. A far corner of the view lies on the sphere. Counted with the reach, a smoothly moving camera draws S4's far cascade out of turn in 2.4% of Low's frames. The schedule's unit test follows S4's camera path on every preset and allows no out-of-turn frame.
- The shadow distance is in meters. The lens and the slices are in the view's units. So the core multiplies the distance by the forward axis's length: the view's units per meter (R5-22).
- Casters draw only their back faces, as three.js's filtered shadows draw them, or both faces for a double-sided material. The depth-only vertex shader flattens casters in front of a cascade onto its near face, so they still cast into it.
- WebGL2 keeps the same shadow map as WebGPU: a 2D array texture of `DEPTH_COMPONENT16`, which WebGL2 core has. WebGPU calls it `depth16unorm`. A framebuffer draws into one layer at a time with `framebufferTextureLayer`. With the compare mode on, linear filtering is allowed, so the hardware blends four comparisons there too. The atlas of spot and point light tiles stays `DEPTH_COMPONENT32F` ([D-76](decisions/D-76-16-bit-cascades.md)).
- The cascades and the tiles store different depth formats. A render pipeline or bundle draws into one format only. So each caster bucket holds two pipeline ids: the cascades' in its first slot and the tiles' in its second. The depth prepass and the outline mask keep their second pipelines in that slot too. Each id exists only while its kind of shadow is on, so a scene with sun shadows alone builds no tile pipeline. The layouts rebuild when either kind turns on or off. The WebGL2 builder's runs of draws split where either id changes. Without that, the cascades' ids of 0 would join every caster into one run while only the tiles cast. With `?shadowdepth=32` both formats are 32-bit, and the two ids are one.
- Each cascade's box snaps along the light to whole steps of 16-bit depth, as it snaps across the light to whole texels. The steps then stay fixed in the world, and a caster's stored depth rounds the same way in every frame. Without the snap, the box follows the camera continuously along the light. Each move then shifts the grid of steps by part of a step, and tests near a tie flip between frames. S4's stability check fails so on the Automate S25 and Pixel 9. The snap applies with 32-bit depth too, where it changes nothing visible.
- The shadow uniform's spare `kernel.w` carries the step between two stored depths: 1 / 65,535, or 0 for floats. The shader floors the sun's bias toward the light at 1.5 steps in meters, and the receiver plane's margin at 1.5 steps of depth. A step in meters is the step over the cascade's depth per meter, the length of its matrix's third row. The block keeps its size.
- On WebGL2 the job workers cull the casters of each cascade, and that work grows with the number of casters. WebGPU culls them on the GPU.
- The grid-cell order takes every caster, not only the objects with a bucket in the scene's layout. Blended objects draw in the transparent pass and have no bucket. A cell order without them would keep a cascade that culls through it from testing them. A blended object would then lose its shadow wherever cells are active, on both paths.
- A spot light's tile and a point light's six tiles draw again only when something in their reach changes. So a still scene draws no tile. Moving objects appear in the upload list every frame. So the builder keeps each caster's last matrix, sphere and layers, and compares them. A layer change keeps the matrix and the sphere. Without the layers in the comparison, a caster that leaves or joins a light's layers keeps a stale shadow (review finding R5-07).
- A moved caster marks only the tiles whose views its sphere touches, before or after the move. Each test is a sphere against the four side planes of the tile's view, with the filter's margin. So it is never stricter than what the tile draws. A caster below a point light marks one face, not all six.
- A pose can change while the bounding sphere stays the same bit for bit. Hands that move in front of a body move no joint sphere past the others. So the builder keeps a 64-bit hash of each skinned or morphed caster's skinning matrices and weights. It compares the hash in each frame while the caster lies within a shadowed light's range (R5-08). The hash costs one multiply per matrix float; it runs only for posed casters near lights that hold tiles.
- A tile whose view, cut at the light's range, lies wholly outside one plane of the camera's frustum waits, dirty, until it meets the view. No receiver on screen can read it. The test uses the five corners of the cut view, so it is conservative.
- At most 12 tiles draw again per frame (`MAX_REDRAWS`, [D-61](decisions/D-61-shadow-tile-redraws.md)). Tiles that hold no depth of their light yet are outside the cap and draw at once. So a light never shows another light's depth. The cap counts them first. Whole lights take the rest, the longest waiting first, so no light starves and a point light's faces stay in step.
- Each tile's view keeps 3 texels inside each edge, the reach of the 5 x 5 filter. With 1 texel, the filter reads 2 texels past what the tile draws at a face's edge. The sampler clamps those reads to the edge texel.
- The atlas never shrinks while a light casts and the settings stay. An atlas sized to the lights of each frame would declare the render graph again and compile it at each light's shadow toggle. It would also make the atlas again, which drops every tile's depth (R5-09). The atlas keeps the most layers that the lights needed, not the preset's whole budget. At Ultra, one spot light would otherwise hold 24 tiles of 1,024 texels: 96 MiB, against 4 MiB.
- A draw whose pipeline still builds is skipped, so a tile drawn then would stay incomplete. `recordFrame` gets the newest frame drawn with every pipeline built (`Slot.PipelinesBuilt`). A tile counts as drawn only after that frame.
- Point lights take aligned blocks of six tiles from the first tile up, and spot lights single tiles from the last tile down.
- The directional light's filter compares each texel of the shadow map with the receiver's plane at that texel's center ([D-16](decisions/D-16-moving-casters-and-bias.md#one-depth-per-texel)). On WebGPU it reads four texels at once with `textureGather`. So it takes as many reads as a comparison sampler's filter. That needs the map as an `unfilterable-float` texture with a non-filtering sampler, at frame group binding 12. WebGPU's compatibility mode allows only a comparison sampler on a depth texture. GLSL ES 3.00 has no `textureGather`. So the WebGL2 build keeps the map as a depth texture. It compares each texel through the comparison sampler at the texel's center: four reads where WebGPU makes one. In WebGL2's `standard` depth mode, that sampler compares with `ALWAYS`, so every surface stays lit there. A texelFetch of the raw depth would read 1 minus WebGPU's value in that mode.
- The receiver's plane comes from the normal in the cascade's clip axes: the depth's change per texel along each axis is the normal's share there over its share toward the light, scaled by the matrix rows' squared sizes. That holds because each cascade's projection is orthographic, with the light's axes as its rows. It gives the same plane as two directions along the surface and a determinant. That form costs S4 at Low 1.19 ms of GPU time per frame on the owner's iPad ([D-16](decisions/D-16-moving-casters-and-bias.md#the-receiver-planes-cost-on-the-ipad-and-a-cheaper-form)).
- The directional light's cascade lookup runs one pass per cascade at every pixel, and the pixel's distance only chooses the passes that do work. Adreno 830 can run a loop the wrong number of times when its pass count differs within a work group ("Browser faults"). The cascade that a pixel needs differs between neighbors at each cascade's edge. The cascade count comes from the uniforms, so every pixel of a draw runs the same number of passes. No device has shown the fault in the shadows. A multi-cascade shadow run on WebGL2 on the S25 checks it on the device.
- A fixed four passes, whatever the cascade count, cost more than a few compares. They add about 0.08 ms to S4 at Low on the Mac's GPU, 6% of the frame, where the light has two cascades. Passes bounded by the cascade count take 1.380 ms per frame against 1.426 ms for four fixed passes. Each build ran 6 rounds, in turns (Chrome, WebGPU). The scene pass alone takes about 0.63 ms against 0.65 ms. A shader test holds both loops to the cascade count. [Releases](releases.md#s4s-gpu-time-at-low-the-second-comparison) gives the whole comparison.
- A surface that faces away from the sun skips the sun's shadow lookup. The sun gives it no light whatever the map holds, so the image does not change. S4 at Low on the Mac takes 1.481 ms of GPU time per frame with the skip, against 1.547 ms without it. Each build ran 4 times, in turns (Chrome, WebGPU).
- S4 at Low on WebGPU draws 63 draw calls in 5 passes in every frame. The passes are the culling pass, the near cascade, the far cascade, the scene and the final pass. S4's cars drive through the far cascade, and every preset draws a far cascade in every frame while a moving caster touches it (`followMovingCasters`, [D-16](decisions/D-16-moving-casters-and-bias.md)). A test of the benchmark pages (`bench/tests/pages.spec.ts`) holds Low's figures. A change to them needs its reason here: each pass and draw in S4 costs every phone that runs it.
- While `followMovingCasters` is off, the governor takes no far cascade step. A far cascade then keeps its turns around moving casters. A longer interval would only make their shadows trail further. The governor goes from the render scale straight to the filter's step.
- Two shadow choices set most of S4's GPU time at Low. On the Mac, S4 at Low takes 1.19 ms with the far cascade on turns. A far cascade in every frame (#227) brings it to 1.36 ms. The receiver plane of #257 keeps flat casters such as pavements from shadowing their own tops. It adds 0.11 ms to the scene pass, to 1.47 ms. S4 at Low draws its far cascade in every frame, as at 1.48 ms in the table of [Releases](releases.md). The GPU timer times one frame in 8, and a far cascade on turns draws once in 4 frames. So the timed frames can all miss the far cascade, and the build reads faster than it is ([Benchmarks](benchmarks.md#gpu-time-per-pass)). Low follows moving casters by the owner's decision: with the far cascade on turns, every car's shadow jerks behind its car on the iPad ([D-16](decisions/D-16-moving-casters-and-bias.md#why-low-follows-moving-casters)). That costs about 0.1 ms per frame on the cloud iPad (10th generation, Safari): 6.47 ms against 6.36 ms with turns. So a cache of the far cascade's still casters could save at most that, and the engine has none ([D-16](decisions/D-16-moving-casters-and-bias.md#the-still-caster-cache)). On the owner's iPad it costs about 0.3 ms: 11.81 ms against 11.53 ms, both at 60 fps. The owner accepts that cost ([D-16](decisions/D-16-moving-casters-and-bias.md#the-cost-on-the-ipads)).

- The sun's hero shadow is a tile of the atlas, fitted to the object's bounding sphere: square across the light, one radius past the sphere toward the light and sixteen past it away from the light, where the shadow lands ([D-219](decisions/D-219-hero-shadow.md)). The tile takes the atlas's last layer and the atlas gains that layer, so no light loses a tile. Every layer of a texture array has one size, so the tile's `heroTileSize` (1,024, 2,048 or 4,096, with a preset default) sets the size of every layer, and a tile larger than the preset's `shadowTileSize` gives every light's tile more texels. The tile's resolution is the ratio that the done-when measures, so a setting decides it rather than the preset's light tiles. Its key is the box, the size, the layers and the light's biases, so it draws again when the object moves or the light turns, and a caster that moves inside the box marks it. The shader transforms a receiver into the box's clip space before the cascades run: inside the box's two across-light faces and its depth range it reads the tile with the atlas filter, and outside it reads the cascades. A caster that shadows such a receiver lies inside the same across-light extent, so the tile holds every caster its receivers read.

## Light clusters

- On WebGPU a compute pass fills the camera's light grid in three dispatches. They count each cluster's lights, add up the counts with the caps in one workgroup, and write each cluster's lights. On WebGL2 the job workers do the same work. Each scene pass that sees a light has a grid of its own, which the same pass fills with three more dispatches ([D-104](decisions/D-104-scene-passes.md#point-and-spot-lights-in-scene-passes)).
- Both paths share one tile test, which the shader repeats step by step. It keeps to the operations that WGSL rounds as the CPU does. It multiplies by the inverse of the depth row's length, and reads each slice's bounds from a table that the CPU fills. So the GPU lists the same lights as the job workers, word for word, and the `light-clusters` page checks it.
- The pass runs in every frame with lights, because the thread that draws skips the dispatches of a pipeline that is still building. The uploads happen only when the lights or the view change.
- The counting and writing steps test each tile only against the lights that reach the workgroup's slice. On the Mac's GPU the three dispatches for S3's 256 lights take about 0.23 ms that way, against about 0.31 ms with every light tested.
- WebGPU's first frame builds the pass's three pipelines whether or not the scene has lights, so play builds none.
- The render crate's tests write a fixture of light grids for the `light-clusters` page. Linux's math library rounds tangents, logarithms and powers in its own way. So the fixture's parameters may differ from the Mac's by a millionth of their size. The counts, lights and grids must match exactly.
- A listed light's last word holds its first tile of the shadow atlas plus one, and the grid writes that word for every light that it lists. A rectangle or tube light holds its image's layer plus one there instead, because a point or spot light's decay, cone and tile mean nothing to an area light ([`VisibleLight::area`]). So only the lights that take a tile are marked, in `ShadowTiles::mark_lights`: the atlas holds tiles of point and spot lights alone. A mark of any other light wipes an area light's layer. The shader reads the wiped 0 as "no picture", so the area light's picture never reaches a frame.

## Writes that skip a mark

- Development builds report E1110 for a static object whose position, rotation, scale or bounding sphere changed without a setter. They check before each transform update, the late one included (M1-B5, #93, #84, #164).
- They also report a row of a static instance, sprite or point batch that changed without `markDirty` (M2-R6). The core's update of the batches clears their marks, so the check runs right before it, after the late update. It reads the marks through the batch field `DIRTY_WORDS` of `batchArrays`.
- The check of objects reads every static object in each frame. Rows can number hundreds of thousands, so the row check takes turns: it hashes at most 8,192 rows of each batch per frame (`ROWS_PER_CHECK`). In Bun on the MacBook Pro, a check of every row of a batch of 100,000 rows takes 1.4 to 1.5 ms. The slice takes 0.18 ms. A cheaper hash does not change the time. A row's hash may change between its turns, after the core has cleared a mark. So in each frame the check adds the core's marks to marks of its own, one bit a row, and clears a row's bit only when it hashes that row. A row marked and then written again without a mark before its turn goes unreported. That is the price of the bounded time.
- Line batches are left out. Their `markDirty` counts points, while the core marks segments, and the row arrays hold points. A check of them would need its own map from points to segments.

## Raycasts and overlap queries

- Every query checks its input in every build, in `packages/engine/src/scene/queries.ts`. Most API checks run in development builds only. Without them, bad query input can abort the engine in a production build, so these checks stay. [D-30](decisions/D-30-scene-queries.md#the-cost-of-the-input-checks) gives their cost.
- A ray with NaN parts passes every four-box test, empty boxes too. So does a ray whose origin is infinite in 32 bits, and a box that reaches infinity. A walk that trusts the box test then takes the empty child word, `u32::MAX`, as a node index, and the panic aborts the engine. So the walks in `crates/null3d-core/src/bvh/mod.rs` skip empty child words, whatever the box test gives. They stay safe for any input, and for a stored tree whose empty slots hold damaged boxes. Rows of sprites, points and lines take the same walks.
- `WorldRay::toward` makes a ray's unit direction in 64-bit floats. When the squared parts would round the length to 0 or to infinity, it scales the direction by its largest part first. A direction of the usual sizes gives the same bits as without the scale, so hits stay those of three.js.
- The static tree's sync looks again at the objects stamped in the frame of the last sync. A late update can move a static object right after a query in the same frame. The next frame copies that object's row without a new stamp, so a sync that looked only at newer stamps would keep its old box. Only a box or cell that changed refits the tree.
- A hit reports `uv`, the first texture coordinates of the hit triangle blended across its three corners, and `hasUv`. `hasUv` says whether that mesh has such coordinates at all (M3-A1). The triangle test already gives the barycentric weights, and a matrix keeps them. So the weights of a hit in a mesh's own space blend that mesh's uv values. three.js leaves `intersection.uv` undefined for a mesh with no texture coordinates. The engine writes into the caller's hit object and allocates nothing in steady state. So a hit reports the absence in a flag rather than in an absent field. The pair takes 3 of the 14 numbers in the hit record that a query returns.
- A pick reports the same pair, from a ray through the same point with the camera of the frame that recorded the pick. The id target names the source of the pixel, never its triangle, so the ray names the triangle and blends its corners. The core stores that frame's number when the pick's read lands, and `pickFrame` gives it to the sketch, so a later frame's camera cannot answer for an earlier pixel. A ray that meets another source, or none, leaves `hasUv` false rather than report a triangle that the pixel did not show ([D-166](decisions/D-166-gpu-picking.md#a-picks-texture-coordinates)).

## Input

- The sketch reads the input ring once per frame, in `packages/engine/src/sketch/input.ts`. It reads up to two kinds of event that follow a release of the pointer in the same frame: a press, and wheel scroll. Those events and every one after them wait for the next frame.
- A press waits so that a frame's drag belongs to one press.
- Wheel scroll waits because the controls ignore the wheel during a drag, as three.js's controls do. A frame that held a drag's release and the scroll after it would give the controls both at once. They would end the drag and drop the scroll, though three.js's controls, which see each event, dolly. The camera would then stay about 8% farther from the target than three.js's.
- On CI's software GPU the frames are slow, and Playwright's release, move and scroll often reach the same frame. Without the wait, the orbit controls test fails there, with the cameras 0.093 apart after the wheel. [Tests on slow machines](image-tests.md#tests-on-slow-machines) gives the runs with and without the wait.
- Scroll during a drag still counts in the frame that holds it, and the controls still ignore it there.

## Threads and shared memory

- Firefox before 145 has no `Atomics.waitAsync`. The sketch thread's first wait would throw there, so the engine would start but draw no frame. So there the sketch thread's waits end at wake messages (`shared/wake.ts`). The page sends them to the sketch worker, and the thread that draws sends them back through the port that brings it texture images. Any wake ends every wait, so each wait checks its slot again. Job workers block with `Atomics.wait` until the job system exists. `?wake=message` takes this path in any browser, and the browser tests also remove `Atomics.waitAsync` from every thread.
- A job worker without work blocks its thread in a wait (hard rule 5). When Safari stops a thread inside such a wait, it keeps the thread's shared memory until the tab closes, even across reloads. The engine therefore ends the job workers' loops before it stops them, and `destroy()` resolves once they have stopped.
- A page that goes away without `destroy()` stops the job workers inside that wait, because the browser then stops every worker wherever it is. Examples are a page in a frame that its parent removes, a reload, and a visit to another page. Such stops fill the iPad's room for shared memory within a run of the checks plan. The stats test pages leave their engines running, and the runner removes each page's frame. Safari on the iPad then refuses every later engine with E1109 until Safari is force-quit. In Safari on a Mac, each engine in a frame that the page removes while it runs keeps its memory. 35 starts work, the 36th fails after 34 s of tries, and the room stays at 0. Engines in frames that stop their engine first keep nothing: after 45 starts, the room goes from 37 to 36.
- So the page stops the job workers itself, synchronously, on `pagehide` and at the start of each stop (`page/stop-jobs.ts`). The sketch thread creates the job system. It then writes the addresses of the job system's wake word and stop flag into two control slots. The page holds the shared memory, so it can set the flag, add 1 to the wake word and notify it. That is what the core's own shutdown does. A parallel loop that runs at that moment finishes on the sketch thread, which runs every chunk that no worker claimed. With the wake alone, 45 engines in removed frames in each threaded mode mostly leave the room as it was. But a few runs lose 2 places: in low-latency mode once in 10 frames, with the sketch on the page once in 270. The browser stops the workers as soon as the page has gone, and a woken thread may not have left the wait by then. So a page that leaves also waits, for 100 ms at most, until no job worker is inside the job loop. Each job worker counts itself in a control slot while it serves the loop. With the wait, low-latency mode keeps its room over 200 frames. With the sketch on the page, two runs of 100 frames lose 1 and 2 places even with the wait. The reason is not known. So the `frame-restarts-*` checks leave that mode out.
- The core's shutdown cannot wait for the sketch thread to see the stop. A page that goes away never gives it the chance, and a stop would take one more hop between threads. Options rejected:
  - Job workers that wait with `Atomics.waitAsync` between frames. A wake through the worker's event loop takes longer than a blocking wait's, and the job workers wake several times in each frame.
  - A time limit on the blocking wait. Safari stops a thread inside a timed wait just the same.
  - Stopping the whole engine on `pagehide`. The browser can keep a page in its back-forward cache and show it again. That page would then show a dead canvas. With only the job workers stopped, it runs on, with their share of the work on the sketch thread.
- three.js has no worker threads or shared memory, so it has no such problem.
- A start can also stall in Safari, with every worker ready. The first engine in a frame on the iPad, drawing on the page's thread, can draw no frame within 20 s. In Safari on the Mac, about 1 start in 190 in frames does the same, in pipelined mode. In both, the sketch thread starts its setup, and no later step comes. That setup waits for the thread that draws to take each setup frame. The stall comes and goes: 120 such starts in a row can pass. A report of WebKit's own faults matches it. A worker's `Atomics.waitAsync` can stay pending after the notify that should end it. A second notify does not end it either. It ends once the worker's event loop turns for another reason, such as a timer or a message. The report, [libid-org/tlsn#10](https://github.com/libid-org/tlsn/pull/10), counted 9 such stalls in about 102,000 waits. It used Playwright's WebKit on Linux.
- In the single-threaded build the control block is plain memory, which `Atomics.waitAsync` refuses. A wait of a start there waits for the 50 ms timer alone. Hold mode waits so for the built-in room's generator, which counts among the images once its code has loaded.
- So each wait of a start races its `Atomics.waitAsync` with a 50 ms timer, and then checks its slot again (`slotChangeOrRecheck` in `shared/wake.ts`). These are `reached` in `sketch/runner.ts` and the wait for texture images. A start waits a few times, so the timers cost nothing that shows. Options rejected:
  - A time limit on `Atomics.waitAsync` itself. WebKit ends a timed-out wait through the same deferred work as a notify, so the fault can hold it too.
  - The same timer in the frame loop. It would make a timer and a promise in every frame (hard rule 1). Runs of many minutes on the iPad and the Mac have shown no frame loop that stopped.
  - A timer that fires all the time while the engine runs. It would wake the sketch thread when it has nothing to do, on battery too.
- When a start in a frame stalls, the restart page records the frame's own steps and the engine's control slots. The slots tell whether the thread that draws never took the frame (`FramesTaken` below `FramesPublished`) or the sketch thread missed the wake. Each removed frame also records how many job workers were still in the job loop as its page left. Over the 120 starts in frames, none was.
- A browser frees the GPU objects of a stopped worker only when it collects them, and Safari does that late. An iPad runs out of GPU memory after about 400 test pages when each stopped engine's worker keeps its device. So `destroy()` first asks the worker that draws to stop drawing. That worker destroys its textures, its buffers and its device, or loses its WebGL2 context, and then answers. The restart browser tests count each thread's GPU objects (`tests/lib/gpu-ledger.ts`), and fail when a stopped engine still holds one.
- Safari frees some GPU memory later than Chrome does. Destroying a WebGPU device frees none of its textures and buffers: only their own `destroy()` does. A canvas keeps its display buffers, of its size, after `unconfigure()` or a lost WebGL2 context, until Safari collects the context. The engine itself makes only about 2.5 MB of GPU objects for each start of the restart page.
- The restart page starts and stops WebGPU engines in Safari on a Mac. Without the release below, each leaves about 3 GB of GPU memory in the tab's footprint. After 20 starts the tab holds 60 GB, and closing the tab frees it. After the full checks plan, the iPad's restart checks then fail at their first start. After a short plan, they pass.
- A resize while the context holds the canvas replaces the display buffers at once, except the buffer on show. Safari keeps that one until the canvas shows another frame. So a stop shrinks the canvas to one pixel, shows a blank frame and waits two frames, for 100 ms at most. Then it gives up the context and gives the canvas its size back (`gpu/canvas-release.ts`). With that release, the tab stays under about 2 GB over 20 starts in each WebGPU thread mode.
- The GPU ledger counts what Safari keeps. A device's textures, buffers and query sets count until each is destroyed. A canvas counts until its display buffers and its frame on show measure one pixel. So Chrome's restart tests fail when a stop leaves a canvas's buffers behind.
- The restart browser tests count the memories and workers that the page still reaches, with Chrome's `Runtime.queryObjects`. DevTools holds each object that such a count returns until the test releases the count's handles. A count made a moment before the page lets go of a stopped engine's memory and workers keeps them alive. Each later count then finds them again. The test of a start whose drawing fails meets this. On the Mac, with 9 tests at once, it fails 1 to 3 times in 50 that way. So each count puts its handles in one group and releases the group (`reachable` in `tests/image/restart.spec.ts`). The tests also collect garbage and count again for up to 20 s. A worker that has just stopped can hold its objects a moment longer, and CI's machines are slow. With both, 50 of 50 pass on the Mac. CI can still fail the test in sketch-on-the-page mode, with the memory and all 3 workers held after 10 s. So a test that still finds them takes a heap snapshot and names the chain of references that keeps each one alive (`tests/lib/heap-retainers.ts`).
- A thread that fails while the engine starts ends the start. An example is the thread that draws, when the GPU has no memory for a texture. Otherwise the start waits for frames that never come, and the page never gets an engine to stop. Then Safari keeps the engine's shared memory until it quits, because the job workers wait inside a blocking wait. So a failure that a thread reports ends a start under way. A job worker that did not start is the exception. A frame loop on the page reports the error that ends it (E1404). In a worker, that error reaches the page as the worker's failure.
- After the start, every thread's loop reports the error that ends it as E1404 ([D-58](decisions/D-58-failure-handling.md)). A loop without a `try` lets a trap in the core stop the frames with no report. A worker's own `catch` also keeps the error from its `onerror`, so a job worker that failed would go unheard. So a worker posts a `fault` reply, and the page reports it.
- A job worker that dies inside a chunk never counts the chunk as done, and the sketch thread's `parallel_for` spins until it is. With the sketch on the page, that hangs the tab. Each job worker marks the chunk it holds. Its own thread then calls `jobWorkerFailed`, which counts the chunk as done and failed. The wait ends with the core's panic, which the sketch thread reports. A stop flag alone cannot end the wait: live workers may still run chunks whose closure the caller would free. The failure test makes the core's clock throw in job worker 0, which kills it inside a chunk as a trap does.
- A stop stores 1 in the job system's ready slot and 2 in the pause slot before it wakes them. A thread that read the old value just before the stop finds it changed when it goes to wait. So it never sleeps through the stop.
- A canvas moved to a worker cannot come back to the page, and a second `transferControlToOffscreen` throws. So the worker that drew keeps the canvas after its engine stops, without the core and the GPU device. The next engine on the canvas sends it a new start without a canvas. It stays while the canvas is in the document; a `MutationObserver` ends it when the canvas leaves, and a `FinalizationRegistry` when the browser collects the canvas.
- A checks run on BrowserStack's iPhone 16 (iOS 18.6) or iPhone 17 (iOS 26) runs out of room for the engine's memory with parked workers. Safari refuses the memory with E1109 after about 10 engine pages, and then on every engine page, for minutes. The iPhone has room for about 9 such memories. Each test page stops its engine, and then the runner page removes its frame. Without canvas reuse, the iPad runs 833 pages of the plan with a room of 6 and no E1109. The restart checks do not stop an engine and then remove its frame. The restart pages remove each canvas after its stop, and the frame restart pages remove frames whose engine still runs.
- A parked worker can keep the stopped engine's memory in two ways. The page's `Worker` can keep the stopped engine's message handlers, whose closures reach the engine and its memory. In the worker, the drawing host's promise of the start can settle with the stopped drawing, which holds the memory. Chrome's heap counts show both. The engine drops both, so each parked worker's heap holds no stopped engine's memory. The page itself keeps the last memory for its next engine ([D-98](decisions/D-98-memory-pool.md)), and the restart tests count that one.
- Safari keeps the memory even so. It frees a shared memory only after each thread that used it has collected the objects that refer to it. An idle worker allocates nothing, so it never collects, and a refusal on the page collects only the page's heap. In Playwright's WebKit, each parked worker keeps its engine's memory with no reference left. The room falls by about 1 for each engine on a kept canvas, and stays down. A churn of about 400 MB of garbage in each parked worker brings the room back; 16 MB and 64 MB do not. A worker that ends gives the memory back at once.
- So the page ends parked workers when the room is needed. The first refusal of a new engine's memory ends every parked worker whose canvas no engine is starting on. The loader's later tries then find the memory freed. In Playwright's WebKit, with a room of 38, 42 starts on kept canvases pass, and 42 more in a second round. The page also ends its parked workers on `pagehide`, as a page in a removed frame gets: such a page can draw no engine again. A canvas whose worker ended this way fails a later engine with E1419, which names why.
- Playwright's WebKit keeps the memory of every engine in a removed frame, whether the engine ran or stopped, with or without canvas reuse. Safari does not: the frame restart checks pass in CI. So only Safari on a device can check the frames.
- A start waits for the engine that holds its canvas, or the page's core, when that engine is stopping or still starting. It takes the canvas in the same task as it finds it free. A start that takes it one task later lets React's pattern of three starts in a row put two engines on one canvas.
- Frame numbers live in 32-bit control slots and wrap after about 4 billion frames, a kiosk's 207 days at 240 Hz. Compare two frames only with `frameAfter` or `frameReached` (`shared/control.ts`), or `frame_after` in the core, and step them with `nextFrame`. A plain `<` fails once the count passes 2^31, where the slots read negative. The count skips 0 and -1, which mark "no frame yet" and "none", so code may still test those two values with `===`.
- The rule holds for every frame number the engine keeps, not only those in the control slots. Examples are the frame whose list released a texture's image or created a pipeline. Another is the frame stamped on a changed row. Ask "did frame A come before frame B" with `frame_after`, or with `built_by` (`pipelines.rs`) for pipelines. Step to the frame before or after with `previous_frame` and `next_frame`. Never use `+ 1`, `- 1` or `wrapping_add(1)`, because these do not skip the two marks. A plain step fails just after the wrap. The check, after a GPU loss, of which images the thread that draws still holds would drop images that the thread still holds. The copy of last frame's changed rows into the other buffer would leave old matrices in that buffer. Each place that steps a frame has a unit test that runs across the wrap.
- Image ids follow the same rule. The texture store steps them with `next_frame`, so they skip 0, which the WebAssembly glue returns for a failure. The thread that draws puts the newest id it received in the images-arrived slot, in place of a count, and the sketch thread waits with `frameAfter`. A count from `Atomics.add` would pass through 0 and -1, and so get out of step with ids that skip them.
- With `sketchThread: 'main'`, the page starts a core of its own in the engine's shared memory. A start can end during that step, for example when the page cancels it. The page's core then still starts, and with nothing to release it, the page would keep the engine's memory. So the start releases that core once it has started.
- The single-threaded build's core runs on the page. The page keeps it for the next engine, and `destroyEngine` empties it when an engine stops.
- With `sketchThread: 'main'`, the page's core holds the draw lists that the render worker replays. A stop can come while the render worker is inside a frame, after it found the frame's list. So the page calls `destroyEngine` only after the render worker has stopped. Called first, it frees a list that the replay still reads. CI then fails with E1404 about once in 250 page loads ("draw list is truncated"). The restart browser tests hold the render worker inside a frame until the stop, and fail when the core frees the frame's list.
- Safari reserves each shared memory's whole maximum in one address range, which the page and its workers share. It also counts the memories' pages against a budget. A stopped engine's memory counts until the engine's workers have finished, which Safari does a moment after `destroy()`. On a slow machine the next engine can ask for its memory before that. Safari tries one collection and then refuses with "Out of memory", as the restart checks see in CI. So `createSharedMemory` in `page/loader.ts` waits and tries again, for about 10 seconds in all, before it fails with E1109. The error says how many tries it made and how long they took. Tries of about 3 seconds are too short. On a TestingBot iPhone, three pages in a row can fail that way during a checks run before the next pages start again. A new engine first takes the memory that the page kept from a stopped one, and then asks the browser for nothing ([D-98](decisions/D-98-memory-pool.md)).
- Safari gives a shared memory back only after a full collection finds each object that refers to it unused. Its sweeper must then reach those objects. A refused memory runs a full collection but no sweep, so Safari's second try fails too. The sweeper then works in short slices, and each new collection starts it again.
- With `?render=main`, the page holds views of the engine's memory, so the memory also waits for the page's sweep. On CI's Mac that takes seconds. Safari can refuse a start for more than 3 seconds, and 6 seconds after the last stop the room can still be missing. The page reaches none of the stopped engines' memories, and the room comes back later. The engine keeps nothing alive: Safari frees the memory late.
- The restart checks therefore wait before they judge. A start that Safari refuses waits and tries again, for 30 s in all on one page. After the last stop, the page counts the room again after longer and longer pauses until it comes back, for 91 s in all.
- A count that the browser refused ends with one more memory, which Safari refuses too. The collection that the refusal runs finds the counted memories unused, and Safari then frees them, though not always before the next count. Without it, one count's memories take the room of the next count. That fails the single-threaded check, although that mode gives no worker a shared memory. A count that reached its cap asks for no more, since the browser would grant it.
- A production build can load an engine module twice in one thread. The sketch worker's file holds one copy, and the page's file that a sketch imports holds another. Module state that the thread sets reaches one copy only, and each copy has its own classes. Keep state that every copy needs on `globalThis` under a `Symbol.for` key. For `instanceof`, mark a class's objects under such a key and check the mark in a static `Symbol.hasInstance`, as `errors/engine-error.ts` does.
- Safari runs a module worker's entry file again when another file imports it (WebKit bug 324459). Chrome and Firefox reuse the running module. A production build puts the code that a worker shares with its later files into the worker's own file. Those files then import it from there. In low-latency mode, the sketch worker loads the renderer's file, which imports the sketch worker's file.
- A second run of a worker's file replaces its message handler with one that has no state. The page's messages to the sketch then go nowhere. Each worker therefore starts through `startWorker` in `workers/protocol.ts`, which starts it on the first run only. Apart from that call, a worker's file must have no effect when it runs.

## Views of the shared memory

- When the WebAssembly memory grows, `memory.buffer` returns a new `SharedArrayBuffer` object. Each typed array made before the growth keeps the old object alive. All these objects point at the same memory, but Chrome's page memory figure (`performance.measureUserAgentSpecificMemory`) counts each one at its own length. A stale view thus adds a full copy of the memory to the figure of the thread that keeps it. The copy is the memory's size when the view was made.
- A small test page shows it. For a worker that keeps one small view from each of 10 growth steps of a 20 MiB shared memory, Chrome reports 165 MiB. Without the old views it reports 20 MiB.
- The engine's memory grows in many small steps while a sketch sets up its scene. Objects that the sketch writes once and then leaves alone would keep views made at older sizes. Examples are static instance batches and the setting blocks of the sky and the effects. In the Battle comparison, 11 such objects on one 63 MiB memory make Chrome charge the sketch worker 420 MiB. Its own heap is 22 MiB. Chrome then reports the page at 450 to 600 MiB, while the real memory is about the same as three.js's.
- So no code keeps a view of the shared memory across a growth (hard rule 20). Code gets its views from the one place that makes them, and every holder drops its views when the memory grows.
- Before you report a memory figure from Chrome, check it. Take a heap snapshot of each thread and count its `SharedArrayBuffer` objects: each thread should hold one per memory. Also compare each worker's figure with the memory's size plus the worker's own heap. Chrome also counts the one shared memory once in each thread that holds it ([D-116](decisions/D-116-stats-overlay-figures.md)). The overlay's "counted once" figure corrects only that.
- The one place is `shared/memory-views.ts`. A `MemoryViews` wraps one WebAssembly memory on one thread. `view` makes a view for use within one call. `heap` keeps one view of the whole memory per typed array class, and makes it again after a growth. `bytes` gives the memory's size, so no code needs the buffer for that. The sketch's `CoreMemory` extends it. The render worker's frame replay, the page's stop of the job workers and its pool of kept memories use it too, and so does the meshopt decoder for its own memory.
- An object that keeps views between calls implements `ViewHolder` and calls `holdViews(this)` on the memory. The memory holds each holder weakly. When it sees a growth, in `grown`, it steps its generation and calls each live holder's `dropViews`. The holder then forgets its views, keeping empty arrays in their place, and makes them again at their next use. The sketch's refresh after each core call that can grow the memory calls `grown`, and so do `heap` and the read of a world matrix. Holders: the scene, instance, sprite and line batches, the background, environment, post and effect blocks, the queries, the animation table, debug drawing and `CoreMemory` itself.
- Some core arrays move inside the memory without a growth. The scene's arrays move when the scene grows. The animation table's arrays move when it grows or makes its joint overrides. The new arrays can fit in free memory, so the memory does not grow. The core counts each such move in one word (`ARRAYS_MOVED`, read through `arraysMovedAddress`). `CoreMemory.refresh` steps the generation when the count changes. So every core call that gives a viewed array new memory steps the count. A holder also sizes each view from the core's current capacity, never from a start figure. A growth of the animation table that misses either rule lets the animator write into freed memory. It also puts objects past the 1,024th out of its views ([D-158](decisions/D-158-growable-animation-table.md#views-follow-the-grown-table)).
- `dropViews` is a member of the exported `ViewHolder` interface, so the built declarations must keep it. It must not carry an `@internal` tag, because the package build strips such members (`--stripInternal` in `tools/lib/packages.ts`). The emitted class would then implement `ViewHolder` without `dropViews`, and a consumer's type check fails with `error TS2420`. The static check fails on a holder that marks its `dropViews` `@internal`, and `bun run test:packages` checks the built declarations.
- wasm-bindgen's glue keeps views of the memory too, for passing strings and arrays. It makes them again only at its next such call. So a view from before a growth keeps the old buffer object, as the browser test shows in the sketch worker. So the build adds `dropMemoryViews` to the threaded build's glue (`addReleaseInstance` in `tools/build-wasm.ts`), and `CoreMemory` calls it at each growth. `MemoryViews` also tells a growth by the memory's size, so it keeps no buffer of its own.
- A static check enforces the rule: `bun tools/check-memory-views.ts`, which `bun run check` runs, and so CI's checks job. It reads the TypeScript types of `packages/engine/src`, test files left out, so it finds a memory however the code names it. It fails on:
  - code outside the accessor module that reads a WebAssembly memory's `buffer`, by a property, an index or a destructuring;
  - a view made around the buffer of a view that the accessor made;
  - a class that stores the accessor's views on itself without implementing `ViewHolder` and calling `holdViews(this)`.
  A view in a local variable, or one that a function returns, passes. `tools/lib/memory-views.test.ts` checks each case on small programs. The check reads the engine only, so a bench page or a test sketch can break the rule without it seeing. S1's page adds particles, passes and setters after its batches, and its memory grows. A switch such as `decals` that read a batch's rows once at setup would then write through a stale view in every frame. So read the rows inside the frame step, as the swarm's switches do.
- A browser test enforces it at run time: `tests/image/memory-views.spec.ts`, in CI's browser jobs on Chrome. Its sketch sets a static instance batch, the sky, the sky's environment, bloom and the vignette once. It then grows the memory in 24 steps, each a batch of 16,384 rows written once, and the test needs at least 8 growths. The test takes a heap snapshot of the page, the sketch worker and the render worker. It fails when any of them holds more than one `SharedArrayBuffer` object over one store of memory, and names what keeps the extra objects. It then fails when Chrome's figure for either worker (`performance.measureUserAgentSpecificMemory`) passes the memory's size plus the worker's own heap plus 16 MiB. The page measures through `measurePageMemory`, which releases idle job workers while Chrome measures. On SwiftShader, whose headless browser offers no page measurement, the test checks the heap snapshots alone. The guard also scans browser tests, where a direct call can bypass the release helper.
- Playwright's sessions reach pages only. `tests/lib/shared-buffers.ts` reaches the workers through the page's session: it attaches to them without flattening and sends each command inside `Target.sendMessageToTarget`.

## Addresses above 2 GiB

- WebAssembly memory addresses are unsigned 32-bit numbers, and a memory can reach 4 GiB. The engine's maximum is 1024 MiB by default, and a page may raise it to 4096 MiB ([D-04](decisions/D-04-memory-maximum.md)).
- wasm-bindgen returns `u32` values as unsigned numbers. An address that passes through a signed array does not stay unsigned. For an address at 2 GiB or above, `Atomics.load` on an `Int32Array` returns a negative number. A view made at that offset then points outside the memory. So does a word index made from it with `/ 4`.
- The engine passes such addresses through the shared control slots (`Int32Array`). The render worker reads the draw list's address there (`render/scene-renderer.ts`), and the page reads the job workers' wake, stop and yield addresses (`page/stop-jobs.ts`). With the default maximum every address stays below 2 GiB, so no run has shown the fault.
- Every such read converts with `>>> 0` (M2-R37). The static check `tools/check-address-reads.ts` refuses a read that lacks the conversion, and `bun run check` runs it. The browser test `tests/image/signed-address.spec.ts` asks for a 4096 MiB maximum and grows the engine's memory past 2 GiB. It makes the draw list move above 2 GiB, then draws and stops the engine on WebGPU and WebGL2.
- Above 2 GiB, a view made at a signed offset fails with "Start offset -2147422160 is outside the bounds of the buffer". The scene then stops. Neon Harbour's 3D scene reaches such an address after about 10 minutes. Without the conversion, its page then keeps presenting frames with a frozen image ([D-172](decisions/D-172-neon-harbour-follow-ups.md)).
- So convert every address read from a signed array with `>>> 0` (hard rule 31), and prefer unsigned arrays (`Uint32Array`) for new address slots. `Atomics` works on both.

## Measuring the page's memory

- Chrome's `performance.measureUserAgentSpecificMemory` answers only once every worker of the page has run the measurement as a task, or after about a minute. An idle job worker blocks in the job loop (`memory.atomic.wait32`), so it never runs the task.
- Night town's comparison pages start 2 to 16 job workers at 1,020 lights, and measure their memory twice. Without the yield below, each page with job workers takes about 120 s longer, or never answers. Polled every 10 s, the page's own thread and every worker stop answering together while the measurement waits. Without the measurement, the same pages answer in 3 s. Pages without job workers answer in 3 s with it.
- So while a measurement runs, the page adds one to the job system's yield word (`yieldJobWorkers` in `packages/engine/src/page/stop-jobs.ts`, at the address in `Slot.JobsYieldAddress`) and wakes the job workers. While the word is not zero, an idle job worker leaves the loop with `LoopExit::Yielded` in place of blocking. It waits for the next frame job with `Atomics.waitAsync`, for at most 4 ms, so its thread runs the measurement, and then serves the job system again. The sketch thread runs every chunk that no worker takes, so no frame waits for a worker that is away.
- The measurement's yield helpers also get their short-lived views from `MemoryViews`. A release makes a fresh view, because memory can grow during measurement. The worker returns the asynchronous wait directly, so no suspended function keeps its view. The static check above refuses a raw buffer read in these helpers too.
- Every measurement goes through `measureWithEveryThread` (`packages/engine/src/shared/page-measurement.ts`), which holds each engine's release while the measurement runs. The stats overlay's samples, `engine.measure`'s heap samples and `measurePageMemory` use it. A unit test fails on any other call (hard rule 24). `tests/image/memory-measurement.spec.ts` starts job workers with a busy scene and checks that a measurement answers within 30 s while the page answers, and that the open stats overlay shows the figure as soon. Without the eager flag, Chrome answers at its next garbage collection: up to 17 s on the Mac.

## The memory register

- The stats overlay's `Memory by system` rows come from a register that each table fills on demand ([D-233](decisions/D-233-memory-register.md)). The page asks the sketch thread for a report while the card is open, in a development build. The sketch publishes three numbers per area in the metrics buffer's header, beside the memory figures.
- A report walks the tables and sums `Vec::capacity` and `Vec::len`. It allocates nothing and runs a few times a second at most. Nothing runs while the card is closed, so a shipped page pays only the bytes of the code.
- The areas, in the overlay's order, are in `crates/null3d-core/src/memory.rs` and `packages/engine/src/shared/memory-area.ts`. Adding one means a constant and a name at the same place in both files, and the table's `account` call.
- A table that keeps memory across frames reports what it holds now. An allocator that reuses its memory every frame reports its high-water mark itself. `UploadArena` records the previous frame's fill when it resets. A quiet frame then still shows the busiest one.
- A scene growth keeps its old world buffers for two frames, so a report in those frames counts both. That is real memory, and it leaves the figure by the third frame.
- Measuring a page's memory against D-130's method: run the scene at two sizes and divide each row's growth by the objects between them. The rows that D-130 named reproduce its figures ([D-233](decisions/D-233-memory-register.md) has the Battle numbers). The rows add up to about half of the WebAssembly memory's growth, because that memory never shrinks. The buffers that a table replaced while it grew stay in the heap, and no live table reports them. Read the rows for what the tables hold, and the engine memory figure for what the heap holds.

## Frames in flight

- When the GPU falls behind, every browser but Safari on WebGPU lets frames queue on it. On the GPU-bound page, Chrome and Brave slow the drawing worker's frame callbacks to the GPU's pace, yet keep 5 to 8 frames queued. Safari's WebGL2 path keeps about 4. Firefox keeps presenting at the display's rate and queues up to 89 frames, seconds of input lag. [D-11](decisions/D-11-frames-in-flight.md) has the figures.
- So the completion tracker (`gpu/completion.ts`) tracks every frame, and the thread that draws takes no new frame while two are unfinished (`Presenter.due` in `render/loop.ts`). In the render worker, the sketch worker then waits on the frame-taken counter, so the hold needs no message.
- Each tracked frame costs one browser object, the queue's promise or the fence, and two clock readings. `bun run bench:allocation` budgets them.
- The tracker learns of a WebGL2 fence only when it checks, at a frame callback. Frames that it finds finished together share the time since the last completion. Firefox can settle several WebGPU promises in one task, at one clock reading, which gives a frame an interval of 0. Such an interval still counts toward the completed rate.
- A frame whose completion never arrives is given up and stops counting as in flight. So a lost signal slows the drawing without stopping it. The GPU works on the oldest unfinished frame from the latest of three times. They are its submit, the latest completion, and the moment the tracker gave up the frame ahead of it. From then, that frame counts for at least a second. On a slower GPU, it counts for four of the slowest GPU frame times of the last eight completions. Each frame given up since the latest completion doubles that time for the next, up to 8 times the undoubled time. With no completion at all, the tracker gives frames up at 1, 3, 7 and 15 s, then every 8 s. A limit of twice the latest interval between completions would let up to four frames wait when a quick frame comes before a slow one. The unit tests in `gpu/completion.test.ts` feed the tracker such frame times, like those of CI's software GPU.
- The tracker never lets through a frame that it cannot track. It has 8 slots. While all 8 hold frames, it counts them all, until it gives the oldest up and frees that slot. A frame that the GPU finishes after its slot was freed leaves no record.
- Two rules would let the limit fail open when the GPU takes seconds over the first frame. One gives up at once every frame that has waited a second since its submit. The other lets the thread that draws take any frame that finds no free slot, untracked. CI's software GPU builds a frame's pipelines while it draws it, and on a busy runner S4's first frame takes 4.3 s. Two frames go in each second meanwhile, and they fill the 8 slots. Every later frame would then go untracked, at up to the display's rate. A preset check round then measures 60 frames presented a second and none completed. The GPU then spends 5 to 15 s on that backlog while the thread draws nothing, and the benchmark's 8 measured seconds count no frame. That fails S4 on WebGL2 in `bench/tests/pages.spec.ts` in 2 of about 120 CI runs. In a Linux container with 2 cores, 3 of 24 runs of S4's and S5's WebGL2 pages measure no frame. Tracking every frame while giving one up each second is not enough. A 7 s first frame then lets 7 frames queue, and 3 of 24 runs measure no whole second. With the doubling, 69 runs pass, 36 of them on WebGL2. The unit tests check both rules. A 4.3 s first frame and then 0.7 s frames let 4 frames wait at most, and two from the 8th second on. With no completion for 60 s, a tracker that fails open lets 965 frames through in its first 20 s and tracks 8 of them. This one lets 11 through and tracks each.
- Firefox settles WebGPU's `onSubmittedWorkDone` about a frame after the GPU finishes, so the limit holds back frames that are already done. That costs Firefox's WebGPU path frame rate when the GPU is busy. Its WebGL2 path loses none.
- Without the limit, Chrome's slower frame callbacks also slow the refresh meter of the thread that draws. It reads 36 Hz on a 144 Hz display. With the limit, the callbacks keep the display's rate, and so does the meter.
- Apple's GPUs work on two frames at once. A frame's GPU time from timestamps can then exceed the time between completed frames.

## A hidden canvas and the display's rate

- Android chooses the display's refresh rate from what the apps send to the screen. On the Galaxy S24+ with Motion smoothness at Standard, the display can run at 10, 24, 30, 48 or 60 Hz. When Chrome sends new frames often, Android keeps 60 Hz. When Chrome sends only a few frames a second, Android rates Chrome's layer as rarely updated and can lower the display to 24 Hz. Chrome's frame callbacks follow the display, on the page's thread and in workers alike, so every frame then comes 41.7 ms apart.
- A canvas that a worker draws, hidden under an opaque element, changes nothing on the screen. Chrome then sends the screen 1 to 5 frames a second, however fast the worker draws. A canvas that the page's thread draws keeps Chrome sending up to 60 frames a second, even when hidden.
- The device runner's report lies over each test page in the plans that check results. The engine page's check limits the median time between frames to 34 ms. With the report over that page, the worker modes fail the check now and then on the S24+, with every interval at 41.7 ms. The low-latency mode fails most, because it often runs just after another hidden worker page, while the display is already at 24 Hz. Two builds run that way passed 8 of 16 runs and 5 of 8.
- Evidence, from the S24+ in Chrome 154:
  - SurfaceFlinger's mode history put the display at 24 Hz during each slow page. It went back to 60 Hz when a page that draws on the page's thread ran.
  - A phone trace of a slow run, with Perfetto's frame timeline and SurfaceFlinger's layer votes, showed Chrome's layer at 1 to 5 frames a second. From 5 seconds in, Android voted "Min" for it. The render rate and the app's vsync then ran at 24 Hz for 22 seconds. In runs that held 60 Hz, the same few frames got the vote "Max (can't resolve refresh rate)". So the outcome was a race.
  - With the report over the page, 7 of 8 worker-mode pages in one run were slow, and 5 of 6 in another. 4 other runs had none. With the report under the page, 23 of 23 engine pages in 3 runs held 60 Hz. The trace then showed up to 60 Chrome frames a second.
  - As the display changed, the page's thread and the drawing worker both moved to 41.7 ms between frame callbacks, in the same half second. Each frame took about 1 ms of CPU. It finished on the GPU before the next callback, so no frame waited for the limit on frames in flight. So the engine did not cause the slower rate, and it measured 24 Hz correctly.
  - In Chrome on the Mac, both worker modes held 60 fps with the page's thread slowed 1 to 20 times. A Mac display does not change its rate with the content.
- So a plan item whose check times frames (`timesFrames` in `tests/lib/runs.ts`) keeps its frame over the report. The engine page's items set it. With the frame over the report, 4 runner runs on the S24+ pass 80 of 80 pages, among them 48 low-latency pages. A unit test in `tests/lib/runs.test.ts` fails when an engine check in such a plan would run under the report.
- The runner page's own reading of the refresh rate has the same fault. It can time frame callbacks while the screen does not change, after a few changes of the report. On the S24+ such a reading gives 24 Hz for 2 of 35 pages. So while it measures, the runner page changes its report's background by one shade on every frame. It starts the timing after half a second. [Devices](devices.md#a-display-whose-refresh-rate-changes) has the figures.
- The engine needs no change. A user's canvas that is on screen keeps the display at its full rate. A canvas that the page covers draws frames that nobody sees, at the rate that Android then chooses. Once the canvas shows again, its frames reach the screen, and Android raises the rate within about a second.

## Captures

- A capture draws the frame that the thread that draws took last a second time, into an offscreen target, and reads it back. It must not do that as soon as the request comes. On a slow GPU the readback holds the thread up: CI's software GPU takes about 1.2 s for each WebGL2 readback. A page that captures back to back would then send its next request before the frame loop has a turn. Every capture would then replay the same frame. In single-threaded mode on WebGL2, a whole capture runs without giving the thread back. There, captures back to back would give the same frame on any GPU.
- So a capture first waits for the frame loop to take a new frame. It checks in the thread's own animation frame callbacks. The loop asked for its callback first, so in each refresh the loop takes and draws any frame that is ready before the check runs. The wait never blocks the thread, and the frame loop keeps its pace.
- The wait ends at once while the engine is paused or stopped, and in hold mode, since no new frame comes then. It gives up after 120 callbacks without a new frame, as when an error stopped the sketch. The capture then gives the frame taken last. A hidden page runs no callbacks, so its capture waits until the page shows again.
- `capture()` waits on the thread that draws, as every capture does, and not on the page's thread.
- Hold mode draws its frame on the canvas, and once more for the pixels that the start reads back. A further draw for each `capture()` can fail on a heavy frame. On the owner's iPad in Safari 26.6, the visual check page's "reference" scene can give E1414 ("map async was not successful") that way. That scene has the heaviest frame of the page: 4096-pixel shadow maps and the widest shadow filter. The page captures 6 engines before it, and the same page can pass in the next run. The readback code has no race. Each readback maps a buffer of its own once, and destroys it after the unmap. The page stops the engine only after the capture. The likely cause is the GPU failing that one frame's work, from too little memory or a GPU time limit. The page's stop right after the failure also silences any loss report.
- So `capture()` in hold mode encodes the held frame's pixels, which the page keeps, and the GPU draws nothing more. A browser test loses the GPU after the hold and still gets the held image from `capture()`.
- Safari gives the same "map async was not successful" for every failed map, so the message named no cause. A WebGPU readback makes its texture, its drawing, its buffer and the copy inside an out-of-memory error scope. When the map fails, the error names an allocation that ran out of memory, or else a loss of the device with its reason. The loss can come just after the failed map, so the readback waits briefly for it. Unit tests in `gpu/readback.test.ts` give a fake device each failure.
- The back-to-back capture test runs in every thread mode on both GPU paths. Without the wait for a new frame, it fails in all 10 on the Mac's GPU and in all 10 on SwiftShader. Each gives the same shade 6 times, such as 84, 84, 84, 84, 84, 84. With the wait, all 10 pass on each set, and so does the held-frame test after a GPU loss, on WebGPU and on WebGL2.

## Draw-list readback

GPU picking copies its small id target into a buffer (`CopyTextureToBuffer`), then reads the buffer back into engine memory (`ReadBuffer`). A frame with a pick request emits both. The contract in `drawlist.rs` and the mock state and check these rules. With them the two GPU paths agree, and the core emits no list that WebGPU rejects:

- The copy reads an `RGBA8_UNORM` or `RGBA32_UINT` texture. WebGL2 copies with `readPixels`, whose required format and type give WebGPU's bytes for these two formats only. A half-float target, for example, reads back as 32-bit floats on WebGL2.
- The copy's buffer offset and bytes per row are multiples of 256, as WebGPU requires. WebGL2 would otherwise ignore the bytes per row and pack its rows tightly. So it sets `PACK_ROW_LENGTH` from them around the `readPixels`, and row `r` lands at the same place on both paths.
- The copy's x and y address texels as stored, as every other copy does. In a texture that a render pass drew, WebGL2's first stored row is the bottom row. So the code that emits a pick flips y and the row order on that path, as shaders flip their texture coordinates.
- A read's offset is a multiple of 8 and its size a multiple of 4, as `mapAsync` requires. The read names its control slot, the fifth word, and the backends read five words.
- A buffer waits from its read until the read's slot rises: nothing writes it, copies into it or reads it. On WebGPU, a copy into a buffer whose map is pending is a validation error, which drops the whole frame. On WebGL2, a backend that dropped a pending read when the next copy came would never land a pick made in every frame. Code that reads in every frame keeps a ring of buffers, one for each read in flight. The mock refuses any use of a waiting buffer until a test calls `finish_reads`.
- A capture replays a frame that the frame loop drew already. Its copies into buffers and its reads would land a second time, perhaps in memory that the sketch uses for something else by then. Both backends skip them while they draw a capture.

How each backend runs a read:

- WebGL2 puts a fence after the commands before the read. At the end of each later replay, it collects the reads whose fences have signaled, with `getBufferSubData`. The bytes pass through an array of its own, since WebGL may refuse a view on shared memory. A read never stalls on the GPU.
- WebGPU maps each read's buffer once the frame's commands are submitted. It copies the bytes into engine memory, unmaps the buffer, and only then raises the slot. So the code that waits for the slot can use the buffer again at once.
- Both deliver through one `ReadSink` (`gpu/readback.ts`), which the frame replay makes from its own memory views. Each backend keeps its read records in a pool, so a read in every frame allocates nothing of its own. The one exception is WebGPU's view of the mapped bytes.
- A WebGPU map fails when the buffer is destroyed during it, which drops the read on purpose. It also fails when the device is lost, which the loss path reports. A map that WebGPU rejects also raises a validation error, which the renderer's error watch reports in every build. Development builds also log each failure that is not a destroyed buffer's.
- `gpu/webgl2/backend.test.ts` and `gpu/webgpu/backend.test.ts` replay a copy and a read with fake contexts. They check the row spacing, the bytes in engine memory and one rise of the slot. They also check the skip in a capture, and the dropped read of a destroyed buffer.

The pick template (`pick.wgsl`) tests the scene's depth for equality. It has SKIN and MORPH builds. A custom material with a vertex offset has PICK builds of its own (`lit.wgsl`). So each object picks where it draws. On WebGL2 in Chrome on the Mac, two programs can place a vertex a rounding step apart, though both programs mark the position invariant ([D-43](decisions/D-43-webgl2-prepass.md)). So the pick pass needs a page that reads back its own picks on that path before it ships, as `pick.wgsl` says.

## Canvas size

- A canvas with no CSS size shows its drawing buffer at one CSS pixel per buffer pixel. On a screen with a pixel ratio of 2, each new buffer doubles such a canvas, and the resize observer doubles it again. In Safari 26.6 on a Mac, every WebGL2 start on the restart page then fails with E1404 (status 0x8cd6). The canvas grows from 600 x 300 to 9600 x 4800, where the multisampled targets are incomplete.
- So at its start the engine doubles the canvas's buffer for a moment and reads its computed CSS size. A side whose CSS size follows the buffer keeps the size it showed, as an inline style. A canvas that CSS sizes keeps its shape and gets no style.
- The drawing buffer stays within the GPU's largest texture: WebGPU's default limit of 8192, or WebGL2's `MAX_TEXTURE_SIZE`. A larger canvas draws at a lower pixel ratio, which `engine.viewport.pixelRatio` reports.
- CI's browsers run at a pixel ratio of 1, where such a canvas never grows. The browser tests run a project on a high-density screen to cover it.
- When the canvas changes size, the render graph makes its textures again under the same ids. A bind group that names one of them must be made again too, even when the id it names is the same. Take the occlusion culling pyramid's group. Made again only when its buffer grows or its depth target's id changes, it would still bind the destroyed depth texture after the canvas shrinks. WebGPU would then refuse the frame. Phones, where occlusion culling is on, meet this when the page or the screen turns. So the group is made again whenever the graph makes its textures again. A Rust test shrinks the canvas and checks that the group binds the new texture.

## Writes to storage in WGSL

- WGSL lets a store to one component of a vector in a storage buffer access the whole vector. A GPU may do it as a read of the vector, then a write of all of it.
- So two invocations that write different components of one `vec4` race, on any GPU, and one write can be lost. Give each invocation whole vectors of its own, or use atomics.
- The vertex shaders that read instance data by index (D-23) write one index per entry. With four 32-bit indices in each 16-byte entry, one per invocation, SwiftShader draws every image right, and Apple's GPUs lose writes.

## The splats add-on's chunk cut

- `chunkSplats` cuts a cloud on a grid over its bounds. So a splat's cell follows its position and the cloud's bounds alone, and one cloud always cuts the same way.
- Each axis takes as many cells as the cube root of the cloud's splat count divided by the target chunk load. A bigger cloud then makes more, smaller chunks, which is what lets a camera stream a cloud larger than its budget.
- An axis's cells are equal widths across the bounds, and the highest index takes the maximum itself.
- A width that multiplies by one cell fewer than the count makes the last cell a zero-width plane at the maximum. Almost every splat then falls into the first cell. A cloud of 100,000 splats then makes 4 chunks, one of them 99,997 splats, and a cloud of 400,000 makes 11, one of 56,557. Neither can stream.
- With equal widths, those clouds make 8 chunks of about 12,500 splats and 27 chunks whose largest holds 36,936. A cloud that fills only part of its bounds makes fewer, larger chunks, because a cell holds the splats that fall in it.
- The selection spends a budget in two passes. Every chunk the budget reaches first keeps its coarsest prefix. The rest of the budget then refines the nearest chunks, up to the level that each one's distance asks for. A small budget therefore thins the whole cloud rather than deleting its far parts. A near chunk is still denser than a far one of the same size.
- A chunk's level measures its distance in the radius of the whole cloud, not in the chunk's own radius. A finer cut makes smaller chunks, and a smaller chunk measured against itself passes for a farther one, so the same view draws fewer splats. Measured in each chunk's own radius, the 36,000-splat demo cloud draws 22,026 with its 8 chunks, and 12,563 when cut into 27. With the cloud's radius as the unit it draws 36,000 and 35,403, and the distance still thins a cloud viewed from far: 4,503 at 50 m either way.
- A rule that takes the first chunks in distance order at their full level and gives the rest nothing starves the far chunks. With a budget of 9,000, it keeps only the two nearest of the 36,000-splat demo cloud's eight chunks. The far half of the knot vanishes. The two passes keep all eight chunks. A stream of the 400,000-splat test cloud fetches 6 of its 27 chunks, against 3 under that rule.
- A chunk that draws one splat still costs its whole file. So a base level for every chunk would make a stream fetch the whole cloud. The passes reach chunks in distance order and stop when the budget can give a chunk no base. A budget large enough for every level selects exactly what the distance-order rule would. The selection's test checks that.
- `chunks.test.ts` checks the cut of a lattice cloud against the target load. It also checks the same cut made twice, and the same chunks when the cloud lists its splats in another order.

## Failures on the GPU

- A derivative call (`dpdx`, `dpdy`, `fwidth`, or `textureSample` without a level) must run in uniform control flow. A branch on the material's row, a `var<private>`, before a derivative in the lit fragment makes WebGPU reject every lit build with `'dpdy' must only be called from uniform control flow`, naming the branch. So the lit fragment reads each derivative before a run-time branch on the material, and its per-material map branches sample with explicit gradients (`textureSampleGrad`). The shadow catcher's branch sits after the specular anti-aliasing kernel, with the alpha hash's threshold and alpha to coverage's width hoisted above it ([D-163](decisions/D-163-shadow-catcher-material.md)).
- WebGL2 counts a context as lost at once, but the `webglcontextlost` event comes later, in a task of its own. The rest of a frame then runs on the lost context. In Chromium 153, `checkFramebufferStatus` answers `FRAMEBUFFER_UNSUPPORTED` (0x8cdd), and the WebGL specification says `getProgramParameter` answers null. A backend that throws on those answers ends the engine with E1404 instead of recovering. So the WebGL2 scene renderer drops an error from a frame only while `isContextLost()` is true; any other error ends the loop ([D-58](decisions/D-58-failure-handling.md)).
- Without a listener that calls `preventDefault()`, the browser never offers a lost WebGL2 context back. So `createRenderer` listens before its first wait, the shader download. A loss in that wait waits for the restore, and the renderer then listens for itself in the same task.
- A stopped engine loses its WebGL2 context on purpose, with `WEBGL_lose_context`. The GPU then frees the engine's memory at once, not when the browser collects the context. A canvas keeps one context for good, so the next engine on the canvas gets that same context, lost. The `WEBGL_lose_context` specification lets `restoreContext()` bring it back only after the `webglcontextlost` event has run and was canceled. A lost context also answers no extensions. A renderer that stopped listening before it lost the context would leave the event uncanceled. The next engine would then wait 5 s for a restore that never comes, and fail with E1405, "the WebGL2 context did not come back". So `releaseContext` keeps the extension and cancels the event. Then `reclaimContext`, in the next `createRenderer`, waits for that event and asks for the context back. Until a next engine asks, the context stays lost and holds no GPU memory. The test of engines that follow one another on one canvas (`tests/image/failures.spec.ts`) runs on WebGPU, compatibility mode and WebGL2, in every thread mode.
- What a stop keeps for the next engine sits in a `WeakMap` keyed by the canvas. The map is on the thread's global object under a `Symbol.for` key, so each copy of the module in a thread finds it. It holds the canvas's own context and its `WEBGL_lose_context`, never a renderer, the engine's memory or its workers. It goes with the canvas. The key is the canvas, because a renderer that times its GL calls draws through a stand-in of the context. The stand-in's extension would also keep its timing state. So the stop gives up the context that the canvas itself returns.
- WebKit keeps a canvas alive while it has a `webglcontextlost` or `webglcontextrestored` listener and its context may still come back. Its Metal translator gives the type `constant ... &` only to the inputs that it adds itself to carry its uniform structs (`RewritePipelines`). It keeps that mark in a table (`SymbolEnv`) whose keys hash by the variable's address in memory but compare by its symbol number. A plain input marked that way was matched to the wrong entry. Which entry matches depends on memory, not on the source, so the same shader links at the next try. Nobody has proved what makes the entries match.
- So when a link fails and its log holds "MSL compilation error", the WebGL2 backend links the program once more. It does this when the program is first used. It compiles both shaders again, into a new program, with a comment added to the end of each source. The comment makes a browser that keeps translated shaders by their source translate them again.   - Rewriting the GLSL to avoid the construct. No construct causes the fault: it hit three unrelated functions, and the same source passed before and after.
  - A build check that refuses a uniform passed to a function, with a copy into a local first. The build already copies every uniform into a local, and the iPad's failure took a local value.

- In Chrome, a WebGL2 framebuffer's completeness check (`checkFramebufferStatus`) waits for the GPU process to run every command before it. On a cloud Pixel 10 (PowerVR, Chrome 149) each check takes about 1.5 ms of the drawing thread's time. On the Mac, Chrome makes no framebuffer per frame in the same test, so the Mac does not show the cost. So the backend never makes a framebuffer in the frame loop. It keeps each one it makes, by color target and depth target, and makes one again only when a target is made again.

- The effect cost page finds such a wait. With `?gltiming` it reports each WebGL call's time and count per frame on the drawing thread. A call that waits for the GPU process stands out at its count, as the checks do at 2 a frame.

- With cell offsets in a uniform table, the Galaxy S25 (Adreno 830, Chrome 149) draws objects more than 512 m away in the wrong place. This happens on WebGPU and in compatibility mode. In the depth precision scene, the surfaces at 1.6 km and 4 km vanish. The pair at 10 km covers the whole screen. WebGL2 draws the scene right, as do the Pixel 11 and the Galaxy Tab A9 Plus (Adreno 619) on WebGPU.
- The culling shader moves each source by the offset from the camera to its grid cell ("Large worlds" in the concepts docs). Such a shader reads the offset from a table in its parameters, a uniform buffer, at the index of the source's own cell. A probe build that dumps the GPU's buffers after a capture finds the right offset for each cell in the table. But every row that the shader writes takes the same cell's offset. It takes the origin cell's zero when the view culls runs of the cell order, and cell 1's with `?cells=off`. That is the cell of the group's first thread both times. Reads from storage buffers at an index from the same value, such as each bucket's record, are right. So the driver reads the uniform array at one thread's index for every thread. The far sources keep their place relative to their cell's center. That puts them behind the camera, or around it for the 10 km pair, which is 4.7 km wide.
- A probe page runs that culling shader alone, on 512 synthetic sources in 4 cells. Each source's cell differs from its neighbor's. On the S25, 384 of the 512 rows take another cell's offset, in core WebGPU and in compatibility mode alike. Every thread takes one cell's offset. Three changes still give 384: a clamped index, a read of the offset before the first early return, and no return in the plane loop. Two changes give 0: the parameters in a storage buffer, and a copy of the whole table into a local variable before the read. A uniform table of 512 entries in a smaller struct, read at a per-thread index, is right in the compute, vertex and fragment stages. So the fault needs the shape of the culling parameters, not just a read at a per-thread index. The probe does not narrow it further.
- So the offsets sit in a data texture of 32-bit floats, with one row per view and one texel per cell. Each thread reads the texel of its own cell. The culling parameters stay a uniform buffer, and name the view's row. Parameters in a storage buffer also fix the S25. But with occlusion culling's pyramid, the stage would bind 9 storage buffers, past the portable budget's 8 ([D-95](decisions/D-95-culling-cell-offsets.md)). A Rust test checks that each view writes its offsets into its own row. The `cells` image tests span cells too.
- On the same S25, without the capture targets below, every capture of the texture arrays test comes back empty in compatibility mode. That holds in all 5 thread modes. - On the Galaxy S25 (Adreno 830, Chrome 149, WebGPU), S1's scene pass takes about 4.8 ms more GPU time per frame. It pays this once it draws anything besides the swarm: 13.24 ms against 8.45 ms. A small unlit box costs it with or without depth writes, and so does every kind of background. A box and a background together cost 0.2 ms more than either alone, so the step comes once per pass. - The Adreno 619 of a Galaxy Tab A9 Plus stores every value that a GLSL structure holds at 16 bits. The shader's declared precision does not matter. `highp` on the members changes nothing. A float rounds to half precision with flush: `1234.567` reads `1234`, and `1e-5` reads 0. A whole number keeps only its low 16 bits: `0x89abcdef` reads `0xffffcdef`. A probe finds the fault in a structure local, a constructor, and a helper's result and parameter. It also finds it in a structure of scalars, one with a `uvec4` or an array member, and a fragment stage's gathered inputs (`VertexOut in_ = VertexOut(...)`). A copy of a uniform block's structure into a local is wrong too. A plain local, a varying, a structure member read in place (`block.field`), and a uniform block's own member are exact. The GLSL that naga writes holds each stage's inputs, each helper's arguments and results, and each function's locals in structures. So the shader build rewrites each function before the writer sees it. A structure argument becomes one argument for each member, a helper's result becomes one `out` parameter for each member, and a structure local becomes one local for each member. A private structure global becomes one global for each member. No structure value is materialized, so naga never bakes one into a local. The one structure that remains is the value that an entry point returns, which WGSL requires, and the build inlines it in the text. The shader crate's test checks every built shader for a structure-typed local, parameter or result ([Driver bug reports](driver-bugs.md)).
- The split above runs on custom materials' and effects' WGSL too, which can hold three shapes that the engine's own shaders never use. Unsplit, a pointer parameter to a struct stops the shader compiler with a panic, which the page reports as an internal error. A private struct variable's initial value is lost on WebGL2 alone, so the two paths draw different values. The results of `modf` and `frexp` stay in structs, because naga's writer makes a helper function that returns one. So a pointer parameter to a struct becomes one pointer parameter for each member, in the same address space. Each caller passes a pointer to each member's own variable. WGSL lets such a pointer name only a whole variable, so the members never alias. A private struct variable's members take their parts of its constant initial value. The build works out `modf` from WGSL's definition: the whole part is `trunc(x)`, and the fraction is `x - trunc(x)`. It reads `frexp` from the float's bits: the exponent field less 126, and the mantissa with the exponent of one half. Zero multiplies both to zero, because GLSL ES 3.00 has no `mix` that picks whole numbers by a boolean vector. The fallback that naga has for `frexp` on GLSL ES 3.00 takes `log2` of the value, which gives NaN for a negative one. The pass returns an error instead of panicking, so a shape it cannot split stops the build with a problem that names the function. An array of structs stays one value, and a struct inside one is composed in place. The `STRUCTURED` shader in the shader crate's build tests covers each shape.
- Work around a browser's fault with an order or a call that is valid everywhere, as the staging ring does. Where browsers differ in speed, time the choices on the device, as the upload routes do. When neither works, detect the fault with a feature test, never from the user agent (hard rule 14). The one exception is Safari 26's indirect draw fault, which only a GPU hang shows ([D-87](decisions/D-87-webkit-indirect-arguments.md)).
- A dev server sends each file of a worker's script, and each file that the script imports, as a module file of its own. On CI's Linux machines, Firefox can fail to load one worker's files. In run 39191671424 it did so on 6 pages of one shard, each about 200 ms after the page started. The same worker as a second copy loaded 66 to 234 ms later, so the fault passes. The dev server's log held no error, and the other Firefox shards passed. Without a retry, the engine reports E1405 at once, and each page fails. A worker that has not reported the first step of its start, `loaded`, has no state to lose. So the engine starts one more copy of it when its script does not load, and reports E1405 only if that copy fails too. A worker whose script ran is never replaced. The page also holds every message for a worker until the worker reports `loaded`: a copy then gets each message in order, and no canvas or port moves to a worker that never ran. A worker that an engine before kept reports no step, so it takes its messages at once. `engine-worker.test.ts` covers the retry, the held messages and the second failure. `restart.spec.ts` aborts the render worker's first download and requires the start to finish, then aborts every download and requires E1405. The retry does not cover a worker from another origin: its bootstrap reports the reason, such as a missing CORS header or a policy that blocks it, in the error message, so the page reports that reason at once.
- The retry needs a listener that hears every failure. Firefox sends a failed script load as a plain `Event`. Whether a worker's `onerror` property receives such an event depends on the Firefox build. Playwright's Firefox 1543 passes a probe with a plain event to both the property and a listener. CI's Firefox 157 runs no listener set through the property. Chrome calls the property, so the Chromium tests cannot show the fault. With the property, 3 of 20 CI runs hung on Linux Firefox WebGL2 pipelined pages. Each page's trail showed a render worker that did not load, a second copy of it that loaded 141 ms later, and nothing after that. The page's harness listens with `addEventListener`, so it heard the failure and started its copy, while the engine neither started a copy nor reported the failure.
- So the engine listens for a worker's error through `addEventListener` (`watchWorkerError` in `shared/worker-start.ts`), which hears the plain event and an `ErrorEvent` alike. The glTF, panorama, task and capability probe workers share the listener, because through `onerror` a failed load could leave their waits forever.
- The retry answers any failure that arrives before a worker reports `loaded`, whatever the browser's message says. Chrome's message for the same fault is not empty. It makes one copy of the same script, and it reports a failure that the engine already named at once: the bootstrap of a worker from another origin names a policy or a missing header, and a copy would fail the same way.
- The engine warns in the console when it starts a second copy, naming the worker and the script's resolved address, which is the built file's address in a production build. A page and its tests can see the recovery there. If the copy fails too, E1405 names the worker and that address. `engine-worker.test.ts` fires a plain `Event` at a stand-in that is an `EventTarget`, so a return to the `onerror` property fails the test. `restart.spec.ts` covers the recovery and the double failure in the pipelined and main-thread starts, and reads the warning and the error's message.
- Safari 27.0 cannot compile a shader that calls `atomicCompareExchangeWeak`, on storage or workgroup memory. WebKit adds a Metal helper for the call whose result type names the `thread` address space, and the Metal compiler of the 27 releases rejects that. The pipeline then fails to build, and the page with it (E1404). Safari 26 and the Metal compiler of macOS 26 accept the same helper, so a Mac on macOS 26 does not show the fault. WebKit fixed the helper in 321006@main, after Safari 27.0 shipped. The other atomic built-ins become plain Metal calls with no helper. A form of the culling shader that claims table slots with the call fails every page on a BrowserStack iPad with Safari 27.0. A claim with atomic loads and stores in turns between barriers compiles there ([D-100](decisions/D-100-workgroup-counters.md)). The engine's shader build fails on the call, and users' shaders build with a warning that gives that form as the fix ([WGSL rules](../docs/shaders/wgsl-rules.md#atomic-compare-exchange)).

## Safari's frame path

Safari 26 does work for each WebGPU frame that no GPU timestamp covers. It shows only in `gpuLatencyMs` and in the frame rate. [Benchmarks](benchmarks.md#safaris-own-work) says how to see it.

- Safari 26 encodes a render bundle that holds an indirect draw again at every `executeBundles`. Each time, it also builds a Metal indirect command buffer of 16,384 commands, because a command count wraps below zero.
- On an M5 Max, that takes Safari's GPU process 9.6 ms of CPU per frame, in S1-static and in S2 alike. WebKit has fixed it, and Safari 27.2's beta notes list the fix.
- So the WebGPU backend makes no native render bundles. It keeps each bundle's recorded commands and replays them into the render pass. In Chrome, S2's 100 draws add about 15 microseconds to the render worker's frame.
- A worker's WebGPU canvas reaches the page through two synchronous calls after each frame callback. The second copies the frame into the page's canvas, and it first waits for the GPU to finish the frame.
- So the worker stays blocked until Safari's GPU process has run all the frame's commands and the GPU has drawn the frame. Safari's own work, the GPU time and the copy add up to the worker's frame.
- `gpuLatencyMs` counts from the submit until the drawing thread sees the frame finish, so in Safari it includes that blocked time. With native bundles on the Mac, most of its 11 ms is Safari's command buffer build.
- Safari runs a worker's `requestAnimationFrame` from a 15 ms timer, not from the display. After the worker sleeps through most of a frame, the timer fires about 3 ms late.
- So the frame loops set a timer at the start of each callback in a worker, due 4 ms before the next callback. The worker then sleeps too briefly for Safari's timer to fire late. In S1-static at 240,000 boxes on a busy Mac, Safari presents 62.5 frames per second with it and 54.4 without. On a quiet Mac, the timer fires less late, and Safari presents 59.4 to 60 without it.
- Safari's worker timer then calls the worker about 64 times a second, more often than a 60 Hz display shows frames. On the iPad, the worker draws 61 frames per second, and on the Mac 64.7, so some frames are never shown.
- So the page measures the display's refresh period from its own frame callbacks, which follow the display in every browser. It writes the period to the control block. A worker whose callbacks come at a rate that matches no display's holds its frames to that period. Chrome's worker callbacks follow the display, so Chrome draws at the display's pace, even when a busy page thread measures a slower rate.
- With the hold, Safari on the Mac's built-in screen presents 60.0 frames per second in 4 of 4 runs. Safari runs the page's frame callbacks at 60 Hz on that 120 Hz screen, and at 72 Hz on a 144 Hz screen. On the 144 Hz screen, the worker's 64.6 frames per second stay below the page's rate, so the hold skips no callback there.
- Safari writes no timestamps, or stale ones, for a pass without work. The GPU timer's start mark therefore dispatches one invocation that does nothing.

## Safari's WebGL2 path

Safari runs WebGL2 in its GPU process, through ANGLE on Metal. A call that returns a value waits until that process has run every call before it. `fenceSync` is such a call. The completion tracker places a fence at the end of each frame, so the render worker waits there until Safari has run the frame's calls. Any wait inside Safari then shows in the render worker's time per frame. [WebGL call times](benchmarks.md#webgl-call-times) finds the call that waits.

- A render pass that draws into a color target with no depth attachment need not invalidate the depth. Each fullscreen step of an effect is such a pass. `endPass` names only the attachments the pass has. Safari runs the invalidate on the thread that draws before it draws the pass, so a wasted call costs it. The iOS call profile puts three such calls in ambient occlusion's frame.
- On Safari 26.6 and 27.0, ambient occlusion costs the WebGL2 render worker about 3.6 ms a frame on an iPhone 18 Pro. It costs the same at render scales 1 and 0.5, against 0.2 ms on Safari 26.5. The cost follows the prepass's stand-in color, not the ambient occlusion steps ([D-269](decisions/D-269-the-prepass-stand-in-color.md)). Safari charges time for a framebuffer that holds a color the pass never writes, and then invalidates it. That time follows the texture's size. A stand-alone page with no engine code added 4.10 ms for one such texture on the iPhone 18 Pro, and 0.02 ms on an iPhone 17 with Safari 26.5.
- The cost is flat across the render scales because it follows the texture's size rather than the drawn corner. Safari charges it for the whole target, wherever the render scale draws. A smaller target, as each of bloom's chain's levels is, costs proportionally less.
- On WebGL2 the three steps' targets start from what the texture holds. Each read of them clamps inside the drawn corner, which the step writes whole. So no clear is needed ([D-193](decisions/D-193-ambient-occlusion-targets-start-without-a-clear.md)). The WebGPU path keeps its clear, which is cheap there. The Mac's Safari 26.6.2 hides the cost: ambient occlusion adds 0.04 to 0.12 ms at render scale 1 and 0.16 to 0.20 ms at 0.5 there, which is the noise of its 0.6 ms frame. The call profile shows ambient occlusion adding one clear a frame, the prepass's depth, against four with the clears. Yet the cloud iPhone run at `7c69473f9` shows no saving. The render worker goes from 0.78 to 4.44 ms at render scale 1 and from 0.88 to 4.44 ms at 0.5, as with the clears. So the clears are not the 3.6 ms. The prepass's unwritten stand-in color is.
- So a pass never attaches a color it does not write. A prepass that a screen step splits from the opaque pass draws into a depth-only framebuffer. The framebuffer of a depth-only pass names no draw buffer, so no color is attached at all. Keeping the stand-in color and clearing it does not remove the charge ([D-269](decisions/D-269-the-prepass-stand-in-color.md)).
- The iPads pay this cost in frame time, by the same rule that the charge follows the texture's size. A stand-alone page measured 3.26 ms on the iPad 10 and 12.28 ms on the iPad Pro 13. In the engine, the prepass's stand-in color cost the iPad 10 4.8 to 7.2 ms of frame time at render scale 1, and 3.1 to 5.6 ms at 0.5 ([D-269](decisions/D-269-the-prepass-stand-in-color.md)). The depth-only framebuffer removes it: at that device's preset it took the interval rise from 10.26 to 5.49 ms at full scale. The render worker's own rise shows only a slice there, 0.52 against 0.64 ms, because the frame is GPU-bound. The earlier iPad figures of 0.2 to 0.7 ms came from the Medium preset's frame. That frame was measured before the prepass's stand-in color became a load.

- ANGLE lays out a uniform block by Metal's rules, where a `vec3` takes 16 bytes. WGSL lets a scalar follow a `vec3f` at byte 12. Where the two layouts differ, ANGLE converts the block on the CPU before a draw that reads changed data.
- ANGLE writes a buffer that the GPU still reads with a GPU copy. The conversion then reads the buffer on the CPU, so it waits for the GPU to finish every frame queued before. A fog block with a `vec3f` before a scalar makes S3 spend 22 ms of each WebGL2 frame in `fenceSync` on the iPad.
- The shader build therefore fails when a uniform block lays out differently by ANGLE's Metal rules (`metal_layout` in `crates/null3d-shaders/src/glsl.rs`). Fill each `vec3f` with a scalar into a `vec4f`.
- With a fog block that ANGLE need not convert, the render worker takes 1.1 ms per frame on the iPad in S3, against 25.9 ms.
- Safari writes texels into a texture that the GPU still reads only after the GPU has finished with it. The resident texture of world matrices takes such a write whenever a scene object moves. In S4, one direct write per frame waits about 16 ms on the iPad.
- So a later write into a data texture of 32-bit values goes through a pixel unpack buffer. The GPU copies the texels into the texture in order with its other work, and the render worker does not wait. A ring of three such buffers serves one frame each: the frame being replayed, and the two frames that may be in flight.
- A texture's first write, and every write into a color texture, goes straight into the texture. Through an unpack buffer, Chrome on the Mac stores sRGB texels brighter.
- A cool iPad Pro 11 compared three ways to write the texture again, in S4 on WebGL2. The pages took turns over three runs each (run `20261003-003951-bench`).

| Way | Render worker, ms per frame | Frames per second | Upload per frame |
| --- | --- | --- | --- |
| Direct writes | 25.4 | 34.9 | 0.05 MB |
| Through the ring of unpack buffers (kept) | 1.50 | 35.9 | 0.05 MB |
| Into a ring of three copies of the texture | 1.43 | 35.6 | 0.10 MB |
| WebGPU, as a control | 0.20 | 36.6 | 0.01 MB |

- The GPU limits S4 on the iPad. All three ways and the WebGPU control ran in one session, with the pages taking turns, and drew 34.9 to 36.6 fps. So the unpack buffers cost no frames, and they free the render worker of about 24 ms of waiting per frame.
- The ring of copies frees the render worker as well, but it costs more. Each frame writes the next copy, which no frame in flight reads. That copy first takes the rows that the other copies took since it was last in use, so the upload doubles. The ring also keeps each texture's texels on the CPU, and three textures on the GPU in place of one. It needs about 150 more lines of code. The unpack buffers add one copy on the GPU for each write, of the same bytes.
- The S24+ phone in Chrome drew S4 at 59.9 fps with all three ways (run `20261002-222010-bench`). Its busiest thread took 3.8 to 4.0 ms with each way, so Chrome had no wait to remove. Firefox was not timed.
- Compare frame rates only between pages that took turns in one session. Separate runs can make the unpack buffers seem to cost frames. They gave 48.7 fps with direct writes, against 35.3 fps with the fog layout and the unpack buffers. The iPad is at a different temperature in each run, and its GPU limits S4.
- A warm run with the pages taking turns gave 43.6 fps with direct writes against 36.6 fps with the unpack buffers. The cool run a few hours later gave no such gap. In both runs, the governor took one quality step down with direct writes and none with the unpack buffers. So the direct writes drew lighter frames.
- The Mac shows neither wait. Its GPU finishes each frame before the next frame's writes, so nothing waits.
- Many small writes in one frame hold up the GPU, even in Chrome on the Mac. A resident texture that takes one write for each run of scene rows that changed together shows it. S5's knights each lose 5 of their nodes, and the freed slots split each knight's rows into about 3 runs. At 500 knights, the frame then makes about 1,500 writes. Each write is a buffer bind, a write into the unpack buffer and a texture write from it. The render worker takes only 0.71 ms per frame, but Chrome draws 8.4 frames per second, and the GPU runs 233 ms behind. At 100 knights it holds 120 frames per second, and at 200 it falls to 16.9.
- So the upload joins runs of rows that lie at most 64 rows apart into one write. The code is `joined_rows` and `MERGE_GAP_ROWS` in `crates/null3d-render/src/frame.rs`. Both world buffers hold every row's latest matrix, so the rows between two runs go up unchanged. Rows that no draw reads cost only their bytes. With the joins, S5 makes 3 writes into the resident texture per frame. Chrome draws 200 knights at 119 frames per second and 500 at 89, where three.js's WebGL renderer draws 20.4. The WebGPU path writes its buffers with no unpack buffer.
- GLSL ES 3.00 has no `textureLod` for an array or cube comparison sampler. So naga writes a comparison at level 0 as `textureGrad` with zero gradients. ANGLE on Metal turns that into a Metal comparison with explicit gradients. So the GLSL build writes those reads as `texture()`, at the texture's own level (`implicit_comparison_levels` in `crates/null3d-shaders/src/glsl.rs`). Shadow maps have one level, so the result is the same. In S4 at Medium, WebGL2's GPU delay on the Mac is 8.2 ms with `texture()`, against about 17 ms with zero gradients. Its frame on the iPad is 59 ms against 62 ms ([D-16](decisions/D-16-moving-casters-and-bias.md#the-shadow-reads-on-webgl2-on-apple-gpus)).
- ANGLE on Metal draws `blitFramebuffer` as a render pass of its own. A multisampled pass's targets are therefore stored to memory before its resolve reads them, and a discard after the blit comes too late. The backend's `endPass` discards a pass's unneeded depth, and its color when the pass neither stores nor resolves it, before the blit. It discards a resolved color after the blit. On the iPad, these discards save 7 ms per frame in S4 at Medium, even with FXAA instead of 4x multisampling.
- Without the depth prepass, WebGL2 on the iPad costs about three times WebGPU's GPU time per pixel, at every preset. S4 at Medium then takes 62 ms per frame on WebGL2. On WebGPU it takes 17 ms, with 18 to 19 ms of GPU time. The frame follows the pixel count: 37 ms with the pixel ratio capped at 1.5, and 27 ms at Low. Fewer cascades, the far cascade's interval, the cascade blend and occlusion culling each change it by 1 ms or less. This cost, not the shadow reads, makes WebGL2 slow on the iPad.
- In S4, WebGL2 shades hidden pixels on the iPad, and a depth prepass restores their early rejection. The cause is under investigation. ANGLE's helper sample mask costs hidden surface removal on the Mac. The owner reported it as [WebKit bug 326660](https://bugs.webkit.org/show_bug.cgi?id=326660) and [ANGLE issue 570876469](https://issues.angleproject.org/issues/570876469). A standalone WebGL2 page on the iPad keeps the fault, so the engine's own shaders are being checked ([D-43](decisions/D-43-webgl2-prepass.md#why-webgl2-is-slow-on-the-ipad-without-the-prepass)). So every preset draws the depth prepass on WebGL2. On the iPad, S4 draws 60 fps at Low with it, against 38 without, and 37.1 fps at Medium, against 17.3. WebGPU keeps it off, where it costs up to 4 ms ([D-43](decisions/D-43-webgl2-prepass.md#the-prepass-on-webgl2-at-every-preset)).
- S4 at Medium on WebGL2 still takes about 27 ms per frame on the iPad, against WebGPU's 15 ms. The MSAA resolve and the 5 x 5 shadow filter are the likely costs, and not measured yet.

## The generated shader set's weight

The build writes the engine's shader modules into `packages/engine/src/generated`. Measured without
the shared paragraph tables below, the set held 1,343 files and 847 MB. They were 987 GLSL modules at 775 MB,
352 WGSL modules at 72 MB, and four small framework files. The weight is a build, checkout and
memory cost. It is not a download cost, because a page fetches the modules its features need and a
module compresses about twenty times over.

Two facts organize everything else.

**The start file is not the problem.** The module a page needs before its first frame is 8.5 MB, one
percent of the set. The other 99 percent already sits in modules that load on first use, so moving
more shaders into first-use files saves almost nothing ([D-56](decisions/D-56-first-use-shader-files.md)).

**The device permutations multiply what is left.** A device fixes three bits: whether the draw index
comes from a texture, whether tone mapping runs in the shader, and whether half precision applies.
GLSL has all three, so the build writes eight targets of about 96 MB each. WGSL has no draw-index
bit, so it writes four of about 18 MB. No GLSL target is more than two percent larger than any
other. The draw-index targets alone are 387 MB, 46 percent of the set, and they differ from their
pairs by about one percent of text.

**Most of the rest is duplication.** Inside one device target, the tables of shader paragraphs repeat
82 percent of their text. There 408,882 stored copies hold 15,374 distinct paragraphs, so one paragraph is
stored about ten times over, once per feature set. The texture binding lists repeat 91 percent and
the uniform block lists 98 percent. No two module files are byte-identical, so no file can be
dropped as a duplicate.

### One table of shared paragraphs for each kind of device module

The build writes a paragraph that at least twenty feature-set device modules of one kind hold once,
in a table of its own. Each module imports the constants it uses. A kind is a GPU target and one
value of the bits a device fixes, so there are twelve tables. Measured on the 1,331 device modules,
with the levels the size report uses:

| | Without the tables | With the tables | Saving |
| --- | --- | --- | --- |
| Uncompressed | 846.1 MB | 681.9 MB | 164.2 MB, 19 percent |
| After gzip | 152.3 MB | 111.1 MB | 41.2 MB, 27 percent |
| After Brotli | 41.9 MB | 31.7 MB | 10.2 MB, 24 percent |

The twelve tables are 5.0 MB uncompressed and 294 KB after Brotli together. The largest is
`shader-paragraphs-glsl-tone-map-half.js` at 593.0 KB uncompressed and 31.4 KB after Brotli, inside
the 1,792 KB and 56 KB that a shader file of a feature that loads on first use may take.

The tables touch only the feature-set modules. The twelve modules of the start are byte-identical
with and without them, so a page that uses no feature downloads the same files. A kind's table
loads with the first feature of that kind, not at the start. No image changes either, because
every feature-set module builds the same shader text. A production build of the test project
checked that for all 1,331 device modules of both targets.

The count is the named constant `SHARED_PARAGRAPH_MIN_USES`. Lowering it saves more text and grows
the tables; the ladder in [D-181](decisions/D-181-shared-shader-paragraphs.md) gives the figures.
A table of a whole target rather than of one kind was measured too: 8.9 MB uncompressed and 192 KB
after Brotli for WebGL2, over all three limits of a shader file.

### What would help

- **Derive the draw-index build from its pair.** This has the highest ceiling, up to 387 MB or 46
  percent. The difference is a require line, a draw variable, an instance lookup, and a swap of the
  draw table from a uniform block to a texture. All of it sits inside generated text rather than
  beside it. The risk is high, so it wants a probe before a change.

That change, like the tables, changes the output of the shader build, which changes the compiler
stamp that the cache is keyed by. Either one means a full rebuild on every checkout and a cold
shader build in CI.

### New shader code keeps the shared paragraphs shared

The paragraphs share only text that matches exactly. naga's writers give each name in a build one
spelling. When two places use one name, they number it: `at`, `at_1`, `at_2`. A new function can take
a name that the build already uses, such as `at`, `uv` or `pixel`, for a parameter or a local. That
renumbers every later use of the name in the build. A build that holds the function then shares
almost no paragraph with one that does not. And a branch on a build's bits inside a long function
makes the whole paragraph of that function differ between the builds.

The depth check of surfaces that let light through and the masked-surface rule for ambient occlusion
show both. Written without the rules below, they grow 454 shader files by more than the size
check's 2%. All the shader files grow by 0.95 MB after Brotli. Glass's own files grow 4 to 10%, and
families without glass 2 to 4%. The three rules bring that down to 13 files: the twelve tables of
glass's paragraphs and one file at 2.1%.

- The new functions take names that no other code of those builds uses (`code_place`, `surface_at`).
- The masked-surface rule reads a constant that the build's bits set (`NEAREST_SPEAKS`). The
  function that reads the screen texture then has the same text in every build, and only the
  constant's line differs.
- No library module gains a module constant that every build would carry. A constant of an imported
  module lands in every build, whether it reads it or not, while unused functions do not.

Check a shader change's cost with `bun tools/build-wasm.ts --check-size --base <commit before it>`.
To see why a file grew, load one build's text from the old module and from the new one, from each
module's `SHADERS` export. Then compare the two texts.

### What would not help

- **Shipping the text compressed.** The whole set is about 40 MB on the wire. It saves nothing on
  build time, memory or checkout size, because the build still writes 847 MB and Vite still reads it.
- **Dropping permutations that draw the same picture.** Measured: no two module files are identical,
  so the saving is zero.
- **More first-use files.** The start file is one percent of the set, and a page that uses two
  features would fetch two modules whose contents overlap. That is the merge problem in another form.

### The duplication is also across the device targets

The paragraph text repeats across the eight GLSL targets of one feature set, not only across feature
sets inside one target. This was measured by streaming the modules one at a time and hashing each
paragraph, so it reads no whole file into memory.

- Two targets that differ in the draw-index bit agree on all but nine of their paragraphs, 99.8
  percent of the text. The remaining difference is under one and a half thousand bytes.
- The 115 feature sets that have all eight targets store 267 MB of paragraph text between them. The
  distinct text is 99 MB, 37 percent. So the eight targets fall into about three families of
  paragraph text. The half-precision and tone-mapping bits rewrite paragraphs; the draw-index bit
  does not.
- The composed sources are not where the duplication is. They are the same programs written with
  different paragraph numbers, because the writer numbers a paragraph by where it first appears. Ten of
  eleven composed sources differ between two targets whose paragraphs agree. Share the paragraphs, and
  never the composed text.

### The build's work is a product of its bits

The manifest makes 53,762 GLSL builds and 19,227 WGSL builds, the figures that `BUILD_BUDGET`
records. The translucency bit of M2-EX36 joins the lit, standard-material, probe grid and custom
material templates, and its two subsurface templates add one more pair. The count includes the
probe grid's translucency builds, which the engine draws when a translucent mesh stands in a scene
with a probe grid. The still view adds an accumulate build on each target, and the motion pass's
template adds 50 GLSL and 17 WGSL builds (M2-EX25). The reflections' two full-screen passes, the
pyramid's reduce and the trace, add two more on each target. The reflection probes' template
(D-149) adds one on each target. It holds one variant for each target and no free bits, because its
three pipelines differ by entry point rather than by def.

A build counts once for each target that its variant writes, so a variant that writes both targets
adds to both counts. The figure is a count of the manifest and its bit table, not of files on disk.
A variant may carry more than one pipeline, and so hold several programs. A variant builds once for
each combination of its free bits, so removing any free bit halves it. Tone mapping is the dearest
bit by a wide margin. In a manifest of 116 variants, 45 list it, and it accounts for about half of
all builds. Skin, alpha masking, received shadows, half precision and vertex color each cut 46 to 50
percent of the large variants. The rare lit features cost less: area lights and coat-sheen about
8,600 builds each, and weighted transparency 2,600.

### The count the manifest may not pass

`BUILD_BUDGET` in `crates/null3d-shaders/src/manifest.rs` records the figures above, and a commit
that adds builds on purpose raises them here and in the constant together. The test
`the_manifests_builds_stay_within_the_recorded_figure` in the shader crate counts the manifest's
builds and fails when either target passes its figure. The test builds no shader, so it costs a
test run almost nothing. Its problem names the figure, the file that holds it and this guide.

The figure counts every build that the shader build compiles for the repository's manifest. It
does not count the builds that one page downloads. A page loads a subset: the device module of its
GPU path, then the first-use modules of the features it uses. The manifest's count bounds that
subset, and the shader build pays for all of it. The figures come from the manifest and its bit
table through the engine's own enumeration, not from a page's downloads.

A build costs twice. The shader build compiles every one of them, and a page downloads the builds
of its own GPU path. A permutation bit on a lit template multiplies the count: area lights and
coat-sheen add about 8,600 builds each. With nothing to hold it, the count can grow four times in
two days. The cold build then grows past the CI job's time limit
([Branches and parallel work](pull-requests.md)). On one runner class, the CI build job takes 6.5
minutes for 14,997 builds (run 39097238563) and 13.5 minutes for 21,909 (run 39099279063). The
split of the shared tables brings that cost back down
([D-190](decisions/D-190-hold-relief-until-the-split.md)).

The relief materials of M2-J4, bump, displacement and parallax, add three bits to the standard
material's maps templates. That makes their builds 3.33 times as many
([D-190](decisions/D-190-hold-relief-until-the-split.md)). The shader build splits the shared
paragraph tables, so the extra builds stay out of every page's start.

A commit that adds builds on purpose raises the figure it passes and records the reason here, or in
a decision record. A commit that raises the figure and gives no reason is the growth that this
guard refuses.

### What each device bit costs, in files and in bytes

The build counts above count the manifest, not the files on disk. The bytes below are read from
the modules themselves, by pairing each module that carries a device bit with the twin that lacks it.

| device bit | modules carrying it | their bytes | their twins | it adds over the twins |
| --- | --- | --- | --- | --- |
| `TONE_MAP` | 648, 49 percent of the files | 428 MB | 416 MB | 11.8 MB, 1.4 percent of the set |
| `HALF` | 618, 46 percent | 426 MB | 415 MB | 11.4 MB, 1.3 percent |
| `DRAW_INDEX` | 484, 36 percent | 387 MB | 387 MB | 0.6 MB, a tenth of a percent |

So a device bit costs the set almost nothing in text and a great deal in near-copy files. Each one
doubles the file count and adds about 400 MB of modules whose twin already holds the same content.
`DRAW_INDEX` is the extreme: 387 MB of modules against 387 MB of twins.

That is the shape of the largest saving available. A bit that becomes a runtime branch is deleted
from the build and grows its twin by its own percent. Tone mapping would delete 648 modules and
428 MB, and grow 416 MB of twins by 12 MB. That saves about 416 MB, or 49 percent of the set. Half precision
is worth about the same and the draw-index bit about 387 MB. The three do not add up, because they
compose: together they multiply the GLSL weight by eight while changing a few percent of the text.
The price is a branch in the shader, and these are lit paths on devices where a branch can cost.

### The demand-driven build would not help

A build that emitted only the feature sets a page asks for would not shrink the set. Two measurements
close it. The test suite compiles every variant of every generated module, so all 140 GLSL feature sets
are needed. And `shaders.ts` names every device module by URL, so a bundler copies all of them into
every page's build whatever the page draws. Grouping those copies only defers the download.

### A page build's memory follows its largest worker build

With a set of 5,962 files and 2.8 GB, the engine test page's production build peaks at 15.9 GB of
resident memory. The page's own build of the shader graph costs 6.3 GB. One worker build of the
same graph costs 15.0 GB when it runs in a process of its own, and the page build's peak is about
that figure. Two worker builds do not add up, because Vite frees a worker's bundle when it ends.
Writing the set adds nothing to the peak.

Vite's worker plugin copies a worker's 5,566 device assets into the bundle of the build that
triggered the worker. In the page build the page already holds those assets, so the duplicate check
skips them. In a build of the worker alone the copy is made, which is why a child process does not
lower the peak. The plugin therefore builds workers in the page build's process, as Vite does.

The plugin's transform skips the device modules when it looks for sketch scripts. Otherwise it would
take `new URL('./shaders-<name>.js', import.meta.url)` inside a generated module as a possible sketch
address, and read each file in full to look for `defineSketch(`. That is a pass over 5,566 files and
2.8 GB in every page build. A generated shader file is never a sketch, so the plugin skips the
address without reading the file.

The set's own size lowers every copy at once, so the savings in the sections above also lower this
peak.

## One core and one checkout

- A page stops with E1402 when its engine core was built from other Rust sources than the checkout holds. The generated shader modules and the cores have separate caches. After a commit that changes Rust, run `bun run build` before any page test. The error names the missing function or the stamp.
- A run that spans a change of the checkout has mixed results. Even a small commit can stop a page that loads after it. Start a gate run when the tree is still, name the commit in the run's record, and run one showcase scene at a time so a stop costs one scene.
- Bind group layout ids are unique for each WebGPU renderer. The constants live in `bind_layout` in `crates/null3d-gpu/src/drawlist.rs`, and the generated TypeScript constants follow them. If the motion-vector pass took the subsurface blur's id 43, every WebGPU page would fail at the render worker's start with E1405. A unit test that checks the ids are unique would catch such a collision before a run.
- Run one device runner at a time. Two runners on one checkout write the same run folder, and the results mix.
