# Branches and parallel work

Work lands on main by direct push, without pull requests ([D-157](decisions/D-157-direct-pushes-to-main.md)). Merge `origin/main` into the branch, run the local checks, and push the branch's commits to main without waiting for main's CI. Fix main at once if your push turned it red.

This guide covers how a branch lands, generated files, and how to merge main into a branch. It also covers commit messages, what CI runs and why its jobs are split as they are, and several copies of the repository on one machine. [AGENTS.md](../AGENTS.md) holds the commit gates.

## Before you land a branch

Record the reasons for the change in `.dev/`, in the same branch, as [AGENTS.md](../AGENTS.md#record-the-reasons) says. Each kind of reason has its place:

| Kind | Place | Example |
| --- | --- | --- |
| A design choice or an owner's ruling | A decision record, new or rewritten to the new state: the problem, the figures, the options rejected and why, and who decides | [D-92](decisions/D-92-safari-removed-frames.md) gives the memory that Safari kept on CI, the options, and the owner's confirmation |
| A bug fix | The cause and why the fix is right, in the record or guide that owns the area | The framebuffer fault on the Pixel 10: [D-71](decisions/D-71-custom-effects.md) gives the cause, the per-call timings and the unit test |
| A device or benchmark run | A new run file in [tested devices](tested-devices.md), or a row in the [benchmark results](benchmark-results.md) | The run file of the iPad's custom effects, in the iPad Pro's folder |
| A process or tooling lesson | The guide that covers it | Put each trailer on a plain commit, because the trailer check reads only plain commits, in [Commit messages and pushes](#commit-messages-and-pushes) |

The `Docs-Checked:` trailer names the page that holds the reason, or says why the change has no new reason.

### Guidance from demos and showcase scenes

The owner set this rule for every demo in `examples/` and every showcase scene. Developers copy these scenes as the model of good visuals for their own projects. Work on any one's look or behavior may show a better way to use the engine, or a pitfall that users will hit too. The same change then adds that guidance to the user docs and to the agent skills. It is part of done for that work, not a follow-up. A fault in the engine itself is fixed in the engine, not worked around in the scene.

- Put it on the docs page of the feature that it concerns, and in the skill reference that covers that feature. A pitfall also gets a row in the troubleshooting table of `skills/null3d-develop/references/testing-and-debugging.md`.
- Say what happens, why, and what to do, with a short code example where it helps. Write for a developer who never saw the demo.
- Extend the text that a page already has, rather than adding a second place for one fact.

For example, the creek showcase's cave rock needs a layer that the sun's mask holds, or the sun shines through the rock. [Render layers](../docs/concepts/render-layers.md#layers-and-shadows) and the develop skill say that a light's mask picks its shadow casters. They also say what happens when the mask lacks a caster's layer.

## Generated files

Never commit a generated file, unless [D-105](decisions/D-105-generated-files-out-of-git.md) gives the reason to keep it. A generated file changes in every branch that changes its source, so it clashes between them. Git can also merge its text cleanly into a result that no generator makes. So git ignores each generated file, and these steps build it.

| Generated files | Source | Generator |
| --- | --- | --- |
| The skills copy for Claude Code, `.claude/skills/` | `skills/`, without each skill's evals | `bun run skills` |
| The API reference pages, `docs/api/reference/` | The doc comments on the engine's exports | `bun run docs` |
| The list of all pages, `docs/pages.md` | Each page's front matter | `bun run docs` |
| The error pages, `docs/errors/` | The engine's error table | `bun run docs` |
| The quality preset tables, `docs/concepts/quality-preset-tables.md` | The quality chooser's constants and the preset table | `bun run docs` |
| The page of shaders that load on first use, `docs/guides/first-use-shaders.md` | The shader manifest's `[first_use.*]` tables, and the descriptions in `tools/lib/first-use-docs.ts` | `bun run docs` |
| The shader library page, `docs/shaders/library.md` | The WGSL library's doc comments | `bun run docs` |
| The three.js mapping page and the porting skill's 2 copies of the mapping | `docs/data/threejs-mapping.json` | `bun run docs` |
| The placeholder pages of planned pages | The page inventory in `tools/lib/docs.ts` | `bun run docs` |
| The tested device tables, `.dev/tested-device-tables.md` | The README of each folder in `.dev/tested-devices/` | `bun run docs` |
| The shader modules in `packages/engine/src/generated/` | The shader crate | `bun run shaders` |
| The WebAssembly files, and each package's built JavaScript | The Rust crates and the packages' TypeScript | `bun run build`, and each package's pack step |

`bun run docs` writes every file of the docs generator and the skills copy, with `bun tools/generate.ts`. These steps run it:

- The install step, `bun install`. A fresh clone therefore has `.claude/skills/` and every docs page after it. The step runs no Rust build.
- The git hooks after each checkout, merge, pull or rebase, and the pre-commit hook.
- In CI: the docs job, which then checks that the generators wrote no file that git keeps. The engine package's pack step writes the docs that the package holds.
- After each full run on main passes, CI pushes main's commit with every generated file to the `generated` branch. Links that must work on GitHub point there, such as the docs link in each engine error message.
- Each release tags a commit that holds every generated file, for the Claude Code plugin, `bunx skills add` and the skill zips.

Every command that reads the shader modules builds them first: the build, the type check, the unit tests, the dev server and the browser tests. The docs generator reads the engine's types, which import the shader modules. Without them, the engine's API reference leaves out the shader features, and `bun tools/generate.ts` says so. Run it again after `bun run shaders` or `bun run build`.

After you clone, run `bun install`. After a branch switch or a pull, the hooks write the generated files again. When a hook did not run, as in a worktree before its first `bun install`, run `bun install`. A branch that adds a workspace package needs it before its type check can pass. Until then the pre-commit hook refuses every commit without naming the package, so each commit seems to fail for its own content.

### Builds

One Cargo job at a time per worktree. Two Cargo processes in one checkout take the machine's package
cache and that checkout's target folder in an order that can deadlock, and the pair then waits at zero
processor time while every other build queues behind them. When a build sits at
zero processor time, do not kill it on the number alone: sample it with `sample <pid> 1` and read
what it waits on, then tell the coordinator which lock it is. A build that is compiling shows
processor time, and one in a lock shows none.

A job waiting for a lock is not the fault: the holder is. The holder may itself be a wrapper
waiting on a busy child, so sample the child before deciding. A parent at zero per cent with a child
at several hundred is a build doing its work. A sample of a waiter shows it waiting, but the holder
goes on blocking the lane after the waiter dies. Read the lock's own file for the holder's process
and sample that one. Killing the waiter gains the lane nothing but a lost job.

On a loaded machine, run every cargo command with `RUSTC_WRAPPER=''`. The shared compiler cache runs
at background priority, so at a load of 80 or more its processors sit at zero and a build makes no
progress, which looks exactly like a deadlock. A commit whose pre-commit hook compiles through the
cache can then wait for hours. With the wrapper empty the compiler runs at normal priority and the
same check finishes in minutes. A commit stalls the same way as a build, so a pre-commit that hangs
is this fault and not a failing check.

A cache server can also wedge on its own, with no load to blame. It still answers on its port but
compiles nothing. Every `rustc` of the build's tree then sits at zero processor time for an hour or
more. A server that has run for days can do this. Sample the whole tree rather than one process.
When every compile is idle and the server's own processor time does not move, stop the server and
start a fresh one. The queued compiles then finish. The heavy lane leaves the wrapper out unless a job
asks for it with `NULL3D_SCCACHE=1`, because a stalled cache costs more than a shared crate saves.

That "leaves the wrapper out" needs one care. `~/.cargo/config.toml` sets
`[build] rustc-wrapper = "sccache"` for every checkout, and unsetting `RUSTC_WRAPPER` does not
override a Cargo config file. So a job that wants no wrapper must set an empty one:
`RUSTC_WRAPPER= cargo ...`, or `CARGO_BUILD_RUSTC_WRAPPER=` in the job's environment, since Cargo
treats an empty value as no wrapper. A job that only unsets the variable still compiles through the
server. When the server wedges, such a job sits at zero processor time. It holds its target
folder's lock meanwhile, so the next job in that checkout waits behind it too.

A queue job runs at normal priority. By the owner's ruling, the queue clamps a job to background
priority in one case only: while a timing run measures. Clamped jobs can sit frozen, with seconds of
processor time in an hour. Meanwhile one shader rebuild at normal priority uses thirteen of the
machine's eighteen cores. A blanket clamp on a Mac set aside for the team buys nothing and costs
hours. A clamp on recent use of the keyboard or pointer freezes the fleet whenever the owner sits at
the machine. That is most of a working day. A build that runs slowly beside them beats one that
does not run. The queue sets a job's priority when it starts, so a waiting job keeps its rule.
Restart it after a change of rule. The page-build lock refuses to be taken at
background priority, so a job clamped that way says so rather than hanging.

One flag, `PRIORITY=1`, sorts a job ahead of every other waiting job in its lane. The gate that checks
and pushes a landing may set it for its own checks only. Those are the unit suite, the heavy checks,
the size check, the limits report, the type check and the Rust compile check, on every range that
gate handles. The gate reports each use to the landing session for the status log. A helper never
sets it, and nobody sets it for a helper's build, picture run or measurement. It is never used while
a timing window is open. The jobs that it passes keep their order among themselves.

A build compiles the Rust crates for two WebAssembly variants and the build tools, writes the shader
modules for every feature, and then builds the test page for the size report. It is the longest step
in a landing, so keep the count down. Every build cache lives under one root, `null3d` under
`XDG_CACHE_HOME` or `~/.cache/null3d`, each in a named subfolder: `shader-modules`, `shader-cache`,
`wasm-artifacts`, `samples`, `gpu-check-baselines`, `size-memo` and, when sccache is installed,
`sccache`.
`NULL3D_BUILD_CACHE` names another root, and each per-cache variable names one folder.
Clearing the root is always safe, because every entry is a pure function of its inputs, so re-checking
a branch on a moved main is cheap.
[D-176](decisions/D-176-wasm-artifact-cache.md) and
[D-177](decisions/D-177-build-cache-module.md) give the keys, and
[Benchmarks](benchmarks.md#build-caches) the figures.

- `bun run build --pages-only` while developing and looking at a scene; the full `bun run build` when a
  landing needs the size check. `NULL3D_NO_CACHE=1`, or `--no-cache`, builds every file again.
- The build keeps the page build's printed report, which lists every file it writes. The first-use
  shader files are split by feature family, so the report passes a megabyte. The capture's default
  limit would kill the child, and the build would report only "the production build failed" with no
  error. So the capture holds 64 MB. The test tool's page build prints the same kind of report. Its
  capture holds 256 MB, because the texture-cache page's build fills the default limit.
- A cache is used only when its entry is whole. The shader modules cache, for example, requires every
  module that `shaders.ts` loads, from its imports and the device module names its tables hold, and a
  record that names the bytes of each of them. A set that misses one, or holds a file with other bytes
  than its record, is a miss, so the build runs again rather than reporting "up to date" while a file
  is absent or half written.
- A checkout's own record of its modules also keeps each module file's size and time of change, to
  the second. When every file still has them, the modules are the ones the record hashed, and the
  check reads no byte; otherwise it hashes the set, about 2.8 GB. Each commit's type check and test
  run starts with this check. It takes 8.6 to 36 s by hashing, and 0.3 s with the sizes and times.
- Each cache prunes itself: while it holds more than 24 GiB it removes its least recently used entries,
  and an entry used within the last two hours stays, because another checkout's build may be reading
  it. A cache key names every input of the build, including the build's own code, and a build hashes
  its inputs again before it stores anything, so an edit that lands while a build runs is never stored
  under the key of the state before it.
- Never a build beside a browser or image run of the same worktree. A half-written core makes a page
  fail for no reason (`E1402`, `E1406`). Builds themselves may run at the same time: each stages its
  output in a folder of its own, named for the build's process, and Cargo locks a target folder while
  it writes. A size check takes the checkout's own lock, `target/build.lock`. The base commit is built
  with that commit's own build script, in a base tree under this checkout's target folder. Size checks
  of two checkouts therefore run at the same time.
- Each checkout builds Rust into its own `target` folder. Never point two checkouts at one Rust build
  folder, with `CARGO_TARGET_DIR` or `NULL3D_CARGO_TARGET`. Cargo finds the engine's crates at the
  same workspace paths in every checkout and judges them fresh by file times. So a shared folder lets
  one checkout compile or link against another checkout's build of `null3d-gpu`, `null3d-render` or
  the shader compiler. The caches above then store that output under the right key, and the bad entry
  outlives the build. A branch can then get a stale shader compiler, another branch's GPU constants,
  or a core without its own feature.
  [D-177](decisions/D-177-build-cache-module.md#one-rust-build-folder-per-checkout)
  gives the reasons.
- sccache, when installed, compiles the dependency crates once for every checkout. The build uses it
  through `RUSTC_WRAPPER` when it finds `sccache` on the `PATH` and no wrapper is set; an empty
  `RUSTC_WRAPPER` turns it off. sccache keys each compile by the contents of its sources, flags and
  dependencies, never by file times, so sharing it across checkouts is safe. Without sccache the
  build runs with no wrapper, as in CI.
- When a core change seems to be ignored, build with `NULL3D_NO_CACHE=1`, and check the flags word
  that a material row holds before looking anywhere else.

A project that the Vite plugin builds has a shader cache of its own. The plugin keeps every compiled
shader in that project's `node_modules/.cache/null3d-shaders`. The key is the WGSL, the path, the
variant spec and the compiler's version. A game's second `vite build` therefore compiles only the
shaders that changed. On a small project of eight shaders a cold build took 2.87 s and the next took
0.30 s. The plugin cannot load repository tooling. So it repeats
[D-177](decisions/D-177-build-cache-module.md)'s three rules on its own: an atomic write, a miss when
an input changes, and one opt-out. `NULL3D_NO_CACHE=1`, or Vite's `--force`, ignores it.
[D-175](decisions/D-175-vite-plugin-shader-cache.md) gives the figures and the key.

The engine's own shader build has a per-entry cache too. `bun run shaders`, and every command that
runs it, passes `--cache ~/.cache/null3d/shader-cache/<folder>` to `shader-build`. The build keeps
each entry's compiled output under that folder. A change to one shader then compiles only that
shader, and a change to a library module compiles only the entries that import it.

The folder is the one whose `compiler` file records the same fingerprint as the compiled
`shader-build` program's bytes, and the fullest one when several match. A compiler source change
that leaves the program identical, such as a comment or a test in a dependency crate, therefore
reuses every entry: all 79 entries in 19 s, against 50 to 70 minutes for a rebuild of every
entry. A change that alters the program gives other bytes, and the
build reads a folder that only that compiler wrote. The source stamp names a new folder, and it is
the compiler part of CI's cache keys; when a folder of that name already holds another compiler's
entries, the new compiler takes `<stamp>-<fingerprint>`. [D-248](decisions/D-248-shader-cache-compiler-program.md)
gives the reasons and the measurements.

CI's restore falls back, after the prefixes that name a stamp, to one that names none. A source
change that leaves the program identical therefore also restores the entries of an earlier stamp.
The action saves the folder that the build used, and the build job passes that folder to the shader
tests. A shard hands over its new entries under the name of the folder that holds them, and the
build job unpacks them into its cache by that name, so a shard that filled an earlier stamp's
folder fills the folder that the build reads. The program goes under the current stamp's folder,
where a build looks for it first.

On the Mac, with a manifest of 54 entries, a cold build of all of them took 442 s. A
second run with nothing changed took 10.6 s and compiled none. A change to the one file that the two
cull entries share took 10.4 s and compiled 2 entries. A change to `lib/math.wgsl` compiled the 31
entries that import it, through `null3d::lighting` and `null3d::area_lights`, and took 356 s.
`--no-cache`, or `NULL3D_NO_SHADER_CACHE=1`, compiles every entry again.
[D-56](decisions/D-56-first-use-shader-files.md) gives the reasons and the key. CI keeps the same two
shader folders in the Actions cache, under the same keys ([CI's jobs](#cis-jobs)).

The folder of a stamp also keeps the `shader-build` program of that compiler, in `program/`. The
stamp covers every source of the program, so a kept program is the one that cargo would build. A
build of the same compiler runs it and compiles nothing, in any checkout. Cargo builds it only for
a new stamp, and the folder then keeps it. The Rust cache keeps no crate of the workspace. So
without the kept program, every CI job that runs the shader build would compile the program first.
That compile takes about 45 seconds in each `shader-entries` job and again in the `build` job, which
every later job waits for (run 40056066922).

`bun tools/shaders.ts --entries-shard i/n` compiles shard `i` of `n`, counted from 0, of the
manifest's entries. It stores them in the same per-entry cache and writes no module. It splits the
builds by build cost, as the shader tests do. So an entry that costs more than an even share goes to
the shards in parts. The cache keeps each part in a file of its own, named for the entry, its key
and the part. An entry's key reads only its own source, its manifest table and the stamp, and a
shard keeps every library module. So an entry that a shard stored is the entry that a whole build
looks for. A whole build that misses an entry joins a complete set of its parts of one count into
it. It then stores the entry whole and removes the parts. The join reads one part at a time, in its
stored form, and writes the joined entry as it goes. So it holds no more than a read of the whole
entry.
A shard whose part the cache holds as a whole entry reads the part's builds from it
([D-235](decisions/D-235-shader-entry-parts.md)). `--entries-out <folder>` copies the entries that the run stored into
the folder, and none that the cache held before. Shard 0 also copies its program there, so the job
that joins the entries does not compile it. Several machines can then each fill a share of the
cache. A build that first copies their folders into the folder that
`bun tools/shaders.ts --cache-keys` names, `<entries-dir>/<stamp>`, which a run with an empty
entries cache writes, compiles none of their entries. One entry,
`standard_maps`, makes 77.8% of the builds. With whole entries, its shard took about three quarters
of a whole build: 23.2 minutes in run 39799984654.

### A clash on a generated file

Never merge a generated file by hand. Take main's side, run the file's generator, and commit what the generator writes.

- For a file that git does not keep, main's side is its deletion: `git rm --cached <path>`. The file stays on disk, and the generator writes it again.
- Git keeps the constants that TypeScript shares with Rust, `packages/engine/src/generated/core.ts` and `gpu.ts`, and the render graph's text dump in `crates/null3d-render/tests/snapshots/`. Take either side, then run `NULL3D_UPDATE_GENERATED=1 cargo test -p null3d-wasm -p null3d-gpu -p null3d-render`, and stage what it writes. Run it after every merge of main, also when git reports no conflict.

### Generated files that git keeps

[D-105](decisions/D-105-generated-files-out-of-git.md) gives the reason for each. They are:

- The constants shared with Rust, and the Rust tests' snapshots
- The three.js test fixtures, the meshopt test files and the image references
- The vendored Basis and meshopt builds
- The benchmark records and the README's animation
- What a release writes: the version numbers, `CHANGELOG.md` and the plugin's marketplace file
- The lock files and the sample content's manifest
- The list of milestone task IDs that a `Task:` footer may name

A new kind of generated file goes into `.gitignore`, unless its branch adds its reason to D-105.

## Merge main into a branch

- Merge main into your branch. Do not rebase a branch that you pushed, because a rebase needs a force push (see [Commit messages and pushes](#commit-messages-and-pushes)).
- Never merge a generated file by hand. [Generated files](#generated-files) says how to resolve a clash on one.
- A merge commit holds only the resolution of its conflicts and mechanical fixes. Mechanical fixes are files that a generator writes again, renumbered entries, and edits that the other side's change forces, such as a renamed import. Write anything else in a normal commit before or after the merge: a feature, a test, a shading change or docs text. No history search finds a feature or a measured figure that a merge holds.
- Before a push, `bun tools/hooks/check-merges.ts <base>..HEAD` reads each new merge against git's automatic merge, as `git show --remerge-diff` does. It refuses a merge with more than 30 words of new work, or any new shader code. It also refuses a binary file that the merge changed itself. To fix a refused merge before you push it, undo the new work with `git commit --amend`, then commit it again on top. When the check cannot tell that an edit is mechanical, add a `Merge-Edit:` trailer to the merge's message. It names the edit and says why, such as `Merge-Edit: lit.wgsl passes main's new finish() argument`.
- Check the shared numbers after the merge. Two branches can each take the next free number, and git then merges both lines without a conflict. The shared numbers are the error codes (`packages/engine/src/errors/codes.ts`) and the scene command numbers (`crates/null3d-wasm/src/constants.rs`). They are also the draw list's opcodes and pipeline template numbers (`crates/null3d-gpu/src/drawlist.rs`), and the decision record numbers. The engine's own templates take numbers below 128, the first custom template. Custom materials, effects and tone curves take numbers from 128 up, which the sketch gives out at run time. The engine's techniques, those of [D-142](decisions/D-142-more-techniques-before-1-0.md) among them, use nearly every number below 64, so the line at 128 leaves them room. A unit test checks that each engine template has its own number below 128. The bindings and slots that a shader and its bind group layout share are shared numbers too. A unit test catches a clash in some of these lists, such as the opcodes, but not in all of them. The docs check, `bun run docs:check`, refuses two decision records with one number.
- Build and run the quick checks again before you push the merge: lint, types, docs, skills and unit tests. Then rerun the browser and image tests only of the areas that the merge's conflicts touched. CI runs every test once the branch is on main.
- Run a branch's own copy of a hook's tool, such as `tools/hooks/check-trailers.ts`, from that branch's checkout. Another checkout's copy can be older, and refuse a valid `Size-Growth:` name.
- A merge that brings Rust changes leaves the built WebAssembly cores older than the checkout. Every browser run and picture run in that tree then fails with `E1402`. The message says the threaded engine core was built from other Rust sources. It reads like a packaging fault. The cure is a rebuild, so rebuild after such a merge, before any browser run.

## Commit messages and pushes

- A push to main runs a check first, `tools/hooks/pre-push.ts`, which the owner approved ([D-157](decisions/D-157-direct-pushes-to-main.md)). A landing's push to the milestone branch, which the CI session makes, runs the commit checks and the guards below. It reads the messages and trailers from where the branch left main, as CI's `commits` job does. The GPU check's and the Mac references' trailers are read over the whole range. So an earlier commit of the branch may carry the trailer that a later one needs. It reads the merges and the copies over the commits that the landing adds. With `NULL3D_LANDING_CRATE_TESTS=1`, a landing that changes Rust also runs the tests of the crates it changes, in the job queue's CPU lane. That is opt-in, because a landing's push can wait half an hour for a CPU slot without starting cargo. A timeout then leaves the hook waiting. CI's Rust tests catch a crate's fault a run after the landing. A push to any other branch runs nothing, so saving a branch stays fast. The check prints each command it runs and why. It runs commitlint and the trailer check over every commit that the push adds to main, as CI's `commits` job does. It runs the merge check and the copy check over them too. Then it runs the guards over the tree, which a landing on the milestone branch runs too. Those are the decision record check, the repository's quick check (`bun run check`: the lint, the picture references and the add-on checks), and the unit tests that read every package or spec (`GUARD_TESTS` in the hook). The tests cover the release guide's package table, the CDN build's add-ons, the shipped network calls, the timing specs' switch names, and CI's workflow against the scripts and files that its jobs read. They also cover the size report's list of the engine's parts. They take seconds, where the unit suite takes minutes. They are there because a merge skips the commit hook. Two records can each take the next free number on their own branches, and only meet at the merge. A merged package, network call or cost spec can miss the guide or the record in the same way. Without the guards, CI catches each such fault only a run after the push. So a bad message, a bad trailer or a merge that carries new work is caught before the push, not by a red main after it. When the push changes Rust code or Cargo settings, it also runs `cargo check --workspace` and the tests of each changed crate. The tests run through cargo-nextest's `ci` profile with `--no-fail-fast`, or through `cargo test` where nextest is missing. A changed workspace `Cargo.toml`, `Cargo.lock` or Rust setting tests every crate. The test that builds every shader runs in CI only, as it takes half an hour or more.
- A push that changes no Rust file skips the cargo steps, because the merged Rust tree then holds main's own bytes, which main's CI has compiled. The type check still gates the push, since it reads the merged tree. The cargo check follows as its own queued job, and a failure there is fixed by the next push. Two things must hold: the branch's own diff changes no Rust file, and the merge that it just resolved changes none. [D-157](decisions/D-157-direct-pushes-to-main.md#a-rust-free-push-needs-the-type-check-only) gives the ruling and the criterion.
- The check compares with the commit that git reports for main before the push. When that commit is not in this checkout and no local main ref meets the pushed commit, it refuses the push and asks for a `git fetch origin main`, since it cannot say which commits the push adds.
- The cargo steps compile the working tree, so push from a clean checkout of the commit that you push. They use the checkout's own Rust folder, or `CARGO_TARGET_DIR` when it is set.
- On the Mac that runs the helpers, the git setting `null3d.jobQueue` names the job queue script. The check then runs the message and trailer checks in the queue's quick lane and the cargo steps in its CPU lane. So a push does not load the Mac outside the queue. A push may therefore wait for a slot. The guards over the tree run outside the queue, as they take seconds. Through the quick lane, at a load near 100, the wait for a slot plus their own run can pass the lane's five-minute limit. The lane then refuses a landing that passes when run directly. The environment's `NULL3D_JOB_QUEUE` names the script too. Elsewhere the steps run directly.
- git opens the connection to the remote before it runs the check, and holds it, saying nothing, until the check returns. The hook needs the ref list that the negotiation produced. A peer closes a connection that says nothing for about six minutes. After that, git writes the push into a socket that has gone, and prints nothing. Nothing is pushed, and the status says only that a write failed. A held session to `github.com` that writes nothing ends after about 365 seconds. The check reads the remote's URL from git's own hook arguments, which the hook's body passes on. So the check refuses a push whose remote it reaches over ssh, when nothing keeps that connection alive. It names the setting to add. Put `ServerAliveInterval 20` under the host in `~/.ssh/config`. A checkout may name it instead, through `core.sshCommand`. A queue makes the check long, and so a machine that runs a queue needs this most. The cargo steps take about 390 seconds of test time through the queue, against 135 seconds run directly. Only the longer time outlives the connection.
- Only in an emergency, skip the check with a `Push-Check-Skipped: <reason>` trailer on a commit of the push. The reason names the emergency, such as a red main that this push fixes while the job queue is stopped. The check prints the reason and runs nothing. `git push --no-verify` skips every hook, so never use it.
- Push over the ssh remote fails while the key agent refuses to sign. The message reads `signing failed ... agent refused operation`. A fetch on the same machine can then hang until it times out. The web address works, through the GitHub CLI's saved login: `git -c credential.helper='!gh auth git-credential' push https://github.com/null3d-engine/null3d.git HEAD:main`. It runs the same pre-push check. The check reads the working tree, so the address does not matter. The agent can go on refusing for the rest of the session, so send each landing over the web address until it signs again.

- A hook that waits is not a hook that is wrong. When a commit or merge hook stops on a lock that another job holds, the machine is loaded, not faulty, and the wait ends when that job ends. Stop and tell the coordinator rather than making the commit with `--no-verify`. A merge made past the hook must be checked by hand before it lands.
- A merge commit must pass the commit-message check, as every commit does. A message such as `Merge origin/main into <branch>` passes, and so do git's own merge messages. A message such as `merge origin/main` fails, because the check reads it as a commit without a type.
- Never force push a branch that you pushed, so never amend, rebase or squash a commit that you pushed.
- Only the owner may allow a rewrite. An example is rewording pushed commits that skipped the hook and lack a trailer, since the commit check reads every commit of the branch. Such a rewrite changes only those messages. Prove every file byte-identical to the tip it replaces, and check the trailers over the whole branch. Then push with a lease that names the commit it replaces. No other exception exists.
- A `Task:` footer names a listed milestone task that the commit delivers part of, or says `none`. The commit-msg hook (`tools/hooks/check-task.ts`) refuses free text and IDs that are not in `tools/hooks/task-ids.txt`. A footer can name a task whose work the commit does not deliver, so the milestone count reads only each task's audited status.
- Main keeps every commit of a branch, its merge commits too, so every plain commit's subject becomes a release-notes line, and the commit-message hook checks each one. A pushed commit with a bad message stays on the branch, and on main once it lands.
- Put each trailer on a plain commit, never on a merge commit; an empty commit can carry it. The one exception is `Merge-Edit:`, which explains an edit in the merge itself (see [Merge main into a branch](#merge-main-into-a-branch)). Main keeps the messages of a branch's plain commits and drops the merge commits' messages. CI's trailer check and size check therefore read only the plain commits, so a trailer on a merge commit counts for nothing ([Benchmarks](benchmarks.md#download-size)).
- To fix a bad message on a branch that is not on main yet, put the branch's files in one clean commit on a new branch. For example, `git switch -c <new-branch> origin/main`, then `git merge --squash <old-branch>`, then commit with a good message. Land the new branch, and delete the old one. Do not force push the old branch.
- The same applies when a branch carries copies of commits that main already holds, and a commit gate rejects one of the copies. Put the branch's files in one clean commit on a new branch from main, land it, and delete the old branch. Do not force push either branch, and do not loosen the gate. A copy can fail a gate that its original passed, such as a `Size-Growth:` trailer that names shader files by their names before a rename. The owner approved this way.

## Landing a branch

A branch lands on main by direct push ([D-157](decisions/D-157-direct-pushes-to-main.md)). No reviewer reads it first, so the author runs every check that the change needs.

1. Push the branch to its own remote branch as you work, to save it: `git push origin HEAD:<branch>`.
2. Fetch, and merge `origin/main` into the branch. Resolve each clash section by section, and keep both sides' additions. Take main's copy of a generated file and generate it again.
3. Run `bun install`, then build, then compile the merged tree at once: `cargo check --workspace` and `bun run typecheck`. A merge that keeps both sides of a struct or a constant is often valid text, so only a build finds the fault. A plain `bun install` can report "no changes" and still leave a workspace link missing. The type check then fails on an import of the package that the merge added, such as a new add-on in `tests/package.json`. Run `bun install --force` in that case, which writes the link.
4. Run the local checks: `bun run check`, `bun run typecheck`, the unit tests, `cargo nextest run` for each crate that changed, the docs, style and skills checks, and the browser and image tests of the parts that the branch changes. An image change needs both reference sets. Run `bun run build:check-size`, and [the GPU check](#the-gpu-check) when the branch changes how the GPU draws. A change that adds an engine module or a first-use file needs that size run every time: the picture and unit checks do not build the pages, so a module that the size report does not name stops every production build, and every helper's worktree with it. Check the trailers with `bun tools/hooks/check-trailers.ts origin/main..HEAD`.
5. Push with `git push origin HEAD:main`. When git refuses the push because main moved, merge `origin/main` again, rerun the checks that the new commits touch, and push again.

- A helper never pushes the milestone branch. The pre-push hook refuses a push to `m3-start` unless the session that checks the landings sets `NULL3D_MILESTONE_LANDING=1`. Push your branch to its own ref and let the coordinator land it. Unfinished work on the milestone branch reaches every other helper and CI.

- A landing may not add a problem to the milestone status. The pre-push hook runs the status tool's check, `bun tools/pr-status.ts --check`, on the pushed commit and on the branch's commit on the remote. It reads the remote's commit in a worktree of its own. It refuses the push when the pushed commit has a `stale:` or `owed:` line that the remote's commit lacks. The refusal names each line and its task. A landing may remove such lines. When the landing session changes the status on purpose, the CI session pushes with `NULL3D_STATUS_CHANGE=<reason>`. The hook then prints the reason and the lines it lets through. The check must run on the pushed commit, so the hook refuses a push from a checkout without the plan. A first push of the branch compares with where it left main. The check does not run there, so such a push needs the reason. A push to any other branch runs no such check, so a helper can always save work.

- The CI session checks and pushes the milestone branch, by the owner's decision ([D-259](decisions/D-259-landing-push-gate.md)). The CI session is the session that keeps CI working. The coordinator's landing session merges branches in its own checkout. It then hands the CI session each range, with its base and head, and names the CI session's own commits in it. The CI session runs seven checks on the range, in the landing checkout, and sends each slow one through the job queue. Nothing commits in that checkout until they end, or the later checks read another tree. They are `bun run limits` read row by row, the type check, `cargo check --workspace`, the size check, the whole unit suite (`bun run test`) and the heavy checks (`bun run test:heavy`). The heavy checks are the tests that hold gigabytes of memory, which the unit suite leaves out. Every range also runs the fresh-project test (`bun run test:packages`), as CI's `packages` job runs on every push. A list of trigger paths can miss some of the test's inputs, so no range skips the test ([D-259](decisions/D-259-landing-push-gate.md#decision)). The CI session pushes only when all of them pass, with `NULL3D_MILESTONE_LANDING=1`. It runs every unit test and heavy check, not only the tests of the changed code. A test far from a change can pin a figure that the change moves. The command line tool's add-on check, `check-addon`, for one, holds its own copy of the budget for a file that loads after the start. Its test compares that copy with the engine's. The push hook then runs the commit checks and the guards, the quick check (`bun run check`) among them. When a check fails, the CI session refuses the range, and names the commit, the file and the command that shows the fault. It never pushes its own commits on its own read: a fresh helper reads them first.

- Three sessions share the milestone's work, by the owner's set-up ([D-268](decisions/D-268-three-sessions.md)). The landing session runs the helpers and merges their branches in the landing checkout. It keeps the task ticks, the pull request's description and the status notes. The CI session checks and pushes each range, as above, and improves CI. It also makes every build faster and cuts the memory that each build needs, in CI and on the machines that build the milestone. A task in the milestone plan that does such work goes to the CI session ([D-268, addendum](decisions/D-268-three-sessions.md#decision)). The PR audit session audits the pull request's task ticks, as [Coordinating helper agents](#coordinating-helper-agents) says.

- A new push to main cancels main's running CI run, by the owner's choice: only the newest main matters.
- Never wait for main's CI before a push: not for a running run, and not for a red one. When a finished run on main fails because of your push, fix it at once. Others keep pushing meanwhile.
- When a job on main fails, read its log, and find whether a push caused the failure. `gh run view <run> --log-failed` prints the failed steps. A test that fails only under load, or a run that GitHub cancelled when a runner shut down, says nothing about the code. Run the failed jobs again with `gh run rerun <run> --failed`. Otherwise fix the cause and push. Record the cause in `.dev/` either way.
- A run that a later push cancelled still holds the jobs that had already finished, and those failures are the signal. Read them with `gh run view --job <id> --log`, which answers once the cancellation has gone through; `--log-failed` on the run itself does not. A run's status says whether it finished, not whether its finished jobs still count. A run dismissed as cancelled can hold the only readable account of several failing jobs. Read the finished jobs before deciding a run told you nothing.
- A cancelled job reports no test results at all, so a list of failures taken from a run that lost jobs is not complete. Its conclusion is `cancelled`, it prints no summary of the tests it ran, and the tests it never reached appear nowhere else in the run. The faults inside it then read as faults that never existed. A time limit that cancels four browser shards can hide three faults that are red on main. None of them then appears in any summary of the run (run 38824482127). A later landing then takes the blame for a regression it did not cause. So when a run has cancellations, read each cancelled job's own log before trusting any list of failures. Use `gh run view --job <id> --log`. Read the jobs that never reported as missing evidence, not as jobs with nothing to say. A run whose verdict matters and that lost jobs is run again rather than reasoned about. Run every job of it afresh with `gh run rerun <run>`. [Image tests](image-tests.md#ci) lists the shards and their limits.
- Two tests are known to fail only on a loaded machine. One is the GPU loss test "draws on after a GPU loss" on SwiftShader. It got no frame in its fixed recovery wait, in full local runs while the Mac's load was 21 to 30. The other is the benchmark page test of S4 on SwiftShader. It drew no frame in its short run, in CI runs 37289400132 and 37578361814. Both passed when they ran again. In each, the slow software GPU took longer than the test's fixed window to draw the first frame after a start or a loss. A rerun alone shows whether a failure is this ([Image tests](image-tests.md#tests-on-slow-machines)).
- The Safari and Firefox jobs compare the image tests with the Mac's `chrome-real-gpu` references. A test without one of these references, or without its SwiftShader reference, fails `bun run check` ([Image tests](image-tests.md#references)).
- CI's last job, `ci-passed`, waits for every other CI job, and it passes only when each one passed. Only a push to a milestone branch may skip jobs, and only the full run's jobs. The one other job that may skip is a pass-keyed job whose every part passed in an earlier run, as the `passes` job names it. Main's rules require `ci-passed`, not each job, so a CI job can split into more shards and change its name with no change to the rules.

### A pull request of a long branch

A pull request remains useful for a long piece of work. On a pull request, the `commits` check
reads every commit from the merge base with main, not only the latest push. A branch that lives for
weeks carries commits from before a rule tightened, and those commits fail the check. Most such
findings are subjects that name a decision record and `Size-Growth:` values that name no measured
file.

A squash merge keeps the pull request's title and drops every commit message, so those findings
never reach main. To avoid a red gate before the merge, squash the branch to one commit first:

```
git reset --soft "$(git merge-base origin/main HEAD)"
git commit -F message.txt
```

Check the whole range before the merge: `bun tools/hooks/check-trailers.ts origin/main..HEAD` and
`bunx commitlint --from origin/main --to HEAD`. A direct push has no such problem: the pre-push
hook and CI read only the commits that the push adds.

### Before you push to main

Two branches that change the same code files land one after another. The smaller or readier one lands first, and the other merges main again and runs its checks before it pushes.

- Run `bun run build:check-size` with current main merged. A file that passes against an older main can grow past the limit against a newer one.
- Run an add-on check in a checkout with `bun packages/cli/bin/null3d.js check-addon <folder>`, not `bunx @null3d/cli check-addon`. `bunx` starts the command under Node, and a checkout's Vite plugin exists only as TypeScript source there, so the `shaders` and `sizes` gates skip. A skipped gate reads as a pass in the summary, so test those two gates with the `bun` form.
- Two branches that add text at one place of a file clash when the second one merges main. Resolve the clash by keeping both sides. To avoid such clashes, each run in the record of [tested devices](tested-devices.md) is a file of its own ([D-97](decisions/D-97-tested-devices-per-file.md)).
- Main's run after the push is the last check of the combined code. The size check of a run on main compares with the commit before.

### The GPU check

CI's benchmark job has no GPU timer, so it cannot see a change that slows only the GPU. A change can make S4 and S6 on WebGPU 5 to 33 times slower on the Mac's GPU and still pass every CI job ([D-109](decisions/D-109-gpu-time-guard.md)). So a branch that can change the GPU's work runs the GPU check, and records the result. The check needs a computer with a GPU of its own.

- It must run when the branch changes `crates/null3d-shaders/src/`, `crates/null3d-shaders/wgsl/` or `crates/null3d-shaders/shaders.toml`. It must also run when the branch changes `packages/engine/src/gpu/`, `packages/engine/src/render/` or `packages/engine/src/quality/`. Changes to tests there do not count.
- Run the check in two steps once the branch's code is final. First run `bun run bench:gpu-check --prepare`, which uses only the CPU. It builds the branch and its benchmark pages. It also makes sure that a shared cache holds a build of the branch's merge base with origin/main. Then run `bun run bench:gpu-check --measure` on a Mac whose load is low. It builds nothing. It runs S4 and S6 on WebGPU at Medium and at High, in turns, in Chrome. With neither option, the check runs both steps in turn. [Benchmarks](benchmarks.md#the-gpu-checks-two-steps) says how the cache works and what each step costs. Set `NULL3D_PORT` to a port of your own: the check takes that port and the next.
- It prints one line, such as `GPU-Checked: 061177262..a0a7c1777 passed: s4 medium 1.86 to 1.90 ms (+2.2%, same, noise 0.5%); ...`. Put that line on a plain commit, an empty one if need be, such as `test: record the GPU check`. The trailer check reads every commit of the range, so the line may go on any of them. Run the check once the code is final. Run it again after a later change to those files, so that the line measures the code that lands.
- Each page's figure gives its direction and, beside it, the noise it was judged against: `same`, `faster` or `slower`. Two tests decide it, not one. The first is the page's allowance for its measure, which is 25 per cent and 0.3 ms for GPU time. The second is twice the standard error of the rounds' ratios. A reader does not have to work the direction out from the percentage.
- Each millisecond pair in that line is one build's median GPU time per frame, over its kept runs. The percentage is a different statistic: the median, over the rounds, of each round's ratio of the new build to the baseline. Its noise is the standard error of that median. The two differ whenever the rounds spread, because the ratio of two medians is not the median of ratios. The verdict rests on the percentage and its noise, not on the medians. A reader who divides one median by the other and gets another figure has not found a fault.
- CI cannot run the check, since its machines have no GPU timer. So the trailer is the author's record that the check ran, and what it measured. The trailer check only fails when the trailer is missing or says nothing. It cannot check the figures.
- `failed`: a page's GPU time grew more than 25% and 0.3 ms. Find the cause and fix it. A slowdown on purpose needs a `Bench-Expected:` trailer that names it, such as `Bench-Expected: s4/null3d-webgpu/gpu-time: a second shadow pass`, and then a new run.
- `not measured`: the browser gave no GPU times, as on a machine without a GPU timer. Run it on a computer with one.
- `not judged`: the benchmark pages changed between the two commits, so the builds drew different work. The line still gives the figures, and the reviewer judges them.
- A change that cannot change the GPU's work, such as a comment in those folders, still needs the trailer. It then says why no check ran, such as `GPU-Checked: not run; only comments change in packages/engine/src/gpu/`.
- Each night, the owner's Mac runs the same check on main against the night before. That catches what slips past a branch's own check, within a day.

## What CI runs where

Each push to main runs every job, on the pushed commit ([D-157](decisions/D-157-direct-pushes-to-main.md)). Main's jobs also keep the caches, and `wasm-checks` keeps the commit's sizes. Each push to a milestone branch, such as `m3-start`, runs the quick checks. A run started by hand runs every job on the branch that it names: `gh workflow run ci.yml --ref <branch>`. The workflow answers no pull request event. A milestone's pull request still shows the push runs of its head commit, since GitHub lists every check of that commit. [D-249](decisions/D-249-milestone-push-runs.md) says why the quick checks run on the branch's pushes and not on its pull request.

- A new push to main cancels main's running run, so only the newest main is tested.
- A newer push to a milestone branch never cancels the branch's run in progress. The newer run waits, and GitHub keeps only the newest waiting run, dropping an older one before it starts any job. So every started run ends with a result, and a burst of landings collapses into the next run. Only a cancel by hand, as when a full run is started, ends a branch's run early. A fixed wait before each run's jobs does not help: a run that outlives the wait starts every job and is then cancelled. [D-244](decisions/D-244-pull-request-runs-wait.md) has the figures.
- A newer push can drop a waiting run, so a quick run checks the whole milestone, not only its own push. The commit check reads every commit after the merge base with main. The size check compares with that merge base.
- A milestone branch's push runs and the full runs started by hand on it share the branch's caches. A part that passed in one is not run again in the other. Each also reuses the shader entries, the Rust builds and the size memo that the other saved. Start a full run when the quick run of the same commit has ended, or cancel that quick run first. Otherwise the two run the same jobs at once.
- The quick run's `ci-passed` passes with the full run's jobs skipped. So the milestone's pull request stays a draft until a full run of its head passes, and the release gate counts only a full run (`bench/lib/gate.ts`).
- CI's Chrome tests draw on SwiftShader only, and Firefox on Linux draws with a software renderer. The Mac's real GPU gets no run in CI, apart from Safari. So run the browser and image tests of the areas that a branch touches once on the Mac's GPU, before it lands. Run `bun run test:browser` with Playwright's `--grep` or a spec file, and `bun run test:images` with `--grep`. A change that Safari or Firefox may treat differently also runs `bun run test:real-browsers Safari Firefox` ([Device sessions](devices.md)).

| Event | Jobs |
| --- | --- |
| Push to main | Every job, on the code that the merge made. Main's jobs also keep the caches, and `wasm-checks` keeps the commit's sizes |
| Push to a milestone branch | The quick checks: `shader-entries`, `build`, `docs-and-tools`, `commits`, `rust-lint`, the parts of `rust-tests`, `size-base`, `size-parts`, `wasm-checks`, `heavy-checks`, `browser-caches`, `shader-compiler`, `shader-compiler-plugin` and `packages` |
| Started by hand | Every job, on the branch that the run names: `gh workflow run ci.yml --ref m3-start` |

## CI's jobs

- Every CI job should take at most 15 minutes, and its limit stops it at 20, by the owner's rules. A job should take at most about 12, so that a slow runner still fits. A long job is a symptom: [Efficient jobs](#efficient-jobs) says how to find the work it does twice or needs not do. A limit close to a job's time stops the job on a busy runner before it fails or passes. The cancelled job then fails a run that has no fault. The jobs that build shaders keep longer limits, since a cold build of every shader takes longer than 20 minutes. They are `build`, `size-base`, `shader-compiler`, the parts of `rust-tests`, the benchmark workflow's `build` and the weekly newest-nightly Rust job. Their limits come down when those jobs' times are read again. The newest-nightly job runs the tests through cargo-nextest as `rust-tests` does, with a Rust cache of its own. The cache's key holds the compiler's version, so each new nightly builds the dependencies once. The release workflow's jobs keep longer limits, as [Releases](releases.md#making-a-release) says why. The shader build compiles the builds of every entry across the machine's cores. Each build hands its entry the library files it read, in place of a second pass over the preprocessor output. The shader build has a Cargo profile of its own, `shader`. It inherits the release profile and turns off its link-time optimization and its single code unit. So the tool runs optimized, where the development profile leaves the crate's own parsing and validation code unoptimized.
- One `build` job builds the WebAssembly files and the shader modules, and every browser, benchmark and macOS job downloads them. That saves each browser shard 1.5 minutes of building. The artifact carries the engine's whole generated folder, so a new kind of file needs no new path. An artifact that names each kind of module by path misses a new kind. Every job that downloads it then finds the modules stale and builds the shaders again. That takes about 6.5 minutes in `heavy-checks`, enough to push `packages` past its limit (run 38888705807). Every job that downloads it sets `NULL3D_REQUIRE_FRESH_SHADERS`, which `tools/lib/shader-modules.ts` reads. A set that does not match its record then fails that job at once, and names the files it lacks. The `shader-compiler` shards read the native build from the entries that the `build` job saved in the Actions cache, and build only through the compiler ([D-218](decisions/D-218-efficient-ci-jobs.md)).
- CI keeps the built shaders in the Actions cache between runs, through the action `.github/actions/shaders`. It keeps the same two folders as a local build ([Builds](#builds)). One holds the module sets, by the hash of their inputs. The other is the per-entry cache, under the compiler's stamp. `bun tools/shaders.ts --cache-keys` prints the folders, the input hash, the stamp and the Actions keys, which hold the stamp, the branch and the hash. A run whose inputs match restores the module set and compiles no shader. On a machine that GitHub hosts for CI, each module of a restored set links to the cache's file. So the 3 GB set is not written twice. A machine that keeps its cache copies the set instead. Through a link, a build that rewrites a module in place would change the cache for every checkout. A run with the same compiler restores that stamp's entries and compiles only the entries whose own key changed. A new compiler restores nothing. The tools check each entry's key themselves, so a restored entry never serves other inputs. Before a save, the action deletes every other stamp and module set, so the cache does not grow. A failed or cancelled build still saves the entries it finished, under a key of its own. That matters on main, where each push cancels the run before it. The `build` and `size-base` jobs and the benchmark workflow's `build` use the action. The newest-nightly job restores the cache but never saves it.
- The organization is on GitHub Enterprise, the owner's choice ([D-194](decisions/D-194-ci-jobs-in-parallel-on-enterprise.md)). It runs up to 500 jobs at once, 50 of them on macOS. On the free plan's 20 jobs at once, a full run's last Safari shard waits 24 minutes for a machine (run 39064752033). GitHub's standard runners cost nothing on a public repository, on any plan. So CI splits its slow jobs into many short ones, and a run takes about as long as its longest job.
- The browser tests run in 37 shards, and the tests that run alone in 3. The production build's tests run in one job, `browser-production`, in two parts, each of which builds the production pages that its tests load; the other browser jobs build none ([D-220](decisions/D-220-production-pages-once.md)). The showcase HUD tests run in 3 jobs, and the benchmark page tests in 7 shards. S1's three scenes run in a shard of their own. One shard with S1, S3, S4 and S5 takes 22.9 minutes of tests (run 39854225392). The visual tests of the shadows run in a shard of their own, away from the page benchmarks. No browser shard takes more than about 10 minutes of tests, and no other shard more than about 8.
- Playwright splits the browser tests by count, so the `browser` job weights its shards. [Image tests](image-tests.md#ci) says how to retune the weights and when to add a shard.
- The size check's job, `wasm-checks`, measures the `build` job's files against the base's sizes. The `size-base` job builds those sizes beside the `build` job, or finds them in the Actions cache ([Benchmarks](benchmarks.md#download-size)). The shader compiler test runs in a job of its own, `shader-compiler`, in 20 shards that split the shaders by build cost. The split weighs each entry by the native build's cost, and the compiler's share of the work differs. Run 40056066922 built every shard. There, the 12 shards' tests took 180 to 401 s each, and their jobs 4.3 to 8.1 minutes, with about 75 s of setup. So the job runs 20 shards, where the run's 500 jobs at once leave room. Each shard reads its share's native build from the entries that the `shader-entries` jobs compiled, and runs every check that reads that build, each distinct GLSL text once across the cores. Then it builds the same share through the compiler and compares the two. The compiler builds through WebAssembly, one thread to a process, with a process for each core. 4 shards took 20 to 25.5 minutes in run 39291513923, and 8 shards 7.8 to 13.6 minutes in run 39744891020. The Vite plugin's compiler tests run in `shader-compiler-plugin`, in two parts, so no shard runs them after its own share ([D-218](decisions/D-218-efficient-ci-jobs.md)). With the compiler test in jobs of its own, `wasm-checks` takes about 0.8 minutes. Building the head, then the base, then running that test in one job takes 11.1 minutes (run 37248715227).
- Sixteen `shader-entries` jobs compile the shader entries that the caches lack, each a share of the builds by build cost ([Builds](#builds), [D-194](decisions/D-194-ci-jobs-in-parallel-on-enterprise.md), [D-235](decisions/D-235-shader-entry-parts.md)). The `build` job then joins their parts and reuses every entry. A run whose module set the Actions cache holds skips their work after one lookup. Alone, the `build` job compiles all 73 entries in about 26 minutes (run 39274030849). Whole entries split unevenly. A job with `standard_maps` holds about 78% of the builds and takes 23.2 minutes, while every later job waits for it (run 39799984654). One runner can also run the same work 2 to 3.6 times slower than another. So a job with a sixth of the builds can run out of its 20-minute limit halfway (runs 39968242466 and 40016767660). With an eighth each, the jobs compile for 198 to 265 s and take 3.9 to 5.2 minutes (run 40046196327). That is still on the longest chain of a run that changes the shaders, so the builds go to sixteen jobs. Each job hands its entries on as one archive ([D-235](decisions/D-235-shader-entry-parts.md)). The artifact's own zip packs each file alone. Six jobs' zips come to 1.28 GB, and the `build` job takes 94 s to download them (run 40022423739).
- The size check measures the engine test page in 4 `size-parts` jobs at once, and `wasm-checks` judges their sizes together ([Benchmarks](benchmarks.md#download-size)). Compressing the page's files took 23 of the check's 24 minutes in run 39261942127. Each part also compresses on every core of its machine.
- The `allocation` job runs the per-frame allocation check, `bun run bench:allocation`, on S1. WebGPU and WebGL2 each get a machine of their own. The job exists by the owner's ruling. A check that runs only by hand and in the Mac's gate can fail on main with nobody seeing it. The job runs in every full run: each push to main and each run started by hand. On SwiftShader the check draws 1,000 boxes and keeps budgets of its own for a few places ([Benchmarks](benchmarks.md#allocation-and-profiling)). Its job takes about 4 minutes there, less than a browser shard ([D-125](decisions/D-125-allocation-check-in-ci.md)).
- Formatting and Clippy run in `rust-lint`, and the tests in `rust-tests`. `rust-tests` runs the tests through cargo-nextest, which runs the tests of every test file at once. Then `cargo test --doc` runs the documentation tests, since nextest runs none. `cargo test` runs the test files one after another, which takes 6.2 of a 6.7-minute Rust job. Locally, `cargo nextest run --workspace` runs them the same way.
- `rust-tests` runs in parts at once. Four split every other test by nextest's partition, and one runs the determinism check of the test that builds every shader. That test itself runs only in `shader-compiler`, which makes the same native build with the same checks and compares the compiler's build with it. A run of it in `rust-tests` without the compiler adds no check ([D-218](decisions/D-218-efficient-ci-jobs.md)). The profiles `ci` and `whole-shader-build` in `.config/nextest.toml` pick the tests, so each test's name is written in one place. All parts run with `--no-fail-fast`, so a run reports every failing test, not only the first. In one job with every other test, the whole shader build takes about 29.5 minutes. A 20-minute limit then stops the job before the other tests report (run 38673968972). The shader module exports test builds only two small entries, among the other tests. A whole build through the WebAssembly compiler would cost it more than 1,440 seconds (run 39191671424). The determinism check covers every kind of module ([D-218](decisions/D-218-efficient-ci-jobs.md)).
- The shader parts split their tests into shards with `NULL3D_SHADER_SHARD=i/n`, with `i` from 0. The shader library splits the manifest's entries by estimated build cost: the number of builds that each entry makes (`ShardPlan` in `crates/null3d-shaders/src/shards.rs`). The costliest entry goes first, to the shard with the least work so far. The split reads only the manifest, so every job makes the same one. Each shard prints the whole split in its log, with each shard's share.
  - The textured standard material, `standard_maps`, makes 77.8% of the manifest's 68,369 builds by count, and about 80% by timed sample builds on the Mac. A split that gives each shard every nth entry is uneven. On the Mac, the shard that held `standard_maps` took 1,862.9 s, and another shard took 6.9 s.
  - So the whole shader build's shards cut an entry that costs more than an even share into parts. A part holds every kth build of the entry, in build order, and a shard holds one part of an entry at most. Four shards then hold 25.1% of the builds each, and eight hold 12.6%. The tests build without the per-entry cache. The `shader-entries` jobs split the same way, and the cache keeps each part beside its entry's key.
  - The module exports test renders whole modules, so a shard of it would keep whole entries. The shard with `standard_maps` would then hold 77.8% of the builds, however many shards there are. So the test builds no shard. It asks the compiler's `prepare_modules` export for two small entries, `pick` and `timer_mark`, and renders every module of that build. The exports hand each name to the library's module set, so the kinds of module are the determinism check's to cover.
  - The check that two builds write the same modules has a job of its own, `NULL3D_SHADER_SHARD=determinism`, and no numbered shard runs it. It builds its own list, `lit`, `environment`, `pick` and `timer_mark`, twice, at 11.4% of the builds each time. A list with `standard_maps` would build that entry twice: more than one and a half times the builds of a whole build. With its own list the check takes 113.6 s on the Mac, against 1,862.9 s for a shard that holds `standard_maps`.
- The determinism part of `rust-tests`, a shard of `shader-compiler` and a part of `shader-compiler-plugin` pass at once when an earlier run passed them with the same inputs ([D-194](decisions/D-194-ci-jobs-in-parallel-on-enterprise.md)). The key hashes exactly the files that the part reads: the shader crates, `null3d-gpu`, the Cargo files and the toolchain. The `rust-tests` key adds nextest's settings. The `shader-compiler` key adds the build tool that builds the compiler, the runner script that the Rust test starts, and the Vite plugin, whose code the runner calls. The `shader-compiler-plugin` key adds the shader module tools, the test helper that its tests import, and the WGSL that each part compiles. Each key also ends with a hash of its job's definition, as the workflow file parses: its steps, commands, tools and matrix. The hash also covers the repository's own actions that the job runs: each action's definition as it parses, and the other files in its folder. So a part runs again when how it runs changes. A YAML comment drops out, but a step's name, an action's description and a comment inside a script count. The workflow's top-level settings are not in the hash, so a setting that changes how one of these parts runs belongs in its own job's settings. A wider key runs the part again for no reason, and a narrower one reuses a pass that no longer holds. `tools/lib/ci-workflow.test.ts` fails on a script that a part starts and its key leaves out. The key also names the part's share, such as `0/12`, so a new shard count tests every share again. A passing part saves a small marker under its key, and the job summary names a reused pass. Most pushes change no shader input, so their runs skip these parts. The `passes` job works out every part's key once, from the hashes in its own step (`tools/lib/ci-passes.ts`). It looks each key up in the Actions cache's list of entries. It counts only an entry that the run could restore: one saved on the run's own branch or on main. A job whose every part passed starts no runner, and `ci-passed` counts it as passed. A job with a part that did not pass runs every part. Each part still looks its own key up, so only that part builds. A lookup that fails counts as no pass, so its job runs. A part reads its key from the `passes` job, so each key has one source. GitHub's default condition for a job needs every job before it, even several steps back, to have passed, and a skipped job is no pass. So a job after `ci-passed` reads `ci-passed`'s own result, and `tools/lib/ci-workflow.test.ts` fails on one that does not. For the same reason `shader-entries` keeps a runner per shard to find its set: every job after the build would skip with it.
- `.config/nextest.toml` runs each test of the 5 test files that count allocations with the machine to itself, as `cargo test` does. These tests count the job workers' allocations too. Under the load of the other tests, such a test can count frees from job workers that an earlier case stopped. So the counter stops counting a worker when its work returns ([Implementation notes](implementation-notes.md)).
- Those tests run first, and the one test that builds every shader next. A test that needs the whole machine waits until every running test ends. In the default order, such a test holds the run back behind the slow tests each time. The tests then take 8.2 minutes in CI, against 2.8 minutes without the isolation. In this order the tests take 2.5 minutes on 4 threads of a MacBook Pro.
- No test runs a full shader build of its own. One test in the shader crate's `build` tests builds every shader. Every check that reads the whole output runs on that build. A second build of a few entries, which together make one module of every kind, runs at the same time on another thread, for the check that two builds write the same modules. CI runs that check in its own job, as the shards above say. Other tests build only the shaders that they read, through the tests' `subset` module: the command line tests run the command on 4 shaders, and the effect tests build only their 2 hosts. A test that reads only a material's uniforms and textures builds the smallest share of its builds, since the material's source alone decides them. nextest runs each test in a process of its own, so a cache in one test's process never serves another test. A full shader build takes 280 to 590 seconds on a 4-core runner. So 17 tests that each build every shader push `rust-tests` past its limit (run 38096978506). A new check of the whole output goes into the one test, and does not add a build. CI runs that test in `shader-compiler` alone. There the shader compiler builds every entry of the manifest, one entry at a time within each of a few processes that run at once, and compares every result with the test's native build of the same builds. An entry that costs more than an even share of the processes goes to them in pieces, each a part of its builds. There is one process for each core, and no more than the available memory holds at 2 GiB each, where Linux reports that memory. One entry with no other shader is the scale a build tool asks for, and a failure names the entry; the module's answer for an entry comes back in pieces, for the reason [Implementation notes](implementation-notes.md) gives.
- Every CI run saves its caches, and every run restores its own branch's first, then main's. These are the Rust builds, the packages, Playwright's Chromium, the sample content, the built shaders and the base sizes. The workflow's `SAVE_CACHES` decides it. A branch's run saves under the branch's own ref, so the next push to it reuses what this one built. The repository's cache limit is 30 GB, which the Enterprise plan allows ([D-194](decisions/D-194-ci-jobs-in-parallel-on-enterprise.md)). Past the limit, GitHub drops the least recently used caches. A scope that no run reads any more still keeps its newest caches longer than older ones that runs do read. So when a branch goes, or an event stops running, delete its caches: list them with `gh cache list --ref <ref>` and delete each with `gh api -X DELETE repos/null3d-engine/null3d/actions/caches/<id>`. Such a scope can hold about 11 GB, as a milestone pull request's caches do, which no run reads under [D-249](decisions/D-249-milestone-push-runs.md). The benchmark workflow saves only on main, apart from a branch's own shader entries. Each run of it saves the city's files under a key of its own, which a branch's runs would multiply. The package install with its cache is the action `.github/actions/bun-install`.
- The `commits` job checks the commit messages with commitlint and the trailers with `tools/hooks/check-trailers.ts`. On a push to main it reads every plain commit after main's commit before the push.
- The `ci-passed` job tells a time-out from a cancel. GitHub calls both "cancelled". `ci-passed` reads each cancelled job's messages and marks a job that hit its time limit as an error: a time-out is a failure of that job. A job that a newer push cancelled gets a warning.
- Each nextest profile of CI gives every test a time limit: 15 minutes in `ci` and 120 in `whole-shader-build`. The determinism part's job stops at 25 minutes, since balanced shards and optimized shader crates keep it short ([D-194](decisions/D-194-ci-jobs-in-parallel-on-enterprise.md)). The newest-nightly job's whole shader build builds every shader twice. It takes more than 85 minutes (run 39177518706), so its job stops at 135. nextest stops a test past its limit and reports it as failed. Without a test limit, nextest waits on long tests until the job's limit after one test fails. The job then reads "cancelled" and shows no result (913613695).
- The shader cache action writes each run's shader build into the job summary: the minutes it took, the cache it restored, how many entries it compiled and reused, and the entry and module counts and sizes. From run to run, the build's growth shows. A run whose inputs match the restored module set compiles nothing, and prints no compiled-and-reused line; the record names that case. The record only reports the log. The build step has already decided the job, so a missing line shows in the summary instead of failing the build. A search that finds nothing ends a step under the shell's `-e` and `pipefail`. A failed `build` then skips every job that needs it (96b955566). `tests/lib/shaders-action.test.ts` runs the record step over each shape of log, so a missing line cannot fail a job.
- A step that reads a tool's output must let the tool's failure fail the step. In a step such as `echo "sha=$(bun tools/build-wasm.ts --print-base)"`, the tool's failure leaves the step green. An empty value then travels on, and the job fails steps later, far from the cause (run 38894339212).
- A step that runs for minutes must print progress while it runs, and it must print the reason when it fails. A job whose log holds nothing tells a reader nothing. A job that hits its limit inside a silent step leaves an empty log. A server that compresses its page builds for 15 minutes in silence does this. So a silent step is a defect even when the work fits the limit.
- A test whose subject is not download time must not be affected by when a file is compressed. The load server compresses a file when a load first asks for it, so compression runs while a measured run goes on. By the owner's ruling, if a real-browser run's item times move because of that, the test changes, not the server. The run checks the engine rather than the server, so a test that moves with the server's compression measures the wrong thing. The tests that time a download are the exception: compression is their subject, so they keep seeing it. The server does not compress the page builds before the first load. That warm-up buys a warm cache and costs every shard that serves production builds 13.6 to 16.1 minutes of silence. So find and measure work that looks slow, and do not answer it with a warm-up.
- Main's rules require `ci-passed`, not each job, because a job that splits into more shards changes its name. Without that job, a new shard would strand every open pull request.
- Playwright's Chromium and its Ubuntu packages stay in the Actions cache. Ubuntu's package mirror stalls for 30 to 110 seconds on some files, and the install can take 11.5 minutes. The cache's key is Playwright's version in `bun.lock` and the runner's image. On a hit, only the packages that the image lacks install, from the cached files and the image's own package lists, with no request to the mirror and no upgrade of a package that the image has; a package that the cache lacks sends the step to the full install. On a hit the step took 16 s in a check run, against 68 s in the packages job of run 39813598275, where a full install with the cache spent 46 s on two upgrades at 44 kB/s. The `browser-caches` job fills this cache and the sample content's at the start of a run, so a cache that misses fills once, minutes before the browser jobs start, not in every one of them at once. No job waits for it, and its steps cannot fail the run. Ubuntu's mirror can take minutes for each package, and a cache miss then runs out both 5-minute attempts of the install.
- The Rust caches are keyed by the workspace's `Cargo.toml`, because the cache's own key leaves out the build profiles. Without that key, each run after a profile change restores a stale cache and compiles the dependencies again, for about 3 minutes.
- Development builds optimize the dependencies (`[profile.dev.package."*"]`), so the shader tools' tests and `bun run shaders` parse and validate WGSL about 4 times faster. CI's Rust test and shader compiler jobs also build the shader crates themselves optimized, through `.github/actions/optimized-shader-crates`. Their tests build every shader, and the crates' own unoptimized code made such a test about four times slower than the build job's shader tool.

### Efficient jobs

CI does each piece of work once, and only the work that its checks need (AGENTS.md hard rule 37, [D-218](decisions/D-218-efficient-ci-jobs.md)). A slow machine can make a good job slow, so a time limit finds only the symptom. These rules find the cause. The owner's words: "it's more about ensuring the jobs are architected efficiently, use cacheing where possible, avoid duplication of work or unnecessary work."

How the jobs avoid repeated and needless work, with the runs that measured each cost:

- The Vite plugin's compiler tests run in `shader-compiler-plugin`, apart from the `shader-compiler` shards. They take about 11.4 minutes and do not depend on a shard's share of the build test, which takes about 10.1. In one shard the two take 22 minutes (run 39744891020).
- The module exports test builds two small entries, and the determinism check builds four entries that make one module of every kind. A build of `standard_maps`, 77.8% of all shader builds, takes 18.1 minutes to check six renders.
- Only the `shader-compiler` shards run the test that builds every shader, since they make its checks and also compare the compiler's build with it. Parts of `rust-tests` that run it add no check.
- The `load-pages` and `load-startup-pages` jobs build the benchmark pages and the startup pages that the 44 `real-browsers` shards load ([D-222](decisions/D-222-load-pages-once.md)). Built in each shard, those pages take up to 11 minutes of a 23-minute Safari job, in silence (run 39554447893).
- Only `browser-production` builds the production pages, since only its tests read them ([D-220](decisions/D-220-production-pages-once.md)). Built in every browser job of a full run, they take 283 s on average, and only 2 of 40 shards read them (run 39554447893).
- `browser-production` runs in two parts, each of which builds only the pages that its test files load. It makes no CDN build, which none of its tests read ([D-220](decisions/D-220-production-pages-once.md#two-parts-and-no-cdn-build)). Its seven page builds take about 10 GB each and cannot run at once in one machine. In one job they take 18 minutes (run 39813231961).
- The `packages` job's pack builds each package once. Each package's own pack script would build the packages that it needs. One pack would then compile the engine six times, for about 3 minutes in CI ([Releases](releases.md#the-fresh-project-test)).
- The key of Playwright's browser cache names Playwright's version and the runner's image, since the browser changes only with them. `browser-caches` fills the cache ahead of the browser jobs. A key that hashes the test and benchmark package files changes about 10 times a month. Without a job that fills the cache first, each change makes every browser job download Chrome and its packages at once. That takes about 45 s each, with a 20-second stall at the mirror (run 39813231961).
- S1's three scenes run in a benchmark shard of their own. With S1, S3, S4 and S5, the first shard takes 24.3 minutes and sets the run's length. The others take 6.6 to 13.9 (run 39854225392). A split by hand needs a new measurement when its tests grow.
- The visual tests of the shadows run in a shard of their own. They read many frames on SwiftShader, and a page benchmark counts frames for a few seconds. In a shard with those tests on the other worker, S2's pages take 50 s to their first frame and count no frame (run 39869813447). A Mac starts the same pages in 4 to 5 s. A test that times frames does not share a shard with a test that loads the processor.
- The showcase HUD's sky check and fog check are separate tests, each with a job of its own. They share only the page's setup, 204 s of it, and as one test they take 20.9 minutes, the longest browser job (run 39869813447).
- The two load pages jobs link equal files, and each ships one archive that holds each content once ([D-222](decisions/D-222-load-pages-once.md#each-content-once)). Each page's build writes the whole shader set. So the startup and benchmark pages hold 8.52 GB in 19,827 files, of which 7,271 contents and 2.90 GB are distinct. As plain files, their 51 downloads take 86 runner-minutes (run 39854225392).
- The build job ships its 2.8 GB of files as one tar file that `zstd` compresses on every core: about 122 MB, in seconds. The artifact's own zip compresses each file on its own and on one core. It comes to 510 MB in 77 s, on the path of every later job, and about 125 jobs download it (run 39869813447).
- The build job keeps the build script's folder of WebAssembly builds in the Actions cache, under the script's own key of every input. It fetches wasm-bindgen only when a build misses. Most runs change no Rust source. A fresh build of the engine's two WebAssembly files and the tools' modules costs 103 s of cargo and wasm-opt (run 39944103955). The download of wasm-bindgen adds 15 s.
- The shaders test's browser leaves out ANGLE's pipeline warm-up. ANGLE builds a whole Vulkan pipeline for every program it links, to warm a cache that the test never draws from. SwiftShader then compiles each pipeline to machine code. The test checks only what ANGLE's compiler and linker report. With the warm-up, each part takes about 25 s on SwiftShader and keeps 12 to 15 cores of the browser's GPU process busy. Without it, part 1 takes 3.4 s on one core ([Image tests](image-tests.md)).
- The size memo keeps each file's compressed sizes by the hash of its bytes, so a `size-parts` job compresses only the files that changed. Each of the four parts compresses a quarter of the engine test page's 6,046 files, 718 MB, at the highest gzip and Brotli levels. Without the memo that takes 154 to 302 s in each part, 17 runner-minutes on every run (run 39900270572). Yet most files hold the same bytes as in the run before. When the memo was measured from the same shader modules, the build job runs one part. Four parts would each build the page to compress nothing ([Download size](benchmarks.md#download-size)).
- A pass key names exactly the files that its part reads. A key that holds all of `tools/lib` rebuilds every shard after a change to the size report (e970ab6a1). A key that leaves out the compiler's runner script, or the WGSL that the packing test compiles, reuses a pass after a change to them.
- Each transfer step through `.github/actions/archive` stops after 5 minutes, or 6 where a second try follows, and `tools/lib/ci-workflow.test.ts` fails on one without a limit. A transfer takes at most about 30 s. When GitHub's job API fails, an upload can stall until the job's own limit. Every push to the milestone branch then queues behind the run (run 40114017712).
- The `shader-compiler` key names the three files of the Vite plugin that the shards' runner script imports, and no package lock. A key that holds the whole plugin and the lock rebuilds all 20 shards for a change to the plugin's other files and tests. That costs about 80 job-minutes. Of 39 landings that changed such a key, 12 changed only those files or the lock.
- The `passes` job finds the pass of every part of `rust-tests`, `shader-compiler` and `shader-compiler-plugin` at once, in about 5 s. A job whose every part passed starts no runner. With a runner per part to find its pass, a run that changes no Rust or shader file starts 30 of them (run 40142024570). Each is up for 7 to 15 s and billed as a whole minute.
- The four parts of `rust-tests` that run every workspace test have a pass key. It names every crate and the eight files outside the crates that the crates' code names. `tools/lib/ci-workflow.test.ts` fails on a file outside the crates that the key leaves out. The parts cost about 16 job-minutes a run, and in one day 172 of 192 landings changed no file that they read.

The ways to reuse work:

| Work | How a job reuses it |
| --- | --- |
| The WebAssembly files, the shader compiler and the shader modules | The `build` job's archive, `page-wasm`, through `.github/actions/archive`. A job that downloads it sets `NULL3D_REQUIRE_FRESH_SHADERS`, so a stale set fails the job instead of a slow build of it again. The build job keeps the WebAssembly files and the tools' modules in the Actions cache, under `bun tools/build-wasm.ts --cache-key`, so a run that changed no Rust source, flag or tool runs no cargo |
| Rust builds | `Swatinem/rust-cache`, keyed by the workspace's `Cargo.toml` |
| The type check | TypeScript's incremental record of each project, `target/typecheck`, which `docs-and-tools` restores from the newest run and saves after its check. TypeScript compares each file's text with the record, so a record of an older commit is safe. On the Mac the check took 9 s with the record of the same tree and 27 s without one |
| Shader entries and module sets | `.github/actions/shaders` and the `shader-entries` jobs ([Builds](#builds)) |
| A test that reads the whole shader set, and the workspace's Rust tests | A pass marker in the Actions cache, under a key of the files that the part reads |
| The size check's base | The `size-base` cache, by commit |
| The size check's compressed sizes | The size memo, by the hash of each file's bytes: each `size-parts` job restores the newest, and `wasm-checks` keeps the parts' entries when a part compressed a file ([Download size](benchmarks.md#download-size)) |
| The city's files | The `load-pages` job's artifacts, built there or taken from the city cache |
| Packages, Playwright's Chromium and the sample content | `.github/actions/bun-install`, `.github/actions/playwright-chromium` and `.github/actions/samples` |

Before you add or change a job or a step, answer these questions:

1. What does it check that no other job checks? When another job makes the same check on the same inputs, keep it in one of them.
2. Which files does it read? Those files are its cache or pass key, no more and no fewer. A script that it starts, and every file that the script imports, are inputs too.
3. Can it reuse an artifact, a cache or a pass instead of building?
4. Does it build more than its checks read? Build the smallest input that still holds every case that the check needs. Fail when a case is missing, as the determinism check fails on a missing kind of module.
5. Does it run slow steps one after another that do not depend on each other? Give each a job or a process of its own. When memory keeps them from running in one machine at once, split the job by what each part's checks read.
6. Does it use every core? Does its split follow measured cost, and does the costliest unit split?
7. Does it need to run on every push? Let it reuse its pass when its inputs seldom change, or give it the full-run condition when a milestone branch's push can do without it.
8. Does the change touch a file that a cache's key covers, without changing what the cache holds? Keep test-only code in the tests, outside the key. Test code in the shader library changes the compiler's stamp, and every shader then compiles again, on the Mac and in CI ([D-218](decisions/D-218-efficient-ci-jobs.md)).
9. When it hands many files or large files to other jobs, does it use `.github/actions/archive`? The action packs them into one tar file that `zstd` compresses on every core and across files, which the artifact's own zip does neither of. With `link`, builds that share files ship each content once. A small artifact can stay a plain one ([D-218](decisions/D-218-efficient-ci-jobs.md)). The unpack passes with a warning when zstd meets a closed pipe after tar has unpacked the whole archive, and fails on any other error.
10. Does its checkout fetch only the files it reads? The image tests' references are 197 MB of a 236 MB checkout, in two sets: the real GPU's and CI's software GPU's. A job that reads no reference checks out without them, a browser job without the real GPU's set, and a real-browser job without the software GPU's, through a sparse checkout that fetches no file it leaves out. In run 40051531298 such a checkout took 4 to 7 s where a whole one took 9 to 13, on Linux and on macOS. Only `docs-and-tools`, whose reference check reads both sets, and the jobs that check out history keep the whole checkout. `tools/lib/ci-workflow.test.ts` fails on any other job that does.

How to review a run:

1. List its jobs by time: `gh api --paginate "repos/{owner}/{repo}/actions/runs/<run>/jobs?per_page=100" | jq -s '[.[].jobs[] | select(.conclusion == "success") | {name, minutes: ((((.completed_at|fromdateiso8601) - (.started_at|fromdateiso8601))/6|floor)/10)}] | sort_by(-.minutes)'`.
2. For each slow job, read its steps' times in the same answer (`.steps[]`), then the log of its slowest step: `gh api repos/{owner}/{repo}/actions/jobs/<job>/logs`. A job's log gives each test's time.
3. Follow the chain of `needs` that ends at the slowest job. That chain sets the run's time.
4. Look for reused passes: the step "Name the earlier pass" runs in a part that reused one.
5. Compare with earlier runs of the same jobs, since one run can meet a slow machine.
6. Record what you find, with its figures, in this guide or in a decision record.

`tools/lib/ci-workflow.test.ts` checks the parts of these rules that the workflow file shows. Every job that runs `cargo` or `rustup` restores a Rust cache. Every job that downloads the build job's files sets `NULL3D_REQUIRE_FRESH_SHADERS`. Only `shader-compiler` runs the test that builds every shader, apart from the determinism part. Each pass key names every script that its part starts, with the files that the scripts import. A part that reads the build job's shader modules names the files they are built from.

Five unit test files read the workflow file: `tools/lib/ci-workflow.test.ts`, `tests/lib/runs.test.ts`, `tools/hooks/ack-hooks.test.ts`, `tools/lib/links.test.ts`, and `tools/lib/ci-passes.test.ts` through the pass keys' tool. Run all of them before a workflow change lands: `bun test $(grep -rlE 'workflows/ci\.yml|ci-passes' --include='*.test.ts' tests tools bench)`. A change can pass `tools/lib/ci-workflow.test.ts` and still fail `tests/lib/runs.test.ts`, which reads each job's needs.

## Several copies on one machine

People and agents often work in several copies of the repository at once, such as git worktrees.

- Give each copy its own ports with `NULL3D_PORT`, as [AGENTS.md](../AGENTS.md#performance-work) says. Each copy then uses its port and the three ports above it.
- A run refuses the dev server of another copy. Playwright's runs off CI reuse a server that already answers on their port, and so does `startServer` in `tests/lib/server.ts`. Every copy takes port 5173 unless `NULL3D_PORT` names another. So a run on another copy's server draws that copy's code and compares it with its own copy's references. References written that way differ from main's own drawing ([Image tests](image-tests.md#references)). The dev server answers `/__null3d/checkout` with its copy's folder (`checkoutServer`). Playwright's global setup `tests/lib/checkout-setup.ts` and `startServer` refuse a server that names another folder. They also refuse a server that names none, such as one started from code without the check: stop it and run again. The ports stay fixed. A port worked out from the copy's folder would move the ports that phones and tablets reach, and two folders could still share a port. The unit test `tests/lib/server.test.ts` checks the refusal.
- Stop only your own servers. Find the process on your port with `lsof -nP -iTCP:<port> -sTCP:LISTEN -t`, and stop that process. Never stop a server or a browser by its name: every copy starts its dev server with the same command and the same arguments, so a name stands for every copy's server, and the test that tells them apart is the working folder, `lsof -p <pid> | grep cwd`, and not the name.
- Close the browser tabs that you open as soon as each test ends, as [Device sessions](devices.md#the-runner) says.
- Never let two copies share one Rust build folder. Cargo judges the engine's own crates fresh by their files' times. So one copy's build can reuse crates that another copy compiled from other sources, such as a stale shader compiler or another branch's GPU constants. By the owner's ruling, each copy builds Rust into a folder of its own. The copies share only the compiled dependencies, through a compiler cache. [Builds](#builds) says how.
- The dev server skips the repository's own `.claude`, `.dev` and `.internal` folders, anchored to the folder it runs in (`tools/lib/watch-ignored.ts`). A dev server in a worktree under `.claude/worktrees` therefore sees its own edits. A pattern that matches a `.claude` folder anywhere in the path skips the whole worktree. Its server then serves old files after every edit until it restarts. A unit test checks that a worktree's own files are watched.
- Agent tools can lock a worktree. `git worktree list` shows "locked", and `git worktree list --porcelain` gives the reason, which can name a process id. When that process no longer runs, the lock is stale, and `git worktree unlock <path>` clears it.
- The size check builds main in a worktree of its own, `target/.size-base/tree`, inside each copy that runs it ([Benchmarks](benchmarks.md#download-size)). `git worktree list` therefore shows one under each such copy. The check locks that worktree, with a reason that `git worktree list` shows, and reuses it. `git worktree remove`, even with `--force`, and `git worktree prune` leave a locked worktree. Never remove one by other means: a check may be building in it. A removal that the lock cannot stop, such as `rm -rf` of a copy's `target` folder, does not fail the check. When the build fails, the check looks at the worktree. A tree that is gone, or whose checkout is damaged, is made again and built once more. After you delete a copy's folder, run `git worktree unlock` on its base worktree's path, then `git worktree prune`.
- The hooks come from the tracked `.githooks/` folder, so every worktree has them, with or without an install of its own. The install only points git's hooks path at it ([D-182](decisions/D-182-git-hooks-from-a-tracked-folder.md)). A brand-new clone is unguarded until that install. Git calls no hook when no hooks path is set, so the `commits` job covers that state.
- A git hook names its repository to every process it starts, through `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE` and `GIT_PREFIX`. Git obeys them over the working folder. So a test or tool that runs git in a folder of its own removes all eight first. Otherwise it commits into the repository that the hook guards, such as the one being pushed. It can also set `core.bare` in the config that every copy shares, and git then stops in every copy. `repositoryEnv` in `tools/lib/git-env.ts` removes them. The release-notes reader, the push hook and the gate's CI-jobs reader all call it. The test "leaves the repository the hook names unchanged" in `tools/lib/release.test.ts` points `GIT_DIR` at another repository's linked worktree. It then checks that the branches and `core.bare` of that repository stay as they were.

## Coordinating helper agents

One coordinator session often runs several helper agents at once, each in its own copy of the repository. These rules keep their work moving.

- **One agent tool for the helpers.** The coordination works with more than one agent tool. A helper is a subagent of the coordinator's Claude Code session, or a session of the opencode agent tool. One setting of the coordinator picks which ([D-178](decisions/D-178-process-rulings.md)). Never use both at once, because two helpers must never work in one copy. The waits, the load limiter and the check-ins are shared scripts, and they work the same with either tool. Only the way that the coordinator reaches a helper differs. The rules that differ by tool, such as how long one tool call may run, sit in the helpers' brief. It has a part for each tool. A Claude Code helper that ends its turn tells the coordinator, which answers it directly. An opencode helper gets a prompt from a wake service when its job ends. The helpers are Claude Code subagents. When the opencode sessions' model service stops answering, every opencode helper stops mid-step.
- **Never start an opencode server by accident.** Any opencode command without a server address starts the tool's background server, and that server resumes the sessions that it held. A resumed session can begin a commit in a copy that a new helper owns. So the scripts call opencode only with the address of a server that the coordinator started, and they stop when nothing answers there.
- **Wait inside the turn.** A helper never ends its turn while one of its jobs runs or waits in the queue. An ended turn sits idle until something wakes the helper, and a landing has four to six such waits. The helper starts each long job detached, through a wait command that records the job's process and its exit status. A tool call can stop before the job ends, as Claude Code stops one after 10 minutes. The job runs on. The helper then waits on the same job again by its name, until the job ends. It then reads the exit status and the end of the log.
- **Read a failure the moment it appears.** A long run reports each check as it ends, so the first failures are readable while the rest of the run is still going. Diagnose and fix from those lines instead of waiting for the run to finish: a run that names twelve failures in its first minute has told you what is wrong twelve times over, and waiting adds nothing but time. The names of the failing checks and the page they ran often show the cause. The rule cuts both ways: a failure that reads as a timeout or a device fault is a reason to keep an eye on the run, not to start changing code, so separate what the line says from what you want it to say.
- **A task marked complete is merged.** The pull request's list marks `[x]` only for a task whose code is on the milestone branch. A task whose work sits on a helper branch stays `[ ]` with that state in its note until it is merged, because a reader sent to the branch by the list cannot find the work. The owner's ruling: "if an item is completed it should be merged into main pr branch, not just sitting on a helper."
- **A finding becomes work, not a task.** A fault that a reader, a check or a helper finds is fixed in the task it belongs to, whose tick then waits for the fix, or by a helper started on it at once; a plan task is added only when the fault cannot be fixed now, and its entry says what blocks it. The owner's ruling: "in existing tasks".
- **Clean up each check-in.** Remove the copies whose work is merged and which hold nothing uncommitted, and stop the helpers that have finished; a copy with uncommitted work or an unmerged branch stays until its work is landed. Another session may be working in the same repository at the same time, so a copy is removed only when its owner is known and its work is merged: check the branch, the recent activity and the process's working directory first, and leave anything whose owner is unclear. The owner's ruling: "as part of the regular check-in, clean up all old helpers and worktrees" and "dont remove stuff that other session depends on." 

- **Keep the pull request true.** After every landing, and whenever a task is added or its state changes, run `bun run pr-status --apply`. The body is generated from the milestone plan, so a new task goes into the plan first and the pull request follows it. The owner's ruling: "keep pr title and desc updated ... pr list of tasks should match m3 plan and milestone tasks."
- **Keep the fleet full.** At every check-in, count the helpers that are working. If one has finished, or a task in the backlog has never started, start the next task at once. The owner's ruling: "I shouldn't have to tell you to start new tasks - you should proactively do so." Take the next task from the milestone's remaining list, then from the red work, then from the follow-ups a landing recorded. Read that list with `bun run pr-status --ready`, which prints the open tasks the plan does not block and, under them, the ones that wait with the tasks they wait on. A task is blocked only by a task it names and that is not done: without that reading a coordinator takes a whole section as blocked because one task in it is, and leaves work that could start sitting idle. A task in the milestone plan that makes a build faster or cuts the build's memory goes to the CI session instead ([D-268, addendum](decisions/D-268-three-sessions.md#decision)). At the helper limit, give the task to an idle helper by message, so its context is reused; a finished helper never sits idle while a startable task exists.
- **A milestone behind its landings gives its work to the ticks.** The owner's ruling: when the number of ticked tasks falls behind the number of landed branches, the sessions' work goes to whatever turns a landed branch into a ticked task: a run, a record, a line of evidence. A change whose only benefit is a faster or cheaper CI waits, because a branch that has landed and cannot be ticked counts for nothing against the milestone.
- **Check every 5 minutes.** The coordinator checks each running helper every 5 minutes, on a timer, also at night, as the owner set. It judges progress by evidence: new commits, logs that grow, CI checks that move, jobs in the queue. A helper's own message is not evidence. Sometimes a helper waits on a run or a CI job that has already ended. The coordinator then gives it the next step at once. A helper that stays stuck is replaced by a fresh one. Without the timer, a finished CI run can wait hours for its helper. A quiet window can stay idle for hours after its run ends.
- **Find each job's real copy.** The check-in gives each job to the copy of the repository that the job works in. It first reads the folders that the job's command changes into. Then it reads the folders of the job's running processes, and last the folder that the job started in. A helper's shell can start in the coordinator's copy, as a Claude Code subagent's does. By its start folder alone, every such helper's job looks like the coordinator's, and a busy helper reads as idle. One shape of job escapes even this rule. Its shell starts in the coordinator's copy, and its own folder becomes its working folder only inside the step script it runs. So no running process names it until that step begins. Read the helper's own log folder as the marker for a job of that shape, and ask the helper to confirm the job is queued rather than record it as missing.
- **Read the task's own finish line before a tick.** An evidence line says what proves a task; it does not say the task is done. A tick given on an evidence line alone can name figures that no record holds. It can describe work that draws nothing or fails on CI's software GPU. It can also fall short of the line its own task sets, or need an owner ruling that nobody made. Read the plan's "Done when" line, and the section's rule, and tick only when the evidence meets them.
- **Count a task as landed only when its audit says done.** The milestone count takes a task as landed only when the task's audit marks it done. A `Task:` trailer on some commit is not enough, because commits on main can carry a task's trailer while its feature is still on its branch. A branch on main is not enough either, because the task's whole definition of done may not be met yet.
- **A task is not done because its author says so** (the owner's rule). When a helper reports a task complete, a fresh agent tries to disprove it. It reads the task's own finish line, the helper's evidence and the code. It runs the tests that the task names, opens the pictures that it cites, and checks the trailers. Only a cleared verdict lets the task be ticked or its branch land. The checker is never the author, and never the session that pushes that branch. Red runs often come from a task that its author believes finished, with a fault that the author's own check does not show. Examples are a repeated part name in the size report, or a sky layer that never reaches its map. The PR audit session, the third session in [Landing a branch](#landing-a-branch), audits every tick on the milestone's pull request in this way. A tick that it refuses goes back to the status tool's list of unfinished tasks, and its finding becomes the task's note ([D-268](decisions/D-268-three-sessions.md)).
- **Keep notes for a restart.** Each helper keeps a notes file current as it works. The notes give its branch, its commits and whether they are pushed. They also give the runs in flight, the figures and what is left. Another session must be able to resume from the notes alone.
- **Use the right queue lane.** The load limiter has four lanes, each with its own slots. Browser, image, benchmark and GPU runs take the browser lane, which waits for a low load and for the quiet window. Builds, cargo commands and the full type check take the CPU lane. Short jobs take the quick lane: installs, lint, docs checks, and unit tests that build nothing. Cloud device runs take the cloud lane (below).
  **A clamped job runs at about a quarter of the machine's speed.** [Builds](#builds) gives the rule for when the queue clamps a job. A clamped CPU job runs under `taskpolicy -b`. While a timing window is open, the CPU lane also sets `CARGO_BUILD_JOBS=2` and `RAYON_NUM_THREADS=2`. The same fixed work on eighteen processes finished 30 to 44 seconds of work per 3 seconds of wall clock at normal priority. Under the queue's priority it finished 8.2 to 8.6 seconds. Each was measured twice, back to back. A wall-clock figure from the queue is therefore not comparable with CI's, whose runners carry no such policy. It also explains a load average of 30 beside ten idle cores. Background-priority threads are runnable, so they raise the count without using a core. Hard rule 30 of [AGENTS.md](../AGENTS.md) bans timing at background priority, and it is why a timing run must never go through the queue.
  **Whole-core jobs have their own slots.** They build the engine, its pages or its shaders, or type check, or build for the GPU check. A clamped one takes the utility clamp, which keeps whole cores and normal disk reads, rather than background priority. Its children, the bundler among them, take the same priority. Under the utility clamp a size check's page build took over 30 minutes at a load of 50 to 140. At normal priority it took 73 s. These jobs take the whole-core slots, named w1, w2 and so on, in an order of their own. So they never wait for slots that clamped background jobs hold frozen. Frozen jobs can hold every CPU slot for an hour or more, on under 5 s of processor time each.
  **Quick jobs follow the same rule.** A clamped quick job takes background priority, and the lane's five-minute limit still applies.
  **A waiting window frees the CPU lane.** While its timing run still waits for a normal run to end, CPU jobs start without the window's caps. Holding them would bring the timing run no closer, and builds would wait for nothing.
  **A busy window closes.** A timing run loses its window when it sees no quiet minute in 10 minutes. The cost tests time only under a 1-minute load of 8. The queue writes the reason into the run's slot, as a `window-closed` file, and starts a drain. The run's quiet waits then fail at once, instead of after ten minutes for each test. Builds outside the queue can keep the load high for as long as such a run holds the window.
  **The page-build lock watches its holder.** A page build at background priority refuses to take the machine-wide page-build lock, and says why. Every 2 s a waiter reads the processor time of the holder and each of its children, and keeps a child's time after it exits. Every 2 minutes it says who holds the lock and what the holder has used. A holder that uses under 30 s of processor time in 10 minutes makes no progress. The waiter then ends a holder at background priority, which no call can raise, and takes the lock. It never ends a holder at any other priority: it stops waiting and says why. A page build at background priority can hold the lock for most of an hour on seconds of processor time. The coordinator's stall check flags a lock whose holder has gone, runs at background priority, or uses almost no processor time.
  **The shader build, measured both ways.** The same cold build took 518 seconds through the queue, with every entry compiled and the cache off. At normal priority it took 105 seconds, 4.9 times faster, and it used 10.1 cores against 2.26. So the machine rebuilds the whole shader set in about a minute and three quarters. A figure of about forty minutes comes from a debug-profile single-threaded build through the queue, and overstates the time by roughly twenty-five times. Both runs left the module set unchanged: a cold rebuild of the optimized, parallel build reproduces every generated module byte for byte.
  **The shader build is the one job that does not go through the queue.** It takes the machine-wide shader lock, so the time it holds that lock is the time every other build waits. Through the queue it can hold the lock for forty minutes while builds and picture tests queue behind it. At normal priority the same cold build finishes in under two minutes. Run it directly, at normal priority, and let the lock keep it to one at a time. Every other build still takes the queue.

  **A change to the shader compiler rebuilds every shader at its commit.** A compiler whose program gives other bytes reads a cache folder that only it has written. So the commit hook's type check compiles every shader, on every core and outside the job queue. It can then run beside another build of every shader, on a machine with 36 GB. The compiler's program changes with `crates/null3d-shaders/src/` and that crate's `Cargo.toml`, with a crate it builds on such as `crates/null3d-gpu/`, and with the workspace's `Cargo.toml`, `Cargo.lock` and `rust-toolchain.toml`. Before you commit such a change, run `bun tools/shaders.ts` once in the checkout, while no other shader build runs. The hook then finds the modules up to date.

  **A type check does not wait for another checkout's shader build.** The commit hook's type check brings the shader modules up to date first. When that needs a build while another checkout holds the shader lock, it checks against the modules already in place. It builds them and checks again only when a project fails, and then prints no result from the first check. A commit that waits for the lock can sit for minutes at no processor time. On CI no other build holds the lock, so CI always checks against modules that match their sources.
  **A direct job that forks across every core starves the queue.** The queue caps its own jobs at two or so build jobs each, which is what keeps the machine usable. A job run outside it has no such cap. A debug compile of the shader crate can take ten cores and leave the shader build an eighth of one. The shader build then holds the shader lock longer, which holds a page build and the picture run behind it. When you run a heavy job outside the queue, cap its parallelism and leave the rest of the machine to the jobs that are waiting. `CARGO_BUILD_JOBS=4` caps how many crates build at once, and `RAYON_NUM_THREADS=4` caps one binary that parallelizes inside itself, as the shader crate's build script does; capping only the first left that script using eleven cores.
- **Short jobs never wait behind builds.** The queue sizes the quick lane's slots from the machine's cores and memory, as it does every lane's. It holds a job until enough memory is free. A job there starts without waiting for a low load, and the lane stops any job that runs past 5 minutes. Such a job goes back to the CPU lane. Without the quick lane, a docs check of a few seconds can wait hours behind builds in the CPU lane. The owner approved the quick lane.
- **Compile after a merge, and check before a push.** After a branch merges `origin/main`, compile the merged tree before anything else: `cargo check --workspace` and `bun run typecheck`. A merge that keeps both sides of a struct or a constant is often valid syntax, so only a compile finds it. The owner also approved the check that runs before each push to main ([Commit messages and pushes](#commit-messages-and-pushes)). It checks the trailers, runs `cargo check --workspace` and the tests of the Rust crates that the push changes, and sends its heavy steps through the load limiter.
- **A job that cannot start blocks the jobs behind it.** The lanes serve jobs in the order they arrive, so a job at the front whose turn has come but which cannot pass the limiter's own conditions is not waiting. It holds every job behind it. Clear that job and ask its owner to send it again. Such jobs can hold the front for hours while dozens of jobs wait behind them. A job can even hold its place with no process at all. Its shell was stopped, and its wait command lives on with no parent. Clear the process as well as the place, and read a job's own process, not only its place in the queue, before calling it healthy.
- **Read the deepest process before calling a step hung.** A step that waits on a child step shows almost no processor time in the parent, which reads exactly like a hang. Follow the process tree to its deepest process and read that one's time before you stop anything or change the limiter.
- **Time on a quiet machine.** Timing figures need a machine whose load stays below 8. Every browser, image, benchmark or Rust suite runs through the load limiter, which caps how many run at once. For a timing run, the coordinator turns on the limiter's quiet window, which lets only that helper's runs start. The helper reports the moment its timing runs end. At each check, the coordinator also looks at the window's runs itself, and passes the window on or ends it once they are done.
- **Run cloud devices without waiting.** A run on [BrowserStack Automate](devices.md#browserstack-automate) never waits for the owner's go-ahead. The owner ruled so ([D-178](decisions/D-178-process-rulings.md)). Such a run barely loads the Mac. In a browser slot of the load limiter, it would hold the slot for the whole job, up to about 85 minutes. Local browser runs would wait meanwhile. So, with the owner's approval, cloud runs have a lane of their own. It has one slot, because the BrowserStack plan allows one session at a time. A cloud run in that lane never takes a browser slot or a CPU slot. It never waits for the load limit or the quiet window. Cloud runs queue in their lane in turn.
- **Pause before the usage limit.** At 95% of the usage limit, each helper writes its state into its notes, commits and pushes its work, and stops. Work resumes with fresh helpers once the limit's reset time has passed. A low reading of the usage figure alone is not enough, because the reading can be wrong.
- **Say the working folder, not its name.** A helper inherits the coordinator's working folder, so a brief that names the helper's own copy is not enough. A helper's git commands can run in the coordinator's copy and move it onto the helper's branch. The coordinator's next commit then lands on that throwaway branch. Give the exact form: write every command with `git -C <folder>`, or have the helper make that folder its shell's working folder first. A helper confirms `git rev-parse --show-toplevel` names its own copy before it commits. Anyone who sees a commit report an unexpected branch name stops and reads that line, because it is the only warning this fault gives.
- **A picture test you did not run is not evidence.** `bun run check` says only that every image test has its references. The reference check proves a file exists, never that it matches. A branch can draw one sphere where the saved picture draws six, and only the picture test says so. A change to the draw path, which is culling, levels, materials or post passes, runs its picture group (`bun run test:images -g "<feature>"`) and the helper puts the pass or fail line in its report. A new picture test needs the same run: it compares against a reference only after that reference is drawn and looked at.
- **A job at no processor time is the owner's to stop.** A queued job whose leaf process gains no processor time over a few minutes is wedged, and it holds its slot against everybody behind it. Such a job can sit at a few hundredths of a second for over an hour. Its owner stops it and re-runs it; the coordinator stops it when the owner has gone quiet. Run jobs from your own checkout, never from the shared one.
- **Read a limit from main, not from your branch.** A budget constant lives in the code, and a branch carries whatever the constant was when it last merged main. A helper that measures against its branch's stale figure can report a failure that main no longer has. Read the constant from `origin/main` before you quote it.
- **A budget that stops the build is a stop-the-line job, not a task for later.** While the build stops, code keeps landing, but every picture reference, graphics timing, device run and size line waits behind one number. Helpers queue size checks that can never pass. When a build stops on a budget or on a file that the size report cannot name, raise the budget or trim in the same hour, put the reason and the paying trim beside the figure in the source, and tell the owner what changed. The owner's standing word is to raise it without waiting for them.
- **A check that fails closed must say why.** The load limiter's start gate closes while the machine is busy, which is what it is for. A fault in the reading can close the gate on every pass, so no job starts for hours while nothing says there is a problem. The gate names the value it refused and says that no job can start until the sampler works. A closed gate and a busy machine look identical from outside, so a check of this kind must report the difference.
- **A place in the queue with no live process is a fault too.** The lanes serve jobs in arrival order, so a place held by a job whose process has gone blocks everybody behind it. Such a place can survive for hours when the job's shell is stopped and its wait command lives on with no parent. Read a job's own process, not only its place in the queue, before calling it healthy, and clear the place as well as the process.
- **The queue says what holds its slots and what a job waits for.** A slot records the command it runs and when it was taken. A waiting job prints one line a minute, and at once when the line changes. The line names the lane, the slots with their holders, commands and ages, the jobs ahead, and the gate's own idle and load readings. Without that line, a lane whose slots are all held and a queue that has jammed look alike from outside. A process table misleads. Every ancestor of a build sits at 0 per cent while the work happens two levels below. Each job also carries a `caffeinate` child that runs nothing at all. Read that line before a process table, and read the deepest process before calling a step hung.
- **A picture run takes neither gate, and the cap is a wait, not a waiver.** A run that compares pixels measures no time, so it does not need a quiet machine. Start it with `HEAVY_MIN_IDLE=0` and `HEAVY_MAX_LOAD=0`. A load cap is not permission to run above that load: the lane waits until the machine falls below it. Such a wait can read as a queue. Zero means no cap.
- **A timing run through the lanes takes the quiet slot.** A browser or bench run that judges frame rates or times starts with `QUIET_OK=1`. The lane then waits until no other normal run holds a slot. The quiet window that its slot opens keeps other timing runs back. A run without the flag can share the Mac with another browser run, and its figures then measure the load rather than the change. A figure from a shared run is not a verdict. The window must stand for the whole run. It also caps other sessions' queued work. A commit made elsewhere sends its full type check through the CPU lane. There the window allows one job on two threads under a load of six. Without a window that check runs on every core, and a figure measured beside it is a figure about the machine. A commit in another session can start such a check in the middle of a GPU check.
- **A slot whose work has gone is freed by the queue.** The queue reclaims a place whose live process has died. A wrapper can also sleep on after its work has gone. So the slot records the process that does the work. The queue frees the slot when that process is gone, and says which slot it freed. A run that launchd accepted but never started releases its slot after ninety seconds rather than waiting for a status that can never come.
- **Never write a running script in place: it serves broken content, not only a shifted read.** The load limiter and any other runner that queued jobs execute must be written as a new file and renamed over the old one. zsh re-reads a running script through its open file by byte offset, so a job that started before an in-place edit resumes after its wait loop in text that has moved, and fails without running its command. That is the narrower half of the hazard. An in-place write with a fault in it also leaves the file broken until the fault is fixed. Every wrapper that *starts* in that window reads the broken copy. Each such job logs a failed command lookup and a figure with no value, once per waiting turn. A job that starts after the edit is not protected by its timing, because opening the file is how the broken content is picked up. Write the new file, check it with `zsh -n`, rename it over, and read its content once more before it goes live: the cost of a mistake is paid by every job that starts until the file is right again.
- **A pattern in a stop command is a machine-wide action.** `pkill -f "<text>"` reaches every process on the machine whose command line contains the text, not only the caller's own, so a pattern that is not narrow enough stops other people's work. `pkill -f "bun tools/build-wasm.ts"` or `pkill -f "vite build"` stops every copy's build, even one at its final step after an hour. That build's log ends at the production page step, and its shell records the exit code of a process stopped by the termination signal. The rule that says to confirm a process is yours before stopping it applies to the pattern, not only to a process id. List the matches with `pgrep -f`, check each one's working folder, and stop that number; where a pattern cannot be avoided, make it name your own working copy as well as the command. **A server is the same hazard under a narrower name.** `pkill -f "vite"` stops every copy's dev server, because they all run that command. The copy that loses its server reports a failed run whose log names nothing about a stop. Read the port's owner, or each match's working folder, and stop that process alone.
- **A job's age in the process table counts its wait as well as its work.** A runner that waits an hour for a slot and then works for a minute still shows an hour in the process table, so an old wrapper is not evidence of a hang. The queue's own line separates the two cases, and a slot's recorded age counts from the moment it took the slot, which is the moment its work began. Read the waiting line before the process table, and read the slot's age rather than the wrapper's before calling a step stuck.
- **Read your own commits before a push.** Before a push to main, run `git log origin/main..HEAD` and confirm every commit in it is yours. A helper inherits the coordinator's working folder, so a helper's commit can be sitting in the coordinator's branch, and the coordinator's push is what puts it on the trunk, under the coordinator's name and without the checks the helper owed it, such as the measurement of an allocation fix.
- **Do not change a working copy's files while its own queued job runs.** A job can wait hours in a lane before it starts, and its owner goes on working meanwhile. A shader job that starts part way through a merge compiles across it and links a compiler from before the merge. It then fails for a reason that has nothing to do with the change. The same job passes on the settled tree. Settle the tree first (merge, commit and leave it alone) before queueing a job that reads it. Otherwise wait for the job to finish before touching the files.
- **Several limits judge a branch at once, so name them all before a push.** A branch can be red on several checks at once. Examples are missing picture references, a memory ceiling that a suite outgrows, and files over the growth limit with no trailer. Each comes from a different change, and each reads as a mystery until someone opens its job log. Run `bun run limits` before a push. It reports the picture references, the commit gates and the start budget of the last build. It also names the command for each limit that only a build or a heavy run can measure. A commit that changes what a limit measures carries a `Limits-Checked:` trailer that says what the report found.
- **A page run after a merge needs that copy's own build, and the core's error says so.** A worktree that merges the milestone branch keeps the WebAssembly core that it built before the merge, and every page then refuses with E1402. The error names the cause and the fix: build the copy again. A picture, device or browser run right after a merge starts with `bun run build`, or waits for a build that already runs there. Read the first error of a failed run before you read its picture count, because E1402 means the run drew nothing at all. A core copied from another worktree fails the same check, even when the two commits' Rust sources match: the stamp covers the files that the build read, and another copy's working tree can hold uncommitted edits. A fresh worktree builds its own core before its first page run.
- **A browser run adopts a dev server that is already listening, so do not stop one while a run uses it.** The image and browser harness looks for a server on its port and refuses a server that does not name its own copy of the repository. When its server stops while the run sets up, the run fails minutes later with that complaint. Before a picture or browser run, check that nothing else listens on its port. While one runs, leave any server on it alone, or give the run a port of its own through `NULL3D_PORT`.
- **A milestone pull request's description is rebuilt after every landing, not written once.** A description written by hand goes stale within hours of a landing, and lists the tasks of an older plan. The description is generated: `bun run pr-status` reads the plan's task headings and the `Task:` trailers of the branch's commits, marks each task landed, part landed, on a helper branch or open, and prints the list. `--apply` writes it to the pull request. Run it after each merge into the milestone branch, in the same breath as `bun run limits`. The three tables in the tool carry the judgement a trailer cannot: what part of a task landed, and what a task's outcome was.
- **A pause order that arrives after the resume is void, and helpers must be told so.** A helper's mailbox can hold an order from before a pause ended. The helper acts on it when it next wakes, and stops again after work has resumed. When a pause is lifted, send each helper a message that says the pause ended and gives the local time it ended, and tell them to ignore any pause order older than that. A helper that stops for no visible reason should check the time of the order before it obeys it.
- **Stopping a queue wrapper does not stop the job under it.** The queue runs a command as a child, so killing the wrapper leaves the build running with no owner, and it holds whatever machine-wide locks it took. A `bun tools/build-wasm.ts` left under a killed `heavy.sh` wrapper can hold the page lock for an hour, and every other page build queues behind it. Stop the deepest process of the job, confirm with `pgrep -f` that none of its children survive, and check the locks the job could hold (`~/.cache/null3d/*.lock`). The rule about reading the deepest process before calling a step hung cuts both ways: it is also the process to stop.
- **After a landing, build once before any helper merges.** A worktree whose merge changes the shader inputs rebuilds the whole shader module set, about 5.8 GB, and takes that work's hour on a loaded machine against four minutes when it is quiet. It also holds the lock that every commit's type check waits on. So after a landing the coordinator builds the main checkout once: that fills the shared cache with the tip's set, and every helper that merges afterwards copies it in seconds. Without that build, each worktree that merges the tip spends about an hour rebuilding the same set. A checkout whose set the shared cache holds copies it without taking the lock, so only a real build waits for another.
- **Before pushing the milestone branch, read what else is in it.** A landing push sends every commit on the branch, not only the merge that prompted it, and another session's commits can be sitting there under a hold of its own. The push can then send commits whose author still waits for the owner's word, and so cross the owner's condition without their knowledge. Run `git log origin/m3-start..HEAD` before a push and know whose every commit is; when one belongs to another session, ask it whether its hold still stands.
- **A push to a milestone branch runs no browser jobs.** Its run runs only the quick checks, so the browser, showcase, benchmark and real-browser jobs skip. A CI change that only affects those jobs therefore cannot be measured by a push. Measure it with a full run: `gh workflow run ci.yml --ref <branch>`. That run gets a concurrency group of its own, so it cancels nothing, and the pushes after it do not cancel it either. On the milestone branch it shares the branch's caches with the push runs. On any other branch it reads only that branch's caches and main's, so it builds every shader entry, the shader modules, the WebAssembly files and the size memo again, and its times are not the milestone's.
- **Do not build in the main checkout unless you are the coordinator.** It is the shared tree: another session may be timing a package run or holding it still for a measurement, and a build there starts a full rebuild under everyone. Helpers build in their own worktrees. A helper's work in the main checkout holds the shared locks, such as the shader lock for a type check. A reset of the tree wipes that work, with any timing run beside it. An edit there harms every run before it is built: the core no longer comes from the sources in the tree, so each page fails the E1402 guard and draws nothing. A gate's parity step then reports hundreds of refusals, none of them about parity.
- **Claim a decision record's number against the newest tip, not against your branch's base.** A branch started an hour ago does not know which numbers a landing took since. Several tasks can each write the same number, and some land before the clash shows. Read the numbers on `origin/main` and on the milestone branch at the moment you write the record, and renumber before you land if a newer tip took it.
- **A stuck build is a tree, not a process.** Builds run through `caffeinate -d -i`, which keeps the original process and makes `caffeinate` its child, and a page build leaves a `vite` child behind. Stopping only the `build-wasm` process therefore leaves the real work, and the page-build lock, alive, so two large page builds can then run at once. Walk the children before killing, and stop the whole tree. A build that looks hung may only be slow. A job started at macOS background priority throttles its disk reads. A page build inside it can then hold the shared lock for twenty to ninety minutes at a fifth of a core. Page-building commands in the CPU lane need a milder clamp, which `taskpolicy -c utility` gives without the background I/O throttle.
- **Work moves without being asked, and its helpers and worktrees go as it finishes.** The coordinator starts the next task whenever a slot, a lane or a helper frees, and never waits for a person to say continue (the owner's rule). A helper is shut down the moment its task lands or its work is handed over, and a worktree is removed as soon as its HEAD is an ancestor of the milestone branch, its tree is clean and no process works in it. This happens as each piece finishes, not in a tidy-up at the end: a night that leaves thirty idle helpers and a hundred worktrees is the fault this rule exists to stop.
- **A gate or a long measurement holds the browser and timing lanes, not the day.** Code work, commits and tests continue beside it through the heavy lanes; any figure a step measures while another job runs carries that note in its record rather than waiting for a quiet machine.
- **A worktree a live agent is working in is never removed. Git-clean does not mean unused.**
  A worktree whose branch has landed and whose tracked files are clean can still hold a run's result
  files and notes, which git ignores. Three checks before removing one. No session is working in it,
  and a helper that declined a shutdown is still working whatever its branch says. Nothing in it is
  worth keeping outside git: a run's results, a bench figure, a note.

  And no process has its working directory in the tree. A helper between commits looks idle by branch
  and tree, and a build started from a folder keeps running after the folder goes. So the process's
  own working directory is the only thing that says whether work is in flight:
  `lsof -d cwd | grep <path>` lists them cheaply, where `lsof +D` walks the whole tree. A removal
  while a build runs costs the helper that build, and its commits too unless it pushed first.
