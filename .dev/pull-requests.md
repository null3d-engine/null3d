# Branches and parallel work

Since 13 October 2026, work lands on main by direct push, without pull requests ([D-157](decisions/D-157-direct-pushes-to-main.md)). Merge `origin/main` into the branch, run the local checks, and push the branch's commits to main without waiting for main's CI. Fix main at once if your push turned it red. [D-99](decisions/D-99-no-merge-queue.md) holds the earlier pull-request flow, as history.

This guide covers how a branch lands, generated files, and how to merge main into a branch. It also covers commit messages, what CI runs and why its jobs are split as they are, and several copies of the repository on one machine. [AGENTS.md](../AGENTS.md) holds the commit gates.

## Before you land a branch

Record the reasons for the change in `.dev/`, in the same branch, as [AGENTS.md](../AGENTS.md#record-the-reasons) says. Each kind of reason has its place:

| Kind | Place | Example |
| --- | --- | --- |
| A design choice or an owner's ruling | A decision record, new or an addendum: the problem, the figures, the options rejected and why, and who decided and when | [D-92](decisions/D-92-safari-removed-frames.md) gives the memory that Safari kept on CI, the options, and the owner's confirmation on 7 October 2026 |
| A bug fix | The cause and why the fix is right, in the record or guide that owns the area | The framebuffer fault on the Pixel 10: [D-71](decisions/D-71-custom-effects.md) gives the cause, the per-call timings and the unit test |
| A device or benchmark run | A new run file in [tested devices](tested-devices.md), or a row in the [benchmark results](benchmark-results.md) | The iPad's custom effects run of 7 October 2026, in the iPad Pro's folder |
| A process or tooling lesson | The guide that covers it | Put each trailer on a plain commit, because the trailer check reads only plain commits, in [Commit messages and pushes](#commit-messages-and-pushes) |

The `Docs-Checked:` trailer names the page that holds the reason, or says why the change has no new reason.

### Guidance from demos and showcase scenes

The owner set this rule on 20 October 2026, for every demo in `examples/` and every showcase scene. Developers copy these scenes as the model of good visuals for their own projects. Work on any one's look or behavior may show a better way to use the engine, or a pitfall that users will hit too. The same change then adds that guidance to the user docs and to the agent skills. It is part of done for that work, not a follow-up. A fault in the engine itself is fixed in the engine, not worked around in the scene.

- Put it on the docs page of the feature that it concerns, and in the skill reference that covers that feature. A pitfall also gets a row in the troubleshooting table of `skills/null3d-develop/references/testing-and-debugging.md`.
- Say what happens, why, and what to do, with a short code example where it helps. Write for a developer who never saw the demo.
- Extend the text that a page already has, rather than adding a second place for one fact.

For example, the creek showcase's cave rock sat on a layer that the sun lacked, so the sun shone through the rock. The fix gave the sun that layer. [Render layers](../docs/concepts/render-layers.md#layers-and-shadows) and the develop skill now say that a light's mask picks its shadow casters. They also say what happens when the mask lacks a caster's layer.

## Generated files

Never commit a generated file, unless [D-105](decisions/D-105-generated-files-out-of-git.md) gives the reason to keep it. A generated file changes in every branch that changes its source, so it clashes between them. Git can also merge its text cleanly into a result that no generator makes. So git ignores each generated file, and these steps build it.

| Generated files | Source | Generator |
| --- | --- | --- |
| The skills copy for Claude Code, `.claude/skills/` | `skills/`, without each skill's evals | `bun run skills` |
| The API reference pages, `docs/api/reference/` | The doc comments on the engine's exports | `bun run docs` |
| The list of all pages, `docs/pages.md` | Each page's front matter | `bun run docs` |
| The error pages, `docs/errors/` | The engine's error table | `bun run docs` |
| The quality preset tables, `docs/concepts/quality-preset-tables.md` | The quality chooser's constants and the preset table | `bun run docs` |
| The page of shaders that load on first use, `docs/guides/first-use-shaders.md` | The shader manifest's `[first_use.*]` tables, and the descriptions in `tools/lib/first-use-docs.ts` | `bun run docs` |
| The shader library page, `docs/shaders/library.md` | The WGSL library's doc comments | `bun run docs` |
| The three.js mapping page and the porting skill's 2 copies of the mapping | `docs/data/threejs-mapping.json` | `bun run docs` |
| The placeholder pages of planned pages | The page inventory in `tools/lib/docs.ts` | `bun run docs` |
| The tested device tables, `.dev/tested-device-tables.md` | The README of each folder in `.dev/tested-devices/` | `bun run docs` |
| The shader modules in `packages/engine/src/generated/` | The shader crate | `bun run shaders` |
| The WebAssembly files, and each package's built JavaScript | The Rust crates and the packages' TypeScript | `bun run build`, and each package's pack step |

`bun run docs` writes every file of the docs generator and the skills copy, with `bun tools/generate.ts`. These steps run it:

- The install step, `bun install`. A fresh clone therefore has `.claude/skills/` and every docs page after it. The step runs no Rust build.
- The git hooks after each checkout, merge, pull or rebase, and the pre-commit hook.
- In CI: the docs job, which then checks that the generators wrote no file that git keeps. The engine package's pack step writes the docs that the package holds.
- After each full run on main passes, CI pushes main's commit with every generated file to the `generated` branch. Links that must work on GitHub point there, such as the docs link in each engine error message.
- Each release tags a commit that holds every generated file, for the Claude Code plugin, `bunx skills add` and the skill zips.

Every command that reads the shader modules builds them first: the build, the type check, the unit tests, the dev server and the browser tests. The docs generator reads the engine's types, which import the shader modules. Without them, the engine's API reference leaves out the shader features, and `bun tools/generate.ts` says so. Run it again after `bun run shaders` or `bun run build`.

After you clone, run `bun install`. After a branch switch or a pull, the hooks write the generated files again. When a hook did not run, as in a worktree before its first `bun install`, run `bun install`.

### Builds

A build compiles the Rust crates for two WebAssembly variants and the build tools, writes the shader
modules for every feature, and then builds the test page for the size report. It is the longest step
in a landing, so keep the count down. Every build cache lives under one root, `null3d` under
`XDG_CACHE_HOME` or `~/.cache/null3d`, each in a named subfolder: `shader-modules`, `shader-cache`,
`wasm-artifacts`, `samples`, `gpu-check-baselines` and, when sccache is installed, `sccache`.
`NULL3D_BUILD_CACHE` names another root, and the older per-cache variables still name one folder.
Clearing the root is always safe, because every entry is a pure function of its inputs, so re-checking
a branch on a moved main is cheap.
[D-176](decisions/D-176-wasm-artifact-cache.md) and
[D-177](decisions/D-177-build-cache-module.md) give the keys, and
[Benchmarks](benchmarks.md#build-caches) the figures.

- `bun run build --pages-only` while developing and looking at a scene; the full `bun run build` when a
  landing needs the size check. `NULL3D_NO_CACHE=1`, or `--no-cache`, builds every file again.
- The build keeps the page build's printed report, which lists every file it writes. On 19 October 2026
  that report passed a megabyte after the first-use shader files were split by feature family. The
  capture's default limit killed the child, and the build reported only "the production build failed"
  with no error. The capture now holds 64 MB. The test tool's page build prints the same kind of
  report, and its capture now holds 256 MB for the same reason: the texture-cache page's build fills
  the default limit, which killed builds of the browser checks.
- A cache is used only when its entry is whole. The shader modules cache, for example, requires every
  module that `shaders.ts` loads, from its imports and the device module names its tables hold, and a
  record that names the bytes of each of them. A set that misses one, or holds a file with other bytes
  than its record, is a miss, so the build runs again rather than reporting "up to date" while a file
  is absent or half written.
- Each cache prunes itself: while it holds more than 24 GiB it removes its least recently used entries,
  and an entry used within the last two hours stays, because another checkout's build may be reading
  it. A cache key names every input of the build, including the build's own code, and a build hashes
  its inputs again before it stores anything, so an edit that lands while a build runs is never stored
  under the key of the state before it.
- Never a build beside a browser or image run of the same worktree. A half-written core makes a page
  fail for no reason (`E1402`, `E1406`). Builds themselves may run at the same time: each stages its
  output in a folder of its own, named for the build's process, and Cargo locks a target folder while
  it writes. A size check takes the checkout's own lock, `target/build.lock`. The base commit is built
  with that commit's own build script, in a base tree under this checkout's target folder. Size checks
  of two checkouts therefore run at the same time.
- Each checkout builds Rust into its own `target` folder. Never point two checkouts at one Rust build
  folder, with `CARGO_TARGET_DIR` or `NULL3D_CARGO_TARGET`. Cargo finds the engine's crates at the
  same workspace paths in every checkout and judges them fresh by file times. So a shared folder lets
  one checkout compile or link against another checkout's build of `null3d-gpu`, `null3d-render` or
  the shader compiler. The caches above then store that output under the right key, and the bad entry
  outlives the build. On 14 and 15 October 2026 this gave branches a stale shader compiler, another
  branch's GPU constants, and a core without its own feature.
  [D-177](decisions/D-177-build-cache-module.md#addendum-15-october-2026-one-rust-build-folder-per-checkout)
  gives the reasons.
- sccache, when installed, compiles the dependency crates once for every checkout. The build uses it
  through `RUSTC_WRAPPER` when it finds `sccache` on the `PATH` and no wrapper is set; an empty
  `RUSTC_WRAPPER` turns it off. sccache keys each compile by the contents of its sources, flags and
  dependencies, never by file times, so sharing it across checkouts is safe. Without sccache the
  build runs as before, as in CI.
- When a core change seems to be ignored, build with `NULL3D_NO_CACHE=1`, and check the flags word
  that a material row holds before looking anywhere else.

A project that the Vite plugin builds has a shader cache of its own. The plugin keeps every compiled
shader in that project's `node_modules/.cache/null3d-shaders`. The key is the WGSL, the path, the
variant spec and the compiler's version. A game's second `vite build` therefore compiles only the
shaders that changed. On a small project of eight shaders a cold build took 2.87 s and the next took
0.30 s. The plugin cannot load repository tooling. So it repeats
[D-177](decisions/D-177-build-cache-module.md)'s three rules on its own: an atomic write, a miss when
an input changes, and one opt-out. `NULL3D_NO_CACHE=1`, or Vite's `--force`, ignores it.
[D-175](decisions/D-175-vite-plugin-shader-cache.md) gives the figures and the key.

The engine's own shader build has a per-entry cache too. `bun run shaders`, and every command that
runs it, passes `--cache ~/.cache/null3d/shader-cache/<stamp>` to `shader-build`, where the stamp
hashes the compiler's sources. The build keeps each entry's compiled output under that folder. A
change to one shader then compiles only that shader, and a change to a library module compiles only
the entries that import it. On the Mac on 14 October 2026, all 54 entries from cold took 442 s. A
second run with nothing changed took 10.6 s and compiled none. A change to the one file that the two
cull entries share took 10.4 s and compiled 2 entries. A change to `lib/math.wgsl` compiled the 31
entries that import it, through `null3d::lighting` and `null3d::area_lights`, and took 356 s.
`--no-cache`, or `NULL3D_NO_SHADER_CACHE=1`, compiles every entry again.
[D-56](decisions/D-56-first-use-shader-files.md) gives the reasons and the key. CI keeps the same two
shader folders in the Actions cache, under the same keys ([CI's jobs](#cis-jobs)).

`bun tools/shaders.ts --entries-shard i/n` compiles shard `i` of `n`, counted from 0, of the
manifest's entries. It stores them in the same per-entry cache and writes no module. It splits
whole entries by build cost, as the shader tests do. An entry's key reads only its own source, its
manifest table and the stamp, and a shard keeps every library module. So an entry that a shard
stored is the entry that a whole build looks for. `--entries-out <folder>` copies the entries that the run stored into
the folder, and none that the cache held before. Several machines can then each fill a share of the
cache. A build that first copies their folders into `<entries-dir>/<stamp>`, the folder that
`bun tools/shaders.ts --cache-keys` names, compiles none of their entries. One entry,
`standard_maps`, makes 77.8% of the builds, so its shard still takes about three quarters of a whole
build. A cache entry per part of an entry would remove that limit.

### A clash on a generated file

Never merge a generated file by hand. Take main's side, run the file's generator, and commit what the generator writes.

- For a file that git does not keep, main's side is its deletion: `git rm --cached <path>`. The file stays on disk, and the generator writes it again.
- Git keeps the constants that TypeScript shares with Rust, `packages/engine/src/generated/core.ts` and `gpu.ts`, and the render graph's text dump in `crates/null3d-render/tests/snapshots/`. Take either side, then run `NULL3D_UPDATE_GENERATED=1 cargo test -p null3d-wasm -p null3d-gpu -p null3d-render`, and stage what it writes. Run it after every merge of main, also when git reports no conflict.

### Generated files that git keeps

[D-105](decisions/D-105-generated-files-out-of-git.md) gives the reason for each. They are:

- The constants shared with Rust, and the Rust tests' snapshots
- The three.js test fixtures, the meshopt test files and the image references
- The vendored Basis and meshopt builds
- The benchmark records and the README's animation
- What a release writes: the version numbers, `CHANGELOG.md` and the plugin's marketplace file
- The lock files and the sample content's manifest
- The list of milestone task IDs that a `Task:` footer may name

A new kind of generated file goes into `.gitignore`, unless its branch adds its reason to D-105.

## Merge main into a branch

- Merge main into your branch. Do not rebase a branch that you pushed, because a rebase needs a force push (see [Commit messages and pushes](#commit-messages-and-pushes)).
- Never merge a generated file by hand. [Generated files](#generated-files) says how to resolve a clash on one.
- A merge commit holds only the resolution of its conflicts and mechanical fixes. Mechanical fixes are files that a generator writes again, renumbered entries, and edits that the other side's change forces, such as a renamed import. Write anything else in a normal commit before or after the merge: a feature, a test, a shading change or docs text. Five merges of 12 to 14 October 2026 held features: area lights in reflection passes, automatic exposure in the two-step output, and a new clear coat roughness. Four more held measured figures of D-174. No history search finds them.
- Before a push, `bun tools/hooks/check-merges.ts <base>..HEAD` reads each new merge against git's automatic merge, as `git show --remerge-diff` does. It refuses a merge with more than 30 words of new work, or any new shader code. It also refuses a binary file that the merge changed itself. To fix a refused merge before you push it, undo the new work with `git commit --amend`, then commit it again on top. When the check cannot tell that an edit is mechanical, add a `Merge-Edit:` trailer to the merge's message. It names the edit and says why, such as `Merge-Edit: lit.wgsl passes main's new finish() argument`.
- A branch from before git stopped keeping the shader modules gets a conflict on each module that it changed when it merges main. Resolve them all with `git rm --cached packages/engine/src/generated/shaders*.ts`, which keeps the files for the next build to replace.
- Check the shared numbers after the merge. Two branches can each take the next free number, and git then merges both lines without a conflict. The shared numbers are the error codes (`packages/engine/src/errors/codes.ts`) and the scene command numbers (`crates/null3d-wasm/src/constants.rs`). They are also the draw list's opcodes and pipeline template numbers (`crates/null3d-gpu/src/drawlist.rs`), and the decision record numbers. The engine's own templates take numbers below 128, the first custom template. Custom materials, effects and tone curves take numbers from 128 up, which the sketch gives out at run time. The first custom template was 64 until 11 October 2026. The techniques of [D-142](decisions/D-142-more-techniques-before-1-0.md) used nearly every number below it, so it moved to 128. A unit test checks that each engine template has its own number below 128. The bindings and slots that a shader and its bind group layout share are shared numbers too. A unit test catches a clash in some of these lists, such as the opcodes, but not in all of them. The docs check, `bun run docs:check`, refuses two decision records with one number.
- Build and run the quick checks again before you push the merge: lint, types, docs, skills and unit tests. Then rerun the browser and image tests only of the areas that the merge's conflicts touched. CI runs every test once the branch is on main.
- Run a branch's own copy of a hook's tool, such as `tools/hooks/check-trailers.ts`, from that branch's checkout. Another checkout's copy can be older, and refuse a valid `Size-Growth:` name.
- A merge that brings Rust changes leaves the built WebAssembly cores older than the checkout. Every browser run and picture run in that tree then fails with `E1402`. The message says the threaded engine core was built from other Rust sources. It reads like a packaging fault. The cure is a rebuild, so rebuild after such a merge, before any browser run. Two helpers each lost a cycle to it on 16 October 2026.

## A branch from before generated files left git

Git kept the generated files until 8 October 2026 ([D-105](decisions/D-105-generated-files-out-of-git.md)). A branch from before then conflicts with main once, when it merges main. Fetch main, then run main's merge script from the branch's copy:

```sh
sh -c "$(git show origin/main:tools/merge-main.sh)"
```

The script merges main. A generated file that main deleted stays deleted, and the file stays on disk. Where a written page conflicts on its old generated part, such as an API reference, the page list or a table, it keeps main's side. Then it runs `bun install`, which writes every generated file, and commits the merge. It stops and lists any other conflict. Resolve those by hand, then run `git commit --no-edit`. Last, check that `bun run docs:check` passes.

A test on 8 October 2026 used a branch that edited a skill, its copy, an API page's prose and reference, an error page, the page list and a preset table. After the script, the branch differed from main only in its edits to sources: the skill and the prose.

## A branch that edited the old table of tested devices

The record of [tested devices](tested-devices.md) was one table until 7 October 2026, and each run added text to a cell of its row. Now each run is a file of its own ([D-97](decisions/D-97-tested-devices-per-file.md)). A branch that edited the old table conflicts with main on `.dev/tested-devices.md`. Move its edits into the new files in one step:

1. Note the branch's last commit before the merge: `tip=$(git rev-parse HEAD)`.
2. Fetch and merge main. Take main's page for the conflict: `git checkout --theirs .dev/tested-devices.md`.
3. Run `bun tools/tested-devices.ts --branch $tip`. It compares the branch's table with the table where the branch started, its merge base with `origin/main`. It writes a run file for each row's new plans and results, and a new folder for each new row. It puts changed facts and new known issues in each README.
4. Read its notes. A note names each cell that the branch changed in place rather than added to, and each fact that it changed. Check those files by hand.
5. Run `bun run docs`. Stage the page and the new files, and commit the merge.

## Commit messages and pushes

- A push to main runs a check first, `tools/hooks/pre-push.ts`, which the owner approved on 15 October 2026 ([D-157](decisions/D-157-direct-pushes-to-main.md)). A push to any other branch runs nothing, so saving a branch stays fast. The check prints each command it runs and why. It runs the commit message and trailer checks (commitlint, then the trailer check) over every commit that the push adds to main, as CI's `commits` job does, and the merge check over the merges among them. So a bad message, a bad trailer or a merge that carries new work is caught before the push, not by a red main after it. When the push changes Rust code or Cargo settings, it also runs `cargo check --workspace` and the tests of each changed crate. The tests run through cargo-nextest's `ci` profile with `--no-fail-fast`, or through `cargo test` where nextest is missing. A changed workspace `Cargo.toml`, `Cargo.lock` or Rust setting tests every crate. The test that builds every shader runs in CI only, as it takes half an hour or more.
- A push that changes no Rust file skips the cargo steps, because the merged Rust tree then holds main's own bytes, which main's CI has compiled. The type check still gates the push, since it reads the merged tree. The cargo check follows as its own queued job, and a failure there is fixed by the next push. Two things must hold: the branch's own diff changes no Rust file, and the merge that it just resolved changes none. [D-157](decisions/D-157-direct-pushes-to-main.md#addendum-15-october-2026-a-rust-free-push-needs-the-type-check-only) gives the ruling and the criterion.
- The check compares with the commit that git reports for main before the push. When that commit is not in this checkout and no local main ref meets the pushed commit, it refuses the push and asks for a `git fetch origin main`, since it cannot say which commits the push adds.
- The cargo steps compile the working tree, so push from a clean checkout of the commit that you push. They use the checkout's own Rust folder, or `CARGO_TARGET_DIR` when it is set.
- On the Mac that runs the helpers, the git setting `null3d.jobQueue` names the job queue script. The check then runs the message and trailer checks in the queue's quick lane and the cargo steps in its CPU lane. So a push does not load the Mac outside the queue. A push may therefore wait for a slot. The environment's `NULL3D_JOB_QUEUE` names the script too. Elsewhere the steps run directly.
- git opens the connection to the remote before it runs the check, and holds it, saying nothing, until the check returns. The hook needs the ref list that the negotiation produced. A peer closes a connection that says nothing for about six minutes. After that, git writes the push into a socket that has gone, and prints nothing. Nothing is pushed, and the status says only that a write failed. A held session to `github.com` that wrote nothing ended after 365 seconds on 16 October 2026. The check reads the remote's URL from git's own hook arguments, which the hook's body passes on. So the check refuses a push whose remote it reaches over ssh, when nothing keeps that connection alive. It names the setting to add. Put `ServerAliveInterval 20` under the host in `~/.ssh/config`. A checkout may name it instead, through `core.sshCommand`. A queue makes the check long, and so a machine that runs a queue needs this most. The cargo steps took 390 seconds of test time through the queue against 135 seconds run directly, and only the longer one outlived its connection.
- Only in an emergency, skip the check with a `Push-Check-Skipped: <reason>` trailer on a commit of the push. The reason names the emergency, such as a red main that this push fixes while the job queue is stopped. The check prints the reason and runs nothing. `git push --no-verify` skips every hook, so never use it.
- Push over the ssh remote fails while the key agent refuses to sign. The message reads `signing failed ... agent refused operation`. A fetch on the same machine can then hang until it times out. The web address works, through the GitHub CLI's saved login: `git -c credential.helper='!gh auth git-credential' push https://github.com/null3d-engine/null3d.git HEAD:main`. It runs the same pre-push check. The check reads the working tree, so the address does not matter. On 16 October 2026 the agent refused for the rest of the session, and every landing went over the web address.

- A merge commit must pass the commit-message check, as every commit does. A message such as `Merge origin/main into <branch>` passes, and so do git's own merge messages. A message such as `merge origin/main` fails, because the check reads it as a commit without a type.
- Never force push a branch that you pushed, so never amend, rebase or squash a commit that you pushed.
- A `Task:` footer names a listed milestone task that the commit delivers part of, or says `none`. The commit-msg hook (`tools/hooks/check-task.ts`) refuses free text and IDs that are not in `tools/hooks/task-ids.txt`. Before 15 October 2026, footers carried text such as `main CI repair`. Four shader commits carried `Task: M2-J4`, though they delivered none of its materials. The milestone count read those footers and counted tasks that were not done. Now it counts only each task's audited status.
- Main keeps every commit of a branch, its merge commits too, so every plain commit's subject becomes a release-notes line, and the commit-message hook checks each one. A pushed commit with a bad message stays on the branch, and on main once it lands.
- Put each trailer on a plain commit, never on a merge commit; an empty commit can carry it. The one exception is `Merge-Edit:`, which explains an edit in the merge itself (see [Merge main into a branch](#merge-main-into-a-branch)). Main keeps the messages of a branch's plain commits and drops the merge commits' messages. CI's trailer check and size check therefore read only the plain commits, so a trailer on a merge commit counts for nothing. On 7 October 2026, #397's `Size-Growth:` trailer sat on a merge commit. Its own size check passed, and the merge queue's check of the squash failed ([Benchmarks](benchmarks.md#download-size)).
- To fix a bad message on a branch that is not on main yet, put the branch's files in one clean commit on a new branch. For example, `git switch -c <new-branch> origin/main`, then `git merge --squash <old-branch>`, then commit with a good message. Land the new branch, and delete the old one. Do not force push the old branch.
- The same applies when a branch carries copies of commits that main already holds, and a commit gate rejects one of the copies. Put the branch's files in one clean commit on a new branch from main, land it, and delete the old branch. Do not force push either branch, and do not loosen the gate. On 8 October 2026, #417's branch held old copies of the commits of M2-K1 and the S25 skinning fix. The trailer check failed on one of them, because its `Size-Growth:` trailer named shader files by their names before a rename. A later branch held the same files as #417's last commit, in one commit merged with main, and replaced it. The owner approved this way on 8 October 2026.

## Landing a branch

A branch lands on main by direct push ([D-157](decisions/D-157-direct-pushes-to-main.md)). No reviewer reads it first, so the author runs every check that the change needs.

1. Push the branch to its own remote branch as you work, to save it: `git push origin HEAD:<branch>`.
2. Fetch, and merge `origin/main` into the branch. Resolve each clash section by section, and keep both sides' additions. Take main's copy of a generated file and generate it again.
3. Run `bun install`, then build, then compile the merged tree at once: `cargo check --workspace` and `bun run typecheck`. A merge that keeps both sides of a struct or a constant is often valid text, so only a build finds the fault. A plain `bun install` can report "no changes" and still leave a workspace link missing. The type check then fails on an import of the package that the merge added. Run `bun install --force` in that case, which writes the link. Seen on 17 October 2026, when main's impostors add-on reached `tests/package.json`.
4. Run the local checks: `bun run check`, `bun run typecheck`, the unit tests, `cargo nextest run` for each crate that changed, the docs, style and skills checks, and the browser and image tests of the parts that the branch changes. An image change needs both reference sets. Run `bun run build:check-size`, and [the GPU check](#the-gpu-check) when the branch changes how the GPU draws. Check the trailers with `bun tools/hooks/check-trailers.ts origin/main..HEAD`.
5. Push with `git push origin HEAD:main`. When git refuses the push because main moved, merge `origin/main` again, rerun the checks that the new commits touch, and push again.

- A new push to main cancels main's running CI run, by the owner's choice: only the newest main matters.
- Never wait for main's CI before a push: not for a running run, and not for a red one. When a finished run on main fails because of your push, fix it at once. Others keep pushing meanwhile.
- When a job on main fails, read its log, and find whether a push caused the failure. `gh run view <run> --log-failed` prints the failed steps. A test that fails only under load, or a run that GitHub cancelled when a runner shut down, says nothing about the code. Run the failed jobs again with `gh run rerun <run> --failed`. Otherwise fix the cause and push. Record the cause in `.dev/` either way.
- A run that a later push cancelled still holds the jobs that had already finished, and those failures are the signal. Read them with `gh run view --job <id> --log`, which answers once the cancellation has gone through; `--log-failed` on the run itself does not. On 15 October 2026 a push cancelled main's run part way, and dismissing it as cancelled threw away the only readable account of six failing jobs - a run's status describes whether it finished, not whether what it did still counts. Read the finished jobs before deciding a run told you nothing.
- A cancelled job reports no test results at all, so a list of failures taken from a run that lost jobs is not complete. Its conclusion is `cancelled`, it prints no summary of the tests it ran, and the tests it never reached appear nowhere else in the run. The faults inside it then read as faults that never existed. On 15 October 2026 the browser job's 20-minute limit cancelled shards 1, 7, 9 and 10 of run 38824482127. Three faults that were red on main lived only in those four logs. They are the coat-and-sheen behavioural test in shard 1, the forest demo in shard 7, and the shader library page in shard 9. The forest demo differed in 37 per cent of its pixels. None of the three appears in any summary of that run. A batch landing the next day was blamed for a regression it had not caused. So when a run has cancellations, read each cancelled job's own log before trusting any list of failures. Use `gh run view --job <id> --log`. Read the jobs that never reported as missing evidence, not as jobs with nothing to say. A run whose verdict matters and that lost jobs is run again rather than reasoned about. Run every job of it afresh with `gh run rerun <run>`. [Image tests](image-tests.md#ci) lists the shards and their limits.
- Two tests are known to fail only on a loaded machine. One is the GPU loss test "draws on after a GPU loss" on SwiftShader. It got no frame in its fixed recovery wait, in full local runs while the Mac's load was 21 to 30. The other is the benchmark page test of S4 on SwiftShader. It drew no frame in its short run, in CI runs 37289400132 and 37578361814. Both passed when they ran again. In each, the slow software GPU took longer than the test's fixed window to draw the first frame after a start or a loss. A rerun alone shows whether a failure is this ([Image tests](image-tests.md#tests-on-slow-machines)).
- The Safari and Firefox jobs compare the image tests with the Mac's `chrome-real-gpu` references. A test without one of these references, or without its SwiftShader reference, fails `bun run check` ([Image tests](image-tests.md#references)).
- CI's last job, `ci-passed`, waits for every other CI job, and it passes only when each one passed. A job may skip only when the first job, `changes`, passed and said that the job does not run. Main's rules require `ci-passed`, not each job, so a CI job can split into more shards and change its name with no change to the rules.

### A pull request of a long branch

Work lands by direct push since 13 October 2026. A pull request remains useful for a long piece of
work. On a pull request, the `commits` check reads every commit from the merge base with main, not
only the latest push. A branch that lives for weeks carries commits from before a rule tightened,
and those commits fail the check.

On 19 October 2026, 22 of 1,299 commits on the M2 branch failed it: 28 findings, mostly subjects
that named a decision record and `Size-Growth:` values that named no measured file. The rules
changed after those commits were made. None of the recent work was at fault.

A squash merge keeps the pull request's title and drops every commit message, so those findings
never reach main. To avoid a red gate before the merge, squash the branch to one commit first:

```
git reset --soft "$(git merge-base origin/main HEAD)"
git commit -F message.txt
```

Check the whole range before the merge: `bun tools/hooks/check-trailers.ts origin/main..HEAD` and
`bunx commitlint --from origin/main --to HEAD`. A direct push has no such problem: the pre-push
hook and CI read only the commits that the push adds.

### Before you push to main

Two branches that change the same code files land one after another. The smaller or readier one lands first, and the other merges main again and runs its checks before it pushes.

- Run `bun run build:check-size` with current main merged. On 6 October 2026 a change failed its size check for two files that had grown 2.0% against a newer main.
- Two branches that add text at one place of a file clash when the second one merges main. Resolve the clash by keeping both sides. The record of [tested devices](tested-devices.md) had many of these clashes, so each run there is now a file of its own ([D-97](decisions/D-97-tested-devices-per-file.md)).
- Main's run after the push is the last check of the combined code. The size check of a run on main compares with the commit before.

### The GPU check

CI's benchmark job has no GPU timer, so it cannot see a change that slows only the GPU. On the Mac's GPU, pull request 389 made S4 and S6 on WebGPU 5 to 33 times slower. Yet it passed every CI job ([D-109](decisions/D-109-gpu-time-guard.md)). So a branch that can change the GPU's work runs the GPU check, and records the result. The check needs a computer with a GPU of its own.

- It must run when the branch changes `crates/null3d-shaders/src/`, `crates/null3d-shaders/wgsl/` or `crates/null3d-shaders/shaders.toml`. It must also run when the branch changes `packages/engine/src/gpu/`, `packages/engine/src/render/` or `packages/engine/src/quality/`. Changes to tests there do not count.
- Run the check in two steps once the branch's code is final. First run `bun run bench:gpu-check --prepare`, which uses only the CPU. It builds the branch and its benchmark pages. It also makes sure that a shared cache holds a build of the branch's merge base with origin/main. Then run `bun run bench:gpu-check --measure` on a Mac whose load is low. It builds nothing. It runs S4 and S6 on WebGPU at Medium and at High, in turns, in Chrome. With neither option, the check runs both steps in turn. [Benchmarks](benchmarks.md#the-gpu-checks-two-steps) says how the cache works and what each step costs. Set `NULL3D_PORT` to a port of your own: the check takes that port and the next.
- It prints one line, such as `GPU-Checked: 061177262..a0a7c1777 passed: s4 medium 1.86 to 1.90 ms (+2.2%); ...`. Put that line on a plain commit, an empty one if need be, such as `test: record the GPU check`. The commit must be the last one that changes the files above, or come after it. A later change to those files needs a new run.
- CI cannot run the check, since its machines have no GPU timer. So the trailer is the author's record that the check ran, and what it measured. The trailer check only fails when the trailer is missing or says nothing. It cannot check the figures.
- `failed`: a page's GPU time grew more than 25% and 0.3 ms. Find the cause and fix it. A slowdown on purpose needs a `Bench-Expected:` trailer that names it, such as `Bench-Expected: s4/null3d-webgpu/gpu-time: a second shadow pass`, and then a new run.
- `not measured`: the browser gave no GPU times, as on a machine without a GPU timer. Run it on a computer with one.
- `not judged`: the benchmark pages changed between the two commits, so the builds drew different work. The line still gives the figures, and the reviewer judges them.
- A change that cannot change the GPU's work, such as a comment in those folders, still needs the trailer. It then says why no check ran, such as `GPU-Checked: not run; only comments change in packages/engine/src/gpu/`.
- Each night, the owner's Mac runs the same check on main against the night before. That catches what slips past a branch's own check, within a day.

## What CI runs where

Each push to main runs every job, on the pushed commit ([D-157](decisions/D-157-direct-pushes-to-main.md)). Main's jobs also keep the caches, and `wasm-checks` keeps the commit's sizes. A run started by hand runs every job on the branch that it names: `gh workflow run ci.yml --ref <branch>`. The workflow still answers pull-request events, but no branch opens a pull request now. [D-99](decisions/D-99-no-merge-queue.md) records what those events ran, the docs-only skip among them.

- A new push to main cancels main's running run, so only the newest main is tested.
- CI's Chrome tests draw on SwiftShader only, and Firefox on Linux draws with a software renderer. The Mac's real GPU gets no run in CI, apart from Safari. So run the browser and image tests of the areas that a branch touches once on the Mac's GPU, before it lands. Run `bun run test:browser` with Playwright's `--grep` or a spec file, and `bun run test:images` with `--grep`. A change that Safari or Firefox may treat differently also runs `bun run test:real-browsers Safari Firefox` ([Device sessions](devices.md)).

| Event | Jobs |
| --- | --- |
| Draft pull request, which no branch raises now | The quick checks: `build`, `docs-and-tools`, `rust-lint`, the three parts of `rust-tests`, `size-base`, `wasm-checks`, `shader-compiler` and `packages` |
| Docs-only pull request, which no branch raises now | `build` and `docs-and-tools`, and `skill-sketches` when the change touches the skills' or the cookbook's Markdown ([The docs-only skip](#the-docs-only-skip)) |
| Pull request ready for review: opened, pushed, reopened, or marked ready, which no branch raises now | Every job: the quick checks, the `browser` shards, the job of the tests that run alone, the showcase HUD's job, the 2 `bench` shards, and the `real-browsers` shards in Safari and Firefox |
| Push to main | Every job, on the code that the merge made. Main's jobs also keep the caches, and `wasm-checks` keeps the commit's sizes |
| Started by hand | Every job, on the branch that the run names: `gh workflow run ci.yml --ref main` |
| Merge queue | Every job, only while main's rules still use the queue |

- Before 6 October 2026, every pull request and every push to main ran the full suite, about 100 runner minutes each. GitHub Free runs 20 Linux jobs at once, so the queue's runs waited for runners for about half of their 32 minutes. From 6 to 7 October 2026, pull requests ran only the quick checks, and the queue ran the rest ([D-86](decisions/D-86-ci-runs-per-event.md)).

### The docs-only skip

A pull request that changed only docs files ran only the checks that read them, and CI reads the same path list when it decides the jobs of a push to main. CI's first job, `changes`, decides it from the diff of the merge commit with main. A renamed file counts as its old path and its new path.

- Docs files are Markdown files anywhere, and every file in `.dev/`, `docs/` and `skills/`. Only the `docs-and-tools` job reads them, in its docs, style, skills and type checks, the skill validator and the unit tests. Nothing in the engine, the Rust crates, the benchmarks or the test pages reads them. That holds for `docs/data/threejs-mapping.json` too: only the docs generator, the skills check and their unit tests read it.
- `build` still runs, because `docs-and-tools` needs its shader modules.
- The browser tests draw each complete sketch in the skills' and the cookbook's Markdown (`tests/image/skill-sketches.spec.ts`). So when a change touches Markdown in `skills/` or `docs/cookbook/`, the `skill-sketches` job runs that one test file. In a full run, the `browser` shards draw the sketches, and `skill-sketches` skips.
- Every other job skips. That is the Rust jobs, the size check, the shader compiler and the packages test. It is also the browser, benchmark page, allocation, Safari and Firefox jobs.
- A change to any other file runs every job. That includes `.github/`, `package.json` and the tools.
- Each push to main runs every job, so main's run still tests the docs change with everything else.
- The reason: a full run takes about 30 jobs. GitHub Free runs 20 Linux jobs at once, and few macOS jobs. On 11 October 2026, with 6 or more branches in flight, main's own run waited over 90 minutes for runners. A docs-only run takes 4 short jobs, `ci-passed` among them, or 5 with the sketches.
- A new test that reads a docs file must run in `docs-and-tools`. If it cannot, add the file's path to the `changes` job as a code path. Otherwise a docs-only change skips the test, and only main's run finds a failure.
- The `changes` job's log lists the changed files and its four answers: `code`, `full`, `allocation` and `sketches`. `ci-passed` prints them too.

The cache's key holds the compiler's version, so each new nightly still builds the dependencies once. - One `build` job builds the WebAssembly files and the shader modules, and every browser, benchmark and macOS job downloads them. Before, each browser shard built them again, which took 1.5 minutes. The artifact's paths named each kind of module, and on 16 October 2026 they missed the shared-paragraph tables that arrived that day. `isShaderModule` counts those tables (`tools/lib/shader-modules.ts`). A set that does not match its record then fails that job at once, and names the files it lacks. The `shader-compiler` job builds the shaders itself, so it does not set the switch.
- CI keeps the built shaders in the Actions cache between runs, through the action `.github/actions/shaders`. It keeps the same two folders as a local build ([Builds](#builds)). One holds the module sets, by the hash of their inputs. The other is the per-entry cache, under the compiler's stamp. `bun tools/shaders.ts --cache-keys` prints the folders, the input hash and the stamp, and the Actions key holds the stamp and the hash. A run whose inputs match restores the module set and compiles no shader. A run with the same compiler restores that stamp's entries and compiles only the entries whose own key changed. A new compiler restores nothing. The tools check each entry's key themselves, so a restored entry never serves other inputs. Before a save, the action deletes every other stamp and module set, so the cache does not grow. A failed or cancelled build still saves the entries it finished, under a key of its own. That matters on main, where each push cancels the run before it. The `build` and `size-base` jobs and the benchmark workflow's `build` use the action. The newest-nightly job restores the cache but never saves it. A size check base or a benchmark baseline from before the action builds every shader.

Under the load of the other tests, the light grid's allocation test failed once in CI. It counted frees from job workers that an earlier case had stopped. In the default order, it held the run back behind the slow tests each time. The tests then took 8.2 minutes in CI, against 2.8 minutes without the isolation. The new order took 2.5 minutes on 4 threads of a MacBook Pro.

One test in the shader crate's `build` tests builds every shader. Every check that reads the whole output runs on that build. A second build of a few entries, which together make one module of every kind, runs at the same time on another thread, for the check that two builds write the same modules. CI runs that check in its own job, as the shards above say. Other tests build only the shaders that they read, through the tests' `subset` module: the command line tests run the command on 4 shaders, and the effect tests build only their 2 hosts. nextest runs each test in a process of its own, so a cache in one test's process never serves another test. Before this rule, 17 tests each built every shader, for 280 to 590 seconds each on a 4-core runner. As the shaders' variants grew, the `rust-tests` job grew from 14 minutes to past its 25-minute limit. CI cancelled it on main and on #484 on 11 October 2026 (run 38096978506). A new check of the whole output goes into the one test, and does not add a build. The test runs in its own part of `rust-tests`, and again in `shader-compiler`. There the shader compiler builds every entry of the manifest, one entry at a time within each of a few processes that run at once, and compares every result with the test's native build of the same builds. An entry that costs more than an even share of the processes goes to them in pieces, each a part of its builds. There is one process for each core, and no more than the available memory holds at 2 GiB each, where Linux reports that memory. One entry with no other shader is the scale a build tool asks for, and a failure names the entry; the module's answer for an entry comes back in pieces, for the reason [Implementation notes](implementation-notes.md) gives.
- Every CI run saves its caches, and every run restores its own branch's first, then main's. These are the Rust builds, the packages, Playwright's Chromium, the sample content, the built shaders and the base sizes. The workflow's `SAVE_CACHES` decides it. A pull request's run saves under the pull request's own ref, so the next push to it reuses what this one built. Until 19 October 2026 only main's runs saved them. On 5 October 2026, the repository's caches held 10.7 GB against GitHub's limit of 10 GB. Past the limit, GitHub drops the least recently used caches. Pull requests and merge queue runs each saved copies that only their own later runs could restore. On 19 October 2026 the Enterprise plan let the owner raise the limit to 30 GB ([D-194](decisions/D-194-ci-jobs-in-parallel-on-enterprise.md)). A pull request's saves no longer push out main's. The benchmark workflow still saves only on main, apart from a branch's own shader entries. Each run of it saves the city's files under a key of its own, which a branch's runs would multiply. The package install with its cache is the action `.github/actions/bun-install`.
- The `commits` job checks the commit messages with commitlint and the trailers with `tools/hooks/check-trailers.ts`. On a push to main it reads every plain commit after main's commit before the push. Before 15 October 2026 it ran only on pull requests, so after the move to direct pushes no CI check read a message or a trailer.
- The `ci-passed` job tells a time-out from a cancel. GitHub calls both "cancelled". `ci-passed` reads each cancelled job's messages and marks a job that hit its time limit as an error: a time-out is a failure of that job. A job that a newer push cancelled gets a warning.
- Each nextest profile of CI gives every test a time limit: 15 minutes in `ci`, 60 in `shader-module-exports`, and 120 in `whole-shader-build`. The shader module exports part allows 90 minutes. On 19 October 2026 the M2 feature families pushed the whole shader build past its old 85 minutes: it built every shader twice and stopped at 5,100 seconds on run 39177518706. The job's limit rose to 135 minutes with it. On 20 October 2026, balanced shards and optimized shader crates cut each shader part's limit to 25 minutes ([D-194](decisions/D-194-ci-jobs-in-parallel-on-enterprise.md)). The module exports' limit is 45. nextest stops a test past its limit and reports it as failed. Before, on 913613695, one test failed and nextest waited on two long tests until the job's limit, so the job read "cancelled" and showed no result.
- The shader cache action writes each run's shader build into the job summary: the minutes it took, the cache it restored, how many entries it compiled and reused, and the entry and module counts and sizes. From run to run, the build's growth shows. A run whose inputs match the restored module set compiles nothing, and prints no compiled-and-reused line; the record names that case. The record only reports the log. The build step has already decided the job, so a missing line shows in the summary instead of failing the build. Until 15 October 2026 the step read a missing line as an error, because a search that found nothing ended it under the shell's `-e` and `pipefail`. Main's run 96b955566 failed its `build` job that way, on a restored module set, and a failed `build` skips every job that needs it. `tests/lib/shaders-action.test.ts` runs the record step over each shape of log, so a missing line cannot fail a job again.
- A step that reads a tool's output must let the tool's failure fail the step. On 16 October 2026 the size job's base step read `echo "sha=$(bun tools/build-wasm.ts --print-base)"`. The tool named the commit it could not resolve, and the step stayed green. An empty sha then travelled to the artifact's path, and the job failed three steps later. A push that replaced main's history is what removed that commit (run 38894339212).
- A step that runs for minutes must print progress while it runs, and it must print the reason when it fails. A job whose log holds nothing tells a reader nothing. On 16 October 2026 ten of the fourteen real-browser shards died with empty logs. The load server compressed both page builds before the first load, in silence, for 13.6 to 16.1 minutes, and the jobs then hit their limit with no output at all. So a silent step is a defect even when the work would have fitted the limit.
- A test whose subject is not download time must not be affected by when a file is compressed. The load server now compresses a file when a load first asks for it, so compression runs while a measured run goes on. The owner's ruling of 16 October 2026: if a real-browser run's item times move because of that, the test is what changes, and not the server. The run exists to check the engine rather than the server, so a test that moves because the server got lazier is measuring the wrong thing. The tests that time a download are the exception: compression is their subject, so they keep seeing it. The warm-up does not come back. It bought a warm cache and charged 13.6 to 16.1 minutes of silence to every shard that served production builds, so work that later looks slow is to be found and measured rather than answered by restoring it.
- Main's rules require `ci-passed`, not each job, because a job that splits into more shards changes its name. Without that job, a new shard would strand every open pull request.
- Playwright's Chromium and its Ubuntu packages stay in the Actions cache. Ubuntu's package mirror stalls for 30 to 110 seconds on some files, and the install once took 11.5 minutes of a 4-minute shard.
- The Rust caches are keyed by the workspace's `Cargo.toml`, because the cache's own key leaves out the build profiles. After a profile change, each run restored the old cache and compiled the dependencies again, for about 3 minutes.
- Development builds optimize the dependencies (`[profile.dev.package."*"]`), so the shader tools' tests and `bun run shaders` parse and validate WGSL about 4 times faster. CI's Rust test and shader compiler jobs also build the shader crates themselves optimized, through `.github/actions/optimized-shader-crates`. Their tests build every shader, and the crates' own unoptimized code made such a test about four times slower than the build job's shader tool.

## Several copies on one machine

People and agents often work in several copies of the repository at once, such as git worktrees.

- Give each copy its own ports with `NULL3D_PORT`, as [AGENTS.md](../AGENTS.md#performance-work) says. Each copy then uses its port and the three ports above it.
- A run refuses the dev server of another copy. Playwright's runs off CI reuse a server that already answers on their port, and so does `startServer` in `tests/lib/server.ts`. Every copy takes port 5173 unless `NULL3D_PORT` names another. So until 21 October 2026 a run could draw another copy's code and compare it with its own copy's references. The Creek demo's Mac references of 20 October came from such a run. Its sun's heading differed between main and a branch. Runs on main's own server then drew 2.1% to 2.9% of the pixels differently ([Image tests](image-tests.md#references)). The dev server now answers `/__null3d/checkout` with its copy's folder (`checkoutServer`). Playwright's global setup `tests/lib/checkout-setup.ts` and `startServer` refuse a server that names another folder. They also refuse a server that names none, as a server started before the check does: stop it and run again. The ports stay as they were. A port worked out from the copy's folder would move the ports that phones and tablets reach, and two folders could still share a port. The unit test `tests/lib/server.test.ts` checks the refusal.
- Stop only your own servers. Find the process on your port with `lsof -nP -iTCP:<port> -sTCP:LISTEN -t`, and stop that process. Never stop a server or a browser by its name: every copy starts its dev server with the same command and the same arguments, so a name stands for every copy's server, and the test that tells them apart is the working folder, `lsof -p <pid> | grep cwd`, and not the name.
- Close the browser tabs that you open as soon as each test ends, as [Device sessions](devices.md#the-runner) says.
- Never let two copies share one Rust build folder. Cargo judges the engine's own crates fresh by their files' times. So one copy's build can reuse crates that another copy compiled from other sources. On 14 and 15 October 2026 this gave branches a stale shader compiler and another branch's GPU constants. The owner ruled on 15 October that each copy builds Rust into a folder of its own. The copies share only the compiled dependencies, through a compiler cache. [Builds](#builds) says how.
- The dev server skips the repository's own `.claude`, `.dev` and `.internal` folders, anchored to the folder it runs in (`tools/lib/watch-ignored.ts`). A dev server in a worktree under `.claude/worktrees` therefore sees its own edits. Until October 2026 the patterns matched a `.claude` folder anywhere in the path, so such a server served old files after every edit until it restarted. Pictures taken against it showed the code from its start. A unit test now checks that a worktree's own files are watched.
- Agent tools can lock a worktree. `git worktree list` shows "locked", and `git worktree list --porcelain` gives the reason, which can name a process id. When that process no longer runs, the lock is stale, and `git worktree unlock <path>` clears it.
- The size check builds main in a worktree of its own, `target/.size-base/tree`, inside each copy that runs it ([Benchmarks](benchmarks.md#download-size)). `git worktree list` therefore shows one under each such copy. After you delete a copy's folder, `git worktree prune` removes the worktrees whose folders are gone.
- Until 16 October 2026 the hooks lived in `.husky/_`, which `bun install` wrote and git ignored. A worktree with no install had none, so its commits and pushes ran no check and said nothing. That day a commit made that way carried a commit type that commitlint rejects, and the `commits` job failed on run 38892912324. The hooks now come from the tracked `.githooks/` folder, so every worktree has them. The install only points git's hooks path at it ([D-182](decisions/D-182-git-hooks-from-a-tracked-folder.md)). A brand-new clone is unguarded until that install. Git calls no hook when no hooks path is set, so the `commits` job covers that state.

## Coordinating helper agents

One coordinator session often runs several helper agents at once, each in its own copy of the repository. These rules keep their work moving.

- **One agent tool for the helpers.** The coordination works with more than one agent tool. A helper is a subagent of the coordinator's Claude Code session, or a session of the opencode agent tool. One setting of the coordinator picks which ([D-178](decisions/D-178-process-rulings-2026-10-15.md)). Never use both at once, because two helpers must never work in one copy. The waits, the load limiter and the check-ins are shared scripts, and they work the same with either tool. Only the way that the coordinator reaches a helper differs. The rules that differ by tool, such as how long one tool call may run, sit in the helpers' brief. It has a part for each tool. A Claude Code helper that ends its turn tells the coordinator, which answers it directly. An opencode helper gets a prompt from a wake service when its job ends. Since 15 October 2026 the helpers are Claude Code subagents. That morning, the model service of the opencode sessions stopped answering, and every helper stopped mid-step.
- **Never start an opencode server by accident.** Any opencode command without a server address starts the tool's background server, and that server resumes the sessions that it held. On 15 October 2026 a check-in script asked opencode for its sessions in this way. The old sessions came back, and one of them began a commit in a copy that a new helper owned. So the scripts call opencode only with the address of a server that the coordinator started, and they stop when nothing answers there.
- **Wait inside the turn.** A helper never ends its turn while one of its jobs runs or waits in the queue. An ended turn sits idle until something wakes the helper, and a landing has four to six such waits. The helper starts each long job detached, through a wait command that records the job's process and its exit status. A tool call can stop before the job ends, as Claude Code stops one after 10 minutes. The job runs on. The helper then waits on the same job again by its name, until the job ends. It then reads the exit status and the end of the log.
- **Check every 5 minutes.** The coordinator checks each running helper every 5 minutes, on a timer, also at night. The owner set 10 minutes on 10 October 2026, and 5 on 13 October. It judges progress by evidence: new commits, logs that grow, CI checks that move, jobs in the queue. A helper's own message is not evidence. Sometimes a helper waits on a run or a CI job that has already ended. The coordinator then gives it the next step at once. A helper that stays stuck is replaced by a fresh one. Earlier gaps had cost hours. On 7 October a finished CI run waited 4.5 hours for its helper. On 10 October a quiet window stayed idle for 3.5 hours after its run ended.
- **Find each job's real copy.** The check-in gives each job to the copy of the repository that the job works in. It first reads the folders that the job's command changes into. Then it reads the folders of the job's running processes, and last the folder that the job started in. A helper's shell can start in the coordinator's copy, as a Claude Code subagent's does. So before this rule, every such helper's job looked like the coordinator's. On 15 October that flagged three busy helpers as idle. Later that day another job still looked idle, and the rule above cannot place it: its shell starts in the coordinator's copy, and its own folder becomes its working folder only inside the step script it runs, so no running process names it until that step begins. Read the helper's own log folder as the marker for a job of that shape, and ask the helper to confirm the job is queued rather than record it as missing.
- **Count a task as landed only when its audit says done.** The milestone count takes a task as landed only when the task's audit marks it done. A `Task:` trailer on some commit is not enough. On 15 October four shader commits on main carried M2-J4's trailer, while M2-J4's feature was still on its branch. A branch on main is not enough either, because the task's whole definition of done may not be met yet. With this rule, the count went from 160 of 171 tasks to 138 of 169 on 15 October 2026.
- **Keep notes for a restart.** Each helper keeps a notes file current as it works. The notes give its branch, its commits and whether they are pushed. They also give the runs in flight, the figures and what is left. Another session must be able to resume from the notes alone.
- **Use the right queue lane.** The load limiter has four lanes, each with its own slots. Browser, image, benchmark and GPU runs take the browser lane, which waits for a low load and for the quiet window. Builds, cargo commands and the full type check take the CPU lane, at background priority. Short jobs take the quick lane: installs, lint, docs checks, and unit tests that build nothing. Cloud device runs take the cloud lane (below).
  **A queued job runs at about a quarter of the machine's speed.** The queue starts every job under `taskpolicy -b`, and the CPU lane also sets `CARGO_BUILD_JOBS=2` and `RAYON_NUM_THREADS=2`. The same fixed work on eighteen processes finished 30 to 44 seconds of work per 3 seconds of wall clock at normal priority. Under the queue's priority it finished 8.2 to 8.6 seconds. Each was measured twice, back to back, on 16 October 2026. A wall-clock figure from the queue is therefore not comparable with CI's, whose runners carry no such policy. It also explains a load average of 30 beside ten idle cores. Background-priority threads are runnable, so they raise the count without using a core. Hard rule 30 of [AGENTS.md](../AGENTS.md) bans timing at background priority, and it is why a timing run must never go through the queue.
  **The shader build, measured both ways.** The same cold build took 518 seconds through the queue, with every entry compiled and the cache off. At normal priority it took 105 seconds, 4.9 times faster, and it used 10.1 cores against 2.26. So the machine rebuilds the whole shader set in about a minute and three quarters. The figure these notes carried before, about forty minutes, was a debug-profile single-threaded build measured through the queue. It is pessimistic by roughly twenty-five times, so do not quote it again. Both runs left the module set unchanged: a cold rebuild of the optimized, parallel build reproduces every generated module byte for byte.
- **Short jobs never wait behind builds.** The quick lane has 2 slots. A job there starts without waiting for a low load, and the lane stops any job that runs past 5 minutes. Such a job goes back to the CPU lane. On 15 October 2026 a docs check of a few seconds waited about 2 hours behind 30 builds in the CPU lane. The owner approved the quick lane that day, and it has run since then.
- **Compile after a merge, and check before a push.** After a branch merges `origin/main`, compile the merged tree before anything else: `cargo check --workspace` and `bun run typecheck`. A merge that keeps both sides of a struct or a constant is often valid syntax, so only a compile finds it. On 15 October 2026 three branches held merged trees that did not compile. The owner also approved a check that runs before each push to main. It checks the trailers, runs `cargo check --workspace` and the tests of the Rust crates that the push changes, and sends its heavy steps through the load limiter. That check is being built.
- **A job that cannot start blocks the jobs behind it.** The lanes serve jobs in the order they arrive, so a job at the front whose turn has come but which cannot pass the limiter's own conditions is not waiting. It holds every job behind it. Clear that job and ask its owner to send it again. On 15 October 2026 eleven CPU jobs of this shape held the front for hours, some for three hours and more, while dozens of jobs waited behind them. One of the eleven had no process at all: its shell had been stopped earlier, and its wait command had survived with no parent, still holding its place in the queue for almost four hours. Clear the process as well as the place, and read a job's own process, not only its place in the queue, before calling it healthy.
- **Read the deepest process before calling a step hung.** A step that waits on a child step shows almost no processor time in the parent, which reads exactly like a hang. Follow the process tree to its deepest process and read that one's time before you stop anything or change the limiter. On 15 October 2026 three helpers and the coordinator read a shader build that was working normally as a hang, and time was spent on the wrong cause twice before the tree was followed.
- **Time on a quiet machine.** Timing figures need a machine whose load stays below 8. Every browser, image, benchmark or Rust suite runs through the load limiter, which caps how many run at once. For a timing run, the coordinator turns on the limiter's quiet window, which lets only that helper's runs start. The helper reports the moment its timing runs end. At each check, the coordinator also looks at the window's runs itself, and passes the window on or ends it once they are done.
- **Run cloud devices without waiting.** A run on [BrowserStack Automate](devices.md#browserstack-automate) never waits for the owner's go-ahead. The owner ruled so on 15 October 2026 ([D-178](decisions/D-178-process-rulings-2026-10-15.md)). Such a run barely loads the Mac. Yet it held a browser slot of the load limiter for the whole job, up to about 85 minutes. Local browser runs waited meanwhile. So from 15 October 2026, with the owner's approval, cloud runs have a lane of their own. It has one slot, because the BrowserStack plan allows one session at a time. A cloud run in that lane never takes a browser slot or a CPU slot. It never waits for the load limit or the quiet window. Cloud runs queue in their lane in turn.
- **Pause before the usage limit.** At 95% of the usage limit, each helper writes its state into its notes, commits and pushes its work, and stops. Work resumes with fresh helpers once the limit's reset time has passed. A low reading of the usage figure alone is not enough: on 9 October such a reading was wrong.
- **Say the working folder, not its name.** A helper inherits the coordinator's working folder, so a brief that names the helper's own copy is not enough. On 15 October 2026 a helper ran its git commands in the coordinator's copy, which moved that copy onto its own branch, and a coordinator commit then landed on the helper's throwaway branch. Give the exact form: write every command with `git -C <folder>`, or have the helper make that folder its shell's working folder first. A helper confirms `git rev-parse --show-toplevel` names its own copy before it commits. Anyone who sees a commit report an unexpected branch name stops and reads that line, because it is the only warning this fault gives.
- **A picture test you did not run is not evidence.** On 22 October 2026 a helper reported its level-of-detail work verified because `bun run check` said every image test had its references; it had not run the pictures. The branch then drew one sphere where the saved picture draws six, and only the picture test said so. The reference check proves a file exists, never that it matches. A change to the draw path, which is culling, levels, materials or post passes, runs its picture group (`bun run test:images -g "<feature>"`) and the helper puts the pass or fail line in its report. A new picture test needs the same run: it compares against a reference only after that reference is drawn and looked at.
- **A job at no processor time is the owner's to stop.** A queued job whose leaf process gains no processor time over a few minutes is wedged, and it holds its slot against everybody behind it. On 22 October 2026 a `bun run shaders` job sat at four hundredths of a second for over an hour. Its owner stops it and re-runs it; the coordinator stops it when the owner has gone quiet. Run jobs from your own checkout, never from the shared one.
- **Read a limit from main, not from your branch.** A budget constant lives in the code, and a branch carries whatever the constant was when it last merged main. On 15 October 2026 two helpers measured against stale figures - 160 KB for a start budget already raised to 165 KB, and 32 KB for a first-use limit already raised to 49 KB - and each reported a failure that no longer existed. Read the constant from `origin/main` before you quote it.
- **A budget that stops the build is a stop-the-line job, not a task for later.** On 22 October 2026 the start download passed its 176 KB line at 01:55 and no build completed until the figure was raised at 06:47. Code kept landing, but every picture reference, graphics timing, device run and size line waited five hours behind one number, and helpers queued size checks that could never pass. When a build stops on a budget or on a file that the size report cannot name, raise the budget or trim in the same hour, put the reason and the paying trim beside the figure in the source, and tell the owner what changed. The owner's standing word is to raise it without waiting for them.
- **A check that fails closed must say why.** The load limiter's start gate closes while the machine is busy, which is what it is for. On 15 October 2026 a fault in the reading made the gate close on every pass, so no job started for hours while nothing anywhere said there was a problem: the symptom of the fault was the absence of a symptom. The gate now names the value it refused and says that no job can start until the sampler works. A closed gate and a busy machine look identical from outside, so a check of this kind must report the difference.
- **A place in the queue with no live process is a fault too.** The lanes serve jobs in arrival order, so a place held by a job whose process has gone blocks everybody behind it. On 15 October 2026 one such place survived for almost four hours: its shell had been stopped, and its wait command lived on with no parent. Read a job's own process, not only its place in the queue, before calling it healthy, and clear the place as well as the process.
- **The queue says what holds its slots and what a job waits for.** A waiting job printed nothing at all until 16 October 2026: every wait branch was a bare `sleep`, so a lane whose slots were all held and a queue that had jammed looked exactly alike from outside. A stall that evening was inferred from a process table half an hour later, and the reading was wrong. The jobs were working: every ancestor of a build sits at 0 per cent while the work happens two levels below, and each job also carries a `caffeinate` child that runs nothing at all. A slot now records the command it runs and when it was taken, and a waiting job prints one line a minute, at once when the line changes, naming the lane, the slots with their holders, commands and ages, the jobs ahead, and the gate's own idle and load readings. Read that line before a process table, and read the deepest process before calling a step hung.
- **A slot whose work has gone is freed by the queue.** A place in the queue whose live process had died was already reclaimed, but a wrapper that sleeps while its work has gone kept its slot until a person noticed. The slot now records the process that does the work, and the queue frees the slot when that process is gone, and says which slot it freed. A run that launchd accepted but never started releases its slot after ninety seconds rather than waiting for a status that can never come.
- **Never write a running script in place: it serves broken content, not only a shifted read.** The load limiter and any other runner that queued jobs execute must be written as a new file and renamed over the old one. zsh re-reads a running script through its open file by byte offset, so a job that started before an in-place edit resumes after its wait loop in text that has moved: on 12 October 2026 an in-place edit of the load limiter made 11 jobs fail without running their command. That is the narrower half of the hazard. On 16 October 2026 a one-line in-place write left a fault in the file for two minutes and thirteen seconds, and every wrapper that *started* in that window read the broken copy. Five jobs did, and three of them logged it 76 times between them, each logging a failed command lookup and a figure with no value, once per waiting turn. A job that starts after the edit is not protected by its timing, because opening the file is how the broken content is picked up. Write the new file, check it with `zsh -n`, rename it over, and read its content once more before it goes live: the cost of a mistake is paid by every job that starts until the file is right again.
- **A pattern in a stop command is a machine-wide action.** `pkill -f "<text>"` reaches every process on the machine whose command line contains the text, not only the caller's own, so a pattern that is not narrow enough stops other people's work. On 16 October 2026 a helper ran `pkill -f "bun tools/build-wasm.ts"` and `pkill -f "vite build"`, which stopped another helper's build in an unrelated working copy at its final step after 63 minutes: that build's log ends at the production page step, the run reported the polite-quit signal, and its shell recorded the exit code for a process stopped by the termination signal. The rule that says to confirm a process is yours before stopping it applies to the pattern, not only to a process id. List the matches with `pgrep -f`, check each one's working folder, and stop that number; where a pattern cannot be avoided, make it name your own working copy as well as the command. **A server is the same hazard under a narrower name.** In the night of 16 to 17 October 2026 two copies lost work to a stop command: the build above to a wide pattern, and a dev server to `pkill -f "vite"`, which stops every copy's server because they all run that command. The copy that loses its server reports a failed run whose log names nothing about a stop. Read the port's owner, or each match's working folder, and stop that process alone.
- **A job's age in the process table counts its wait as well as its work.** A runner that waits an hour for a slot and then works for a minute still shows an hour in the process table, so an old wrapper is not evidence of a hang: on 16 October 2026 two size jobs were read as hung on exactly that, and most of their hour was waiting. The queue's own line separates the two cases, and a slot's recorded age counts from the moment it took the slot, which is the moment its work began. Read the waiting line before the process table, and read the slot's age rather than the wrapper's before calling a step stuck.
- **Read your own commits before a push.** Before a push to main, run `git log origin/main..HEAD` and confirm every commit in it is yours. A helper inherits the coordinator's working folder, so a helper's commit can be sitting in the coordinator's branch, and the coordinator's push is what puts it on the trunk, under the coordinator's name and without the checks the helper owed it. On 15 October 2026 that published a terrain change whose allocation fix had not been measured, on the same day that a different helper's documentation edit was caught in a commit minutes earlier. The first catch was luck; the second was a missing habit.
- **Do not change a working copy's files while its own queued job runs.** A job can wait hours in a lane before it starts, and its owner goes on working meanwhile. On 15 October 2026 a helper merged `origin/main` into its branch while a shader job of the same working copy was queued; the job began part way through the merge and compiled across it, linked a compiler from before the merge, and failed for a reason that had nothing to do with the change. Re-running it on the settled tree fixed it. Settle the tree first - merge, commit and leave it alone - before queueing a job that reads it, or wait for the job to finish before touching the files.
- **Several limits judge a branch at once, so name them all before a push.** On 22 October 2026 the milestone branch was red on three checks at once. One was missing picture references. Another was a memory ceiling that a suite outgrew by eleven mebibytes. The third was ten files over the growth limit, with no trailer to explain them. Each came from a different change, and each read as a mystery until someone opened its job log. Run `bun run limits` before a push. It reports the picture references, the commit gates and the start budget of the last build. It also names the command for each limit that only a build or a heavy run can measure. A commit that changes what a limit measures carries a `Limits-Checked:` trailer that says what the report found.
- **A page run after a merge needs that copy's own build, and the core's error says so.** A worktree that merges the milestone branch keeps the WebAssembly core that it built before the merge, and every page then refuses with E1402. The error names the cause and the fix: build the copy again. On 22 October 2026 two copies spent a picture run each on this before the message was read carefully: one in the main checkout, one in the weather branch. A picture, device or browser run right after a merge starts with `bun run build`, or waits for a build that already runs there. Read the first error of a failed run before you read its picture count, because E1402 means the run drew nothing at all.
- **A browser run adopts a dev server that is already listening, so do not stop one while a run uses it.** The image and browser harness looks for a server on its port and refuses a server that does not name its own copy of the repository. On 22 October 2026 the coordinator stopped an example server at the owner's word while a picture run was still setting up, and the run then failed with that complaint after seven minutes. Before a picture or browser run, check that nothing else listens on its port. While one runs, leave any server on it alone, or give the run a port of its own through `NULL3D_PORT`.
