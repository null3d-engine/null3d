# Rules for people and agents working in this repository

This repository holds the null3D engine, its tools, its documentation and its agent skills. This file holds the working rules. The pages in [`docs/`](docs/index.md) describe the design, and the [maintainer guides](.dev/README.md) in `.dev/` hold the detail behind these rules.

## Where things are

A file can grow after Brotli against main's build by more than 2%, and by 64 bytes or more. It then needs a reason: a `Size-Growth:` trailer, as "Commit gates" says. A file over its budget fails every build. Each WebAssembly file may take 600 KB after Brotli. The engine's JavaScript that a page downloads at its start may take 165 KB after Brotli, 448 KB after gzip and 3,328 KB uncompressed. Some files of engine code load on a feature's first use, or after the first frame. Each may take 16 KB after Brotli, 24 KB after gzip and 64 KB uncompressed. A feature that a page does not use loads its code on first use, so it adds nothing to the start. Its shader builds load on first use too, from files that its table in the shader manifest declares ([D-56](.dev/decisions/D-56-first-use-shader-files.md)). Each such file may take what one start shader file may: 49 KB after Brotli, 320 KB after gzip and 1,536 KB uncompressed. Only the owner raises a budget, in writing. The owner approved these figures for M2 on 2026-10-04, raised the start's on 2026-10-14 and both Brotli figures later the same day, and raised the start's Brotli figure again on 2026-10-15, as [D-14](.dev/decisions/D-14-js-budget.md) records. [Benchmarks](.dev/benchmarks.md#download-size) says how the check builds main.

## Design principles

These ten principles decide design conflicts, and a higher one wins over a lower one. Speed comes first because it is the reason the engine exists. Ease of use comes last, but it still binds.

1. Measure before and after. Every performance claim has a benchmark in CI. A change that slows a benchmark does not merge without a written reason.
2. Data first. Scene data lives in flat arrays that fit the CPU cache. Code processes the arrays in bulk, not objects one at a time.
3. One copy of each piece of data. The core owns scene data, and TypeScript reads and writes the same memory. There are no mirrored objects and no per-frame sync.
4. Do work once. Cache results (static shadow maps, render bundles, compiled pipelines) and update only what changed, through dirty flags and dirty ranges.
5. Move bulk work off the critical path. On WebGPU it goes to the GPU; on WebGL2 it goes to job workers.
6. The main thread belongs to the page. When a worker is available, the engine does no frame work on the main thread.
7. No garbage in the frame loop. TypeScript hot paths allocate nothing, and Rust uses memory arenas that reset each frame.
8. Pay only for what you use. Optional modules and decoders load only when a sketch needs them.
9. Both backends are first-class. A feature ships only when it works on WebGPU and WebGL2, or when its WebGL2 fallback is documented.
10. Simple for people and agents. There is one clear way to do each task, and every error message says how to fix the problem.

## Hard rules

No reviewer reads a branch before it lands ([D-157](.dev/decisions/D-157-direct-pushes-to-main.md)). So the author checks each rule before the push, and the check or test that a rule names guards it. A rule keeps its number for good, because code and decision records cite rules by number. No rule 25 exists.

1. No per-frame allocation in TypeScript hot paths or in the render worker. Rust frame code uses arenas and pools only, never a general-purpose allocator. The objects that the browser itself returns each frame are the only exception, and `bun run bench:allocation` budgets each of them.
2. The render worker owns every GPU object. No other thread touches browser GPU objects.
3. The render worker draws only inside its own `requestAnimationFrame` callback.
4. No thread waits synchronously for another on the critical path, and no worker makes a synchronous call to the main thread.
5. The sketch worker and the render worker wait with `Atomics.waitAsync` (a `MessageChannel` message on Firefox before 145). Only job workers block with `Atomics.wait`.
6. The WebGPU path stays within WebGPU's default limits. Where the engine supports compatibility mode, it also stays within that mode's lower limits (the portable budget in [GPU tiers and backends](docs/concepts/backends.md#the-portable-budget)). Anything beyond these needs a capability flag and a fallback. For example, compute workgroups use at most 128 invocations.
7. Per-instance data reaches vertex shaders through vertex buffers, never through storage buffers. The one exception is the `?instances=index` test switch on core WebGPU, which [D-23](.dev/decisions/D-23-index-instances.md) measures.
8. Indirect draws keep first-instance at 0. Buckets select their data with vertex-buffer offsets.
9. Dynamic buffer offsets align to 256 bytes.
10. WGSL uses only the three language features that Chrome, Safari and Firefox all report: `packed_4x8_integer_dot_product`, `pointer_composite_access` and `readonly_and_readwrite_storage_textures`. Any other language feature needs a capability flag and a fallback. Flat interpolation uses `@interpolate(flat, either)`.
11. Optional WebGPU features are used only after a capability check. They are transient attachments, immediates, subgroups, timestamp queries, `shader-f16`, `rg11b10ufloat-renderable`, `float32-filterable`, `float32-blendable`, and each texture-compression family. A missing limit counts as absent, not as zero.
12. Float textures that need filtering use 16-bit floats. 32-bit float data textures are read without filtering (`textureLoad`, `texelFetch`).
13. On WebGL2, request each extension by name with `getExtension()`. Never trust `getSupportedExtensions()`, because Brave shuffles it.
14. Never decide anything from GPU names or user agents. Firefox and Brave can hide GPU names.
    - One exception, until Safari ships WebKit's fix: the WebGPU backend copies indirect draw arguments only in Apple's WebKit ([D-87](.dev/decisions/D-87-webkit-indirect-arguments.md), which says how to remove it).
15. Core Rust code never calls APIs that fail on `wasm32-unknown-unknown`, such as `std::time::SystemTime::now()`. Time comes from the engine clock, and a lint enforces this.
16. Tests read pixels back through the engine. They never encode images through a canvas in the page and never rely on browser screenshots.
17. A change that makes a benchmark median more than 3% slower does not land without a written reason, given in a `Bench-Expected:` trailer.
18. A branch that changes a public API also updates the API's docs page and any skill that shows the API. It updates the API's three.js mapping entry too, where one exists.
19. The branch that ships a feature changes its docs status from `planned` to `experimental` or `stable`. Agents never use planned APIs.
20. No code keeps a typed-array view of the engine's shared memory after the memory grows. Get views from the one place that makes them, and drop every view when the memory grows. Chrome's page memory figure counts each stale view's buffer as a full copy of the memory. wasm-bindgen's generated glue caches views too, and the engine drops them at every growth. The browser test `tests/image/memory-views.spec.ts` and the static check in `bun run check` guard the rule ([Views of the shared memory](.dev/implementation-notes.md#views-of-the-shared-memory)).
21. A WebGL2 vertex shader never reads a uniform array at the draw index, or at any index that is the same for the whole draw. Some Adreno drivers then fail to link the program, with an empty log. Read such a table from a texture with `texelFetch` ([Browser faults](.dev/implementation-notes.md#browser-faults)). A unit test checks the multi-draw shaders.
22. Every new WebGPU device draws the engine's first pass before its first frame: one point by a direct draw (`gpu/webgpu/first-pass.ts`). Some drivers draw nothing from the indirect draws of a device's first pass that draws. Image tests cannot see a fault of a device's first frame, because a capture draws the frame again. Check such faults with a page that reads back its own first draws, as the first-draw page does ([Driver bug reports](.dev/driver-bugs.md)).
23. A shader that runs on WebGL2 keeps each value that passes through a struct within half precision's range, from about 6.1e-5 to 65504. The GLSL that naga writes keeps a fragment shader's inputs in structs, and the results of functions that return structs. Some Adreno drivers keep the floats of a struct at half precision, whatever the shader declares. A smaller value then reads as zero, and a larger one as 65504. Scale such values into the range, as the sky keeps its scattering coefficients per million metres ([Browser faults](.dev/implementation-notes.md#browser-faults)). The shader library check page reports the fault on any device that has it.
24. Every measurement of the page's memory (`performance.measureUserAgentSpecificMemory`) goes through `measureWithEveryThread`, or through `measurePageMemory` and `PageMemorySampler`, which use it. Chrome waits until every worker has run the measurement, and an idle job worker blocks in the job loop. A measurement that skips it takes about a minute with job workers, and the whole page can stop answering meanwhile. A unit test checks every call ([Measuring the page's memory](.dev/implementation-notes.md#measuring-the-pages-memory)).
26. No WGSL name is `gl` or starts with `gl_`. GLSL ES reserves those names, and naga's GLSL writer turns the second of two clashing names `gl` into `gl_1`, so the WebGL2 build stops compiling on every device. The GLSL build fails on such a name ([The shader compiler](.dev/implementation-notes.md#the-shader-compiler)).
27. A value of the permutation word names one feature in each shader template. Two features share a value only when no template lists both, and no code makes one's keys from the other's ([D-156](.dev/decisions/D-156-template-scoped-permutation-bits.md)). The shader build refuses a template that lists two names of one value.
28. A post effect that is meant to act on light acts before the tone curve on every path: on the HDR path and on the 8-bit path, and on surfaces that a clear makes as well as on drawn ones. Applied after the curve on one path and before it on another, the two drift apart whenever the curve or the effect's settings change. In October 2026 the vignette's refit for AgX made the 8-bit image differ from the HDR one in 33% of its pixels ([D-77](.dev/decisions/D-77-final-pass-order-and-formats.md)). The 8-bit copies of the image tests and `tests/image/vignette-paths.spec.ts` guard the vignette.
29. Randomness in code comes from integer hashes, never from the fraction of a large sine (`fract(sin(x) * 43758.5453)`). Each GPU works out the sine its own way, so such a hash draws other pixels on other machines, and image tests fail there. In WGSL, use `null3d::noise` (`random`, `random2`, `value2` and the rest). A unit test refuses the sine hash in every file of code ([Image tests in CI](.dev/image-tests.md#ci)).
30. Never time anything at macOS background priority. A process started with `taskpolicy -b` passes that priority to every child, and no call lifts it again. Chrome then draws about 10 frames a second and fires its timers late. The timing tools refuse to start at that priority, and a unit test checks the guard. Start a timing run from a shell where `ps -o pri= -p $$` prints more than 4 ([Device sessions](.dev/devices.md#browser-apps-on-the-mac)).
31. An address in WebAssembly memory is an unsigned number. Code that reads an address from a signed array, such as the shared `Int32Array` slots, converts it with `>>> 0` before it uses it. A page may raise the memory maximum to 4096 MiB ([D-04](.dev/decisions/D-04-memory-maximum.md)), and above 2 GiB a signed read gives a negative address. In October 2026 Rive City's 3D scene stopped on exactly this fault ([D-172](.dev/decisions/D-172-rive-city-follow-ups.md), [Addresses above 2 GiB](.dev/implementation-notes.md#addresses-above-2-gib)). The static check `tools/check-address-reads.ts`, which `bun run check` runs, and the browser test `tests/image/signed-address.spec.ts` guard the rule.

## Performance work

The benchmarks compare null3D with three.js in the same browser. [Benchmarks](.dev/benchmarks.md) says how to run them and read them. [Device sessions](.dev/devices.md) covers phones, tablets and the Mac's browser apps. [Implementation notes](.dev/implementation-notes.md) holds the habits and browser faults behind the hard rules. These points apply to every change:

- A report gives each engine's whole frame and its own work on the busiest thread. The desktop target uses own work, because both engines run the same scene code.
- Do not edit engine or benchmark page files, or the dev server's config, during a browser run. The dev server reloads the pages being measured, and restarts when its config changes.
- The benchmarks measure a production build of the benchmark pages, as developers ship the engine, so the development checks do not count. The tools take `--dev` for the dev server's pages.
- Every tool finds the dev server on port 5173, and uses the one that already answers there. A second copy of the repository, such as a git worktree, would test the first copy's code. Give each copy its own ports with `NULL3D_PORT`, for example `NULL3D_PORT=6173 bun run test:browser`. Its dev server takes that port, the HTTPS server the next one, and the production preview the one after. Tools that drive Chrome through its debugging protocol take the one after that.
- A server makes some files on request with the built tools of the copy that it runs in, such as the sample content's environment maps. A tool that serves another copy's build starts the server in that copy. A cache that copies or builds share keys its files by every input that they name, such as the sample content's pin. On 12 October 2026 both faults broke S6 in CI's benchmark job and never showed on the Mac, whose copies are all built and keep every pin ([Benchmarks](.dev/benchmarks.md#the-benchmark-job-in-ci)).
- The benchmark job in CI compares main's newest commit with the last commit on main that it measured, once a day. Mac machines run its pages in shards, and a last job merges them into one verdict. A run started by hand from the Actions tab compares a branch or a commit with its merge base. It fails when a page gets slower than its rule allows. [Benchmarks](.dev/benchmarks.md#the-benchmark-job-in-ci) says how to read it.
- After a pull that changes the Vite plugin or the Vite config, run `bun run build` and restart the dev server before a browser run. The dev server keeps the plugin it started with, as [Device sessions](.dev/devices.md#the-runner) says.
- Run one device runner at a time. Runs share one file that tells waiting runner pages which run to start.
- Keep hot paths free of allocation with the habits in the implementation notes, and check them with `bun run bench:allocation`. Read a settings object's numbers by their own names, never by keys from a list: the generic read boxes each fraction. When it blames code that you did not change, run it again with `--no-inline` to find the real call site.
- Hand WebGPU fractions only in properties that started as `null`, never in properties or arrays that started as numbers. Chrome's bindings copy each unboxed fraction into a new number object at every call that reads it. Each render pass's clear color cost 48 bytes per frame this way, and put the replay over budget ([Implementation notes](.dev/implementation-notes.md#hot-paths-without-allocation)).
- A call into the engine core takes whole numbers only. Where the browser does not inline the call, each fraction argument becomes a number object. So a setter writes its numbers into the core's call values (`CoreMemory.callValues`) and passes only whole numbers. A unit test (`core-arguments.test.ts`) fails on a core call with a fraction parameter. After a change to a setter, run `bun run bench:allocation --setters` on both GPU paths ([Implementation notes](.dev/implementation-notes.md#hot-paths-without-allocation)).
- Trust a frame rate only for frames that drew something. three.js's WebGPURenderer can return from its render calls at once with no draw, at the display's rate, while it cannot draw a scene. The comparison worker counts only frames with draw calls and reports "no frame" otherwise ([Examples](.dev/examples.md#the-ramp)).
- Judge a ramp by the scene's update rate, a floor of 20 frames a second, not the rate of the page thread's frames or of the drawn frames. Chrome can slow the page thread's frames to 30 a second, or present frames whose update threw, while null3D draws from its workers at 120. The ramp counts completed updates ([D-158](.dev/decisions/D-158-growable-animation-table.md), [Examples](.dev/examples.md#the-ramp)).
- Time comparisons in the Mac's installed Chrome, not Playwright's Chromium. Chromium 153 failed to build one of three.js's WebGPU pipelines for Night town ("swizzle view instruction still has usages after lowering"), and Chrome 155 built it. Chromium 153 also took 90 s to start null3D's WebGL2 Night town at 300 lights, and Chrome 155 took 2 s. Start a three.js measurement only after its first frame that draws ([Examples](.dev/examples.md#the-ramp)).
- A new switch of a benchmark scene goes into the benchmark page's list of switches that reach the sketch (`SKETCH_SWITCHES` in `bench/pages/null3d/harness.ts`). A switch missing there never reaches the sketch, so the scene runs without the feature and every figure measures plain S1. Check that a feature's figures differ from the scene without it, such as in the draw calls ([Benchmarks](.dev/benchmarks.md#allocation-and-profiling)).
- Time frame rates in a visible browser window parked past the screen's edge (`tests/lib/app-window.ts`), never in a headless one. Headless Chrome on the Mac reports a 60 Hz display, so no figure can pass 60 frames per second. Check the display rate that each reading measured. `displayRateCheck` in that file measures it in the reading's window. `bench:run` flags each reading below the screen's highest rate ([Benchmarks](.dev/benchmarks.md#what-a-report-measures)).
- On BrowserStack Automate's Android devices, Chrome can hold the runner page's requests behind a native prompt that the page cannot see. The cloud runner taps Allow and says so in its output. Before you call a cloud page's timeout a fault, look for such a prompt ([Device sessions](.dev/devices.md#a-native-prompt-that-holds-the-page)).
- Run Bun 1.4.3 or newer, the version that `packageManager` names ([D-155](.dev/decisions/D-155-bun-1-4-3.md)). After the commit that moves the version lands, run `bun upgrade`, or the unit tests fail.
- A Bun script starts its browser with `launchChromium` from `packages/cli/src/browser.js`, never with Playwright's `chromium.launch`. Bun 1.3.14 closes Playwright's pipe to Chrome at random. Chrome then ends, and Playwright waits forever, past its own time limits. The guard in `launchChromium` fails the waiting calls at once with `BROWSER_GONE` ([Releases](.dev/releases.md#the-fresh-project-test)).
- Check a memory figure from the browser before you report it. Chrome counts the shared memory once in each thread, and once more for each stale view of it. Its figure can then be many times the real memory ([Views of the shared memory](.dev/implementation-notes.md#views-of-the-shared-memory)).

## Parity with three.js and add-on modules

The owner set these rules on 4 October 2026. [D-52](.dev/decisions/D-52-intent-parity.md) gives the detail and the reasons.

1. Intent parity is strict. null3D shows what files and authors mean: glTF, materials, color spaces, units, and animation curves and sampling. Check them against the glTF specification, with three.js as the reference.
2. Look parity is "equivalent or better". Each feature uses the best technique as its default. The porting skill and the port tools map three.js's settings onto it and list the visible differences.
3. The core engine has no three.js-look modes. The few that a port truly needs go in the opt-in `three-compat` add-on module. That module uses only the engine's public extension points and loads on first use.
4. A benchmark compares equal work: the same scene content and comparable quality settings. Its report gives quality notes beside the timings. The images need not be identical.
5. Pixel tests against three.js cover only shared building blocks: lighting terms, tone curves that both engines offer, skinning poses, animation sampling and glTF interpretation. A feature with a better technique gets null3D's own references, and a looser sanity comparison with three.js.
6. Built-in assets are made at run time. The engine's package never ships them as files.
7. Heavy or niche features ship as add-on modules. Each takes one install and one import, with no manual file copying. It works with Vite and the null3D plugin, the one supported bundler, and from CDNs, under a strict Content Security Policy. Its code loads files the standard way (`new URL('<file>', import.meta.url)`), so other bundlers stay possible ([D-54](.dev/decisions/D-54-addon-modules.md#bundlers)). Its version stays in step with the engine's, and its code loads on first use.
8. What a glTF file or a standard scene needs stays in the core and loads on first use. Examples are morph targets, environment light and Draco. Optional features with heavy machinery of their own are add-ons.
9. Add-ons and the engine's first-use decoders load through the one on-demand loader (`shared/tasks.ts`). It compiles each WebAssembly module once per page and sends it to the workers that run it. Add-ons run in the job workers and start no workers of their own. A decoder's task never holds up a frame. [D-54](.dev/decisions/D-54-addon-modules.md#built) gives the detail.
10. The bundled path comes first. Every engine worker starts through `spawnWorker`, in the form `new Worker(new URL('<file>', import.meta.url), options)`. From a CDN, it adds the engine's one `blob:` bootstrap. Engine code names every file it loads with `new URL('<file>', import.meta.url)` and no Vite-only query. A third-party script that the engine ships makes no code from strings, so a policy without `'unsafe-eval'` runs it. The docs give the policy and the headers that it needs, and the engine names what is missing ([D-54](.dev/decisions/D-54-addon-modules.md)).
11. Each feature lives in one place: the core or one add-on, never both. An add-on extends or replaces a core feature only through that feature's own settings, never through a second API. For example, `three-compat` adds tone curves through the core's tone-curve setting, and flat clouds stay in the core sky ([D-173](.dev/decisions/D-173-addon-hooks.md)).
12. Add-ons and examples reach the engine only through its public entry points, `@null3d/engine` and `@null3d/engine/stats`. This holds for the engine's own add-ons too. When an add-on needs something that the API lacks, a public hook is built with it. So another developer could build the same add-on. `tools/check-addon-imports.ts`, run by `bun run check`, refuses any other engine import. It reads add-ons' shipped code and `examples/` ([D-173](.dev/decisions/D-173-addon-hooks.md)).
13. The engine's team builds the foundation add-ons: physics, Gaussian splats, MSDF text, particles, terrain, water, controls, geometry, impostors and `three-compat`. Each is its own npm package. It pins the exact engine version, checks that version at run time, and compiles its WGSL when it is packed. Other add-ons of the engine's team are example add-ons in `examples/addons/`, never npm packages. A plugin interface version and a listing check for other developers' add-ons come before 1.0 ([D-173](.dev/decisions/D-173-addon-hooks.md)).

## Docs and skills stay in sync

1. One source per fact. The API reference comes from TypeScript doc comments, the three.js mapping from `docs/data/threejs-mapping.json`, and the page inventory from `tools/lib/docs.ts`. Skills link to docs pages by ID and do not copy facts.
2. Never commit a generated file, unless [D-105](.dev/decisions/D-105-generated-files-out-of-git.md) gives the reason to keep it. Git ignores each generated file, and a written page links to a generated page that it needs. [Generated files](.dev/pull-requests.md#generated-files) lists each one, its generator and the step that builds it. The install step, `bun install`, writes them. The git hooks write them again after each checkout, merge or rebase, and before each commit. Run `bun run docs` to see a change of a source at once. A new generator writes only into paths that `.gitignore` names.
3. A placeholder page carries a marker comment, and `bun run docs` rewrites it. Git ignores each placeholder page by name in `.gitignore`. When you write the real page, remove the marker and the page's line in `.gitignore`. The generator then leaves the page alone.
4. Every docs page has front matter: `id`, `title`, `status` (`planned`, `experimental`, `stable` or `generated`), `since` and `summary`.
5. The API reference on the `api/` pages comes from the TSDoc comments on the engine's public exports. Each export needs a summary and a `@category api/<page>` tag that names its page. Each public member needs a summary too. A public declaration may name only types that the engine exports. The generator writes each written API page's reference on a page of its own, `docs/api/reference/<page>.md`. The written page links to it under its "API reference" heading, and the docs check refuses a written page without that link.
6. The skills give each call the first version that has it, such as (0.2) or (after 1.0). A part of the current version that is not built yet says "later in 0.1". A TypeScript code block in a skill that exports `defineSketch(...)` is a complete sketch. The unit tests (`bun run test`) type check each one against the engine. The browser tests (`bun run test:browser`) draw each one in hold mode on every GPU tier. The tests leave out a sketch under a heading that names a later version. Remove the version from the heading when the feature merges.

## Writing docs

Published Markdown (every page under `docs/`, the skills, the README, the package READMEs, `CHANGELOG.md`, this file and the guides in `.dev/`) follows these rules.

- Write plain English in short sentences, at most 25 words each, in the active voice. Simplified Technical English is the model.
- Use sentence case in headings, with no emojis.
- Use no dashes as connectors. Use a comma, a colon, parentheses or a new sentence.
- Use straight quotes and apostrophes.
- A concept page opens with a Mermaid diagram and a plain explanation, followed by examples.
- A page describes what exists now. Its status label says whether the feature is built. When only part of a page's feature is built, the page is `experimental`. The note under its title then names the parts that are not built yet.
- Write for developers who use the engine. Never mention the maintainers' milestones, checkpoints, task IDs, proposals or internal plans, and never explain where a fact came from in those terms. Give the reason when it helps the reader, such as a browser or GPU limit. Name the engine's benchmarks when you cite a figure. Notes for maintainers belong in code comments, in this file or in the guides in `.dev/`. Those files are for contributors, so this rule does not apply to them, but public docs never link to them.
- Commit subjects become lines of the public release notes, so they follow these rules too. A subject names no task ID, decision record number, review thread or milestone, and the commit hook blocks one that does.
- Show commands with Bun: `bun add`, `bun install`, `bun run` and `bunx`, never the npm or npx forms. Run the command line tool as `bunx @null3d/cli <command>`, with the scope. Both rules cover code blocks too.
- Run the humanizer skill over any prose you write or change. This covers user-facing text that lives in data or code too: the mapping notes, error messages and TSDoc comments.

The docs style check catches the mechanical part of these rules. It blocks build-process words such as milestone and checkpoint, and the command line tool run by the wrong name. It checks each commit subject too. The humanizer pass and your own re-reading cover the rest.

## Record the reasons

The owner set this rule on 7 October 2026. Every branch records its reasons in `.dev/`, in the same branch. Commit messages and chat are not enough.

- A design choice or an owner's ruling: a [decision record](.dev/decisions/README.md), new or an addendum. It gives the problem, the figures, the options rejected and why, and who decided and when.
- A bug fix: the cause, and why the fix is right, in the record or guide that owns the area. Examples are the [implementation notes](.dev/implementation-notes.md), the driver bugs, the [image tests](.dev/image-tests.md) and the [benchmarks](.dev/benchmarks.md).
- A device or benchmark run: a new run file in the [tested devices](.dev/tested-devices.md) record, or a row in the [benchmark results](.dev/benchmark-results.md).
- A lesson about process or tools: the guide that covers it, such as [branches and parallel work](.dev/pull-requests.md) or the benchmarks.

The `Docs-Checked:` trailer names the `.dev` page that holds the reason, or says why there is no new reason. [Branches and parallel work](.dev/pull-requests.md#before-you-land-a-branch) gives an example of each kind.

## Commit gates

`bun install` sets up git hooks that keep the docs in line with the code. Never skip them with `--no-verify`: CI runs the same checks on main, and a failure there turns main red for everyone. A push to main also runs the pre-push check below, which reads the commits that the push adds.

Before each commit:

- Biome (errors only) and the TypeScript check.
- When Rust files or Cargo settings are staged: `cargo fmt --check` and Clippy, with warnings treated as errors.
- The generators run clean. The hook writes the generated files, and fails when a public export lacks the doc comments that the API reference needs. It also fails when git would keep a generated file.
- Every command in `package.json` is in the table under "Commands", and every command that this file, the README and the guides in `.dev/` run with `bun run` exists.
- Every decision record starts with its title, then a `Status:` and a `Summary:` paragraph, and no two records share a number.

Before each push to main (`tools/hooks/pre-push.ts`; a push to another branch runs nothing):

- The messages and trailers of every commit that the push adds to main, as CI's `commits` job checks them: commitlint, then the trailer check. The merge check runs over them too, so a merge commit that carries new work is refused.
- When the push changes Rust code or Cargo settings: `cargo check --workspace`, then the tests of each crate that it changes, with `--no-fail-fast`. The test that builds every shader runs in CI only.
- On a machine whose git setting `null3d.jobQueue` names a job queue script, the steps run through that queue.
- Only in an emergency, a `Push-Check-Skipped: <reason>` trailer on a commit of the push skips the check. The owner approved the check on 15 October 2026 ([D-157](.dev/decisions/D-157-direct-pushes-to-main.md)).

On each commit message:

- The message follows [Conventional Commits](https://www.conventionalcommits.org/). The scope names the area, such as `core`, `gpu`, `engine`, `docs`, `tools` or `ci`.
- A commit that changes `crates/*/src/`, `packages/*/src/`, `packages/*/bin/` or `skills/` needs a `Docs-Checked:` trailer. This file, the README and the guides in `.dev/` describe the repository's tools, so a commit that changes the tools needs one too. They are `tools/`, `bench/` apart from its tests, the test runner (`tests/real-browsers.ts` and `tests/lib/`) and `package.json`. The trailer names the docs pages you updated or re-read, or says why none apply. The pass also confirms that those pages speak only to developers who use the engine.
- A commit that changes a package's source, the WGSL shader library, `skills/` or `docs/data/threejs-mapping.json` needs a `Skills-Checked:` trailer. It names the skill files you updated or re-read.
- A branch that changes how the GPU draws needs a `GPU-Checked:` trailer: the line that `bun run bench:gpu-check` prints. It goes on the last commit that makes such a change, or on a later one. This covers `crates/null3d-shaders/src/`, `crates/null3d-shaders/wgsl/`, its `shaders.toml`, and `packages/engine/src/gpu/`, `render/` and `quality/`, less tests. CI's benchmark job has no GPU timer, so the check runs on a computer with a GPU of its own ([Branches and parallel work](.dev/pull-requests.md#the-gpu-check), [D-109](.dev/decisions/D-109-gpu-time-guard.md)).
- A branch that changes a SwiftShader image reference changes the same test's Mac reference in the same tier too. CI draws only on SwiftShader, so it cannot see a stale Mac reference. When the Mac's image still matches its reference, a `Mac-References:` trailer on a commit of the branch says how you know, such as `Mac-References: bun run test:images -g s4 passes on the Mac's GPU with the old references` ([Image tests](.dev/image-tests.md#references)).
- A commit that makes a benchmark median slower on purpose needs a `Bench-Expected:` trailer. It names the benchmarks and gives the reason, as [Benchmarks](.dev/benchmarks.md#mark-an-expected-slowdown) shows. The benchmark job in CI reads it.
- A file that grows after Brotli against main's build needs a `Size-Growth:` trailer on a commit that lands with the growth. This applies when it grows by more than 2% and by 64 bytes or more, and to each new file. Without the byte floor, the hashed file names in a small file fail the check. A push must not fail CI for a failure that anyone can predict ([Benchmarks](.dev/benchmarks.md#download-size)). Put the trailer on a plain commit, not a merge commit: the check reads the trailers of the plain commits only. On main, CI compares each push with main's commit before the push, and reads the trailers of every plain commit after it. The trailer names each file as the size report prints it and gives the reason, such as `Size-Growth: js/page.js +3.1%, the key table of the input ring`.
- Every internal link in the published Markdown resolves, and new external links in changed files answer.
- Changed published Markdown and the commit's subject pass the docs style check. Errors block the commit; warnings only print.

A trailer value must say what you checked. Bare values such as "yes" or "done" are rejected. For example:

```text
feat(engine): add setScale to objects

Docs-Checked: updated docs/api/objects.md; re-read docs/concepts/static-dynamic.md
Skills-Checked: updated skills/null3d-develop/references/api-quickref.md
```

Maintainers also add a `Task:` footer. It names the milestone task that the commit delivers part of, or says `none`. The ID must be in `tools/hooks/task-ids.txt`, and a comma separates two IDs. Work that only prepares for a task says `none`, such as first-use shader files for a material that comes later. The commit-msg hook refuses any other value, such as `main CI repair`, and any ID missing from the list. Add a new task's ID to the list in the commit that first names it. The list also keeps a few process labels that no plan names, such as `M2-process`. The milestone count reads only each task's audited status, never the footers ([D-157](.dev/decisions/D-157-direct-pushes-to-main.md#addendum-2026-10-15-task-footers-and-merge-commits)).

A merge commit holds only conflict resolutions and mechanical fixes. Mechanical fixes are files that a generator writes again, renumbered entries, and edits that the other side's change forces, such as a renamed import. New features, tests, shading and docs text go into a normal commit before or after the merge. Git hides a merge's own edits from `git log -p`, `git log -S` and a review by commit. Before a push, `bun tools/hooks/check-merges.ts <base>..HEAD` compares each new merge with git's automatic merge, as `git show --remerge-diff` does. It refuses a merge with more than 30 words of new work, or any new shader code. It also refuses a binary file that the merge changed itself. When such an edit is mechanical, a `Merge-Edit:` trailer on the merge names it and says why. This is the one trailer that belongs on a merge commit.

## Releases

Work lands on main by direct push, without pull requests ([D-157](.dev/decisions/D-157-direct-pushes-to-main.md)). Push each branch to its remote branch as you work, to save it. To land it, merge `origin/main` into the branch, and compile the merged tree first with `cargo check --workspace` and `bun run typecheck`: a merge that keeps both sides of a struct or a constant often looks valid. Then run the local checks that D-157 lists, and `git push origin HEAD:main`; a new push to main cancels main's running CI run. Never wait for main's CI before pushing; when a finished run on main is red, whoever broke it fixes it at once. Every commit that reaches main, other than a merge, becomes a line of the next release's notes ([D-108](.dev/decisions/D-108-first-release.md#addendum-every-change-goes-into-the-release-notes-15-october-2026)). [Branches and parallel work](.dev/pull-requests.md#landing-a-branch) gives the steps and the checks. It also covers merging main into a branch, what CI runs, and several copies of the repository on one machine, and how a coordinator runs helper agents and their jobs ([D-178](.dev/decisions/D-178-process-rulings-2026-10-15.md)). [D-99](.dev/decisions/D-99-no-merge-queue.md) keeps the earlier pull-request flow, as history. [Releases](.dev/releases.md) covers how a release is made.
