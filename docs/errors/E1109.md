# E1109: Engine memory full

## What happened

The engine could not create or grow its WebAssembly memory. A page with worker threads gives the engine 1 GiB by default, and the memory option of `createEngine()` can raise it to 4 GiB. Many instance rows, a mesh of millions of vertices, or the first frame that copies every mesh can fill it.

<details>
<summary>Technical details: memory figures and the retry</summary>

Each instance row takes about 210 bytes, or about 300 with per-row colors or values. About 5 million rows fill 1 GiB, along with the rest of the scene. Building a mesh with normals to compute takes about 100 bytes per vertex for a moment.

The first frame copies every mesh of the scene. A scene with 84 MiB of meshes peaks at about 270 MiB on the direct path. It peaks at about 205 MiB on the indirect path.

The engine keeps the last 8 MiB under the limit for its own small requests. It tries again for about 45 seconds before it fails, and reports memory-wait through onProgress after 10 seconds.

A browser can refuse memory sooner, as phones often do, or while an engine that stopped before still holds its memory.

</details>

## How to fix it

Measure how near the scene comes to its limit with `engine.measure()`. Compare its `memory.wasmBytes` with `engine.mode.memoryMaximumMiB`, and add `?direct=on` to read the path that needs the most. Use less: share meshes, draw fewer rows, size each batch for its rows, and destroy batches you no longer draw. A scene that still needs more can ask for a larger maximum with the `memory` option of `createEngine()`.

- For a huge mesh: split it into smaller meshes, or simplify it.
- For a batch that draws no colors: give it colors only when it needs them.
- For several engines on one page: destroy the engines you no longer use, or keep one and detach and attach it. A smaller maximum leaves room for more engines.

[Where problems appear](../guides/debugging.md#where-problems-appear) says where each kind of error reaches your code.
