# E1101: Stale handle

## What happened

A call used an object, instance batch or resource after you destroyed it. The engine reuses the freed slot, but a call through the old handle never changes the object that takes it.

<details>
<summary>Technical details: which builds check</summary>

Development builds check every call on a scene object. Release builds skip that check: a destroyed object's setters write to a row that no object uses, and a second `destroy()` frees nothing.

The engine core checks each change that waits for the next frame and logs E1101 for a change to a destroyed object, such as a destroyed parent. Meshes, textures, color tables, probes, environments and instance batches throw E1101 in every build. A batch's array getters do too. An array that you read from a batch before its destroy can point at memory that another batch now uses.

</details>

## How to fix it

Stop using an object after you call destroy() on it. Look for places that still keep a reference, such as arrays of enemies or selection state.

[Where problems appear](../guides/debugging.md#where-problems-appear) says where each kind of error reaches your code.

## Example message

The engine prints the part below, then the fix above and a link to this page.

```text
E1101: setPosition() was called on "Crate" (slot 7), which was destroyed in frame 120.
```
