## Evidence

- packages/cli/src/browser.js:93 sets the code to E1437. Lines 104-111 build it as `Object.assign(new Error(...), { code })`. It is a plain Error, not an EngineError.
- docs/errors/index.md:87 lists E1437 in the table. The front matter summary says "Every EngineError code with its cause and fix." (tools/lib/docs.ts, the index renderer), and the intro (docs/errors/index.md:11) says every error is an EngineError. A reader who checks `instanceof EngineError` for a code from this table is wrong for E1437. This half holds.
- "names the call and the object" is false for many codes. Examples in packages/engine/src/errors/codes.ts: E1105 "the engine core received command 42.", E1301 "no usable GPU path for ?gpu=webgpu", E1303 "this browser runs WebAssembly without SIMD.", E1407 "?hold=1500ms is not a number...", E1404 "the render worker failed: out of memory.". The E1437 example names an archive, not a call. This half holds.
- docs/guides/debugging.md:26 says "Every error that the engine throws is an `EngineError`. Its message starts with a code." It does not say the message names the call and the object, and it speaks of the engine only, not the command line tool. It does not link E1437. It does not contradict the code. The debugging page part of the finding does not hold.
- docs/errors/E1437.md says "The null3D command-line tool did not install..." and nothing about EngineError, so it has no false claim either. The fix belongs on the index page only.

## Corrected claim

The error index (generated by tools/lib/docs.ts) is wrong twice. Its summary and intro call every listed code an EngineError, but E1437 comes from the command line tool as a plain Error with a `code` property. Its intro also says each message names the call and the object, but many messages name neither (E1105, E1301, E1303, E1404, E1407, E1437). The debugging guide and the E1437 page are correct and need no change.
